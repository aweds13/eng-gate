### 1.1 ★ IP 是易变量，instance-id 才是这台机器的身份

**公网 IP 会变。** 按量付费实例停机再开、或换一个弹性公网 IP，都会换掉公网 IP，而 instance-id 不变。
这台机到今天 IP 至少变过两次，两个旧值**都已失效**：

| 公网 IP | 状态 |
|---|---|
| `203.0.113.12` | 已失效（变配前） |
| `203.0.113.11` | 已失效 |
| `203.0.113.10` | **当前** |

两条纪律：

1. **脚本里别硬编码 IP。** 长期用的脚本把主机收进环境变量或仓外配置，换 IP 只改一处；
   文档里的 IP 当「当前值」读，别当常量抄进判据。
2. **换 IP 之后第一件事是确认「还是同一台机器」** —— 能连上不等于连对了实例，
   控制台上点错实例是很容易发生的事：

   ```bash
   ssh -i ~/.ssh/id_ed25519_cloud administrator@<新IP> "hostname"
   # 期望：gates-runner-host
   ```

   判据是三件一起看：`hostname` = `gates-runner-host`、`instance-id` = `i-0123456789abcdef0`、
   `instance/instance-type` = `ecs.u1-c1m4.xlarge`（后两件从实例元数据取）。

证据存档：同一个 `i-0123456789abcdef0` 的旧规格写在 `复盘/交接-重构进度.md` 第 4524 行
（`ecs.e-c1m2.xlarge` 4c8G、公网 IP `203.0.113.12`）—— 与今天的实例元数据一比，变配这件事就闭合了。

**阿里云 instance-id 一实例一号、永不复用** ⇒ 「是不是同一台机器」只认 instance-id，
不认 IP，也不认实例名。变配、停机再开、换 EIP 都改不了 instance-id。

### 给云机喂什么：白名单（卡 E54）

云机上跑门禁，判据读的不只是代码，还有**仓外配置**。这里以前是三处裸奔，都被实测咬过：

| 给定面 | 以前的写法 | 现在 | 咬过的样子 |
|---|---|---|---|
| 仓外配置推送 | `scp *.toml *.json`（把本机私有账本 `accounts.toml`、私有模型开关 `model-switches.toml` 一起推） | 白名单 `cfg_allow=(models.whitelist.toml)`，缺件 `exit 5` fail fast | `test_pool_accounts.py` 两条「账本缺失要报错」判不出来（`DID NOT RAISE`）；`test_wb_dispatch.py::test_account_auth_uses_the_profile_env_and_model` 被判「未授权模型」 |

三条判据钉子：`tests/test_cloud_sync.py` 的 `test_run_gate_pushes_only_the_whitelisted_config`、
`test_run_gate_asserts_the_remote_tree_matches_the_target_commit`、
`test_bootstrap_installs_dev_extras_as_the_single_source`（各自反向都验过红）。

### 两个坑（都踩过，别再踩）

1. **PowerShell 5.1 读 `.ps1` 必须 UTF-8 BOM。** 没有 BOM 时中文注释按 ANSI 解，解析器会报
   「字符串缺少终止符」，而且报的位置跟真因无关，很难查。
   复核命令（本机，看前 3 字节是不是 `EF BB BF`）：

   ```bash
   python -X utf8 -c "print(open('scripts/cloud/bootstrap.ps1','rb').read(3)==b'\xef\xbb\xbf')"
   ```

   判据：输出 `True`。入库这份**带 BOM**，钉子
   `tests/test_cloud_sync.py::test_bootstrap_is_utf8_with_bom`。

2. **`.ps1` 里不要嵌 `python -c "..."`。** PowerShell 会先吃掉里层引号，python 收到的是半句话。
   把 python 代码写成独立 `.py` 文件，`.ps1` 只负责调用它。

3. **解释器版本会改门禁结论（卡 E44，已修但形态要记住）。** 云机钉 Python 3.12.8、本机 3.14.x，
   而 `pathlib.Path.glob("X/**")` 对裸 `**` 的语义**随版本变**：3.12/3.13 只给目录，3.14 连文件
   一起给。`scripts/run_gates.py` 的 `input_hash()` 曾用它展开门输入，`is_file()` 一滤就是空集
   ⇒ **每道门的输入哈希恒等于 `sha256("")`**（`e3b0c44298fc1c14`）⇒ 复用判定永远「没变」，
   改了 `src/**` 也照样复用上一次的绿。现在 `_expand()` 走 `rglob("*")`（与版本解耦），且
   `main()` 开跑前会拦 `python < 3.11`。看到「云机 10 条 `test_gates_reuse_line` 红、哈希全是
   `e3b0c442…`」，就是这条的旧形态；`gates/last.json` 现在记 `python` 字段 —— 先看它是哪版跑的。

## 3. 仓库怎么搬上去

主分支是 **`line/impl-v1`**（不是 `main`）——先记住这条，`git clone` 默认分支对不上时不要以为仓库坏了。

搬运用 **bundle 单向同步**，云机上不做任何提交（理由见 §5 第 3 条）：

```bash
# ① 本机：以云机当前 HEAD 为基，只打增量对象（比全量小得多）
git bundle create /tmp/inc.bundle <云机HEAD>..line/impl-v1

# ② 送到云机
scp -i ~/.ssh/id_ed25519_cloud /tmp/inc.bundle administrator@203.0.113.10:C:/Users/administrator/inc.bundle

# ③ 云机：导入对象
ssh -i ~/.ssh/id_ed25519_cloud administrator@203.0.113.10 \
  "cd <云机仓库路径> && git bundle unbundle C:/Users/administrator/inc.bundle"

# ④ 云机：对象已进库，直接对齐到目标提交，再校正工作区
ssh -i ~/.ssh/id_ed25519_cloud administrator@203.0.113.10 \
  "cd <云机仓库路径> && git reset --hard <目标sha>"
```

`git bundle unbundle` 只导入对象、不动分支，所以第 ④ 步的 `git reset --hard` 是必需的。
（`<云机仓库路径>` 由使用者自己定，本文档不预设。）

**回传只读产物**：把云机的 `gates/last.json` 与 `gates/logs/*.log` 拷回本机对应卡树，**不要**在云机上提交。

★ **回传的产物必须自证是这一趟写的**（卡 E66 · T-AG526）：`2/5` 会把**上一趟的绿**播种到云机 `gates/last.json`，所以云机在 `4/5` 中途被关机时，那个路径上留着的就是上一趟的读数 —— 它绿、`host` 是云机的、`rev` 也对得上，`wb_land` 的三道自检全过得去。
现在 `5/5` 回传后立刻核一次（`tools/gate_pool.py check-product-fresh`）：产物 `at` 不早于本趟起跑、且与 `gates/diag/seed-<卡号>/last.json` **不逐字相同**；判不出来（缺 `at`）也按不新鲜处理。不新鲜 ⇒ **删掉刚搬回卡树的那份 `last.json`**、日志照常保留、退出码 **9**。
⇒ 看到退出码 9 且 `.wt/<卡号>/gates/last.json` 不见了，不是产物丢了，是「这趟没跑出来」，去 `gates/diag/cloud-gate-<卡号>.log` 的 `4/5` 段看断在哪。

```bash
scp -i ~/.ssh/id_ed25519_cloud administrator@203.0.113.10:<云机仓库路径>/gates/last.json <本机卡树>/gates/last.json
scp -i ~/.ssh/id_ed25519_cloud -r administrator@203.0.113.10:<云机仓库路径>/gates/logs <本机卡树>/gates/
```

验证命令（云机）：`git rev-parse --abbrev-ref HEAD && git status --porcelain`，工作区应为空。

**一条命令跑一张卡（脚本在库：`scripts/cloud/run_gate.sh`）**：

```bash
TF_PROJECTS_TOML=<云机上的项目索引路径> bash scripts/cloud/run_gate.sh <卡号> [端口段]
```

它按 5 步做（每步都 fail fast，退出码写过就没变）：

1. **导出补丁**：本地 `add -A -N` + `git diff HEAD --binary`，但**排除 `gates/last.json`
   与 `gates/reuse.json`** —— 这两件由第 2 步播种，进了补丁就与播种互相盖，`git apply`
   整体不生效（E49 踩过：补丁没装上、却在裸树上跑完门禁，14 条红全是假的）。
2. **对齐 + 清残留 + 播种**：云机 `checkout -f --detach <写补丁那棵树真实的 HEAD>`（不许用
   主仓 HEAD —— 卡树常领先于主树，坑 33）、`clean -xfdq`；`1.5/5` 先杀上一趟留下的
   `python.exe`（ssh 断线会留下孤儿 xdist worker，占着 `docs/traceability.toml` 让下一次
   `git apply` 报 `unable to unlink … Permission denied`）；再把 `TF_LAST_SEED`（默认取 profile 的
   `seed.dir_default` = `gates/diag/seed-<卡号>`；卡 E49 pass8：**不能**是 5/5 的回传目录）里的
   `last.json` / `reuse.json` **播种**到云机 —— 这两件是**入库文件**，
   `clean -x` 清不掉、删了又会让审计 ⑫ 与 `test_docs_fragments` 连坐，所以只能显式播种。
3. **仓外配置**：`0.4/5` 把 `TF_POOL_CFG_DIR`（默认 `C:/poolcfg`）铺到 `TF_POOL_CFG_DST`
   （默认 `C:/infra/pool`）；`0.45/5` 从本机 `scp` `scripts/cloud/pool-config/projects.toml.tmpl`
   再远端渲染 `__REPO_ROOT__`（模板是卡里的新文件，apply 之前云机还没有）。
4. **跑**：`git apply --binary` → `python -X utf8 scripts/run_gates.py`。写文件一律
   `[IO.File]::WriteAllText(..., New-Object System.Text.UTF8Encoding($false))`、读一律
   `[IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)` —— `Set-Content -Encoding UTF8` 写 BOM
   （`TOMLDecodeError: Invalid statement (at line 1, column 1)`）、`Get-Content -Raw` 按 GBK 解码
   （中文台账变乱码，一颗咬 10+ 条）。
5. **回传**：`gates/last.json` 与 `gates/logs/*.log` 拷回 `.wt/<卡号>/gates/`（只读产物，云机上不提交）。
   回传后**必须核验产物是不是这一趟写的**（卡 E66）：不是就删掉产物、退 9，不许留在卡树里冒充读数。

仓外配置（`TF_PROJECTS_TOML`）**必给**：缺了脚本当场退 2、一步都不跑（fail fast）。
模型注册表的真名是 `TF_MODEL_REGISTRY`（`tools/pool/model_registry.py:69`），可选注入。

**两个域各跑一趟（同一台机两条 checkout 并行）**：脚本认一个环境变量 `CLOUD_DIR`（默认 `C:/eng`）。
再建一条 checkout 并装上：

```powershell
git clone -q C:\eng C:\eng2 && cd C:\eng2 && git checkout -q --detach <同一个 commit>
python -m pip install -q --no-deps -e C:\eng2      # 让 C:\eng2 的 timeflow 可导入
```

然后用不同端口段同时跑两张卡（卡树各自的补丁互不干扰，日志各落一份）：

```bash
CLOUD_DIR=C:/eng  bash scripts/cloud/run_gate.sh F1 9381
CLOUD_DIR=C:/eng2 bash scripts/cloud/run_gate.sh E19 9411
```

`CLOUD_DIR != C:/eng` 时脚本第 0 步不从本机传 bundle，而是让 `C:/eng2` 从 `C:/eng` 本地
`git fetch`（`C:/eng` 那边由第一趟同步过），省一次 10 MB 传输。


### 3.1 骨架与 profile 的分界：哪一半归仓，哪一半归机器

`scripts/cloud/run_gate.sh` 是**骨架**：它只认键（`${P_<键>}`），不知道任何仓名、云机目录、分支、
门禁命令。每仓一份 `scripts/cloud/profiles/<仓>.toml` 是**仓专属的那一半**。读 profile 的唯一工具是
`scripts/cloud/profile.py`：`dump` 打「键 US 值」行给 bash 读成 `P_<键>`，`list` 列现有 profile，
`check` 自检，`render` 把「骨架 + 一份 profile」摊成平铺脚本（§3.4 的自查就是用它）。

| 这一半是仓无关的（在骨架里，改它要过判据） | 这一半每仓一份（`profiles/<仓>.toml`） |
|---|---|
| 清树：`git clean -xfdq`（**带 -x**；不带则上一趟的 `gates/last.json` 会被读成本趟判定 → 自指钉子必红） | 云机目录与分支（`cloud_dir` / `branch`） |
| 残留断言：`require_no_residue` 判 `gates/last.json` 不许残留（单测入口 `--check-residue <目录>`，命中退 2） | 同步方式（`sync.mode` = bundle / peer / none） |
| SSH 保活与「证据先落云机盘」的顺序（§3.5） | 仓外配置供给（`cloud_config.*`：中转目录 / 本机源 / 落位 / 白名单 / 保留项 / 模板 / 占位符） |
| 补丁导出：`add -A -N` + `git diff HEAD --binary`，要排除哪几件由 profile 给 | 播种（`seed.*`：目录、文件、是否要求绿） |
| 播种的**机制**：怎么拷、拷完怎么断言绿（红读数不许当「上一趟」） | 开跑前准备（`prepare.*`：命令 / 退出码 / 提示） |
| HEAD 断言：云机 HEAD ≠ 目标提交就退 7 | 门禁命令与超时（`gate.cmd` / `gate.timeout_default`） |
| 回传：按产物清单逐件取、每件试 3 次、一件失败不中断其它 | 产物清单与三份日志路径（`gate.artifacts` / `paths.*`） |
| 产物新鲜度检查与 host 自证的**口径**（判据本体在 `tools/gate_pool.py`） | 哪些仓外变量必给（`requires_env`）、云机上哪些文件必须在位（`required_remote`） |
| 退出码的语义（§3.3 全表） | 注入哪些变量与缺省值（`env.forward` / `env.defaults`） |

骨架的**可执行行**里只剩一处本仓痕迹：`TF_CLOUD_PROFILE` 的缺省值（`--render` 与主流程各一处，都指向
`scripts/cloud/profiles/engineering.toml`）—— 那是为了让本仓历史调用点（不带 `TF_CLOUD_PROFILE`
的写法）原样可用，不是替别的仓猜。（注释里还留着几处本仓的历史注脚，例如播种为什么只数阻断门；判据只扫可执行行，注释不参与。）

> 小注：分界之前这些值全部写死在 `run_gate.sh` 里，第二个仓要用就得 fork 一份脚本，两份各自漂移。
> 现在判据 `tests/test_cloud_profiles.py` 直接扫骨架的**可执行行**，不许出现本仓字面量
> （`C:/eng`、`line/impl-v1`、`run_gates.py`、`C:/infra/pool` 这类），「抽干净没有」不必靠人看。

### 3.4 另一仓怎么接

骨架不用改，接一个新仓只做一件事：写它自己的那份 profile。

1. 复制一份起手：`cp scripts/cloud/profiles/engineering.toml scripts/cloud/profiles/<仓>.toml`。
2. 四个必填键必须换掉：`name` / `repo_root` / `cloud_dir` / `branch`（缺任何一个，
   `profile.py check` 会点出来，rc=2）。
3. 按该仓实际填这三处：没有卡树就 `card_tree = false`（补丁 / 播种 / HEAD 断言三步自动空转）；
   云机怎么拿到树由 `sync.mode` 决定（bundle / peer，云机自己维护就 none）；仓外配置没有要求
   就把 `requires_env` 与 `required_remote` 留空 —— 空数组等于「没有这项要求」，不是漏填。
4. 该仓的门禁命令、超时、产物清单、三份日志路径按它自己的门写。`paths.remote_log` 与
   `paths.local_log` **必写**：缺了 4/5 直接退 2（现场日志是断线时唯一的证据，不许省）。
5. 自查三连（都不执行、不联网）：

```bash
python -X utf8 scripts/cloud/profile.py check --profile scripts/cloud/profiles/<仓>.toml
python -X utf8 scripts/cloud/profile.py list
TF_CLOUD_PROFILE=scripts/cloud/profiles/<仓>.toml bash scripts/cloud/run_gate.sh --render > /tmp/rendered.sh && bash -n /tmp/rendered.sh
```

`check` 查重复键、`sync.mode` / `env.style` 的取值、四个必填键，成功打 `OK <文件名>：共 N 个键`；
`--render` 把骨架摊成平铺脚本（卡号渲染成符号 `$card`），**stderr** 若出现
「⚠ 骨架引用了 profile 没给的键」就是漏了键 —— 此时 rc 仍是 0，别只看退出码。
6. 边界：第二仓的 profile 里**不许出现本仓专属的键值**（`TF_PROJECTS_TOML`、`models.whitelist.toml`、
   `C:/infra/pool`、`scripts/run_gates.py`、`line/impl-v1` 这类）。判据是 `tests/test_cloud_profiles.py`：
   它扫骨架的可执行行，也扫每份 profile（含注释）。第二仓的真值归它自己的仓，本文档不抄。

### 3.5 SSH 保活 / 云侧落盘 / rc 语义（卡 E84）

骨架把 SSH 选项收在 `SSHOPTS` 里，所有 ssh / scp 都用它：

```bash
-o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null -o BatchMode=yes
-o ServerAliveInterval=30 -o ServerAliveCountMax=6 -o TCPKeepAlive=yes
```

前三个是无人值守的老口径（不提问、不记 host key、要密码就失败而不是挂住）；后三个是卡 E84
血换来的。一趟门禁十几分钟，长连接空闲时会被中间设备剪断：实测 A366 那趟本机收到 rc=255，
而云机上那批门**已经跑完**，产物就在盘上 —— 旧写法 `ssh … > 本机临时文件` 让本机只剩断点前那
1026 字节，云机上十几分钟的真输出没人去取。于是定下三条：

1. **保活**：`ServerAliveInterval=30` + `ServerAliveCountMax=6`（约 3 分钟收不到包才判定断线，
   不是几秒）+ `TCPKeepAlive=yes`。没有它，一趟本来要跑完的门禁会被判成「网络失败」。
2. **云侧先落盘**：4/5 的远端命令把门禁输出重定向到云机盘上的 `paths.remote_log`，ssh 一返回
   本机立刻落一份 `paths.local_log`，首行是
   `# rc=… elapsed=… started_at=… timeout=… card=…`，随后 tail 六行。**断线时先看这两份**，
   不要从零重跑（重跑要再等一趟，还会把云机上的现场覆盖掉）。
3. **rc 语义**：`124` = 云机门禁超时 —— 处置是「用 `TF_CLOUD_GATE_TIMEOUT` 放宽后重跑」；
   `255` = 与云机的长连接断了 —— 门禁**可能已在云机上跑完**，现场在云机盘上，处置是
   「5/5 会尽力取回，取不回就手工 scp」。这两个码都不等于「门禁红了」，别照着红门去改代码。

配套的两个口径：

- **起跑时刻用本机时钟**（`date -Iseconds`），不用云机时钟：云机断电重启后 RTC 不可信，
  拿它当新鲜度基准会把这一趟的产物判成旧的（或反过来）。这个时刻既是 `paths.local_log` 的首行，
  也是 5/5 新鲜度检查的 `--started-at`。
- **取回是尽力而为**：5/5 对每件产物试 3 次，失败只打 `[取不回] …` 并继续取下一件 ——
  一件取不回不该让别的证据一起丢。取回后再用 `tools/gate_pool.py check-product-fresh`
  核「是不是这一趟写的」（比对 `--started-at` 与播种源 `--seed`）；不是就删掉
  `gates/last.json` 并退 9，不许留在卡树里冒充读数。

## 4. 关键实测：这台机器**持续不降频**

要回答的问题是"经济型 e 实例会不会用完积分就掉到基准频率"（如果会，全量门禁的 12 分钟会变成
20 分钟，那就得换 u2a/u1）。测法：同一段纯 Python 循环，各测 10 秒窗口，中间空转 60 秒，
对比「0–10 s」与「70–80 s」的 iters/s。

| 机器 | 0–10 s | 70–80 s | 变化 |
|---|---|---|---|
| 云机 4 核 @2500 MHz | 667.1 iters/s | 650.5 iters/s | **−2.5%（噪声级，不降频）** |
| 本机（单核） | 505.8 iters/s | 510.8 iters/s | +1% |

结论两条：

- **变配前**这台 e 实例给的是**持续 2.5 GHz**，没有"积分耗尽就断崖"的现象
  ⇒ **就"降频"这件事本身，不必换 u2a/u1**（同 4c8G 贵 10–20%）。
- 云机单核比本机快约 **24%**（667.1 vs 505.8）。

### 4.1 ★ 更正（2026-10-26，卡 E56）：上面这条**只证明了不降频，没证明算力够**

**变配前**的同一台机（那时是 `ecs.e-c1m2.xlarge`、公网 IP `203.0.113.12`，均已失效）换成约 1.05× 的并行总吞吐探针（`gates/diag/bench_throttle2.py`）后实测：
`n=1 → 3.87M`、`n=2 → 3.87M`、`n=4 → 4.08M`（6 s 窗口同结论）⇒ **4 路并行只兑现单路的 1.05–1.08×**，
等于 4 个 vCPU 里只有 1 个在真干活。这也解释了当时云机全量门禁 835 s 而本机 400 s 出头。

处置：**同一实例变配**（`i-0123456789abcdef0`：`ecs.e-c1m2.xlarge` 4c8G → 2026-10-24 `ecs.e-c1m2.2xlarge` 4 vCPU / 16 GiB → 2026-10-26 `ecs.u1-c1m4.xlarge` 2 物理核 / 4 vCPU / 16 GiB 规格位 = 实报 15.72 GiB），**不是换机器**；公网 IP 随之变成 `203.0.113.10`。同一套全量门禁：

| 侧 | 全量门禁墙钟 |
|---|---|
| 变配前（`ecs.e-c1m2.xlarge`，公网 IP `203.0.113.12`，已失效） | 835 s（pass13） |
| 变配后（`ecs.u1-c1m4.xlarge`，公网 `203.0.113.10`）★ | **417 s（pass15）/ 420 s（pass16）/ 426 s（pass17），后两趟均含第 20 道门 `pytest_chain`** |

教训：**"CPU 计数器不降频" ≠ "算力给够"** —— 虚拟机可以诚实地报 2.5 GHz、同时只让你用一个核。
变配/选型前必须跑并行总吞吐探针，别只看时钟和 `% Processor Performance`（后者读 `\Processor Information(_Total)\% Processor Performance`，
本机在 VM 里常常拿到不可用值或 100，判断力弱）。

验证命令：在云机上跑同一段循环脚本，取两个窗口的 iters/s 相除即可；判据是两数差异 ≤5% 视为噪声。

### 4.2 ★ 新读数（2026-10-29，卡 E65 / T-AG524）：**抢 CPU 的代价有数了，而且它会让红门说谎**

变配后并行总吞吐确实是 2.05×（`n=1 4.40M` / `n=2 7.00M` / `n=4 9.15M`，两次独立测量
分别为 2.05× 与 2.48×）⇒ **原来「4 vCPU 只兑现 1 核」的病根已经没了**。
但 2 物理核 / 4 逻辑核是硬上限，另一件事随之浮出来：**同一棵树上并发跑两套负载，读数会飘。**

| 读数 | 数值 | 说明 |
|---|---|---|
| `pytest` 门单独跑（`-n 4 --dist worksteal`） | **435.16 s** | 1 failed, 3502 passed, 62 skipped（那一条红是当时树上的真实缺陷） |
| 同一道门在整趟门禁里（与 `pytest_chain` 并跑） | **529.0 s** | 争抢代价 **+93.8 s = +21.6%** |
| 22 门秒数合计 vs 整趟墙钟 | 1283.9 s vs 544 s | 平均并发 2.36× |
| `ui_flow` 整道门单跑 | **365.6 s**（26 条流 / 362 项断言全绿） | 并进门禁后**每趟红的流都不同**（`⑬` / `㉒` / `⑮` / `web_live`） |

**后果不是「慢」，是「红不红变得不确定」**：同一棵树、同一份代码，三趟分别红在不同浏览器流上，
而把这些流单跑是绿的。这跟卡 091 的满载竞态签名是同一个病。

处置（卡 E65）：门禁产物新增 `co_tenants` 读数；症状像「等不到东西」的红门标成
`status: "SUSPECT"`（第三种状态，`ok` 仍 `False`）。读法与判据见
[`测试流程.md` §5.1](测试流程.md)。**不要让两套负载共用一台机**；真要共用，先看 `co_tenants`
再决定是改代码还是换机重跑。

代价的账：整趟墙钟 ≈ 总 CPU 秒 ÷ 2.05，想快只有三条路 —— 加核、别叠负载、去掉不该付的税
（`--no-cov` 那一笔：全量 `--no-cov` 232.02 s vs 门里 520.32 s，约 288 s 来自覆盖率、
只有约 102 s 来自用例变少）。分片**不是**杠杆：2.05× 是机器属性，与怎么分无关。

## 5. 跨机口径（三条，必须照做）

两台机器同时跑门禁，会造出"两台各自的真相"。所以：

1. **全量门禁只许一台机器持有。** 门禁锁 `gates/diag/gates-<端口段>.lock` 是**本地文件**，
   两台机器互不可见 ⇒ 同一张卡的门禁只在一台上跑。
   验证：`python -X utf8 gates/diag/gate_lock.py status`（列出每一段的持有者与租约剩余）。
2. **封存指纹以"跑门禁那台"为准。** `gates/last.json` 的 `rev` 必须等于落地提交的**父提交**；
   另一台不许覆盖这个文件。只读从云机拷回，不反向写。
   验证：`python -X utf8 -c "import json;d=json.load(open('gates/last.json',encoding='utf-8'));print(d['rev'],d['tree'],d['ok'])"`，
   再与 `git rev-parse HEAD^` 比对。
3. **合流只走一条线。** 云机不 commit；产物回传本机卡树后，本机从第 ⑥ 步收口：

   ```bash
   python -X utf8 tools/wb_land.py --card <卡号> --task T-… --commit-only
   ```

   `--commit-only` 的含义是「门禁已绿、封存没变」，**跳过重跑门禁**，其余步骤照走；
   trailer 里会如实写「复用已绿的那一趟」（`tools/wb_land.py` 第 11、22 行）。绝不允许两台各写各的。

## 6. 每天怎么用（运维）

### 6.1 只按需开机，不常开

按量计费：**开一天约 10.4 元；落一趟门禁约 0.2 元**（门禁整趟 11–15 分钟，见 [README §2](README.md)）。平时关机。

### 6.2 定时停机（省钱的唯一开关）

阿里云控制台「自动化运维 → 定时开关机」：

| 项 | 值 |
|---|---|
| 周期 | 每天 |
| 开机 | 02:50 |
| 停止 | 03:00 |
| **停止模式** | **节省停机模式**（只收磁盘费 ≈ 0.6 元/天） |
| 首次执行的副作用 | 自动创建服务关联角色 `AliyunServiceRoleForOOSExecutionScheduler`（正常，别删） |

两个红旗：

- **不要设「自动释放时间」** —— 到点会把实例**销毁**，不是关机。
- 改开「**实例释放保护**」，挡住误删/脚本误操作。

### 6.3 开机第一件事：清死主锁

上次硬停机（或定时停机直接掐掉进程）会把 `gates/diag/gates-<端口段>.lock` 留在盘上。
这个锁的判据是**锁文件 mtime**，比 `--stale-after`（默认 **10800 s = 3 小时**，
`gates/diag/gate_lock.py:81`）旧才视为陈旧（`gates/diag/gate_lock.py:29`）——
所以不清它，下一次落地会**干等 3 小时**。

```bash
TF_GATE_PORT_BASE=<端口段> python -X utf8 gates/diag/gate_lock.py release --card <卡号> --force
```

不设 `TF_GATE_PORT_BASE` 时锁名是 `gates/diag/gates.lock`（历史默认段 8531，
`gates/diag/gate_lock.py:89`）；设了就是 `gates-<端口段>.lock` —— **别清错把**。
`--force` 是强解（锁不是你的也能解，`gate_lock.py:54` 退出码 4 的场景）。

### 6.4 作息：02:30 之后不再起新的全量门禁/落地

用户定的作息。留给 03:00 定时停机 30 分钟缓冲 —— 否则 02:40 起的一趟全量门禁会在中途被掐，
正好留下 §6.3 那个死锁。

### 6.5 内存闸

`TF_GATE_MIN_FREE_GB`（默认 **2.0**，`0` = 关掉这道闸）决定"可用内存不够就拒跑"。
云机 8 GB，可以抬到 **4** —— 因为 `pytest_workers()`（`scripts/run_gates.py:347-371`）按可用内存
自适应：可用 < 2.5 GB ⇒ 1 个 worker；< 4 GB ⇒ 2 个；否则 `min(4, cpu)`。
抬到 4 就等于放开到 **4 worker 档**。

```bash
TF_GATE_MIN_FREE_GB=4 python -X utf8 scripts/run_gates.py --quick
```

验证跑法（看那一行）：`=== pytest 跑法：并行（pytest-xdist，-n 4） ===`
现成的日志里可以直接翻：`grep -h "pytest 跑法" gates/logs/*.log | tail -3`。
要钉死 worker 数用 `TF_PYTEST_WORKERS`（显式值优先于自适应）。
