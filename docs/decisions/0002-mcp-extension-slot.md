## 背景与问题

同一批能力要被四个面调用（界面 / ⌘K / 命令行 / AI·MCP）。每往 MCP 里再实现一次，
就多一份会和别处漂的判据 —— 本仓吃过这个亏：MCP 机器可读块被报告正文冒充（卡 117 / T-G215），
以及改 MCP 工具清单时漏掉写死清单的那条测试（卡 142 记的连坐）。

## 候选方案

A MCP 里实现连接与判据（调得动，但同一件事有两份实现要同步）。

B MCP 只留扩展位：class 骨架 + 注册注释 / 工具名，真正的实现留在官方接口或 `tools/` 里，
MCP 只是把同一段代码接进会话。

当时没有正式比较过 A 的收益，只定了 B（D16 定案 C+D）。

## 决定

选 B。落地形态在三处一致：

- 搜索：`McpSearchSource` **只留 class 骨架与注册注释，不实现连接**；
- 框架的只读面：MCP 工具调同一段库，不重写判据（卡 213 的 `workbench_board` 调 `pipeline_view`）；
- 框架的写面：**存在性即授权** —— 服务进程设了 `POOL_MCP_WRITE=1` 才列出写工具（卡 111），
  收申请走子进程不冻 stdio（卡 130）。

放弃 A 的代价：某些能力只能等实现层先有、MCP 才跟着有；换来的是「MCP 面的结论」与
「命令行跑出来的结论」是同一段代码。

## 把握程度

medium —— 三处都有测试钉住，但「什么时候该真的实现一个 MCP 连接」这条边界没正式比较过。
