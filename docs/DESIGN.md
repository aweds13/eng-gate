# DESIGN — 设计决策（know-why）

> 本文件回答：「**这个项目为什么这样设计？**」
> 「必须做到什么」见 `specification/`；「怎样才算做完」见 `contracts/`；「谁负责写」见 `implementation/`。
> **本文件只记"为什么"**——即那些"换个人也会这么做/不这么做"的关键取舍与理由。
> 依据：`intention/needs.md`（N1–N46）+ `specification/conventions.md`（约定）。

---

## 一、为什么是这个产品形态

### D1. 为什么是「本地优先的桌面程序」而不是 Web/云服务？

**决策**：桌面程序（pywebview，双击即用），数据全在本地；移动端用 PWA 做伴生端异步同步。

**为什么**：
- **隐私最小**：管的是个人时间与学业数据，不该上云（N1）。
- **常驻可用**：时间管理工具要随时能开，不该依赖网络。
- **但不放弃移动**：人常离开电脑（N1 的"为什么"原文），所以用 PWA + IndexedDB 离线可记，回到电脑异步对齐。

**代价（明确写出）**：跨端实时同步做不了（首版不做公网远程实时）；移动端只能是"精简核心版"。

### D2. 为什么用「债务/储蓄」而不是传统的任务完成率？

**决策**：核心心智是**如实账本**（逾期=债务、专注=投入、完成悬赏=收益），而非"完成率/打卡"。

**为什么**：
- 传统工具衡量"做没做完"，但**长期投入的均衡性**才是真问题（防突击、防拖延）（N2）。
- 债务/储蓄能把"逾期"这件负面事变成**中性的记账事实**——不制造羞耻感。

**关键取舍**：
- **不折算成精确时间**：债务只记"逾期天数/程度"。因为估不准，硬折算会造假（N3 口径）。
- **不设"目标"实体**：目标是"大的任务分组"，独立成实体属过度抽象（N3 已砍，标为伪需求）。
- **不硬对标**：只用如实记账 + 趋势自判断，**不用算法推荐**（N3）。

**代价**：没有"完成率 87%"这种直观数字，用户要自己看趋势。

### D3. 为什么「温和不施压」是硬约束而不是风格偏好？

**决策**：所有呈现/提醒默认温和、可关闭、无强制红点、**不因逾期天数放大焦虑**。

**为什么**：
- 工具的目的**是帮你管理时间，不是 push 你**（N3 原则原文）。
- 债务越积越高会让人放弃，系统失去正面意义（N5 的动机）——所以还要有"债务重组"这条逃生通道。

**代价**：会"看起来不够有推动力"，不符合"效率工具"的常见期待——这是**故意的**。

## 二、为什么要分这些"层"

### D4. 为什么是五层治理（而非三层/两层）？

**决策**：`intention`（为什么做）→ `specification`（必须做到什么）+ `conventions`（不能违反什么）→ `contracts`（怎样才算做成）→ `implementation`（谁负责）→ `taste`（品味）。

**为什么**（这是本项目最有价值的经验，来自真实教训）：
- 原本只有三层的项目，AI 全自动推进时出现**"做了这个、忘了那个"**。
- 根因诊断（见 `../复盘/意图到规格-产品判断复盘.md`）：**规格只承接了"承诺"，丢了"护栏 + 行为规则 + why + 可验证性"**。
- 后续又发现（见 `../复盘/三层断裂诊断-实现与交互复盘.md`）：**实现只承接了"模块存在"，丢了"操作闭环 + 调用契约"**。

**所以加了两层**：
| 层 | 补什么漏洞 |
|---|---|
| `conventions` | 横切约定（护栏/口径/红线）散落在各功能里 → 集中、简短、必读 |
| `contracts` | "操作做到一半" → 用**六要素**（入口/前置/输入/后续/可逆/反馈）定义"做完" |

**代价**：文档更多、要维护一致性（因此配了 `check_layers.py` 护栏脚本）。

### D5. 为什么业务层（`core/`）不碰 SQL？

**决策**：`core/` 只做领域逻辑，SQL 全在 `storage/`。

**为什么**：
- 改存储不牵动业务（可维护，SR-NF6）。
- 领域逻辑可独立单测，不需要数据库。
- 未来若换存储（如按约定层转向 Markdown 真源），业务代码不动。

### D6. 为什么知识资产「只存引用句柄」？

**决策**：本软件不直接读写 Obsidian/Vault 文件，只存**引用句柄**（Vault 相对路径 / `KB-…` ID）。

**为什么**：
- **避免膨胀**：Obsidian 联动与知识资产管理强相关，独立项目更干净（N24）。
- **避免耦合**：本软件不该知道 Vault 的内部结构。

**代价**：不能直接显示笔记内容，只能"存个链接"；深联动后置。

## 三、为什么用这些技术选型

### D7. 为什么第一版用 SQLite 而不是纯文件？

**决策**：当前实现用 **SQLite**（标准库 `sqlite3`，零运维）；**约定层已定长期方向为"混合"**（Markdown 真源 + 结构化索引）。

**为什么当前是 SQLite**：
- 债务曲线/热力图/周结算/FSRS 调度都需要**聚合查询**，SQLite 是最顺手的。
- 标准库自带，零依赖，符合"轻量"。

**为什么长期要转向混合**：
- 数据要**人/AI/Obsidian 三者可读**、要与知识管理系统联动 → 需要 Markdown 这类通用格式（N24/N25）。
- 但纯 Markdown 的聚合性能差 → 所以配一个"结构化索引"做计算。

> **这是本项目的关键技术债**：当前实现是纯 SQLite，尚未落地"混合"。见 `intention/needs.md` N25 的"已决"标注。

### D8. 为什么复习用现成的 FSRS 库而不自己写算法？

**决策**：直接用现成 Python `fsrs` 库做间隔重复调度。

**为什么**：
- 间隔重复算法（FSRS）有成熟实现，自己写等于重复造轮子且易错（N26）。
- 数据按 FSRS 兼容字段设计，为将来扩展留口子。

### D9. 为什么敏感配置用 `config.example.toml` → 本地 `config.toml`？

**决策**：模板入库（`config.example.toml`），本地实际配置 `config.toml` 加入 gitignore。

**为什么**：
- 开源项目不能提交个人配置（可能含路径、密钥）（N43）。
- 模板入库让新人知道有哪些配置项可调；Pydantic 校验保证配置合法。

## 四、关键机制的设计理由

### D10. 为什么任务/专注/反馈要"自动联动"而不是手动填？

**决策**：专注结束 → 自动记投入 + 自动累加当日反馈 + 自动累加任务时长。

**为什么**：
- 手动填 = 用户负担 = 最终不填 = 数据失真。
- "如实记账"要求数据**自然产生**，不是事后补录（N3/N12/N15）。

**当前状态**：**这条联动在实现层是断的**（见 `../复盘/三层断裂诊断-实现与交互复盘.md` §三），属 MVP 重构要补的 P0 缺口。

### D11. 为什么逾期提醒要"分级"而不是统一处理？

**决策**：学校硬考核逾期 → 强提醒；普通任务逾期 → 温和提示。

**为什么**：
- 学校考核是**硬约束**（会扣分），普通任务是**软约束**（N45）。
- 强度不分级，要么"漏掉重要的事"，要么"到处告警制造焦虑"。

### D12. 为什么"删除/不可逆操作"必须二次确认？

**决策**：删除可撤销；删分组/债务重组/清空等不可逆操作二次确认；债务重组前存快照。

**为什么**：
- 数据是长年积累的资产，误删代价高（N34）。
- 尤其"债务重组"（清零/重新分摊）不可逆，必须有快照兜底。

### D13. 为什么要有 `check_layers.py` 这类护栏脚本？

**决策**：用脚本检查文档/代码的一致性（五层对齐、引用完整性、约定层标注）。

**为什么**：
- 文档快速演进时，"管理文档的元层"最容易脱节（实测教训：脚本只检查老三样，导致"交叉全断"没被发现）。
- **人容易忘，脚本不会**——把一致性交给自动化。

**代价**：脚本自己也要维护，且**必须自测**（否则"永远 PASS"毫无价值）。

## 五、已知的设计债与取舍（诚实记录）

| # | 债 | 现状 | 影响 |
|---|---|---|---|
| 1 | **存储未转向混合** | 纯 SQLite，"Markdown 真源"未落地 | 与知识系统联动受限 |
| 2 | **操作闭环/联动断裂** | 专注不记账、完成不记账等 | 功能"做一半"（MVP 重构解决） |
| 3 | **`stats.py` 声明未建** | `modules.md` 提到但文件不存在 | 可视化无数据支撑 |
| 4 | **DESIGN/LEARN 长期缺失** | 本文件为补建；LEARN.md 仍待建 | 零基础定制指南缺 |
| 5 | **taste 层为空壳** | 只有"可迁移品味"+待完善清单 | 项目自身品味未沉淀 |

> **原则**：设计债**显式记录**，不隐藏。知道欠什么，才知道下一步做什么。
