## 一、已定（✅）

### D1 形态：手机端专用，电脑端不做
- **问**：这东西跑在哪？
- **答**：「手机上要用的。所以必须要能在手机上用。不然的话，我也不会叫你定制了。」「我肯定不是在这上面用，我指的是电脑不用。」
- **推论**：本机 Windows 起 localhost 服务、浏览器打开这条路 **不成立**。
- **影响**：`SR-NF3`（本机存储）不能靠「反正数据在电脑上」蒙混。

### D2 装机：装一次 + 之后热更新
- **问**：能不能用 adb 插线装、看日志？
- **答**：「反正怎么方便怎么来。能热更新的话最好。」（用户说明自己不懂 adb）
- **推论**：设计上**不能假设日常有 USB 调试**；更新路径必须能不重装 APK。
- **影响**：`SR-F9` / `SR-NF5`。这也是选 WebView 壳的**主要理由**（前端 bundle 是 APK 里的一个文件）。

### D3 只做聊天，不做 Agent
- **问**：要不要接工具编排 / MCP / 多 Agent？
- **答**：「它并不是一个全部的 Chat，先暂定这些。」
- **影响**：不做插件系统、不做 agent 循环框架。**唯一的「工具」是搜索与核验，且由用户显式触发**（见 D8/D11）。

### D4 纯官方 API，不抓网页端
- **问**：网页端的问答内容怎么搬进来（扩展 / Playwright / 手动导入）？
- **答**：「算了，直接不要网页端已渲染的搬进来了，我直接登我的 API。」
- **影响**：`❌ T1`。读写都走 `api.deepseek.com`，本地无抓取组件。

### D5 数据只存本机 + 手动导出备份
- **问**：数据放哪（联云 / 只本机 / 登录同步）？
- **答**：选「只存本机 + 手动导出备份」。
- **影响**：`SR-F8` / `SR-NF3`。可导出成文件，换机可恢复；不做账号体系。

### D6 一窗一书 + 页码编号
- **问**：`#编号` 怎么知道问的是哪本书？
- **答**：「我大概率不会在同个窗口问不同的书……以对话窗口来弄」「你要通过页码进行一个编号会比较好」「把那个书的名字绑定过来……先开发一个对话窗口对应一本书。」
- **推论**：**会话绑定教材**；编号形态 = **页码**（书自带目录/页码，用户会拍全）。
- **遗留**：未来「学的东西多了要调用不同资源」要预留入口（`待确认` 具体形态）。

### D7 唤图在本地解析，模型只看到图像块
- **问**：`#p12` 是在提示词里让模型自己理解，还是客户端先换成图？
- **答**（按用户「我不希望我一直反复地发……通过编号就能唤出」的诉求推得，用户同意四段链路）：入库 → 发消息 → **发送前本地解析 `#p12`** → 模型侧只看到图像块。
- **影响**：`SR-F5`。这也是与 Explore 的差异点（它**没有**图片编号体系）。

### D8 计算核验：内置轻量 JS + 懒加载 SymPy，按需触发
- **问**：数学计算交给谁？
- **答**：「我是大学生，大概率是要有各种各样的计算的。还有各种各样的化简。当前模型的能力……我觉得还好吧……就是不需要借助代码，但是，咋说呢，有个代码会让我安心一点。」
- **推论**：**默认不挡路**（模型照常写推导，不强制走 CAS）；每条回答挂一个可点的**核验条**，点了才把关键式子丢给 SymPy 独立算、并排显示。
- **诚实约束**：SymPy 的 `simplify` 自己也会慢、也会化简不到位 ⇒ 它是**第二意见，不是判决书**；对不上时如实摆三方（模型写的 / SymPy 算的 / 数值代入验的），**不许假装通过**。
- **证据（为什么必须真解释器）**：GSM-HARD 上 CoT 20.1 → PAL 61.5；而「模型写代码但自己心算执行」只有 23.2 ⇒ 增益全来自真解释器。见 `intention/evidence.md`。

### D9 模型清单拉下来，用户自己点选
- **问**：界面上要不要做成「快 / 强」两档，自动映射型号？
- **答**（否决我的提案）：「不需要什么快抢模型，你只要把清单拉过来，然后我自由选择什么模型点一下就行。」
- **影响**：`SR-F4`。**不做语义档位映射**；`GET /api/list-models` 原样列出，用户点。型号名会变（用户明确担心过），所以**绝不写死**。

### D10 要 BYOK
- **问**：密钥从哪来？
- **答**：「我也希望有自己可以 byok 的能力。也 OKOK。」
- **影响**：`SR-F4`。key / baseURL / 模型名三者都可自己填，不绑死官方。

### D11 要有联网搜索
- **问**：搜索要不要？
- **答**：「还有一个问题就是联网搜索功能呢。这个还是要有的。额，这个还是要好稍微讨论一下的。」
- **状态**：**需求已定（必须有）**。
- **路径已定（2026-10-23）**：用户拍板「**走官方**」⇒ 用 `POST /v1/tools/search` + `POST /v1/tools/fetch`（原 🟡 D12 的建议被采纳，见下）。
- **同时新增一条**：用户要求「**保留 MCP 能力**」⇒ 见下方 🟡 D16（四种解读待定，**这一条会改变工具层结构**）。

### D12 联网搜索走官方 Search/Fetch API（✅ 2026-10-23 用户拍板：「走官方」）
- **定为**：`POST https://api.deepseek.com/v1/tools/search`（`query` / `count`≤20 / `need_content`）+ `POST /v1/tools/fetch`（`{url}`，≤30 个，正文 20k–50k 字符）。
- **理由**：官方自带 `rerank_score`（0–3，≥1.5 算高质量）、`summary`（600–800 字，给模型读）、`snippet`（100–200 字，给 UI 显示）；省掉自建反爬 + 正文解析的维护面。
- **代价（必须让用户看见）**：**$0.75 / 1000 次成功请求** ⇒ 界面显示「这次搜了几次、累计花了多少」。
- **已否决的替代**：自建 Bing/Brave/Serper + Readability。
- **关键切分**：「搜外网」（花钱、官方 API）与「搜我自己的资料」（本地 SQLite FTS5、免费离线）是**两个按钮**，不合并。

- **用户原话（m00595）**：「走官方，但是保留 mcp 能力吧。」→ 追问后选 **C + D**。

## 二、待确认（🟡，我的建议，等用户点头）

### D13 分发形态：安卓壳 + WebView 前端（离线 bundle）
- **建议**：原生壳（Kotlin，~200 行）+ WebView 加载 APK 内置的离线前端 bundle；API 请求与 SQLite 走 JS Bridge 由原生层做。
- **理由**：① 渲染生态全在 Web（KaTeX/markdown-it/Shiki 直接用）② 热更新 = 换 bundle 文件 ③ 安卓原生 + 树形分支 + 公式的开源项目 **GitHub 上一个都没有**（实测 `android LLM chat kotlin compose latex` = 0 结果）。
- **代价**：长列表性能与滚动手感不如原生 Compose；要在 `SR-NF2` 里立性能判据兜住。

### D14 PDF/电子书导入放第二版
- **建议**：第一版只做「拍照/相册导入 → 按页编号」。PDF（含 700MB+ 电子书）导入、自动切页、OCR、文本层检索放第二版。
- **理由**：切页 + OCR 是另一个工程量级；而用户的实际采集方式是**拍纸质教材**。

### D15 第一版不做：语音输入 / TTS / 分享成图 / PDF 切页
- **建议**：这些在官方 App 里是亮点，但对「啃教材 + 追分支」是旁支。想抄的是**树与编号**，不是全套功能平替。
