# pipe-new —— 从零起一条工作链

一句话：**先定层，再定路**。目录、队列、卡、树、首笔落地，五样按顺序来；跳一步就得回头补，
而越靠后的步骤越贵（首笔落地要跑全量门禁）。

> 本页只写**换仓不变的动作与读法**。队列文件叫什么、卡规格落在哪个目录、树前缀与分支名、
> 建树基点、本仓实测读数、历史证据挂在哪：全在 [本仓绑定](references/repo-bindings.md)（相对链接，只深一层）。
> 换一个仓用这套技能，**只换那一份**，别改本页。

## 0. 先问再写（硬规矩）

在写任何规格、文档层、骨架或代码之前，先用 `grill-me` 与用户一问一答把决策树走完，并拿到用户明确的「确认」。**未确认不得动笔**；确认结论写进卡里（哪一问、答了什么）。

理由：AI 自己补出来的规格大多是编的，事后无法区分「事实」与「填补」。

## 什么时候用

- 一个空目录 / 新目录要接进**已有的工作链**（队列 + 卡 + 树 + 落地）。
- 要判断这个新项目该「铺框架骨架」还是「只登记进工作链的队列」。
- 一批活从没登记过，要把队列条目、卡规格、树一次补齐。

## 什么时候别用

- 只开一张卡：用 `pipe-card`（它管卡规格、派活、申报）。
- 接管一个**已经存在**的项目目录：用 `pipe-takeover`。
- 要一套自带配置文件、门表、钉子的独立骨架：用 `pipe-init`（框架层）。
- 目标在**另一个 git 仓**：链以「一个仓的数据根」为单位，没有「一条命令替别仓落地」的开关 —— 出口（项目索引 / 映射成卡 / 对方仓铺骨架）见 [本仓绑定](references/repo-bindings.md)。

## 前置检查

1. 先定资产层：这活是产品、工作链本身、还是机器 —— 见 [资产层](../softeng-manage/references/asset-layers.md)。
2. 目标目录在**这棵工作树的仓内**：`git rev-parse --show-toplevel` 要指向它；仓外只登记项目索引，不在这里落地。
3. 目标目录有首提交：链条以 git 为真源；空目录先 `git init` + 一次提交。
4. 卡号没被用过：队列文件与卡规格目录都没有这个号。
5. 工作区干净：`git status --porcelain` 为空（落地的第一步会检查主树）。
6. 队列校验器能起来：`<队列校验入口>` 能跑通再往下（真路径见本仓绑定）。

## 真命令

```bash
# 命令名、步骤顺序换仓不变；本仓的确切路径 / 字段名 / 树前缀见 references/repo-bindings.md

# ① 目录与首提交（新项目目录；已有目录跳过这一步）
mkdir -p <目录>
echo "# <项目名>" > <目录>/README.md
git add <目录> && git commit -m "chore(<scope>): <项目名> 起目录"

# ② 队列条目：往队列文件里加一条卡（字段按本仓的队列工具口径），再校验
<队列校验入口>

# ③ 卡规格落盘并**进索引**（四段：问题 / 改法 / 判据 / 证据；落地脚本只认索引）
git add <卡规格文件>

# ④ 建树（默认只打印；--execute 才真建；基点是队列登记的基点）
<建树入口>
<建树入口> --execute

# ⑤ 派活（默认 dry-run；--detach 立刻返回）
<派活入口> --card <号> --spec <卡规格文件> --cwd <卡树> --model <短名> --detach --execute

# ⑥ 首笔落地（八步链；参数面与断点见 pipe-land）
<落地入口> --card <号> --tree <卡树> --task <台账号> --evidence "<读数>" --allow <文件…>
```

首笔落地的时间线与三个最常见的失败：见 [首笔落地](references/first-landing.md)。

## 怎么读结果

- 队列条目立没立住：`python -X utf8 tools/wb_plan.py check` 末行应是「backlog 校验通过：N 张卡，无冲突」；卡数与基点是现算的，**别当常量引用**。
- 树建没建对：`python -X utf8 tools/wb_plan.py worktrees` 打印的 `git worktree add -b <分支> <树路径> <基点>` 与你手上的分支、基点一致（它默认只打印，别把干跑当建好）。
- 首笔落成没落成：`python -X utf8 tools/wb_verify.py --tree .` 五块（提交骨架 / 门禁 / 封存 / 台账 / 审计）逐块对，任一 FAIL 就先修那块。
- 现场六块（队列 / 门禁 / 判决 / 租约 / 栅栏 / 树）：`python -X utf8 tools/pipeline_view.py --json`。
- 卡号与台账号对不上：`python -X utf8 tools/wb_reconcile.py` 的三份清单。
- 队列排批现状（多少张待派、几批）：`python -X utf8 tools/wb_plan.py stats`。

## 起链六步

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | 定层（产品 / 工作链 / 机器） | 能一句话说清改的是哪一层，见 [资产层](../softeng-manage/references/asset-layers.md) |
| 2 | 目录 + 首提交 | `git log --oneline -1` 有新提交，`git status --porcelain` 干净 |
| 3 | 队列条目 | `python -X utf8 tools/wb_plan.py check` 通过 |
| 4 | 卡规格 | 四段齐；`git ls-files --error-unmatch <卡规格文件>` 认得它 |
| 5 | 树 | `git worktree list` 里有那棵树，分支名与队列登记一致 |
| 6 | 首笔落地 | `python -X utf8 tools/wb_verify.py --tree .` 五块无 FAIL |

★ 第 2 步之后先落入口文档：照 [入口文档写法](../pipe-takeover/references/agents-md.md) 写一份，命令必须是真跑过的（新仓没有历史，写 `TODO(verify)` 也要标出来）。

★ 第 4 步的 `git add` 不能省：落地脚本在全量门禁之前先跑一条「卡规格都要在索引里」的钉子，不满足就停手（省下的正是几分钟全量门禁）。

## 常见错与处置

| 现象 | 真因 | 处置 |
|---|---|---|
| 队列校验报同一文件两个写者 | 两张待派卡的写域相交 | 给其中一张加依赖，或把写域拆小 |
| 建树基点很旧 | 队列登记的基点停在旧提交 | 把基点更新到主树当前 HEAD，再建树 |
| 落地脚本退 4（全量门禁之前） | 卡规格没进索引 | `git add <卡规格文件>` 后重跑 |
| 落地脚本退 5（快照之前） | 主树有跟踪改动，且不在白名单 | 把改动挪进卡树；主干只接受合并 |
| 落地脚本退 3 | 卡树 HEAD 不是主树 HEAD 的祖先 | 按脚本提示手工摆树，别让它 `checkout` 抹掉改动 |
| 想给仓外的新仓落地 | 链以这棵树的数据根为单位 | 只在本仓登记卡与项目索引；仓外落地另开一张卡 |

## 自查

1. 我能一句话说清这活属于哪一层，以及为什么。
2. 目录、队列、卡、树、落地五样都有机器产物，不是我口头说「好了」。
3. 我没有把框架层（自带配置文件与门表）和工作链（队列 + 树 + 落地链）混成一条。
4. 目标在仓外时我止步了，没有假装本仓工具能替别仓落地。

> 判据在队列工具、落地链与项目索引三处（本仓分别是哪几个文件见 [本仓绑定](references/repo-bindings.md)）；
> 本技能只讲顺序与前置检查。
