# grill-me：需求拷问（前三层的共同方法）

> 来源：`https://raw.githubusercontent.com/wicanr2/my_skill/main/skills/grill-me/SKILL.md`（2026-10-20 抓取）。
> 上游方法出自 Matt Pocock 的 `grill-me` / `grilling`；许可未核实，本文是**改写摘要**不是原文复制，
> 对外分发前先核实上游许可。

## 什么时候用

**只在前三层**：意图（`docs/intention/`）、规格（`docs/specification/`）、契约（`docs/contracts/`）。
当一项工作会实质改变「目标 / 范围 / 对外接口 / 数据格式 / 验收标准 / 不可逆操作」时用它；
纯实现细节、可从代码或测试查出的事实，**不启动访谈**。

## 四条铁律

1. **事实归 agent，决策归用户**：能查到的（文件、代码、测试、实机、权威网页）先自己查，
   不把查资料伪装成决策题。
2. **一题一答**：默认每轮只问一个会阻塞工作的问题；用户明确要求批量时，才合并互不依赖的问题。
3. **决策树 + 前沿**：父决策未定前不问子问题；每次回答后重算「现在真的阻塞工作」的节点。
4. **不替用户定**：「不知道」「好」「继续」都不是对重大取舍的授权；含糊时只问最小澄清。

## 每个问题的格式（照这个写）

```
已知事实：<文件/测试/证据，标明 exact / 强推断 / 假设 / 未知>
为什么现在要定：<会解锁或暂停哪条分支>
选项：A … / B …（真不同，不凑数）
建议：A，因为 …（建议不是授权）
影响：时间 / 兼容性 / 可逆性
一个问题：你选哪个，或补充，或「不知道」
```

## 对应我们的三层

| 层 | grill-me 帮你定什么 | 落点 |
|---|---|---|
| 意图 | 谁的什么问题、不做什么、怎么算成功 | `docs/intention/needs.md` |
| 规格 | 每条需求的可验证判据、非功能边界 | `docs/specification/functional.md`、`nonfunctional.md` |
| 契约 | 对外接口、数据格式、失败与降级 | `docs/contracts/interactions.md`、`flows.md` |

实现层（`docs/implementation/`）与品味层（`docs/taste/`）**不走访谈**，按已定的规格写。

## 收尾

- 前沿清空后先给「采用 / 排除 / 仍未知 / 受影响的文件」四行摘要，等用户确认；
- 确认后才写进规格；未确认的假设一律标 `假设`，不许写成正式规则；
- 访谈不等于做完：实现仍要过测试与验收。

## 和我们已有流程的关系

- 开卡前用它把「这张卡到底要什么」问清；卡规格里的「要解决的问题」就是访谈产物的浓缩；
- 与 `skills/softeng-manage/references/doc-layers.md` 配合：前三层用访谈定，后两层照规格写。
