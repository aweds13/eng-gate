# 五层文档：每层放什么、什么时候才升到下一层

> 给 `softeng-manage` 用的按需参考。层名与「41 篇」是**本仓 timeflow 实例的读数**，
> 判据在 `scripts/check_layers.py` 与各层自己的门里；本文件只讲怎么落笔、怎么判断该放哪一层。

## 0. 一句话

五层不是五个文件夹，是**五个问题的落点**：为什么做（意图）→ 必须做到什么（规格）→
怎样才算真做成（契约）→ 哪个模块负责（实现）→ 什么算好（品味）。
一份内容只该有一个落点；同一件事写在两层，就是两份会互相漂移的真源。

## 1. 五层各放什么、不放什么

| 层 | 回答的问题 | 放什么 | 不放什么 | 一句话判据 |
|---|---|---|---|---|
| 意图 | 为什么做、不做会怎样 | 需求、用户场景、约束来源、编号（N1…） | 实现方式、字段、命令 | 删掉这段代码，它还照样成立 |
| 规格 | 必须做到什么 | 行为、边界、异常、conventions、可验收条目 | 具体文件与函数 | 用「必须 / 不得 / 当…时」写得出 |
| 契约 | 怎样才算真做成 | 交互、流程、跨域衔接、输入输出形状 | 内部实现步骤 | 两边各自实现后还能对得上 |
| 实现 | 哪个模块负责 | 模块地图、依赖方向、覆盖情况、技术取舍 | 需求本身、验收标准 | 换个实现它就要改 |
| 品味 | 什么算好 | 命名、报错话术、复杂度上限、反面样例 | 功能要求 | 评审时用它吵架，不推翻前四层 |

### 前三层的决策怎么定（意图 / 规格 / 契约）

这三层写的是「为什么做 / 必须做到什么 / 怎样才算真做成」，都要**先问清再落笔**，不是照现状誊写。
方法与四条铁律（事实归 agent、决策归用户、一题一答、父决策未定前不问子问题）见
`skills/softeng-manage/references/grill-me.md`。逐层一句：

- **意图**：先问「谁的什么问题、不做什么、怎么算成功」，编号才落笔 ——
  决策怎么定 → `skills/softeng-manage/references/grill-me.md`。
- **规格**：先问「这条需求拿什么验、非功能边界在哪」，再写「必须 / 不得」 ——
  决策怎么定 → `skills/softeng-manage/references/grill-me.md`。
- **契约**：先问「对外接口、数据格式、失败与降级」，再写交互与流程 ——
  决策怎么定 → `skills/softeng-manage/references/grill-me.md`。
- **实现 / 品味**：不走访谈，按已定的规格与品味条目写。

访谈产物写进对应层之前，先给「采用 / 排除 / 仍未知 / 受影响的文件」四行摘要并等用户确认；
未确认的一律标 `假设`，不许写成正式规则。

写法上的三条硬规矩：

1. **一层只引用上一层，不反向引用**。实现层写「依据 N12」可以；意图层写「见 modules」不行。
2. **跨层的关联走索引，不走正文**（`docs/specification/traceability.md` 是这张索引）。
3. **同一份事实只留一处**：编号留在意图层，验收口径留在规格层，其余地方只写指针。

## 2. 最小可行：两层就够

开始时只需要 **意图 + 实现**：

- 意图层一页：为什么做、给谁、不做会怎样。
- 实现层一页：模块在哪、怎么跑、依赖谁。

**只有**出现下面信号时才补中间三层，不要「先摆五个空目录」。

## 3. 升级时机（出现信号才动，不按项目阶段动）

| 信号 | 补哪一层 | 为什么 |
|---|---|---|
| 第二个使用者或第二个客户端出现 | 契约层 | 两边各自实现，衔接处才是真成本 |
| 同一行为被两处实现、开始不一致 | 规格层 | 需要一份「必须做到什么」来收敛 |
| 返工原因是「没人知道边界」 | 契约层 | 边界是交互问题，不是实现问题 |
| 评审只能凭口味争执 | 品味层 | 把「什么算好」写成可引用的句子 |
| 需求来源说不清、做完被问「这有什么用」 | 意图层 | 先补为什么，再补怎么做 |

不该升的场合：一次性脚本、只服务一张卡的临时目录、纯样例。

## 4. 层与产物的边界（容易混的三处）

- **验收不在五层里**：验收口径写规格层，验收的**记录**写台账（`docs/traceability.toml`）与
  `docs/ACCEPTANCE.md`，两者不重复。
- **卡规格不是五层文档**：卡写「这一笔改什么」，五层写「这个系统是什么」。
  卡里不抄规格层原文，只引用编号。
- **变更记录不是意图层**：`docs/changelog.md` 记发生了什么；意图层记为什么要有。

## 5. timeflow 实例：41 篇怎么分布

取证命令（在本仓根跑，数的是 `docs/` 下五个层目录里的 `.md`）：

```bash
for d in intention specification contracts implementation taste; do
  printf '%-15s %s\n' "$d" "$(find docs/$d -name '*.md' | wc -l)"
done
```

读数（2025 年这次重数）：意图 2、规格 19、契约 14、实现 5、品味 1，合计 41。代表性路径：

| 层 | 入口 | 扩展方式 |
|---|---|---|
| 意图 | `docs/intention/needs.md` | 按编号追加，不重排 |
| 规格 | `docs/specification/README.md`、`docs/specification/conventions.md` | 总纲在根，域细则落在 `docs/specification/domains/` |
| 契约 | `docs/contracts/interactions.md`、`docs/contracts/flows.md` | 交互与流程分文件，域细则落在 `docs/contracts/domains/` |
| 实现 | `docs/implementation/README.md`、`docs/implementation/modules.md` | 模块地图 + 架构 + 覆盖各一页 |
| 品味 | `docs/taste/README.md` | 单页起，条目变多再拆 |

域细则的命名法：两层的域文件**同名对位**（规格层 `docs/specification/domains/F1-tasks.md`
对应契约层 `docs/contracts/domains/F1-tasks.md`，编号到 F10），一眼能对上。
新增一域要先在 `docs/specification/domains/_TEMPLATE.md` 与 `docs/contracts/domains/_CROSS.md`
两份模板里对齐列，再复制出具体域文件。规格层比契约层多一篇模板，其余域文件两层一一对应。

## 6. 五层的常见错

| 现象 | 真因 | 处置 |
|---|---|---|
| 同一段文字在两个文件里 | 两份真源 | 留编号所在的层，另一处改成指针 |
| 意图层出现命令、字段名 | 写成了实现说明 | 下沉到实现层，意图层只留「必须能…」 |
| 规格层写成待办清单 | 混了卡与规格 | 待办进队列，规格只写「必须做到什么」 |
| 契约层写成调用栈 | 写成了实现步骤 | 改写成「谁给谁什么、什么时候、失败怎样」 |
| 加了一层没人看 | 没有消费端 | 先想清楚谁在读它；没有读者就不建层 |

## 7. 怎么自证

```bash
python -X utf8 scripts/check_layers.py
```

它扫 `docs/**/*.md` 里反引号包住的 `.md` 引用，逐条查文件是否存在，输出末行 `LAYER CHECKS: PASS`。
**它不扫 `skills/`** —— 技能里写路径仍要写仓内相对路径，否则读者点不开、机器也不兜底。
