# 复盘 · 提交标签写错（`Task:` 只该写一个卡号）— T-G17

> 触发：用户 2026-09-23 验收本批五张卡时问"什么警告？"—— 我一查，是我自己**提交信息写得不规范**：
> 用户看完说「写成复盘的吧，然后再弄干净」。这份就是那份复盘；弄干净的过程见 §四。

## 一、问题是什么

本项目的提交约定是四行 trailer：

```
Task:  <卡号>            ← 这次提交对应台账里的哪一张卡
Refs:  <文档/编号>        ← 牵扯到哪些规格/契约/复盘
Ledger:<台账怎么动的>
Gates: <门禁结果>
```

规矩是 **`Task:` 里只写一个卡号**。我在这一批的五条提交里，前四条把别的编号也塞进了这行：

| 提交（旧） | 我写成了 | 本该是 |
| --- | --- | --- |
| T-G12 | `Task: T-G12 / OP-33 / SR-F7.1` | `Task: T-G12` |
| T-G13 | `Task: T-G13 / F6 OP-27 延伸` | `Task: T-G13` |
| T-G14 | `Task: T-G14 / SR-F10.1` | `Task: T-G14` |
| T-G15 | `Task: T-G15 / F9 OP-49 延伸 / SR-NF17` | `Task: T-G15` |
| T-G16 | `Task: T-G16` ✅（这条本来是对的） | — |

`OP-33` / `SR-F7.1` 这些编号并没有丢 —— 它们本来就写在 `Refs:` 与 `Ledger:` 行里，
我等于**在两处各写了一遍**，其中一处（`Task:`）不该写。

## 二、为什么没被门禁拦住（这一条值得记住）

`scripts/audit_progress.py` 对 `Task:` 的用法有两处，都要求它**恰好是一个台账编号**：

1. **严格校验**（只审"要提交的那一条"）：`Task:` 的值必须能在台账里找到，否则 FAIL；
2. **台账 ↔ git 对账**（审全部提交）：台账里 `done` 的每张卡，都要能找到一条挂着 `Task:<卡号>` 的提交。

而**门禁里的审计跑的是 `--all` 模式** —— 那个模式**跳过了第 1 项**（历史提交的 trailer 格式从来没查过）。
于是表现成两种症状：

- 手动跑不带参数的 `python scripts/audit_progress.py`（严格模式）时，**HEAD 那条直接 FAIL**：
  `Task: T-G16 / F9 OP-49 延伸 / SR-NF17` 不在台账里 → "做了没登记 / 编号写错"（对，就是编号写错）；
- 历史那四条则表现为**误报**：`[WARN] T-G12: 台账 done，但 git 里没有挂 Task:T-G12 的提交`
  —— 提交明明在，只是标签多带了几个字，对账按整串比对就认不出来。

**为什么五条里只有最后一条 FAIL**：严格模式只审当前 HEAD。前四条在我提交它们的当下不是 HEAD，
等它们变成"历史"时，就只剩误报了 —— 所以我一路都没发现（`--all` 门禁一直是绿的）。

## 三、影响

- **零功能影响**：代码、文档、台账、测试一个字都没错，只是**提交信息不规范**；
- 门禁（`scripts/run_gates.py` 十一项）全程绿；
- 唯一实际代价：严格审计里有 4 行**误报**，以及一条本该 FAIL 的 HEAD（已当场发现并改对）。

## 四、弄干净：怎么改的、怎么验的

**改法**：重建那五条提交，只换提交信息，**文件树一个字不动**。

沙箱下 `git rebase -i` 走不通（git 要 spawn `sh` 建信号管道，被沙箱拒：
`sh.exe: fatal error - couldn't create signal pipe, Win32 error 5`）—— 那是环境限制，不是 git 的问题。
所以改用**不需要编辑器、不 spawn shell** 的路子：

```
git reset --soft <本批之前的那条>       # 分支退回去，工作区/内容不动
每条卡：
  git read-tree <旧提交>                # 索引 = 那条提交的树（原样）
  GIT_AUTHOR_DATE=… GIT_COMMITTER_DATE=…  # 原时间戳照抄（见下"为什么要保留时间"）
  git commit -F <改好的提交信息>
```

**为什么要保留时间戳**：门禁产物 `gates/last.json` 的校验尺子是"它必须比**父提交**更新"
（防沿用旧产物）。如果重建时提交时间变成"现在"，父提交就会比门禁产物还新 → 严格审计会报
"沿用了旧产物"。所以作者/提交时间都照抄原值（连 T-G16 那次 amend 造成的 author/committer 差 2 分钟也照抄）。

**验证**（都是机器判的，不是"我觉得对"）：

1. **逐对比树哈希**：五对旧/新提交的 `^{tree}` **全部相等** → 内容逐字节没变；
   （`1c5b8f74…`/`17f64b15…`/`b97c720f…`/`b29a2b2f…`/`917c7122…`，五对五个相等）
2. **工作区干净**：`git status` 无输出；
3. **严格审计通过**：`python scripts/audit_progress.py` → `审计通过 ✅（豁免 0 项）`，
   且 `[WARN] T-G12…T-G15` 那四行误报**消失**；
4. **trailer 收敛**：五条提交的 `Task:` 现在分别是 `T-G12` / `T-G13` / `T-G14` / `T-G15` / `T-G16`。

新的提交号（旧 → 新，只换标签，树相同）：

| 卡 | 旧 | 新 |
| --- | --- | --- |
| T-G12 | `98896f5` | `166f6ac` |
| T-G13 | `31605ea` | `4a1d6d5` |
| T-G14 | `b931f9c` | `3a54a48` |
| T-G15 | `6844cd8` | `35f10e3` |
| T-G16 | `584ebef` | `c65400e` |

> 这五条提交**只在本机**（没有远端），所以重建不影响任何人；`gates/last.json` 里记的是父提交的
> 短号（那是"门禁跑在哪一版上"的痕迹），短号变了但**时间戳关系不变**，审计照样过。

## 五、教训（一句话）

**`Task:` 只写一个卡号；别的编号写 `Refs:`。** 更一般的那条老教训在这里又出现了一次：
**"我记住了"不算护栏** —— 门禁的 `--all` 模式从来没查过单条 trailer 的格式，所以就漏了。

## 六、遗留（建议，我没擅自做）

门禁里的审计跑 `--all`（跳过单提交 trailer 校验），所以"提交标签写错"这类事**只有手动跑严格模式
才看得见**。想让它在门禁里就拦住，有两条路、都要动门禁口径（属要拍板的事，我没动）：

1. **`--all` 模式也逐条查 trailer 格式**：但老历史里本就有一批"老账"（台账 done 却没有任何
   挂着它的提交），得先定一个基线（从哪条提交起严查），否则一开就红一片；
2. **在提交前加一道本地自检**（比如 `scripts/check_commit_msg.py` + `docs/CODING_GUIDELINES.md`
   里写清格式），把错误挡在提交之前 —— 比事后重建干净得多。
