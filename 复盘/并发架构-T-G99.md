# 并发架构：把「谁和谁能同时跑」做成能跑的调度器（T-G99 · 外包卡 010）

> 一句话：并发一直是**手工**的 —— 主控脑子里记着「哪张卡碰哪些文件、哪棵树空着」，靠记性避冲突，
> 卡数一多必出事。这一版把这套规则做成 `tools/wb_plan.py`：**文件级冲突域 + 拓扑分层 + 同层贪心
> 打包**，拒绝任何会冲突的组合；backlog 落成 `docs/workbacklog.toml`。
>
> 边界（先说）：CLI 侧的速率 / 账号并发**上界未探测**；`worktrees --execute` / `dispatch --execute`
> 这两条"会动世界"的路**没真跑过**（卡 §8 坑 1：别真建树、别真派活）—— 是纸面推理 + 纯函数测试。

---

## 一、角色（权责分明，卡 §2.1）

| 角色 | 是谁 | 只做这些 | 绝不做的 |
|---|---|---|---|
| **规划者 P** | 主控 | 盘点、选题、写卡规格（含**域声明**）、定基点、排批、复核、验收 | 不亲自写代码 |
| **作者 W**（×N） | 工人 | 一棵树一张卡；只碰自己的域；交代码 + 测试 + 自己的复盘 + **台账片段** | 不碰共享文件、不跑全量门禁 |
| **集成者 I**（×1） | 工人或主控 | **串行**收口：cherry-pick 各卡 → 合并台账片段 → 写 changelog/CHECKPOINT/计数 → 全量门禁 → seal → **一次集成提交** | 不改工人的代码内容 |
| **复核者 R** | 工人（只读） | 对**高风险**卡（`risk=high`）做对抗性证伪，写报告 | 不改任何被跟踪文件 |
| **盘点者 S** | 工人（只读） | 挖「还剩哪些活」、分类 A/B/C/D | 不判断产品口径 |

工具把角色关系编码成数据：`docs/workbacklog.toml` 里每张卡带 `tree / files / depends / risk / status`，
四个子命令分别服务 **P（check / plan）** 与 **P+W（worktrees / dispatch）**。

## 二、时序（一轮的固定顺序，卡 §2.2）

```text
T0 P: 盘点 → 选题 → 写规格（含 files 域）→ 建树（基点 = 已复核提交）→ 登记 backlog
T1 W×N: 并行干活（各在自己树里，互不可见）
T2 W×N: 各自提交（只含自己域的文件）
T3 P: 五条机械复核（tools/wb_review.py）；高风险卡另派 R
T4 I: 串行集成（cherry-pick → 台账片段合并 → 共享文件 → 全量门禁 → seal → 一次集成提交）
T5 P: audit + 收尾（拆 worktree、更新面板）
```

`wb_plan.py` 卡在 **T0 的「排批」** 与 **T0/T5 的「建树 / 拆树」**：它不替 P 选题、不替 I 收口，
只回答一个机械问题 —— **给一批卡和上限 N，哪些能同批跑**。

## 三、并发会带来的技术问题 + 已定的解法（卡 §2.3；★ 本卡交付之一）

| # | 问题 | 解法（本项目已定 / 本卡实现的） |
|---|---|---|
| 1 | 同一文件两个写者 | **文件级冲突域**：`validate()` 拒绝两卡 `files` 相交；`greedy_pack()` 同批内再判一次 |
| 2 | 一棵树只能一个写者 | 规划器保证一棵树一个工人：`validate()` 拒同树；`greedy_pack()` 同批内树不重复 |
| 3 | 共享文件冲突（台账/changelog/交接/gates 产物） | 作者**一律不碰**；`PROTECTED_FILES` 六个一律拒单；台账由作者写**片段**，集成者串行合并 |
| 4 | `gates/last.json` 的 rev/seal 只对"最后一笔"成立 | 作者不跑门禁、不碰 `gates/**`；门禁在集成时跑一次，seal 归集成者 |
| 5 | ★ 改 `src/**` 的卡跑不了全量门禁 | `docs_sync_precheck` 读工作区改动并要求同笔改台账 → 作者改 src 时跑门禁必红 → **作者只跑轻门**（机制推出来的，不是口味） |
| 6 | 提交历史线性化 | 用 **cherry-pick**；基点必须是**已复核提交**（`[base].reviewed`）；**禁止作者改写已发布历史**（`reset --soft` 真踩过，会让别人的树基点变孤儿） |
| 7 | 门禁/测试抢 CPU 与端口 | 并发期只跑轻门；起服务的门只在集成时串行跑 |
| 8 | 机器资源（CPU/内存/磁盘） | 并发上限 `--concurrency`（建议 `N ≤ max(2, cores//2)`）；每个工人一个 CLI 进程 + 一份 log |
| 9 | CLI 侧速率/账号并发 | ★ **未知上界** → 本卡**不解决**，只把 `--concurrency` 显式摆出来以便观测（如实记：未探测） |
| 10 | 状态文件名冲突 | 文件名带卡号 → 天然唯一；同名卡跨树靠 `卡@树` 区分（`wb_dash.py` 已做） |
| 11 | 依赖关系（同域串行） | backlog 声明 `depends`；`topo_layers()` 做**拓扑分层**，同层才并行（层号取最长路径，见下） |
| 12 | 失败隔离 | 工人在自己树里失败 = 丢一棵树，主树不受影响；集成失败可 `cherry-pick --abort` |
| 13 | 可观测性 | 面板（多树，`wb_dash.py`）+ `--status`（单卡）+ 本卡 `plan` 的批次输出 |
| 14 | 审计口径与并发 | audit 检查提交范围内 `Task:` 恰好一个 → **集成提交用其中一张卡的 Task，其余写 `Refs:`**；作者提交时台账条目还不存在也没关系（audit 读**最终**台账） |
| 15 | `.wt/` 孤儿树 | 集成后必须 `git worktree remove`；`worktrees` 子命令把该建/该拆的列出来供核对 |
| 16 | 作者越界 | 事后机器检查 `wb_review.py --allow`；卡里要求作者**提交前自跑一次** `git status` 只显示白名单 |

## 四、怎么算批次（实现的机械口径）

1. **拓扑分层** `topo_layers()`：没有依赖的在第 0 层；某卡在第 k 层 = 它的依赖都在 < k 层。
   层号取 **最长路径**（不是最短）—— 一张卡既依赖第 0 层的 A、又依赖第 1 层的 B，它必须在第 2 层
   （等 B 做完）；取最短会把它提前到跟 B 同批。菱形依赖（A→B、A→C、B→D、C→D）下 D 落第 2 层。
   成环 → 抛 `BacklogError`（`validate()` 已经先拦过）。
2. **同层贪心打包** `greedy_pack()`：按序把每张卡塞进第一个**装得下**的批（批 ≤ N 张、同批两两
   `files` 不相交、同批树不重复）；都装不下就开新批。所以"同层三卡两两相交"只能各占一批 ——
   **冲突域是硬约束，并发上限只是第二约束**。批次**不跨层**（依赖靠层保证顺序）。
3. `plan_batches()` = 逐层贪心打包拼接；`plan` 子命令把它渲染成人看的一段段。

## 五、六个受保护共享文件（写死在工具里，卡 §2.4）

```text
docs/traceability.toml, docs/changelog.md,
复盘/交接-重构进度.md, 复盘/新窗口交接卡.md,
gates/last.json, gates/reuse.json
```

`PROTECTED_FILES` 是一个 `frozenset`；测试逐条参数化断言**每一个都被拒**（常量里有、判据不认 =
假护栏）。

## 六、★ check 口径的一处取舍（如实记，这是我定的，不是规格明写的）

卡 §3.2 把「① 两卡 `files` 相交」与「③ 同一批里两卡用同一棵树」都列在 `check`（"只校验，不输出
批次"）下。两条措辞不同 —— ① 没加限定，③ 写着"**同一批**里"。我按**最保守**的一种实现：

- `validate()` 把**整份 backlog 当作同一批**来判 → ①③ 都是**全局**拒单（种子四卡零相交、四棵不同树，
  照过）。
- `greedy_pack()` 里那道"同批内两两不相交 + 树不重复"是**运行时的第二道**（防御：即使有人绕过
  `check` 直接排批，也不会把冲突的卡放进同一批）—— 它单独用纯函数测（"同层三卡两两相交 → 各占一批"）。

**代价（写清楚）**：全局口径下，**串行的两张卡（`depends` 链）不能复用同一棵树**，也**不能碰同一
文件** —— 而顺序复用其实是安全的。也就是说 `check` 比"真需要"严。我选严的这边，理由是
「一份 backlog 就是这一轮要排班的卡，宁可让人把历史卡移出去，也不要漏判」。**这一条若与主控口径
不合，请指出来，我按主控定的改。**

## 九、边界（如实写，没做到的部分）

1. **CLI 侧速率 / 账号并发上界未探测** —— 卡 §2.3 #9 明说本卡不解决；这里只把它做成一个显式的
   `--concurrency` 参数以便观测，**不声称知道上界**。
2. **`worktrees --execute` / `dispatch --execute` 没真跑过** —— 卡 §8 坑 1 明令别真建树、别真派活。
   两条路都实现了（`subprocess` 真调），但没有真机证据；测试只覆盖**命令拼装**（纯函数）。
3. **排班不考虑"卡内部再分片"** —— 一张卡 = 一个不可分的调度单位；卡内并行不在本工具视野。
4. **`plan` 的贪心不是最优打包** —— 只是"按序塞第一只装得下的批"。批数最少是装箱问题（NP），
   本工具要的是**确定性 + 可解释**，不是最优。
5. **`.wt/` 存在性 / 基点是否真已复核** —— 工具只**打印**建树命令，不校验那个 sha 是否真被复核过、
   worktree 是否已存在（`check` 也不校验 `[base].reviewed` 是否合法 sha）。这是"P 的职责"留在人这边。
6. **检查口径偏严**（见 §六）：`depends` 链上的两张卡若复用同一棵树 / 同一文件，会被 `check` 拒。
7. **种子里的 spec 路径**（007/008/009）是**按命名惯例填的**（只 010 那张真存在）——
   卡 §7 只给了 files 域与标题，没给 spec 路径。
