## ① 目标与优先级

### 1.1 优先级（★ 照用户原话写死）

> **自己先能用得好 > 好维护 > 别人也能用。**

三条我**不许调序**：自用优先是第一位（这是本设计的**质量模型**——对齐 **ISO/IEC 25010** 的「功能性/可用性」优先于「可移植性/可复用性」）。「别人也能用」是**副产品**，不是起点。

> **泛用性 = 不绑项目 / 不绑平台 / 不绑某个产品（agent runtime）。**

这三条对应 **ISO/IEC/IEEE 12207**（软件生命周期过程：过程与产品解耦）与 **ISO/IEC/IEEE 24765**（术语中立）。判据是**可验证的**：**能在第二个仓里跑通**（§⑥ 落地顺序的硬条件）。

### 1.2 ★ 为什么**不做成插件**

插件（plugin）**绑死一个 `agent runtime`**：它的加载协议、生命周期、权限模型都由那一个 runtime 定义。换一个 runtime（或换一个版本），插件就废 —— 这正是**泛用性最差**的形态。

- **依据**：`复盘/决策-框架居所与推进.md` §四 明确把「把框架做成插件」列为**被否掉的**（原话口径：「插件绑死一个 agent harness，泛用性最差」）。
- **对齐**：插件生态的契约是**厂商私有**的（各 runtime 自定），没有跨 runtime 的公共标准；做插件 = 把「不绑某个产品」这条**主动放弃**。

### 1.3 ★ 为什么**主体是 CLI + 模板仓**

**CLI** 恰好满足**两类调用者**的契约（★ 照卡 177 术语表 §2）：
- **程序 / agent 调** → 要**稳定退出码** + **`--json`**（结构化、字段不随文案漂）+ **stdio 分离**（stdout 只放数据 / stderr 只放诊断）+ **幂等可重入** + **不弹交互式提问**；
- **人调** → 要 **`--help`**（自描述）+ **人话错误**（说清 what/why/怎么改）+ **默认安全**（危险动作显式旗标，如 `--allow-write`）。

CLI 这条契约的**公共标准**是现成的：**POSIX exit status（0–255）** + **BSD `sysexits.h`** + **GNU Coding Standards**（三者关系见 §③.1）。
**核心是库、CLI 是薄壳**（★ 照卡 177 §4）：别人「只调用」用 CLI，「要扩展」`import` 库。

**模板仓**（`pipe init` 铺出的骨架）是**分发形态之一**：它把「配置 + 目录布局 + 判据 + 钉子」一次性交到用户手上，用户改配置就能用，**不必改框架源码**。取舍：模板仓**铺得快、本地可改**，但**升级难**（用户本地漂移）；包升级易但铺得少。两者的取舍与推荐组合见 **§⑤.4**。

### 1.4 规范对照（本节）

| 我们的决定 | 官方规范 / 协议 | 对齐方式 |
|---|---|---|
| 优先级：自用 > 可维护 > 别人可用 | **ISO/IEC 25010**（产品质量模型：功能性/可用性 > 可移植性/复用性） | 按质量特性排序 |
| 泛用性 = 不绑项目/平台/产品 | **ISO/IEC/IEEE 12207**（生命周期过程解耦）；**ISO/IEC/IEEE 24765**（术语中立） | 过程与产品解绑 |
| 主体 CLI（两类调用者契约） | **POSIX** exit status；**BSD `sysexits.h`**；**GNU Coding Standards** | 见 §③.1 的单表 |
| 核心库 + 薄壳 | 无单一标准；**Diátaxis**（`reference` vs `how-to` 分读者） | 库给 `reference`，CLI 给 `how-to` |
| 模板仓（scaffolding） | 无 ISO 编号；**Diátaxis `tutorial`**（手把手走通） | `pipe init` 产物定位为 tutorial |
| **不做插件** | —— | **out-of-scope，非 out-of-spec**：这是**取舍**（放弃厂商私有契约），不是「覆盖不到」 |

## ② 配置 schema：`pipeline.toml`（草案）

`pipeline.toml` 是**唯一把项目相关值外置的地方**（对齐卡 177 泛用性条件③「项目相关值全部外置」）。它取代现在**散落三处**的项目专有值：`harness.toml`（缝层）、`tools/wb_dispatch.py:132` 的 `MODEL_WHITELIST`、`scripts/run_gates.py` 的端口常量。

## ③ 命令面（草案）

**命令总入口 = `pipe`**（薄壳）。共 **8 条命令**（每条都写：输入 / 输出 / 退出码 / 幂等性 / 能否 `--json`）。8 条命令 = 本仓现有机制的**一个统一命名面**，不新增机制。

### ③.1 ★ 唯一退出码表（先定这一张，别再长第五套）

**病灶（真现场）**：现在有**四套互不兼容**的表（★ 照卡 177 术语表 §1 现算）——`run_gates.py` `0/1/2/3/124`、`timeflow` CLI `0/1/2/3/4`、`wb_dispatch.py` `0/2/4/6/7`、`run_bg.py` `0/2/3`；**`1` 与 `3` 同码不同义**（`1`：门红 vs 用法错；`3`：资源闸 vs 环境错）。这是泛用性条件①（★ **我们现在不满足**）的根。

**设计：一张表，全部命令共用**（`pipeline.toml` 的 `[exit_codes].table_version` 引用它）：

| 码 | 义 | 规范出处 / 对齐 |
|---|---|---|
| `0` | 通过 | **POSIX** exit status |
| `1` | **判据不通过**（门红 / 审计红 / 检查报错） | POSIX 惯例（`grep`/`diff` 的非 0 = 「有差异」，≠「程序错」） |
| `2` | **用法 / 参数错** | ★ **out-of-spec 第 3 条**：`sysexits.h` 用 `64 EX_USAGE`；本表**暂留 `2`**（四套现表共用，改动面最小）→ **对齐路径**：主版本升级时迁到 `64` |
| `3` | **资源闸拒跑**（内存 / 并发不够） | ★ **out-of-spec 第 4 条**：`sysexits.h` 无此义（近 `69 EX_UNAVAILABLE` / `75 EX_TEMPFAIL`）→ 对齐路径：并入 `75`（可重试的临时失败） |
| `4` | **被策略拒绝**（缺 `--allow-write` / 越界域 / 白名单外模型） | **`77 EX_NOPERM`**（无权限）语义 |
| `5` | **前置条件缺失**（文件 / 段 / 键不存在；可修了再来） | **`66 EX_NOINPUT`** + **`78 EX_CONFIG`**（配置错） |
| `6` | **被外部打断**（超时 / 被掐 / 撞上限；**本轮不算数**，可续跑） | **`75 EX_TEMPFAIL`**（临时失败，可重试） |
| `7` | **资源全挂，停止**（模型白名单全被限流） | ★ **out-of-spec 第 5 条**：无标准码；① 为什么只能这么用：它要求「**停止、不再自动重试**」（照 §19.2），与 `6` 的「可续跑」**语义相反**，必须分开；② 对齐路径：并入 `sysexits` 的 **`69 EX_UNAVAILABLE`** |
| `124` | **单道门硬超时**（到点掐整棵进程树） | **GNU `timeout`** 约定（coreutils 手册；`run_gates.py` 文件头沿用） |

**★ 硬禁**（照卡 177 §1 三个雷区）：**永不发** `126` / `127` / `128+N`（shell / 信号层保留）；退出码**只用 0–255**（POSIX 只保留低 8 位，Windows 跨进程传大码走 stdout / 文件）。

### ③.2 八条命令

> 统一约定（照卡 177 §2）：**stdout 只放数据 / stderr 只放诊断**；**不弹交互式提问**；`--help` 自描述且**含退出码表**；`--json` 给结构化（字段不随文案漂）。

#### 1. `pipe init`

- **输入**：`--template <名>`（默认 `minimal`）｜`--dir <路径>`｜`--force`。
- **输出**：铺出的骨架目录 + `pipeline.toml` 初稿；stdout 一行汇总（铺了 N 个文件）。
- **退出码**：`0` 铺好 ｜ `2` 用法错 ｜ `5` 目标已存在且未 `--force` ｜ `4` `--force` 目标在仓外（越界）。
- **幂等性**：**否**（会写文件）；`--force` 覆盖 = 显式动作。
- **`--json`**：**能**（列出铺出的文件清单）。
- ★ 对齐：**模板仓**（§④）；Diátaxis `tutorial` 产物。

#### 2. `pipe gate`

- **输入**：`--only <门名…>` ｜ `--quick` ｜ `--fast` ｜ `--affected <路径…>` ｜ `--seal` ｜ `--json`。
- **输出**：每道门 `exit_code` + `seconds` + 结论；结构化落 `[paths].gates_state`；SARIF / JUnit 落 `[reports]`。
- **退出码**：`0` 全绿（所有阻断门 `exit_code==0`）｜ `1` 有门红 ｜ `2` 用法错 ｜ `3` 资源闸 ｜ `6` 被掐 ｜ `124` 单门超时（落 `last.json`，**整趟非 0**）。
- **幂等性**：**是**（重跑读同一输入得同一结论；真机门有增量执行）。
- **`--json`**：**能**（等价 `last.json` 的 stdout 版）。
- ★ 对齐现 `scripts/run_gates.py`（17 道门；`--seal` 走 `pipe trace seal`）。

#### 3. `pipe doctor` ★ 金丝雀自检：门还活着吗

- **输入**：无（读配置 + 环境）。
- **输出**：对**每道门**跑它的 **`nail`（反例钉子）**：钉子**红** = 门有牙（正常）；钉子**绿** = **门失效**（判据变成注释）。
- **退出码**：`0` 全部门都咬得住 ｜ `1` 有门失效（钉子绿的） ｜ `5` 配置 / 段 / 键缺失。
- **幂等性**：**是**（只读 + 起钉子子进程，**不改仓**）。
- **`--json`**：**能**（每门：`name` / `nail` / `nail_verdict`）。
- ★ 对齐：**Google SRE Workbook「Canarying Releases」**（金丝雀）；术语表 #29；**INV-37**（判据自证看得到东西）。

#### 4. `pipe card new`

- **输入**：`--id <卡号>` ｜ `--title <标题>` ｜ `--domain <路径…>` ｜ `--json`。
- **输出**：从 `[cards].spec_template` 生成 `[cards].cards_dir/<id>-<slug>.md` + 预登记到 `[cards].backlog` 与 `[cards].claims_dir`。
- **退出码**：`0` 生成 ｜ `2` 用法错 ｜ `4` 卡号已存在 / 域含受保护文件（`PROTECTED_FILES`，照 INV-18） ｜ `5` 模板缺失。
- **幂等性**：**否**；**已存在 → `4`**（不覆盖）。
- **`--json`**：**能**（`card_id` / `spec_path` / `domain`）。
- ★ 对齐：卡规格模板（§18.3）；**BPMN 2.0 Task**；**预声明 Preregistration**（Nosek et al. 2018）。

#### 5. `pipe claim`

- **输入**：`--task <任务号>` ｜ `--member <成员号>` ｜ `--status success|failed` ｜ `--files <路径…>` ｜ `--why <一句>` ｜ `--evidence <指针>` ｜ `--json`。
- **输出**：一行申请结果；写入 `[cards].claims_dir`。
- **退出码**：`0` 收下 ｜ `2` 用法错 ｜ `4` 投 `failed`（**挡住集成与发布**，照 §18.3 §5′）｜ `5` 任务 / 成员未预登记。
- **幂等性**：**是**（同内容重复提交不重复记账；不同内容 → 覆盖并留痕）。
- **`--json`**：**能**（`task` / `member` / `status` / `accepted`）。
- ★ 对齐现 `tools/wb_task.py claim`（**成功必须带 `--evidence`**，没证据不叫申请）；域检查按**卡树实际改动 vs 权威域**（照 §23.8 / B-FIX3），**不吃自报清单**。**OASIS WS-HumanTask 1.2** 的 `claim`/`complete` 状态机是最接近的标准。

#### 6. `pipe land`

- **输入**：`--task <任务号>` ｜ `--dry-run` ｜ `--json`。
- **输出**：集成与发布流水线**七步**逐步行（回退派生物 → 迁树 → 文书 → 门禁 → 封存 → 白名单提交 → 审计 → ff）；`--dry-run` 只算不写。
- **退出码**：`0` 落成一笔 ｜ `1` 中间任一步红 ｜ `2` 用法错 ｜ `3` 资源闸 ｜ `4` **集齐条件未满足**（还缺成员申请）｜ `6` 被掐。
- **幂等性**：**是**（开跑前 `reset_derived()` 回退派生物，照 T-G250）。
- **`--json`**：**能**（`step` / `ok` / `detail`）。
- ★ 对齐现 `tools/pool/landing.py` + `tools/wb_land.py`（照 §18.3 §5′）。

#### 7. `pipe ledger check`

- **输入**：`--all` ｜ `--commit <rev>` ｜ `--missing` ｜ `--json`。
- **输出**：逐条证据求值（现支持 `file:` / `text:` / `route:` / `table:` / `column:` / `ui:` / `test:`，照 §22；新增 `sym:` 候选见 §追加 B）+ 不变式核查（`invariants`）。
- **退出码**：`0` 全过**且豁免 0** ｜ `1` 有证据失败 / 豁免非 0 ｜ `2` 用法错 ｜ `5` 台账或登记册文件缺失。
- **幂等性**：**是**（只读）。
- **`--json`**：**能**（每条：`id` / `assertion` / `ok` / `detail`）。
- ★ 对齐现 `scripts/audit_progress.py` + `scripts/check_toml.py` + `tools/wb_invariants.py`。

#### 8. `pipe trace seal`

- **输入**：`--reason <为什么>`（改封存**必须给**，照 §8 坑 5）｜`--json`。
- **输出**：更新 `[paths].gates_state` 的 `tree` 字段（`HEAD^{tree}` 剔 `[seal].ignore`）；事件落 `[events].ndjson_path`。
- **退出码**：`0` 封存 ｜ `1` 差异未清（工作区不干净） ｜ `2` 用法错 ｜ `5` 拿不到 HEAD。
- **幂等性**：**是**（同一棵树重复封存得同一指纹）。
- **`--json`**：**能**（`tree` / `rev` / `algorithm`）。
- ★ 对齐现 `scripts/run_gates.py --seal`；**电子封印 eIDAS (EU) 910/2014** 是「封印」一词的规范出处，**SHA-256** 照 FIPS 180-4。

## ⑤ 扩展点与「严谨改进」的机制

### ⑤.1 项目专属门怎么加：**目录式 `gates.d/*.toml`**（推荐）vs 单文件集中声明

| 走法 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A（推荐）** | 一个门一个文件 `gates.d/<名>.toml` | ① **追加式**改动，并行冲突面最小（照「台账只许末尾追加」的同一精神）；② 单个门可独立 diff / 独立评审；③ 可以按门归属不同的人 | 目录里文件多；需要一次「合读」 |
| B | 全部塞进 `pipeline.toml` 的 `[gates.<名>]` | 一份文件看全 | 两个门卡同时改 → **必冲突**；大文件难 diff |

**决定：A 为主，保留 B 为回退**（`[gates].gates_dir` 不填则回落主文件）。**判据可验收**：`pipe gate` 先读 `gates_dir/*.toml`，再并入主文件的 `[gates.<名>]`；**同名冲突 → `5`（拒跑并点名）**。
**规范对照**：门的声明 ≈ **CI pipeline 定义**；**BPMN 2.0** 里「网关 / 汇聚」表「多道门 + 归集屏障」。

### ⑤.2 ★ 判据随件走：没有反例钉子不许进门

**规则（照 §18.3 + INV-37 + 卡 175 #28/#100）**：**每条判据必须自带反例钉子（counterexample nail）**，钉子是**故意坏掉必须红**的用例名。**没有钉子的门，`pipe gate` 直接拒收（`5`）** —— 这是 `[gates.<名>].nail` **必填**的理由。

- **机器落点**：`pipe doctor` 对每道门**真跑一遍它的钉子**，钉子绿 = 门失效（`1`）。
- **为什么必须这样**：一个「恒绿」的判据等于**注释**（术语表 #12「判据有牙」；INV-37「判据自证看得到东西」）。「先造一个故意坏掉的用例」是本仓的**反空转**纪律（§3 铁律 4）。
- **规范对照**：证伪 **Falsification**（Popper 1963）；回归测试（ISO/IEC/IEEE 29119）；★ 术语表 #28 标「反例钉子」为**自造词**。

### ⑤.3 版本化与向后兼容

| 版本号 | 谁持有 | 规则 |
|---|---|---|
| **框架版本** `framework_version` | 框架自己（SemVer） | 主版本 = 有破坏性变更；次版本 = 加能力；补丁 = 修 |
| **配置 schema 版本** `schema_version` | `pipeline.schema.json` 的 `$id` | **主版本不符 → 拒跑（`5`）并给迁移命令**；次版本 → **兼容读**（新增键有默认） |
| **退出码表版本** `exit_codes.table_version` | §③.1 的表 | 表变 → 版本变；引用它的配置不静默漂 |
| **台账证据语法版本** | `ledger` 文件头的语法声明 | 加前缀（如 `sym:`）= 次版本；改前缀语义 = 主版本 |

**向后兼容策略（可验收）**：`pipe` 启动先校验 `schema_version` 主版本；不符 → 打印「你的配置是 X，框架要 Y，迁移命令：`pipe init --upgrade`」，退 `5`，**不猜、不静默降级**。**规范对照**：SemVer 2.0.0；JSON Schema 2020-12 的 `$schema`/`$id`；SPDX / CycloneDX 的版本化惯例。

### ⑤.4 升级路径：模板仓 vs 包升级（给出取舍与推荐组合）

| 形态 | 升级易度 | 本地漂移 | 推荐用途 |
|---|---|---|---|
| **模板仓**（`pipe init` 铺出） | **难**（用户已改本地文件；框架改了模板，用户怎么并？） | 高 | 铺「配置 + 目录布局 + 钉子」这类**用户会改**的东西 |
| **可发布包**（`pip install -U framework`） | **易**（`pip` 直接升级） | 低（用户不改库） | 升级「核心库 + 薄 CLI」这类**用户不该改**的东西 |

**推荐组合（定案）**：
1. **核心库 + 薄 CLI 走包**（`pip install -U framework`）—— 用户不碰库，升级无痛；
2. **模板仓走 `pipe init`** + 在铺出的骨架里**写版本戳**（`framework_version`）+ `pipe init --upgrade` 做**三方合并**（用户改动 / 旧模板 / 新模板）—— 冲突显式，不静默覆盖；
3. **阶段三（未排）才决定分发形态**（可发布包 / 模板仓的组合），阶段一**不提前设计**（照卡 §追加③：分发形态先不定）。

**规范对照**：模板升级的「三方合并」≈ **git 三方合并**；包升级 ≈ **SemVer 兼容性**；**「标准覆盖不到」** ⇒ 标 out-of-spec。

### ⑤.5 规范对照（本节）

| 我们的机制 | 官方规范 / 协议 | 对齐方式 |
|---|---|---|
| `gates.d/*.toml` | **BPMN 2.0**（Task / Join Gateway）；CI pipeline 定义 | 目录式声明 |
| 反例钉子 | **Falsification**（Popper 1963）；**ISO/IEC/IEEE 29119**（回归） | ★ 术语表 #28 标**自造** |
| 版本化 | **SemVer 2.0.0**；**JSON Schema 2020-12** | `$id` / 三段号 |
| 三方合并升级 | **git 三方合并**；★ **——（超出规范）** | **out-of-spec 第 7 条**：① 无「模板仓升级」的公共标准；② 对齐路径：**CUE**（配置可合并）或 **OCI Artifact** 分发 |
