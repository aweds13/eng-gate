# 接口 500：分组不存在时建任务崩了（T-G33）

> 这张卡是**渲染验证层的副产品**：建种子数据时，`POST /api/tasks` 带一个不存在的分组，直接
> `500 Internal Server Error`。原本只是"我的 fixture 写错了"，但顺手一查，发现是**两个真缺陷**。

---

## 1. 撞到的现象

```
POST /api/tasks  {"title":"补交上周的实验报告","priority":"高","groups":["高数/作业"]}
→ 500 Internal Server Error
```

对照组：`POST /api/tasks` 不带 `groups` → 200，一切正常。把 `groups` 换成**不存在**的 id 也一样 500。

## 2. 根因：一个 `KeyError` 没被接住

```python
# core/tasks/groups.py
def set_task_groups(conn, task_id, group_ids):
    """... 分组不存在 → KeyError（先 create_group 再关联是调用方的事 —— 不在这里偷偷建）"""
    ...
    get_group(conn, key)          # ← 不存在就抛 KeyError(f"分组不存在: {key}")
```

```python
# api/app.py（修前）
@app.post("/api/tasks")
def create_task(payload: TaskIn) -> TaskOut:
    try:
        t = tm.create_task(...)
        if payload.groups:
            tm.set_task_groups(conn, t.id, payload.groups)   # ← KeyError 从这里逃出去
        return _out(t, conn)
    except ValueError as e:                                   # ← 只接了 ValueError
        raise HTTPException(400, str(e))
```

领域层抛 `KeyError` **是故意的**（`tests/test_task_group_names_line.py` 明确钉住"不存在的 id → KeyError，
不静默建一个『差不多』的组"）—— 所以**不该改领域层**，该修的是 API 层没接。

**为什么 `KeyError` 会变成 500 而不是 404**：它一路逃到 Starlette 的异常中间件，
在那里变成"未处理错误"（堆栈里能看到 `unhandled errors in a TaskGroup`）。

## 3. 顺手查出的同族第二处：指错了对象

`PATCH /api/tasks/{task_id}`（编辑任务，也能改 `groups`）抛的**同一个 `KeyError`**，被这条接住了：

```python
    except KeyError:
        raise HTTPException(status_code=404, detail="任务不存在")   # ← 分组不存在也报这句
```

于是"任务好好的、只是分组写错"会得到 **404「任务不存在」** —— 状态码对了，话**指错了对象**。
（这一类"两种错混成一句话"的毛病，与 T-G31 那条『证据只覆盖两个词』是同一族：
**话说得越笼统，越容易糊住真问题**。）

## 4. 修法：把输入**先验干净**，而不是等它抛

只加一个 `except KeyError → 404` 也能让状态码变对，但会留下一个更难看的东西：
**关联是在任务落库之后才做的** —— 失败时任务**已经写进库**，客户端看到报错、库里却多一条，
重试就多两条。所以修法是**先验证、再动手**：

```python
def _require_groups(group_ids: list[str]) -> None:
    """任务上要挂的每个分组都必须已经存在（不存在 → 404，并说清是哪个 id）。"""
    missing = [...]
    if missing:
        raise HTTPException(status_code=404, detail="；".join(missing))
```

- 建任务：`_require_groups(payload.groups)` 放在 `tm.create_task(...)` **之前**；
- 改任务：`if "groups" in payload: _require_groups(...)` 放在 `tm.update_task(...)` **之前**；
- 口径**照抄隔壁那条已有路由**（`POST /api/tasks/{task_id}/group`：任务不存在 404「任务不存在」、
  分组不存在 404「分组不存在」），不另造一句话、不另发明一个状态码。

**残留边界（如实写，不假装解决）**：验完之后若再出数据库级错误，任务仍然会留下 ——
两个 core 函数各自 `commit`，没有跨函数事务。要彻底解决得动事务边界，不在这张卡里做。

## 5. 验证（四层，都可核）

| 层 | 证据 |
|---|---|
| 用例 | `tests/test_task_groups_line.py::test_api_task_create_or_update_with_unknown_group_is_404`：① 建任务带坏分组 → 404 + 说清 id；② **任务不许被留下**；③ 改任务同样 404 且**不再说"任务不存在"**；④ 真任务不存在仍是老口径 |
| **证明不假红** | 把 `app.py` 的修复 stash 掉再跑：用例**当场失败**，堆栈里正是逃出去的 `KeyError: 分组不存在: nope`（"unhandled errors in a TaskGroup"）—— 这条用例确实是拦这个缺陷的，不是摆设 |
| 门禁 | 全套（含 `pytest` / `audit` / `contract` 那几道） |
| 真机 | 渲染层的种子数据现在能造全（`POST /api/tasks` 带 `groups` 走的是**分组 id**）—— 那一层在 fixture 没造全时会**硬失败**，不会拿半份数据建黄金 |

## 6. 教训（一句话）

**"我的 fixture 写错了"值得再往下看一眼。** 这次就因为多看了一眼，把一个 500 和一个
"指错对象的 404"一起收掉了 —— 而它们此前穿过全部 14 道门，因为**没有任何一道门会带一个坏分组去建任务**：
pytest 测的是"用对了就对我"，门禁测的是"能跑通"，而**"用错了会怎样"**只有真的用错一次才会露出来。
