# 复盘 · 门禁跨午夜暴露的时区口径缺陷（T-D12）

> 性质：**缺陷复盘**（问题 / 怎么露出来的 / 为什么以前没发现 / 修法 / 教训）。
> 上游：D 批 · T-D11（口径开关）+ 门禁 `scripts/run_gates.py`。
> 结果：`review.py` 的日期口径从 **UTC** 改回**本地日历**；`SR-NF8`/`T-D11` 的提交被这条挡住过一次。

---

## 一、问题

`tests/test_review_line.py::test_undo_review_restores_card_and_accounting` 断言：

```python
assert state["due_date"] == date.today().isoformat()  # 回到复习前的到期日
```

跑出来是：

```
AssertionError: assert '2026-09-21' == '2026-09-22'
```

**不是测试写错了**：在 `src/timeflow/core/review/review.py` 里

```python
def _now() -> datetime:
    return datetime.now(timezone.utc)          # ← 全项目唯一用 UTC 的地方
```

而 `create_item` 拿它落库：

```python
(rid, title, form, source, _now().date().isoformat(), ...)   # due_date / created_at
```

同一个 `review()` 里，另一处却用本地：

```python
reviewed_on = date.today().isoformat()          # 本地
next_due = new_card.due.date().isoformat()      # UTC ← 同一个函数里两套日历
```

也就是说：**东八区 0:00~8:00 这段时间里，新建的复习卡到期日会存成"昨天"**，
复习后推进出来的下次到期日同样偏一天 —— 而"今天该复习"的判定（`due_items`）用的是本地今天。
前端早就修过同类问题（changelog：「`todayISO()` 按本地时区拼串（不用 `toISOString()`，东八区晚上会差一天）」），
后端这处漏了。

## 二、怎么露出来的（为什么以前全绿）

- 之前所有门禁运行都发生在**本地时间与 UTC 同一天**的时段里（本地 08:00~24:00），
  那时 `_now().date() == date.today()`，断言恒成立 —— 缺陷被时间窗口藏住了。
- 这轮 T-D11 收尾跑门禁时，本机时间已经是 **09-22 07:19（本地）/ 09-21 23:19（UTC）**，
  正好落进那个 8 小时窗口 → 断言当场炸。
- 关键证据（一条命令就能复现）：

```powershell
python -c "from datetime import datetime,timezone,date; print(datetime.now(timezone.utc).date(), date.today())"
# 2026-09-21 2026-09-22
```

**结论：这条失败与 T-D11 的改动无关**（T-D11 只读 `app_settings`、只影响债务读数），
是一处**早就存在、只在特定钟点显形**的缺陷被门禁抓了出来。

## 三、口径依据（为什么按"本地"修，而不是改测试）

规格层写着，没有解释空间：

> `docs/specification/behaviors.md`：**一律本地时区、本地日期；日界 00:00。**

所以：
- 把测试改成迁就 UTC（例如拿 `_now().date()` 去比）**是错的** —— 那等于把缺陷写成口径；
- 正确修法是让 `review.py` 回到全项目统一的本地日历。

## 四、修法（T-D12）

FSRS 的时刻照旧按 **UTC** 走（它算的是"哪个瞬间"，不该动）；**落库/返回的日期一律换成本地日历**：

| 位置 | 改法 |
|---|---|
| `_local_date(moment)`（新） | 把一个时刻落成本地日历日：`moment.astimezone().date().isoformat()` |
| `create_item` | `due_date` / `created_at` = `date.today()`（本地），不再用 `_now().date()` |
| `review()` | `next_due = _local_date(new_card.due)`，UPDATE / 事实 `extra.next_due` / 返回值**三处同一个值** |
| `_card_from_row` | 落库的是本地日历日 → 还原成**本地零点**再交给 FSRS（`.astimezone(timezone.utc)`），否则读回来又差一天 |

回归测试（`tests/test_review_local_date_line.py`，3 条，**与"跑测试时几点"无关**）：

1. 把 `_now()` 钉在"UTC 还是昨天、本地已是今天"的时刻 → 存的仍是**本地今天**（老代码在这里会存成昨天）；
2. 用假 scheduler 把 FSRS 到期**时刻**钉在 UTC 深夜 → 落库/返回/事实里的 `next_due` 都是它的**本地**日期；
3. **往返不变式**：存进去的日期，从 `_card_from_row` 读回来还是同一天（任何时区都成立）。

## 五、教训

1. **"日期"和"时刻"要分清**：`datetime.now(timezone.utc)` 本身没错（跨端同步、FSRS 都需要绝对时刻），
   错在把它的 `.date()` 当"我的日历日"用。**落库的日期字段一律本地日历**。
2. **只在特定钟点失败的测试，价值很高**：它这次挡住了提交。当时的第一反应是"测试太脆"，
   但查下来是**产品口径不一致** —— 遇到"偶发红"，先证明是环境还是缺陷（一条 `utc vs local` 命令即可），
   别急着改断言。
3. **门禁跑在跨午夜时刻**是这次的运气：如果一直在白天跑，这处缺陷会一直被"绿灯"盖着。
   顺带说明**把这类检查做成确定性回归**（用假时钟/假 scheduler 钉住时刻）比依赖真实时间更可靠。
