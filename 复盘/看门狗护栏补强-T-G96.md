## 2. 封顶口径与理由（★ 3600 是主控定的口径，可被质疑）

复核 §3 量出：`2.5 × 历史最长` 是 `max(底线, …)` 的**加法项**，一轮内**不衰减** ——
一次 12 分钟的 `ui_flow` 之后，每次真卡死都要等 30 分钟；一次 60 分钟的调用 → **150 分钟**。
这是**「漏杀」**（该掐的没掐），不是误杀。

**封顶值取 3600 秒（60 分钟），理由**：复核独立扫的三份真 log 里最长一次调用是
**389.3s / 81.2s / 69.1s** —— 60 分钟已是本项目最长门禁（全量 `run_gates.py` ≈ 4 分钟、
冷缓存 worktree 里 `ui_flow` 十几分钟）的**约 5 倍**。所以 3600 既保住了「长调用不被误杀」的余量，
又把「漏杀」的上界从"无上界"压到 60 分钟。★ 复核报告 §3.2 的另一条相关风险
（`--retry` 每轮一个 log 时 `tool_durations` 会不会跨轮串）**不在本卡范围**，见 §8。

两个边界都在用例里钉住：

- `BUSY_STALL_SECONDS = 1800` **仍生效**（封顶 3600 > 1800，在飞那条没被压下去）；
- **没有历史长调用时老口径 480 秒一字节不变**。

## 4. 畸形 log：两层防御 + 10 种形状（§5 证据 2）

第一层（类型判断）后，10 种形状逐条结果（`test_malformed_logs_never_break_the_criteria`，
参数化 10 条全绿）：

| 形状 | `inflight_tool` | 结论 |
|---|---|---|
| `half` 半截（有 use 无 result） | 认得出在飞 | 不炸 |
| `badjson` 坏 JSON / 空行 / 非 dict JSON | `None` | 不炸 |
| `nostamp` 缺 `__timestamp` | `None` | 退回保守（不放大阈值） |
| `cnotlist` `content` 不是 list | `None` | 不炸 |
| `itemstr` `content` 里 item 不是 dict | `None` | 不炸 |
| `stampnum` `__timestamp` 不是 str | `None` | 不炸 |
| `noid` 缺 `id` | 仍按在飞算 | 不炸（偏保守） |
| `inputstr` `input` 不是 dict | 仍按在飞算 | 不炸 |
| **`msgstr` `message` 是 str** | `None` | ★ 复核里会炸 → 现在不炸 |
| **`msgnum` `message` 是 int** | `None` | ★ 复核里会炸 → 现在不炸 |

★ 其中 **`msgstr` / `msgnum` 两条经过 `run_worker` 的循环路径**（`test_runner_survives_a_malformed_log_in_the_loop`）：
畸形事件既没炸看门狗（照样判卡死），也没炸心跳（退回保守口径那句被如实打出来）。
另有一条 `test_runner_falls_back_when_a_criterion_raises`：**故意让 `inflight_tool` 抛异常** →
看门狗退到「没有在飞」的保守口径继续盯，判决里出现「退回保守口径」。

★ 写这条卡时**多逮到一个洞**（复核没提，是我把畸形 log 真喂进 `run_worker` 才暴露的）：
判据本身接住了之后，收尾路径 `_scene()` 仍然调 `wb_status.parse_events()` —— 它对
`message` 不是 dict **同样会抛**，异常照样逃出 `run_worker`（看门狗等于还是失效）。
所以第二层兜底也覆盖了 `_scene()`：渲染失败就退回一句结论，**绝不让"掐进程"这件事本身出不来**。

## 5. 封顶：直接调 `stall_threshold_seconds()` 打印各档（§5 证据 3）

```
=== 1) stall_threshold_seconds 各档（封顶后）===
  无在飞 + 无历史                ->     480s =    8.0 分钟
  在飞 + 无历史                 ->    1800s =   30.0 分钟
  无在飞 + 历史 240s            ->     600s =   10.0 分钟
  无在飞 + 历史 3600s           ->    3600s =   60.0 分钟
  在飞 + 历史 3600s            ->    3600s =   60.0 分钟
  ADAPTIVE_MAX_SECONDS=3600  BUSY_STALL_SECONDS=1800  STALL_SECONDS=480
```

读法：历史 3600s → **3600**（封顶），而不是复核算出的 9000；在飞 + 无历史仍是 1800；
无在飞 + 无历史仍是 **480**（老口径没动）；历史 240s → **600**（2.5 倍仍生效）。

## 7. 真机证据：`--detach` 的子进程活过父进程 + 无控制台窗口（§2.6）

```
spawn_detached 用的 creationflags 含 CREATE_NO_WINDOW：True
父进程立刻返回（0.02s），子进程 pid=71940
此刻 marker 在不在：False（4 秒后才由子进程写）
--- 父进程已退出，等 6 秒再看子进程是否写下了 marker ---
marker 存在: True
子进程还活着 pid=71940 控制台句柄=0
```

读法：父进程**立刻返回**；父进程退出后子进程**照样活着**并把 marker 写下来（**没被
`CREATE_NO_WINDOW` 弄坏 `--detach` 的命根子**）；子进程自报 `GetConsoleWindow() == 0`
（**没有控制台 → 不可能弹窗**）。`DETACHED_PROCESS` 仍在（`test_spawn_detached_keeps_detached_but_adds_no_window` 断言了 flag 位）。

★ **边界（如实写）**：这条真机证据走的是 `spawn_detached()` **本身**（`--detach` 的机制），
**不是**完整跑一遍 `wb_dispatch.py --detach` —— 因为完整那步的四道前置检查要求工作区干净
（`git status --porcelain -uno`），而本卡在提交前工作区**本来就是脏的**（改了代码/测试）。
登录自检那一步也没重跑（省掉一次真派活的钱）。机制一致，但「完整 detach 命令」这一档
**没有**真机证据（T-G95 在干净 worktree 里跑过一次完整 detach，可作参照）。

## 8. 还有什么没修（边界，如实写）

1. **`wb_status.parse_events()` / `turns_seen()` / `tool_signatures()` 在 `message` 不是 dict 时
   仍会抛** —— 它们是**别的东西**（状态器 / 回合计数），**不在本卡白名单**（`tools/wb_status.py`
   一个字不许碰；`turns_seen`/`tool_signatures` 的判据本身也不许动）。本卡只在 `run_worker`
   的调用点**接住**这个异常并退回保守口径；**没修它们自己**。三份真 log 里 0 例畸形，属鲁棒性缺口。
2. **`main()` 收尾那段渲染时间线**（`print` timeline）仍直接调 `wb_status.parse_events()` ——
   畸形 log 会让 `--execute` 的收尾崩。本卡只保证**看门狗/心跳不失效**（卡 §2.2 的原话），
   收尾渲染没接住。真要修得动 `wb_status.py`（另立卡）。
3. **`tool_durations` 跨轮串**（复核 §7-2 提的：`--retry` 每轮一个 log 时旧轮的长调用会不会把
   新轮阈值抬高）**没验**。本卡的封顶把最坏值压到 3600，但跨轮行为仍未测。
4. **真工人身上的真机效果**：本卡只加护栏与封顶，T-G94 的核心修法仍**没在真派活里触发过**
   （真机证据还是桩命令档）。
5. **完整 `--detach` 命令**没真机重跑（见 §7 边界）。
6. `复盘/外包-卡表与规矩.md` §12 表里仍写「静默 ≥ `--stall-seconds`，默认 480 秒」（那是 T-G88
   的表）；本卡白名单**不许**动那份文件（另一张卡正在改它），未同步属残留。
7. **`--status` 的 `[判决]` 取"最新一轮"是按文件 mtime** —— 若两个判决文件 mtime 相同（极罕见），
   排序可能不稳定。用例里显式 `os.utime` 让它确定。
