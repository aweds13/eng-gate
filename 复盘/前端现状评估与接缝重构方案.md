## 二、现状体检（全部为实测数据，非印象）

测量命令：对 `src/web/index.html` 做正则统计（2026-09-18，提交 `7a801d9` 之后）。

| 指标 | 实测 | 含义 |
|---|---|---|
| 文件行数 | **735** | 单文件承载样式 + 状态 + 10 个视图 + 全部事件 |
| CSS 变量声明 | **7 个**（`--accent/--bg/--card/--text/--muted/--danger/--ok`） | 覆盖面不足：没有 `--surface-2`（浅底）、`--line`（分隔线）、`--on-accent`（强调色上的文字） |

| 内联 `onclick/onkeydown` | **56 处** | 唯一的事件机制；字符串插值，标题含引号即需手工转义（习惯名处已出现过一次 `.replace(/'/g,"\\'")`） |
| 函数声明 | **66 个** | 全部平铺在同一个 `<script>` 作用域 |
| `m.innerHTML =` 整页渲染 | **10 处** | 每个视图独占整个 `<main>` |
| `prompt(`/`confirm(` | **8 处** | 系统弹窗，与「温和、可撤销、不打断」的界面基调不一致（且 `prompt` 在部分环境被禁用） |
| `var(--danger)`/`var(--ok)` 实际使用 | **1 次** | 定义了两个状态色，几乎没用起来（SR-NF1 要求状态色可配、统一） |

### 结构性缺陷（数据背后的四条）

1. **视图独占整页**：`renderToday` / `renderFocus` / `renderStats` … 各自 `m.innerHTML = 整页`。
   而 SR-NF4 要的「中列表 + 右详情」是**两个可独立重渲染的区域**——
   现在"选中一个任务 → 刷新详情"只能整页重渲染，**连带丢失计时器状态、输入框内容、滚动位置**。
2. **没有跨视图状态层**：只有 `focusTimer`、`hmCells` 两个模块变量（都是补丁式加的，第一次修的是
   "刷新后习惯消失"——当时靠 `sessionStorage` 存 habitId）。主题、选中实体、面板开合都需要新状态，
   现在**没有地方放**，只能继续加全局变量。
3. **事件机制脆**：56 处内联 `onclick` 字符串插值；三栏布局会让事件来源变成"左导航 / 中列表 / 右详情"三处，
   内联字符串拼 id 的方式会迅速失控。
4. **颜色散落在 CSS 与 JS 两处**：暗色主题不是"加个类"，而是要同时翻 CSS 和模板字符串里的 21 处 hex。

## 三、决策：需要重构，但**不是**视觉重构

### 3.1 反面意见（必须记录，避免一边倒）

**当前形态对"本地优先、打开即用"是最优的**：单文件、零依赖、零构建步骤，
`python -m uvicorn` 起来就能用，PWA service worker 只缓存静态壳。
任何引入框架 / 打包器 / npm 的方案都是**净亏损**，明确不做。

### 3.2 结论

> **保留「无构建、无框架、本地优先」的形态，只把内部接缝理清楚。**

而且要把一件事说透：**SR-NF4 的三栏布局本身就是一次重构**——
它要求"中列表 + 右详情"两个独立渲染区，这跟现在"视图独占整页"的结构直接冲突。
所以选择不是"要不要重构"，而是：

- **有准备地重构**：先立接缝（壳 / 视图契约 / 状态），三栏与暗色变成"壳的事"；
- **或把重构藏进补丁**：往 10 个 `render*` 里逐个塞布局判断，改动面更大、更难验证、遗留更乱。

### 3.3 为什么不采用 feat/ui-refactor 的做法

`复盘/写法参考-feat-ui-refactor分支.md` 记录过那条分支：它做了「瑞士风 + 三文件拆分 + SVG 图标」，
但**模块联动全缺**（专注不记账、完成不联动），且未被合并。
本次范围**严格限定在"接缝 + NF1/NF4 的明确要求"**：不做视觉重设计、不引图标库、不搬视觉风格。

## 四、目标结构（无依赖、无构建）

```text
src/web/
├─ index.html      壳：布局骨架 + 挂载点（左导航 / 中 main / 右 aside / toast）
├─ app.css         设计令牌（:root + [data-theme="dark"]）+ 布局 + 组件
└─ app.js          state（主题/选中实体/计时）+ shell（渲染调度）+ 各视图（只填中列）
```

用原生 ES 模块（`<script type="module">`），**依然不需要 npm / 打包**。三文件不是为了好看，
而是让接缝**可被看见、可被约束、可被测试断言**。

核心契约（重构的实质，不是搬家）：

```js
// 每个视图只做一件事：往中列渲染；返回可选的清理函数
export const views = {
  today: { title: '今日', render(center, state) { /* ... */ } },
  tasks: { /* ... */ }, focus: { /* ... */ },
};
// 壳负责：布局 / 主题 / 计时器常驻 / 右详情面板 / toast / 路由 / 状态
// 事件：统一 data-action 委托，不再内联 onclick
```

## 五、分阶段方案（每阶段结束都能跑、都能用）

| 阶段 | 内容 | 视觉/行为变化 | 验收方式 |
|---|---|---|---|
| **R1** | 抽 `app.css` + 颜色令牌化（含 JS 内联色） | **零变化** | 断言无硬编码 hex 残留；真机取页面 |
| **R2** | 抽壳与状态：`index.html` 只留骨架，`app.js` 有 state + 渲染调度 + 事件委托 | **零变化**（各视图仍独占中列，逐一对齐现有行为） | 先加厚前端烟测（容器 / `data-action` / 各视图入口），再动手 |
| **R3** | 右详情面板 + 计时器常驻（SR-NF4 三栏） | 布局变化（≥1024px 三栏；≤1023px 保持现有单列 + 底部 Tab） | 真机 + 手点确认 |
| **R4** | 暗色主题：加 `[data-theme="dark"]` 覆盖块 + 设置页「亮/暗/跟随系统」 | 新增主题能力 | 断言令牌齐全、切换逻辑存在 |
| **R5** | 状态色统一（`--danger`/`--ok`/`--accent`）、空态组件、间距圆角收敛 | 细节打磨 | 真机 + 手点确认 |

**顺序的理由**：先把接缝做好，再动布局与主题。反过来（先主题后三栏）等于在流沙上盖楼——
这也是我第一轮建议里需要**收回**的部分。

## 六、风险与代价（诚实登记）

1. **我无法在浏览器里验证**。环境只有 PowerShell：我能保证"真机能取到页面、DOM 与接口引用齐全、
   无硬编码色残留"，**但点击手感与布局视觉必须由人工确认**。这是本次工作最大的真实成本。
2. **现有前端测试是"烟测"**：`tests/test_web_frontend.py` 只断言关键字符串存在 + 接口 200，
   **不能发现交互被改坏**。因此 R2 之前必须先把烟测加厚（关键 DOM 容器、事件 `data-action` 齐全、
   各视图入口存在），否则重构可能在"全绿"中悄悄破坏功能。
3. **不做**：拆成更多文件、引入框架/打包器、视觉重设计、搬 feat 分支的风格。
4. **粗估**：R1–R2 是机械活（各一次提交可过）；R3–R5 才是真正的新功能量。
   总体比"直接打补丁"多约 30%，换来 R3–R5 以及后续「OP-33 团队视角页」「OP-24 课程↔任务合流」
   这类涉及多区域的改动都变便宜。

## 七、与既有文档的关系（这是当前最缺的一环）

| 规格 | 现状（本次评估） |
|---|---|
| `SR-NF1`（双主题 / 单一强调色 / 状态色可配 / 字体间距统一） | ❌ **未落地**：仅 7 个变量、无暗色、状态色几乎未使用、间距无统一尺度 |
| `SR-NF2`（打开即 My Day / 一键操作 / 可撤销 / 空态友好） | 🟡 大体满足；剩余：8 处系统弹窗（`prompt`/`confirm`）与温和基调不符 |
| `SR-NF3`（信息可视化） | ✅ 六类形态全覆盖（第 7–9 步） |
| `SR-NF4`（三栏布局 / 一屏不淹没 / 渐进聚焦） | ❌ **未落地**：单列 + 顶部 nav；详情靠 `prompt` |
| `SR-NF5`（反馈与可回退 / 二次确认） | 🟡 toast 与确认已有，但用系统 `confirm`；无动画 |

> 结论：**前端是非功能规格里唯一还空着的一层**；后端与数据链已收口，继续做前端是"推动软件能用"的下一步。
