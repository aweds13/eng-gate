## 二、为什么 DESIGN/LEARN 被撤回

### 判断错误的本质

`DESIGN.md`/`LEARN.md` 是 **SR-NF9（开源文档完整）** 的要求 → 属 **N38 工程生态类** → 前提是"**开源给同学用**"。

但当前真实状态：
- 软件**功能都没闭环**（LC-1~LC-8 多数未达标）
- MVP 尚未重构
- 用户是**自己在用**

> **在此阶段写"给零基础同学看的开源文档"，等于房子没盖好先写《业主手册》。**

### 我犯的三个错

| 错 | 具体 |
|---|---|
| **把"我列的选项"当成"用户的任务"** | "2-3"是我自己列的清单编号，用户只是说"按2-3"，我应先确认优先级 |
| **没做优先级判断** | 我明明在审查报告里写了"遗留：操作闭环未实现"，却先做最不急的文档 |
| **被自己的清单牵着走** | 列了问题清单就顺着做完，没回到"用户现在最需要什么" |

### 正确的优先级

1. **MVP 重构**（让功能闭环）← 用户的真实痛点
2. 其余（文档、开源材料）——**等软件能用再说**

## 三、为什么闭环验收被恢复

`ACCEPTANCE.md` 的「闭环验收」章节（LC-1~LC-8 + LF-1~LF-4）**与 DESIGN/LEARN 性质不同**：

| | DESIGN.md / LEARN.md | ACCEPTANCE 闭环验收 |
|---|---|---|
| 服务对象 | **开源给同学看** | **自己判断"功能是否真做完"** |
| 是否推动软件可用 | ❌ 不 | ✅ **是**——它是 MVP 重构的**验收靶子** |
| 是否必需（当前阶段） | ❌ 可延后 | ✅ 需要 |

**结论**：`revert` 是整包撤销，误伤了这份有价值的验收标准 → 用 `git checkout 2e95f62 -- docs/ACCEPTANCE.md` 单独取回。

## 六、教训（重要·影响后续工作方式）

1. **先判断"是否推动当前目标"，再动手** —— 我列的选项清单不是任务清单。
2. **"清单编号"≠"用户指令"** —— 用户说"按2-3"时，我应先确认这两项**当前是否值得做**。
3. **`git revert` 是整包撤销，小心误伤** —— 提交里若混着"该撤"和"该留"的内容，应拆开提交（本次已用单独 checkout 补救）。
4. **判据**：**「这件事是否直接推动软件能用」** —— 不满足的先不做。
