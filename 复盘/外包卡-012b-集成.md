## §2 ★★ 口径：**压成一笔，绝对不要逐笔 cherry-pick**（这是上一轮踩出来的硬教训）

**为什么**：本项目有一条不变量 —— `tests/test_wb_review.py::test_current_head_passes_the_gate_evidence_check`
要求「**HEAD 这一笔提交里**的 `gates/last.json` 满足 `ok=true` 且 `rev==HEAD^`」。
**`git cherry-pick` 出来的提交必然不满足**（它继承的是**作者基点**的产物，`rev` 指向别人的父提交），
而门禁在提交**之前**跑 → 提交一份 `ok=false` → 下一轮 `assert ok===True` 又红 → **永远红、死锁**。
上一轮集成者就是这么被卡住的（它的诊断在 `复盘/外包卡-012-集成.md` 里，★ 开工先读那份）。

**所以：把改动落进工作区（不产生作者提交），跑一次门禁，再**一笔**提交。**

## §4 ★ 要把这几条**架构教训**写进你的复盘（主控已经替你查清，你照抄+写清即可）

1. ★★ **「一笔提交 = 一笔为它跑的门禁」这条不变量与"逐笔 cherry-pick 集成"不兼容** ——
   cherry-pick 继承的是作者基点的 `gates/last.json`（`rev` 指向别人的父提交），而门禁在提交前跑
   → 提交 `ok=false` → 下一轮又红 → **死锁**。**并发收口必须"压成一笔"（或按文件收）。**
2. ★ **`--status` 会显示过期的判决**：一次被前置检查**拒绝**的派活会写下「没派活」的判决文件，
   而**同一张卡随后派活成功时它不会被清掉** → 第二天早上看 `--status` 会以为没派活，
   其实工人在跑（主控今天就被骗过一次）。**这是观测缺陷，要一张卡修。**
3. ★ **第三类跨卡耦合：台账证据指针** —— A 卡改了函数签名，B 卡（或更早的卡）台账里
   `text:...::def foo(...) -> X:` 这种**整段签名**证据就**字面失配** → audit 红。
   这是**好事**（审计会在 API 变化时把人叫回来），但要知道：**改签名 = 可能要刷旧证据指针**。
4. ★ **测试不许耦合仓库里的"会长"数据文件**：`tests/test_wb_plan.py` 原来断言 backlog
   **恰好四张卡**，而另一张卡的活**就是**往那个文件追加 → 必然红。正确写法是
   **断不变量（子集/唯一/校验通过）+ 相对顺序**，或用 **`tmp_path` 冻结夹具**。
   这类耦合**不会在任一单独工人在自己树里干活时暴露**，只在"两个改动合到一起"时爆 ——
   正是并发架构必须靠**集成时全量门禁**兜住的东西。
