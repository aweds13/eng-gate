## 2. 键盘优先做成「附加层」——可以，但先补一个前提

### 2.1 前提已经量出来了：`:focus-visible` 全表 **0 条**

T-G29 的一致性门跑的第一次就报了这个数。**没有可见焦点，键盘优先是空话** ——
用户按 Tab 走一圈，屏幕上没有任何东西告诉它"现在焦点在哪"。
所以键盘这件事的**第一步不是快捷键，是一条全局焦点环**（这正是 T-G29 登记的 8 条工单之一）：

```css
:focus-visible { outline: 2px solid var(--accent); outline-offset: 2px }
```

### 2.2 更好的一条路：`ACTIONS` 已经是一张命令注册表了

现在的架构里有一个**现成的资产**：`index.html` 里那张 `const ACTIONS = {...}`，
**已经注册了 125 个动作**（`tests/test_web_frontend.py` 还强制"模板里用到的每个 `data-action`
都必须在表里注册"）。所以"给界面加键盘"**不需要新造一套系统**，而是**把这张表升级成一张真正的命令表**：

| 字段 | 现在有没有 | 有了之后谁用 |
|---|---|---|
| `id`（动作名） | ✅ 已有（125 条） | — |
| 中文标题 / 分组 | ❌ | ⌘K 面板、命令列表 |
| **默认快捷键** | ❌ | 快捷键层 |
| 参数（哪个 id、什么值） | 部分（`data-*` 属性） | ⌘K、CLI、AI |
| **是否可逆 / 是否破坏性** | 散落在代码里 | 二次确认、AI 边界（`OP-*` 已有类似口径） |
| **对应哪条 OP / 哪个路由** | ❌ | 台账、CLI、MCP、覆盖检查 |

**一句话**：这张表同时喂**四个面** —— 界面按钮、⌘K 面板、CLI、AI/MCP。
**这才是"附加功能"的正确形态**：不碰鼠标路径、不改那 225 处 `data-action`、移动端完全不受影响。

### 2.3 ★ 关于"你以后也通过虚拟键盘给它命令"——这个直觉对，但有个更稳的顺序

你说的是"AI 通过虚拟键盘给它命令"。这条**能通**，但要认清它的位置：

| 驱动方式 | 稳不稳 | 为什么 |
|---|---|---|
| 合成 DOM 事件（模拟点击/按键） | **最脆** | 它把**界面当 API**，而界面是**最常变的那一层** —— 视觉线一开始改，脚本全废 |
| 命令表 / CLI / HTTP | 稳 | 契约层（`OP-*`）已经在管这一层，改界面不影响它 |
| MCP | 最标准 | 2026 年的"AI 原生"就是它，而且**本 harness（DSH）自己就是 MCP 客户端** —— 接上就能被我用，不用为我写胶水 |

**所以顺序是：命令表 →（HTTP/CLI）→ MCP。合成事件只留一个用途：验证"界面真的能纯键盘走通"**
（那是个**测试**，不是产品接口）。把合成事件当接口用，等于每次改样式都要修一遍自动化 —— 那是维护负担。

## 3. OpenWork 落在哪：它给的其实是「AI 那一半」

`openwork`（`github.com/shopend/openwork`）自称是 **Claude Cowork 的开源替代，powered by opencode** ——
也就是说它不是"好看的任务列表"，而是一个 **AI agent 控制台**：模型在干活，界面要把**这件事**呈现出来。

它的精华不在配色，在四个东西：**run log（跑了什么）/ streaming（正在写什么）/ 工具调用行（做了什么）/
错误与确认（哪里断了、要不要继续）**。

**而这正是我们唯一没做的那块。** 三条线索指向同一处：

1. 台账里只剩一张新卡：**T-G21「AI 写事实回报进展」**（口径已定，只差 `conventions.md` 第 34 行那句话）；
2. 规格里 `SR-F7.3` 的 AI 接口（只读 + 新增 + 勾自己建的）；
3. ★ **T-G26 装的那个 sheleg 包里，正好有一份 `AI_PRODUCT_PATTERNS`**（skill 包内的参考文档，不在本仓库）——
   专讲 chat / agent / streaming output / run logs / model errors / generated content / confirmation states，
   而且它复用 workbench 那套状态令牌（`--info` running / `--ok` done / `--warn` needs a human / `--danger` failed）。

**所以我的判断是**：OpenWork 不是第四个视觉参考，它是**"AI 面"的参考** ——
你之所以觉得它"也不错"却说不太清，是因为它画的是**我们还没画的那一块**。
这一条值得你确认（§6）：AI 面要不要并进这次视觉线，还是等 T-G21 单独做。

## 4. AI 原生 CLI：可以做，但**先别做 CLI**

### 4.1 现状事实（先摆清楚，免得凭印象讨论）

| 已有的 | 情况 |
|---|---|
| `[project.scripts] timeflow = "timeflow.app.main:main"` | **已经有一个 `timeflow` 入口** —— 但它现在只负责**开窗口/起服务**，不是"操作命令" |
| `tools/serve.py` | 开发/运维脚本（起服务），不是产品 CLI |
| 契约层 `OP-*` | **54 条**操作（`docs/contracts/`），已经写成"六要素"（入口/前置/输入/后续/可逆/反馈） |
| 界面命令 | `ACTIONS` **125 条**（见 §2.2） |
| HTTP API | 有，机器可调 |

### 4.2 ★ 反直觉的结论：**直接加一个 CLI，会让维护变差**

你的原话目标是「**更加方便后面的维护，以及功能的扩展**」。但如果现在就加一个 CLI，
结果是**每加一个功能要在四个面各写一遍**：界面 / HTTP / CLI / AI。
**四处手写 = 四处会漂**，比现在更差 —— 而这恰恰是你想避免的。

**维护变好的关键不是 CLI，是那张命令表**（§2.2）：一张表 → 四个面都是**投影**。
（这也是我们项目一贯的做法：契约层 `OP-*` 已经是"唯一的操作真源"，`[contract_ops]` 已经在机器上强制
"每条 OP 都要挂到一张台账卡上"。把它和 `ACTIONS` 对上，就是那张命令表。）

### 4.3 我建议的顺序（每步都能独立验收）

| 步 | 做什么 | 为什么先做它 |
|---|---|---|
| **1** | **命令表**：把 `OP-*` ↔ `ACTIONS` ↔ 路由 三者对起来，补上"标题/快捷键/可逆性" | 它是后面三步的共同地基；而且**对不上本身就是一个发现**（哪条 OP 界面里没有入口、哪个动作没有契约） |
| **2** | **只读 CLI 子命令**（`today` / `overdue` / `review-due` / `stats`…） | **零写入风险**，立刻有用（脚本、自检、我） |
| **3** | **MCP 服务** | 真正的"AI 原生"标准；DSH 本身是 MCP 客户端，接上我就能用 |
| **4** | 写操作 CLI（`add` / `done` / `focus start`…） | 最后做 —— 它牵涉 AI 边界口径 |

### 4.4 代价与要你定的口径

**这是新的产品面**，按项目规矩得你定口径 —— 只要一句：**"哪些操作必须在 CLI 里可达"**。
如果不定，会出现"有的操作能脚本化、有的不能"，那**比完全没有 CLI 更糟**（因为你没法信任它）。
我的建议是：**只读全覆盖 + 写入只做「和界面上一样的那些」（复用同一套口径，不发明第三套语义）**，
并且**默认关**（跟局域网那道门一个口径：默认收严、用户再放宽）。
