# 面板口径跟上派活器看门狗（T-G97 = 并发卡 008）

> 一句话：`tools/wb_dash.py`（工人状态面板）里把「卡死」**硬写成 480 秒**，注释还写着
> 「与派活器看门狗同一口径」—— 而派活器在 T-G94 之后早就是「**有工具在飞 → 1800 秒**，
> 再按 `max(底线, 2.5 × 历史最长一次已完成调用)` 自适应」。于是面板会把一个正在跑长命令
> （全量门禁 4 分钟、`ui_flow` 十几分钟）的工人**误标成「静默 N 分钟（可能卡死）」** ——
> 这正是 **T-G94 修掉的那个病**，面板还没跟上。这一张卡把面板的判据接到派活器上。

## 1. 病灶（为什么有这张卡）

- `tools/wb_dash.py` 原来：`STALL = 480`，`_state()` 用 `if age < STALL: 安静 else 卡死`。
- 派活器 `tools/wb_dispatch.py`（T-G94 之后）：`stall_threshold_seconds()` ——
  ① 有工具在飞 → 底线取 `BUSY_STALL_SECONDS = 1800`；② 再和 `2.5 × 最长一次已完成调用` 取大；
  ③ 两样都没有 → 就是 `stall_seconds`（480）。
- 两张表对同一个工人给出**互相矛盾**的档位：派活器认为「在飞 = 预期静默」，面板却把它算成卡死。
  主控看面板时会白白去看一个健康的工人。

## 2. 做法（复用，不写第二份口径）

★ 本项目的规矩：**不许在面板里写第二份口径**。所以面板直接 `import wb_dispatch`（同目录，
`sys.path` 已挂 `tools/`），只**调**它的判据：

- `wb_dispatch.inflight_tool(lines, now=...)` —— 拿到「在飞的那一次（工具签名 + 已跑秒数）」；
- `wb_dispatch.tool_durations(lines)` —— 拿到历史每一次已完成调用的耗时；
- `wb_dispatch.stall_threshold_seconds(stall_seconds=STALL_BASE, inflight=..., durations=...)`
  —— 拿到**本次阈值**。

`STALL_BASE = wb_dispatch.STALL_SECONDS`（= 480）—— 底线也**取派活器那个数**，不在面板里另写一个。

**四档**（只在 `安静 / 卡死` 的边界上变化，其余一个字没动）：

| 档 | 旧 | 新 |
|---|---|---|
| `收工·结束` | 判决文件 **或** 日志里有 `result` 事件 | 不变 |
| `在跑` | 静默 < 60 秒 | 不变 |
| `安静` | 60 ≤ 静默 < **480** | 60 ≤ 静默 < **本次阈值** |
| `静默 N 分钟（可能卡死）` | 静默 ≥ **480** | 静默 ≥ **本次阈值** |

**行里新增两字段**（既有字段名一个没改、`/api/state` 的顶层结构 `{now, cards}` 没动）：

- `inflight`：`在跑：<工具>（已跑 X 分钟）`（没有在飞 → 空串）；
- `threshold_min`：本次阈值（分钟，浮点）。

面板 HTML 也加了「在跑 / 阈值」一列，主控一眼能看出「是真卡死，还是正在跑长命令」。

五条新用例（都对着**旧实现**会红）：

1. `test_inflight_tool_raises_threshold_instead_of_reporting_stall` —— ★ 本卡的整个要点：

   新实现 →「**安静**」，`threshold_min == 30.0`，`inflight` 以 `在跑：` 开头。
2. `test_threshold_adapts_to_longest_completed_call` —— 没有在飞，但历史最长一次已完成调用
   400 秒 → 阈值 = `max(480, 2.5×400)=1000` 秒 → 静默 600 **仍是「安静」**，`threshold_min == 16.7`。
3. `test_no_timestamp_falls_back_to_baseline` —— ★ 保守口径：调用**没带 `__timestamp`** →
   算不出耗时 → 阈值就是底线 480（`threshold_min == 8.0`），静默 600 **仍判卡死**。
4. `test_threshold_comes_from_dispatch_not_a_second_copy` —— 口径必须是**派活器的**：
   `monkeypatch` 把 `wb_dispatch.stall_threshold_seconds` 换成一个返回 9999 秒的桩 → 面板的
   `threshold_min` 当场跟着变成 `166.7`。若面板自己抄了公式，这一条不会动。
5. `test_dash_reuses_dispatch_functions_by_source` —— 源码级：`wb_dash.py` 里必须**字面**出现
   `wb_dispatch.inflight_tool` / `wb_dispatch.tool_durations` / `wb_dispatch.stall_threshold_seconds`。

原 `test_state_boundaries` 也扩了：`_state(1799.0, False, threshold=1800.0)` → 安静、
`_state(1800.0, False, threshold=1800.0)` → 卡死（证明卡死边界确实**跟着阈值走**）。

```json

 "threshold_min":30.0}
```

即：**旧实现（硬写 480）在这里会报「静默 10.0 分钟（可能卡死）」，新实现报「安静」**。

## 5. 边界（如实写）

- 面板仍**只报「在不在动、动到哪了」，不判断内容对不对**（内容对错是主控复核的事）；仍是**只读** ——
  绝不调用/杀工人、不落任何文件。
- **静默的测法没动**：面板量的是「日志文件 mtime」离现在多久，派活器量的是「最后一条事件到达的时刻」。
  两者都在量「多久没有新事件」，但**不是同一根秒表**；这一卡只对齐**阈值**口径，没去统一静默的测法。
- 面板**没有** `--stall-seconds` 之类的开关，底线直接取派活器的 `STALL_SECONDS`（480）——
  ★ 若将来派活器改了底线（比如给 `--stall-seconds` 默认定成别的数），面板会**自动跟**，因为它读的是那个常量。
- 「在飞」的判定依赖日志里的 `__timestamp`（与派活器同一口径）：**缺时间戳 → 退回底线 480**，
  绝不放大阈值（宁可早报一次「可能卡死」，也不因为读不到时间戳把卡死判成健康）。

## 6. 没动的

- `tools/wb_dispatch.py` / `tools/wb_status.py`（只 **import** 前者、复用后者的 `parse_events`，**一个字没改**）；
- `card_state()` 的**既有字段名**（只加了 `inflight` / `threshold_min` 两个）、`/api/state` 的顶层结构、
  `--port` / `--host` 默认值；
- `src/**`、`docs/**`（全部，含台账与 changelog）、`gates/**`、其它 `复盘/` 交接文档、
  三个外来未跟踪文件 —— 一概没碰（共享文件由主控集成时统一写）。
