## §2 口径（这一节是这一卡最该被读的部分）

1. **顺序只由用户动作产生** —— 拖一下 / 按一次 ↑↓。**没有任何后台逻辑会改它**
   （不是「自动按优先级排」，那还是原来那半条）。
2. **拖过的在前，没拖过的在后**：`myday_rank` 数值小的在前；`myday_rank IS NULL` 的排后面，
   内部仍按老口径（**截止日 → 优先级 → 创建时间**）。两份口径拼在**一处**（`_MYDAY_ORDER_BY`）。
3. **进「今天」= `NULL`** —— 新来的排最后，**不抢**你手动摆好的位置。
4. **离开「今天」= 清空** —— 下次再进来还是排最后（`update_task` 里一并清）。
5. **落点是「放到那一条前面」**，不是「放到第几格」：`{"before": "<任务 id>"}`；`{"before": null}`
   = 放到**末尾**。为什么这样：中间插队、或有条目被隐藏/完成，落点都不会错位。
   —— 这是 `place_myday` 存在的理由，也是它比「目标下标」稳的地方。
6. **两个键要么给一个、要么不给**（都给 / 都给空 → **400**）；**任务不存在 → 404**，
   且这一步**先于**「在不在今天」那一步（与 `move_doing` 同一套次序）。
7. **`myday_rank` 不是 PATCH 可写字段** —— 想改顺序只有那条路由一条路（有测试钉着）。
8. **幂等**：拖到自己前面 = 原地不动；已在头/尾按 ↑↓ = 原地不动（都不报错，也都不写库）。
9. **只排「今天」这一栏**：不做跨视图 / 跨栏拖拽（那是另一件事）。

## §5 ★ 踩到的坑（两条都是**探针先抓到**的，不是我看出来的）

### 5.1 `database is locked`：写顺序却忘了提交

- **现象**：某几条路（400 形状错误、拖到自己、已到头/尾）走完之后，**紧接着的读**抛
  `sqlite3.OperationalError: database is locked`。
- **真因**：`_write_myday_rank` 只写了 UPDATE，**没有 `commit()`**；而那几条「早退」的路会先写一遍
  归一化顺序再返回 —— 那笔写就**挂在事务里**，下一个连接读不到还想写 → 锁。
- **怎么找到的**：`gates/diag/probes/myday_lock_probe.py`（包住 `sqlite3.connect`，打出每一条连接的
  `in_transaction` 与**创建时的调用栈**）→ 指出「第 5 条连接来自 `_myday_sequence`，它 in_transaction=True」。
- **修法**：在 `_write_myday_rank` 里**提交**（每条写就是一次用户动作，本来就是一问一答的粒度），
  并补两条回归断言：**400 之后读一次**、**边界动作之后读一次**。
- ★ 教训：`commit()` 漏掉这种 bug 在「写完之后一定有人再写」的路径上**永远不显形**，
  只在「写完之后早退、下次来的是读」的路径上炸 —— 正是那几条边界路。

### 5.2 属性名读写对不上：看着能拖，其实什么也没发生

- **现象**：拖拽动画、落点高亮全对，松手**什么都没变**，控制台一声不响。
- **真因**：卡片上写的是 `data-myday-id="…"`，拖拽代码读的是 `dataset.id` → 落点 id 恒为 `undefined`。
- **怎么找到的**：`gates/diag/probes/drag_probe.mjs`：接管 `fetch`（打请求体）、给拖拽模块打 `__call`/`__drop`
  标记、监听 `unhandledrejection`。一眼看到「拖拽确实触发了、请求确实发了、`before` 是 `undefined`」。
- ★ 教训：**「能拖」不等于「拖动了东西」** —— 界面层自己会给你一种"它在工作"的错觉，
  所以要有一个**在边界上打点**的探针（接管 fetch 比读代码快得多）。

### 5.3 ★ 顺带修掉**工具自己**的一处假红（值得单独记）

`T.drag()` 第一版分**两次**读两个元素的 rect，而 `rectOf()` 内部会 `scrollIntoView` ——
第二次读把第一次的坐标**作废**了，于是抓手按在了**另一张卡**上（命中测试回话：那个点上其实是路径）。
**修法**：只滚一次，在**同一次求值**里同时读两个 rect；按下前做命中测试；零点/出屏直接报明确原因。
—— 与「判据不许假设两次求值之间世界没变」（T-G76 那条）是**同一个病根**：工具里的时序假设。

## §6 没动的 / 边界（如实记）

- `_ORDER_BY`（老口径）**一个字没改**；`move_doing`（进行中那套序号）照旧 —— 这张卡只新增。
- 离线包格式与合并规则**一个字没改**（`myday_rank` 进了离线字段表，手机只读面跟着字段走）。
- **不做**：跨视图/跨栏拖拽、顺序的撤销、多人协作下的顺序冲突（本地单人工具，不在本卡范围）。
