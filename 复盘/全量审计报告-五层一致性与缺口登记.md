## 一、结论一句话

**功能骨架与主链是完整的（做到 40 条），但"规格里写了、一版要交付"的东西里有 31 条没做完或只做了一半** ——

④ 影响界面的定性项（SR-NF1/2/4/8/13/15/18）**。

```
做到   40 条
半成品  9 条   ← 有后端没界面 / 有字段没联动
没做   22 条   ← 其中 4 条是规格自己标「二版/后置」，不算一版缺口
```

> 口径说明：**"做到"= 规格条目在代码里有对应实现且能指出落点**；不要求每条都有单测（单测覆盖见
> `docs/implementation/coverage.md`）。**"半成品"= 只满足该条的一部分**，例如"后端有、界面没有"。

## 二、审计方法与可信度（先说清楚，免得又"假绿")

| 环节 | 做法 | 为什么这么做 |
|---|---|---|
| 逐条取证据 | 每条 SR 写一条判定（正则/字段/路由/函数存在性），跑脚本产出结论 | 避免"读文档凭印象说做到了" |
| 路由真相 | 从 `api/app.py` 正则解析出 58 条路由，不手抄 | 手抄会与代码漂移 |
| 表结构真相 | 从 `storage/db.py` 解出 17 张表与 tasks 全部 11 个字段 | 字段级缺口只能靠表结构证明 |
| 脚本自身防呆 | 任一源文件读不到就**直接报错退出**；不得静默给"没做"的结论 | 第一版脚本就因拿错文件误判过 SR-NF6 |
| 已知边界 | 判定只做"存在性"核对，**不验证行为正确性**；行为正确性靠 `pytest` 284 项 + 真机脚本 | 存在性 ≠ 正确性，两者互为补充 |

**审计过程中修正的 3 个自身错误（记录在案）**：
1. 判定条件太松（只要有 due_date 就算"任务字段齐全"）→ 已改为逐字段核对。
2. `facts` 源文件缺失导致 `has()` 拿空串匹配 → 误判 SR-NF6「没做」，实为已做；已加防呆。
3. `shadow` 命中的是 CSS 的 `--shadow` 令牌 → 误判 SR-NF8「做到」，实为没做；已改精确匹配。
