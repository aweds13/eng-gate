> 「**最好就是 4 个面集中到一个点，然后调用同一个点的东西，可以吗？排最后。然后先做命令表。**」
> 这一份回答前两个问题，并把第三个问题的答案**做出来**（命令表 + 检查器）。

---

## 1. 一句话结论

**你说的那个"一个点"，本项目已经有了** —— `core/` 就是那个点，`api/app.py` 是唯一的边界，
界面是通过 HTTP 调它的。**缺的不是架构，是一层元数据**（每个操作叫什么、改不改数据、
可不可逆、对应哪条路由、界面哪个入口、AI 能不能碰）。这张表就是本卡做的东西 ——
有了它，**界面按钮 / ⌘K / CLI / AI·MCP 全都是投影**，不用各写一遍。

---

## 2. 「AI 原生 CLI」是什么意思

先拆词。**"CLI"** = 命令行（`timeflow today` 这种）。**"AI 原生"** 不是"给 AI 用的命令行"这么简单，
它指的是一组**让机器（而不是人）好调用**的性质：

| 性质 | 普通 CLI | AI 原生 CLI |
|---|---|---|
| 输出 | 给人看的表格/彩色 | **结构化（JSON）**，能被解析 |
| 输入 | 人在终端里敲 | **每条命令自带 schema**（参数名/类型/枚举），调用方不用猜 |
| 交互 | 会问 `y/n`、会分页 | **非交互**（要么不问，要么用显式 `--yes`） |
| 错误 | 打印一段话 | **稳定的错误码** + 结构化原因 |
| 语义 | 只有 `--help` | **幂等性、可逆性、破坏性**都写在契约里 |
| 发现 | 人读文档 | **自描述**：一条命令能列出"我有哪些命令、参数是什么" |

**关键的一句**：这六条里有五条，**跟"是不是命令行"无关** —— 它们说的都是
**"这个操作有没有一份机器可读的说明"**。所以：

> **★ 2026 年这件事的标准形态其实是 MCP（Model Context Protocol）**，不是自造一个 CLI。
> MCP 就是"给 LLM 用的 CLI"：工具 + JSON schema + 一个协议。而且**本 harness（DSH）自己就是
> MCP 客户端** —— 接上就能被我用，不用为我写任何胶水。
> 所以"AI 原生 CLI"和"MCP 服务"是**同一个想法的两种外壳**，而它们的共同前提是**那张表**。

---

## 3. 「正确顺序」是什么意思

我上一轮说的顺序是：**命令表 → 只读 CLI → MCP → 写操作 CLI**，而合成 DOM 事件排在最外。
理由是一条**依赖关系**，不是偏好：

```
        ┌──────────────────────────────────────────┐
        │  命令表（docs/commands.toml）             │  ← 唯一需要手写的地方
        │  一条操作：标题/参数/可逆/改不改数据/      │
        │           路由/界面入口/AI 可见性          │
        └──────────────────────────────────────────┘
                 │        │         │         │
       ┌─────────┘        │         │         └──────────┐
       ▼                  ▼         ▼                    ▼
   界面按钮             ⌘K 面板    CLI                 AI · MCP
   （已有）           （投影）   （投影）              （投影）
```

- **命令表必须先有**，因为它是**唯一的源**；没有它，四个面各写一遍（这就是"复杂"的来源）。
- **只读 CLI 第二**：零写入风险，立刻能用（脚本、自检、我）。
- **MCP 第三**：它才是"AI 原生"的标准形态；但它要的元数据比 CLI 更多（参数 schema 必须精确），
  所以排在命令表之后、写操作之前。
- **写操作 CLI 最后**：它牵涉 AI 边界口径（用户已定方案 3：AI 只写事实）。
- **合成 DOM 事件（"虚拟键盘"）排最外**：它**把界面当 API**，而界面是**最常变的那一层** ——
  视觉线一动手脚本就全废。它只该留一个用途：**测试**"这个界面能不能纯键盘走通"。

**一句话**：**"正确顺序"= 先把唯一那个源建起来，再让各个面去读它**；
先做的排前面是因为它风险低，后做的排后面是因为它依赖前面那个源。

---

## 4. 所以"四个面集中到一个点"——可以，而且已经是一半了

你问「**可以吗？**」——可以，而且**比你想的更接近**：

| 你说的"一个点" | 本项目现状 |
|---|---|
| 唯一的业务逻辑 | ✅ `src/timeflow/core/` —— 界面和 API 都不自己算口径 |
| 唯一的边界 | ✅ `api/app.py`（152 条路由）—— 界面**只**通过 HTTP 调它，不直连数据库 |
| 唯一的操作真源 | ✅ 契约层 `docs/contracts/**`（**54 条 OP**，每条有"入口/前置/输入/后续/可逆/反馈"六要素） |
| 唯一的界面命令源 | ✅ `index.html` 的 `ACTIONS`（**125 个**动作，护栏强制"模板里用到的必须注册"） |
| **一张把上面这些接起来的表** | ❌ **缺的就是这个** ← 本卡做的 |

**所以"集中到一个点"不是重构，是补一张索引表。** 而且补的过程**本身就会暴露问题**
（哪条 OP 界面里没有入口、哪个动作没有契约、哪条路由没人要）—— 那正是它的价值。

---

## 5. 命令表长什么样（schema）

一条操作一行，字段就是"四个面各自需要的东西"：

```toml
[commands."OP-1"]
title    = "新建任务"                       # 契约里的正名（机器核对）
routes   = ["POST /api/tasks"]             # 必须真的存在于 app.py（机器核对）
ui       = ["data-action=add-task"]         # 必须真的在 ACTIONS 注册过（机器核对）
kind     = "write"                          # write | read | derive —— 改不改数据
reversible = "可删除（见 OP-6）"             # 契约里的原话
ai       = "create"                         # read | create | none —— AI 能否碰（口径已定方案 3）
```

**为什么它不会变成"第二份手抄"**：三个字段有**已有的真源**可以机器核对（§6），
只有 `kind` / `ai` 是判断，而它们直接对应已经定过的口径。

## 6. 检查器检查什么（`scripts/check_commands.py`）

| 真源 | 从哪读 | 核对什么 |
|---|---|---|
| **契约层操作** | `docs/contracts/**` 的 `## OP-n 标题` | 每条 OP 必须有行；行不许有契约里没有的 |
| **HTTP 路由** | `app.py` 的 `@app.<method>("/path")` | 表里每条路由必须**真的存在** |
| **界面入口** | `index.html` 的 `ACTIONS` / `VIEWS` | `data-action=x` / `view=y` 必须**真注册过** |

**"洞"是允许的、也是要报的**：还有多少行没填出路由/界面入口，脚本数出来 ——
那是"这张表还差多少"的进度条（跟两道审美门的登记表一个思路：**逐条留痕、修一条删一条**）。

## 7. 建表结果：54/54 行、0 条硬冲突 —— 以及**建表当场抓到的一个真问题**

| 项 | 数字 |
|---|---|
| 契约层 OP | **54** 条 → 命令表 **54** 行（一条不漏） |
| app.py 真路由 | **152** 条（另有 2 条 `@app.api_route` 通配兜底，故意不做事，不进表） |
| 界面 ACTIONS / VIEWS | **139** 个 / **14** 个 |
| 表里写的路由与动作 | **逐条核对过，硬冲突 0 条** |
| **还没填出路由** | **5** 条：`OP-3b` `OP-8` `OP-39` `OP-43` `OP-49`（每条都写清了"为什么没有"，不是漏填） |
| **还没填出界面入口** | **11** 条：`OP-7` `OP-8` `OP-15` `OP-16` `OP-19` `OP-20` `OP-25` `OP-39` `OP-43` `OP-49` `OP-51` |

> 这 11 条里大部分是**契约自己允许的**（例如 `OP-20` 自检，契约明写「B4 前可无 UI，API 已有」；
> `OP-51` 跨端镜像，契约明写「一个 `data-action` 都不许有」）。**空不等于漏** —— 区别就在于
> 每一条都写了 `note` 说明为什么空。这也正是这张表比"一张清单"值钱的地方。

### ★ 建表当场抓到的真问题：`OP-3b`「暂停 / 继续」没有可走通路

规格 `SR-F3.2` 写的是「**中断三选（暂停 / 放弃 / 记中断）**」，台账里它是 **done**。
表一建就露出来了：

| 面 | 现状 |
|---|---|
| 契约 `OP-3b`「暂停 / 继续」 | **写着** |
| 领域层 | `STATUS_PAUSED = "paused"` 存在、`finish` 也接受它 —— **但没人发过它** |
| `app.py` | **没有**暂停 / 继续路由 |
| 界面 | **0 处** pause / resume；那三个按钮是「**结束（计入投入）**/ 记中断 / 放弃（不入账）」 |
| 「继续」 | **半条路都没有**（要继续只能重新开一段） |

**也就是说：规格里的第 3 项「暂停」在实际做的过程中被「结束」替代了，但规格和台账都没跟着改。**

这跟 T-G23 抓到的番茄钟是**同一类问题**。当时留下的教训是：「声称 done 时，证据要挑
『**这个名字没了它就说不通**』的那种」—— 而 `SR-F3.2` 的证据恰好只覆盖了 `abandoned` 与
`interrupted` **两个词**，第三个词就这么滑过去了。

**我没有擅自改**（这是产品判断），两条路都摆着：
① 把规格 / 契约改成「**结束 / 放弃 / 记中断**」（承认现状是对的）；
② 真做「**暂停 + 继续**」（那就得加路由、加按钮、加"回到原来那段"的状态回退）。
**已登记交接待你定。**

## 8. 顺手发现的一件事：契约层有 6 处「基础篇 + 领域篇」双节

`OP-1 / 2 / 3 / 5 / 7 / 8` 在 `interactions.md` 有基础一节，在 `docs/contracts/domains/F*.md`
又有带「（扩展）」的一节 —— **这是设计如此**（领域篇是在基础契约上再加该域的要求），
不是重复。检查器把它当**提示**报出来、取不带（扩展）的当正名，不当冲突。
（写这一条是因为：不写清楚，下一个人会以为是脏数据而去删。）
