# 复盘 · 面板状态口径：没有判决的日志不许说「可能卡死」（T-G144，卡 052）

## 一、为什么有这张卡

用户 2026-09-26 看着面板问「怎么有个开 2 个小时的任务」。主控把 `wb_dash.api_state()`
的数据捞出来：19 行「未结束」里，`022.r2@.wt/sparse` 显示**静默 228.4 分钟（可能卡死）**、
`022.r3` ≈ 113.3 分钟、`045@.wt/quota` 50.1 分钟 —— 真相是它们都是**直连 CLI** 跑的一轮：
CLI 不写判决文件、也没有派活器心跳，日志早就不动了。面板只有两种「还活着」的证据
（判决文件 / 派活器心跳），两样都没有时它把「我不知道它怎么了」渲染成了「它卡死了」，
而且**永久挂着**。这是状态口径的缺陷，不是工人的问题。

## 二、改了什么（口径）

只动 `tools/wb_dash.py` 的**显示层判据**（`tools/wb_dispatch.py` / `wb_status.py` 一字未动）：

1. **新终态「已停（无判决）」**（`tools/wb_dash.py:75` 一带的 `_state`）：
   没有判决（无判决文件、日志里也无 `result` 事件）+ 没有**在更新**的派活器心跳 +
   日志静默超过本次阈值 → 状态 = `已停（无判决）`（色 `quiet`，黄 —— 不是失败、不下结论），
   行里新增 `note` 字段 = 「没有判决文件：可能是直连 CLI 跑的，或已退出」。
2. **「静默 N 分钟（可能卡死）」加了前置**：只在心跳**在更新**（= 本该在跑）时才允许 ——
   `_state(..., heartbeat=True)` 才会走到 stall 档。心跳是否「在更新」只看本仓真有的证据：
   `wb-<卡>.heartbeat.txt` 的 mtime 距今 ≤ `HEARTBEAT_FRESH_SECONDS = 300` 秒
   （派活器默认 120 秒一跳，留 ≈2.5 跳余量）；没有心跳文件 = 没有。不做进程级猜测。
3. 静默不足阈值的行为不变（`在跑` / `安静`）；有判决或日志有 `result` → `收工·结束` 不变；
   日志整份解不出 → `日志不可解析` 不变（046 口径原样）。

## 三、先红后绿（反证）

  `6 failed, 21 passed`。钉子①原文：
  `AssertionError: assert '静默 10.0 分钟（可能卡死）' == '已停（无判决）'`
  （用例 `test_stopped_no_verdict_no_heartbeat`，造的是无判决/无心跳/静默 600 秒的假 log）。
- **绿**（改后）：`python -X utf8 -m pytest tests/test_wb_dash.py --no-cov` →
  **27 passed**；`python -X utf8 -m ruff check tools/wb_dash.py tests/test_wb_dash.py` →
  All checks passed。
- 四颗钉子（全在 `tests/test_wb_dash.py`）：
  - ① 无判决 + 无心跳 + 静默超阈值 → `已停（无判决）`，且 `可能卡死` 不在状态串里
    （`test_stopped_no_verdict_no_heartbeat`）；
  - ② 心跳在更新 → 不判「已停」：日志新 → `在跑`；日志静默 600 秒但心跳 mtime 是现在 →
    `静默…（可能卡死）`（本该在跑才配说这句）；心跳文件存在但 mtime 600 秒前 →
    `已停（无判决）`（`test_fresh_heartbeat_still_running_never_stopped`）；
  - ③ 有判决 → `收工·结束` 且 `note` 为空（`test_state_finished_by_verdict_file` 加了一行断言）；
  - ④ 真数据对照（见下）。
