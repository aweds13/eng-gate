# 复盘 · 长任务执行协议（自动执行 + 步骤级 checkpoint）

> 时间：2026-09-18
> 来源：本窗口与用户的对话要求。
> 性质：工作协议 + 能力边界记录；不是产品规格。
> 结论：采用**模式 A**——单线程主控 + 执行，自动执行已授权；**不采用**「我直接 spawn sub agent」。

---

## 一、用户原始要求（对话还原）

1. 为支持长任务，执行时必须按工程管理文件走：`specification/conventions.md` → `contracts/` → `ACCEPTANCE.md` → `CODING_GUIDELINES.md`，并维护 `复盘/` 与 `交接-重构进度.md`。
2. 最初要求：「上下文超过 500K 时自动检测并更新复盘/交接」。
3. 后续讨论替代方案：改为**步骤级 checkpoint**；或「我作为主控，把任务分发给 sub agent」。
4. 最终授权：**先执行第 1 步重构，授权自动执行**；执行任务前先写复盘记录本次对话要求；走完第 1 步后说明第 2 步是什么。

---

## 二、能力边界（诚实声明）

| 事项 | 能力 | 说明 |
|---|---|---|
| 步骤级 checkpoint | ✅ | 每完成一个契约级操作 / 一次提交即写快照 |
| 本回合内自动执行 | ✅ | 读文件 → 改 → 跑质量门 → 提交 → 回写复盘/交接 |
| 跨回合 / 后台自唤醒 | ❌ | 回合结束即停止；需要用户或外部调度器发下一条 |
| 真实 spawn sub agent / 新窗口 | ❌ | 本环境只有 PowerShell 工具，无 Task/Agent/API；不能创建会话 |
| 实时监控其它窗口/子代理 | ❌ | 无调度接口；只能接收它们回传的分支/提交/测试结果并验收 |
| 自动检测 500K 上下文 | ❌ | 拿不到自身 token/字符计数；平台截断/压缩不由我控制 |
| 工作区外写入 / worktree | ❌ | 沙箱写权限仅限工作区内；可考虑工作区内 `.worktrees/` |
| 联网 | ❌ | 工具无互联网 |

> 因此：**「500K 自动检测」由「步骤级 checkpoint」替代**；主控/子代理的真实分发需要外部执行器，本文档先把接口与协议定好。
---

## 三、模式 A：单线程主控 + 执行循环

```
① 读工程管理入口（协议 + 交接快照 + 当前任务卡）
② 读当前任务相关的 conventions / contracts / ACCEPTANCE / implementation
③ 实现（最小侵入、不改范围外）
④ 跑「门禁 + 审计」：python -X utf8 scripts/run_gates.py     ← 见 §九（硬约束）
⑤ 提交（Conventional Commits + Task:/Refs:/Ledger:/Gates: trailer）
⑥ 写步骤级 checkpoint（复盘 + 交接快照 + 台账状态变更）
⑦ 判断下一步；若跨窗口，输出新窗口开场白
```

> §九 是 2026-09-18 用户确认的**强制框架**：它把"我以为做完了"变成"机器对完账才算完"。

## 四、停止条件（只在这些点请示用户）

- 破坏性 / 不可逆操作（删数据、破坏性 schema 变更、force push、改历史）。
- 需要产品决策或改 `conventions.md` / `contracts/` / `ACCEPTANCE.md` 的横切规则。
- 超出当前任务卡范围，或需要引入新依赖 / 联网 / 外部服务。
- 质量门红且原因不明确、修复方案有分叉。
- 发现与工程管理文件冲突、或文档与代码出现新的不一致。

## 九、强制框架：git + 台账 + 门禁三方对账（2026-09-18 用户确认）

> 背景：用户指出「文档工作时发生**偏移和缺失**、后端和前端**连接很差**、后端也**做不完整**」，
> 并拍板：「**审计不通过就别提交**」「按你的倾向来（FAIL + YAML 台账 + 门禁落盘）」
> 「**把一条线一条线地做完**，做完前端我验收这一条线，再开下一条」。
> 详细诊断与决策见 `复盘/文档偏移与约束框架复盘.md`；落地物见下表。

### 9.1 五个部件

| 部件 | 作用 |
|---|---|
| `docs/traceability.toml` | **机器可读台账**（单一真源）：每条 SR/OP 一行 = 状态 + 可验证断言 + 缺口说明 |
| `gates/last.json` | **门禁落盘产物**：`scripts/run_gates.py` 真跑出来的结构化结果（含 rev/耗时/结论） |
| `scripts/audit_progress.py` | **六项对账**：任务号 / 登记 / 声称=证据 / 文档同提交 / 门禁产物 / 进度可从 git 重建 |
| `scripts/run_gates.py` | 一次跑完所有门禁 + 审计，落盘 `gates/last.json`；**任一失败即退出码 1** |
| 提交 trailer | `Task:`（任务号）、`Refs:`（SR/OP）、`Ledger:`（状态变更）、`Gates:`（门禁摘要） |

### 9.2 六条硬规矩（对我自己的约束）

1. **无任务卡不开工**：动手前先写任务卡（ID / 改哪些文件 / 触及哪些 SR·OP / 验收命令）。
2. **提交必须带 `Task:`**（与 `任务重规划-剩余工作.md` 的编号一致）；没有任务号的提交 = 无卡开工。
3. **文档与代码同一提交**：改了 `src/` 就必须同时改 `docs/traceability.toml` + `docs/changelog.md`
   + `复盘/长任务执行协议.md`（或交接文档）—— 由 `run_gates.py` 的提交前检查强制。
4. **门禁必须落盘**：`Gates:` trailer 的内容必须有 `gates/last.json` 支撑，且该文件记录的 `rev` 与提交一致。
5. **审计不通过不许提交**（用户明确要求）：`scripts/audit_progress.py` 退出非零 → 不许 commit。
   豁免只能写进台账 `[exceptions]`（**逐条留痕、修一条删一条**），不许静默绕过。
6. **每步 CHECKPOINT 必带"台账状态变更"**：哪几条从 `todo/partial → done`，以及证据断言是否新增。

### 9.3 台账状态词表（只有五个）

`done`（断言必须全过）｜`partial`（半成品，必须写 gaps）｜`todo`（没做，必须写 gaps）｜
`deferred`（规格自标二版/后置，写依据）｜`broken`（**声称 done 但断言对不上 → 审计必须 FAIL**）

### 9.4 标准动作（每一步都照这个来）

```powershell
cd "D:/repo/engineering"
$env:PYTHONPATH = "$PWD\tools\sandbox_shim"

# ① 改代码 + 同提交地改台账/changelog/checkpoint
# ② 跑门禁 + 审计（会落盘 gates/last.json；不通过就别提交）
python -X utf8 scripts/run_gates.py
# ③ 提交（带 trailer）
git add -A
git commit -m "feat(tasks): ..." -m "Task: T-A1
Refs: SR-F1.12, OP-11
Ledger: SR-F1.12 partial -> done
Gates: <把 run_gates 打印的那行粘过来>"
# ④ 审计这次提交（含文档同步、门禁产物、进度对账）
python -X utf8 scripts/audit_progress.py --rev HEAD
```

### 9.5 推进节奏（用户定的"一条线一条线"）

1. **一次只做一条主线**，按 `任务重规划-剩余工作.md` 的顺序；不跨线撒网。
2. **这条线上的交叉点与依赖模块顺手做完**，不单独排线。
3. **每条主线必须把前端一起做完**（交付可达性：后端有入口、界面有位置）。
4. **做完交用户验收这条线**，通过后才开下一条。
5. 主线完成的判据：该线所有条目在台账里是 `done`（`partial/todo` 清零），审计通过，前端自检通过。

### 9.6 这套框架**不**保证什么（诚实边界）

- 不保证"改动对不对"（靠单测/护栏）；
- 不保证"文档写得准"（只保证改了、且声称有证据）；
- 不保证"界面好不好看"（**只能人工过目** —— 本轮已踩过"测试全绿但 UI 崩了"的坑）。
