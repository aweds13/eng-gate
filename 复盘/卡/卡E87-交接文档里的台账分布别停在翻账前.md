## 要解决的问题（已实测，不是推测）

卡 E85 落地那一笔（`10875e82`）落完之后，`scripts/audit_progress.py` 立刻判红：

```
- 复盘/交接-重构进度.md 里写的分布对不上台账：写的是 done=640 / partial=1 / todo=25 /
  deferred=15（共 681 条），实际是 done=641 / partial=1 / todo=25 / deferred=15（共 682 条）
```

逐 rev 实测（`git show <rev>:docs/traceability.toml` 用 `tomllib` 数 `status`，与
`git show <rev>:复盘/交接-重构进度.md` 里那行「台账进度：done a / …（共 N 条」对照）：

| rev | 交接文档写的 | `docs/traceability.toml` 实算 | 结论 |
|---|---|---|---|
| `dbe3a71f`（卡 E83 落地） | 638 / 1 / 25 / 15（679） | 同 | OK |
| `bb6c6479`（卡 E84 落地） | 639 / 1 / 25 / 15（680） | 同 | OK |
| `10875e82`（卡 E85 落地） | 640 / 1 / 25 / 15（681） | **641 / 1 / 25 / 15（682）** | **差一** |
| `5f562922`（我事后补的计数笔） | 641 / 1 / 25 / 15（682） | 同 | OK |
| `e4f8200b`（卡 E86 落地） | 642 / 1 / 25 / 15（683） | 同 | OK |

机制（读源码定死，不是猜）：

- 那行数字由 `tools/sync_counts.py` 刷，它的 `counts()` 数的是 **`docs/traceability.toml`**
  的条目（`LEDGER = ROOT / "docs" / "traceability.toml"`），**不是** `docs/workbacklog.toml`；
- 正常落地路：② `tools/sync_docs.py` 把 `docs/traceability.d/<台账号>.toml` 汇总进
  `docs/traceability.toml`（条目 +1）→ ③ `tools/sync_counts.py` 刷数字（这时数字已对）
  → ⑤′ 翻账只改 `docs/workbacklog.toml`、**不改** traceability ⇒ 审计通过；
- `--commit-only` 路：整个 `if not a.commit_only:` 块被跳过（③ 就在里面，
  `tools/pool/landing.py:2327-2328`），而 **② 也跳过了** —— 可卡树里的
  `docs/traceability.toml` 早在作者手上就被 `tools/sync_docs.py` 汇总过（E85/E86 都跑过）
  ⇒ 这一笔提交照样让条目 +1，而 `tools/sync_counts.py` **一次都没跑** ⇒ 交接文档那行
  停在落笔前的值。
- ⇒ 病根不是「谁忘了一次」，而是**顺序缺陷**：凡是「提交之后会让 traceability 条目变多」的路，
  刷数字必须排在**所有文档改动之后、暂存之前**。而 ⑤′.5 `recount_derived()`
  （卡 E76/E77/E78）已经在那个位置重算了两份现算文档，却**不管这行数字**。

★ 与相邻三张卡的分工（别混进来）：
  · 卡 E76/E77/E78（`T-AG579/581/…`）= ⑤′.5 重算 README 与 `docs/INDEX.md`；
  · 卡 E86（`T-AG593`）= rebase 冲突里那两份现算文档不该停手；
  · 本卡 = ⑤′.5 顺手把那行**台账分布**刷掉，并且**复核**。

## 判据（6 条）

1. **刷数字进 ⑤′.5，排在翻账之后、暂存之前**：`tools/pool/landing.py` 新增
   `refresh_counts(wt) -> list[str]`，真写盘跑 `tools/sync_counts.py`（不带 `--check`、
   子进程、`cwd=wt`、`sys.executable -X utf8`），返回**真被改写**的相对路径。
   调用点在 `for _rel in recount_derived(wt):` **之前**，与它同一段（批/单卡两分支汇合之后）——
   ⇒ `--commit-only` 也走得到。★ **那段 `for _rel in recount_derived(wt):` 的逐字字面不许动**
   （`tests/test_pool_landing.py::_drop_landing_leg` 靠它定位）。
2. **改了的必须进 allow**：`refresh_counts()` 返回的每一条都补进 `allow`（`复盘/长任务执行协议.md`
   不在 `DOCS` 里，漏了就会被 `staged_and_extra()` 判「计划外暂存」而停手）。
3. **刷完必须复核，失败响亮**：紧接着跑 `tools/sync_counts.py --check`，非零 ⇒ **不许提交**，
   打印 `[FAIL]` 级别的一句话并 `sys.exit(2)`（与 E76/E77 的同一条出口，绝不吞成跳过）。
   写模式本身非零同样 `sys.exit(2)`。
4. **安静是常态**：数字本来就对时，`tools/sync_counts.py` 写模式不改任何字节、`refresh_counts()`
   返回空表、日志不出「★ 台账分布改了它」那行；这一笔的文件集合与加卡前一致（不许夹带别的文件）。
5. **这棵树没有那套工具时跳过要说清楚**：树里没有 `tools/sync_counts.py`（测试假仓、老仓）
   ⇒ 打印一行 `· 刷台账分布：这棵树里没有 tools/sync_counts.py（跳过）` 并返回空表；
   **不静默**、也不退 2（否则所有只拷了 landing.py 的假仓全红）。
6. **既有行为一字不变**：`recount_derived()`、`resolve_derived_conflicts()`、`DOCS`/`GATES`/
   `RECOUNT_DOCS`/`RESOLVABLE` 全部不动；`tests/test_pool_landing.py` 的 26 条既有钉子
   一字不改、全绿。
