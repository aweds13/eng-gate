## 要解决的问题

pool 有额度记录，排批却完全不看它：

```python
# tools/pool/plan.py:426（修前）
def greedy_pack(cards: Sequence[Card], limit: int) -> list[list[Card]]:
    """按层贪心打包……"""
    batch: list[Card] = []
    used_trees: set[str] = set()
    for card in cards:            # ← 顺序 = 传入顺序 = 台账登记顺序
        if card.tree in used_trees:
            continue
        ...
```

后果：续期只剩 3 分钟的号会被排在续期还有 5 小时的号**前面**，排进去就只能撞 429 干等。
`wb_dispatch.py:3452` 撞 429 之后才 `sleep(wait_seconds(...))` —— 那是**事后**补救；
本卡补的是**事前**：先派快要回额的，把等待窗口藏进并行里。

magpie 的 `Smart` 就是这件事的成熟答案，四层稳定排序（不是拼一个大元组，因为原件就是一串
`sort.SliceStable`，后一级只在前一级打平时才动）：

1. 按 `tier(used)` 分三桶：`>= 98`（`SpentShare`）用尽了、`>= 90`（`LowShare`）快用完、其余还有余量；
2. `fine` 桶内逐级稳定：`left` 余额大的在前 → `lapse` 截到小时比、空排后 → `soon` 逐窗口截到小时比、
   空排后、窗口多的在前；
3. `low` / `spent` 各按 `used` 升序；
4. 拼成 `fine + low + spent`，`resting` 的沉最后。

★ **输入顺序就是基准顺序**：全程打平的那些号保持原序（保 prompt cache）。

## 判据（10 条）

1. **`tier(share)` 与 magpie 逐字同判据**：`>= 98` ⇒ 2、`>= 90` ⇒ 1、其余 0；`share` 越界
   （`<0` / `>100`）、`NaN`、`bool` ⇒ **抛 `RouteError`**，**绝不 clamp**（`101` 是「这个数从哪来」，
   把它压成 100 等于把上游形状错误洗成一次成功派活）。
2. **三桶顺序**：`tier == 2` 的**绝不**排在 `tier == 0` 之前；`tier == 1` 夹在两者之间。
3. **`soon` 逐窗口截到小时比**、空 `soon` 排后、前缀相同则窗口多的在前；`lapse` 同法作第二判据。
4. **`left` 大的在前**、`None`（没人告诉过余额）排在有值的之后。
5. **`resting` 沉到最后**，且两边各自的相对次序都不动（稳定）。
6. **打平保原序**：`smart_order` 是全稳定排序 —— 所有判据都相等的号，输出索引顺序 = 输入顺序。
7. **`apply_order` 不是排列就 fail-open 回 `identity`**（长度不符 / 越界 / 重复 / 非 int 一律回原序，
   **不抛**）—— 排位是优化，坏掉的排位不该让整轮派活停摆。
8. **`reset_for(model)` 取「最近一次记录」**：跨全部卡比对 `recorded_at` 字符串**最大**那条，
   再用 `pool_quota.parse_reset` 解析 —— 不自己写第三份正则；没有记录 / 文件不在 / JSON 坏 /
   形状不对 ⇒ `(None, "")`，**不抛**（调用方必须当「不知道」，不许当 0 秒、也不许当余额耗尽）。
9. **`ordered()` 在没有额度记录时逐项等于输入顺序**（硬约束：既有排批断言与 prompt cache 都靠它）；
   有记录时「有得等的在前、已过期需重探的次之、**不知道的最后**」。
10. **`greedy_pack` 一字不改**：`limit` / 树唯一 / 文件不相交三条安全判据原样，动的只是「谁先被放进批」。
