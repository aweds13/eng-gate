# 卡 A280 · 对账器认批次围栏（26 条 stale-done 逐张定性）

## 缺口

`wb_reconcile.py` 对 26 张 `status = done` 的卡报黄：「状态 done 但找不到提交 —— 可能是老账，请人看一眼」。
逐张看下来是**两层**原因，都不是「真没落」：

1. **判据被截断**（真 bug）：`_commit_for()` 里 `git log --grep <task> -10` 只取最近 10 条**命中**，
   而 `--grep` 同时匹配提交正文。像 `T-G114` 正文命中 31 条，主题里真点了号的 `ec2121e`
   排在第 11 条之后 ⇒ 被截掉，卡 029 就这么白报了一年。
2. **老账落地用的是「批」**：2026-10 那批卡是攒批收口的（`f4fd27d`「第一次攒批收口：卡 204/207/208/209」、
   `b5f76bf`「第二批：卡 215/216/217」…），提交主题里只有**批次级** Task 号，没有各卡自己的号。
   当时翻 done 的依据写在 `37a079c` 的提交正文里：**「围栏状态 `state == landed` ⇒ 成员都算已落」**。

## 变更

- `tools/wb_reconcile.py`
  - `_commit_for()`：去掉 `-10` 截断（改为扫全部命中，只在**主题**里找 Task 号）。
  - 新增 `_batch_landed(root)`：批次围栏 → `{卡号: (批号, 收口提交)}`，只认 `state == landed` 且
    `landed.commit` 非空；目录缺失/坏 JSON 一律当没有（优雅降级，不抛）。
  - 新增 `_landed_commits(root)`：所有 landed 批的提交集合。**独立扫文件**，不从
    `_batch_landed()` 的 values 取 —— 那张表按卡号做键，多个批都声明 `M-1` 会互相覆盖
    （实测 105 个 landed 批只剩 33 个提交，`d2420b0`/`ad5516c` 就是这么被吞掉的）。
  - 新增 `_spec_commit_in(root, spec, landed)`：卡规格文件是被哪笔**已收口批次**带进 git 的
    （兜底证据，覆盖「批声明的成员号是 M-1 而非卡号」那类）。
  - `check()` 返回值由 2 份变 3 份：`(stale_pending, stale_done, accounted_done)`；
    `accounted_done` 打印成 `[蓝] … 已认账`，`--json` 里多一个 `accounted_done` 键。
- `tests/test_wb_reconcile.py`：5 条老断言改三份解包；新增 2 条钉子 ——
  ① done 卡在 `state=landed` 的批里 ⇒ 认账（不报黄，`commit` 字段带出收口提交）；
  ② 批是 `state=draft` ⇒ 什么都不证明，照报黄（不能拿「登记了」冒充「落了」）。

## 检查点

- `python -X utf8 tools/wb_reconcile.py` 尾行：`[OK ] 没有 stale-pending（stale-done 0 条 / 已认账 26 条，均不算红）`
- `python -X utf8 -m pytest tests/test_wb_reconcile.py -q --no-cov`：7 passed
- `ruff check tools/wb_reconcile.py tests/test_wb_reconcile.py`：All checks passed

## 陷阱

- 判断「某卡是否已落」**不能**只看提交主题里的 Task 号：本仓真实历史大量用批次收口。
  权威判据是围栏状态（`gates/diag/batch/<批号>.json` 的 `state`/`landed.commit`），
  这与 `37a079c` 当初翻 done 的口径一致 —— 本卡只是把它写进判据，没有放宽任何一条红线：
  `stale-pending`（状态不是 done 却已有提交）照旧**红**。

## 影响面

只读工具 + 单测；不动台账、不动卡状态、不写任何文件（`--fix` 仍然未实现，照旧只报）。
