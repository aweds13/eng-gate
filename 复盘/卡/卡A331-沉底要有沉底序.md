# 卡 A331 —— 沉底要有沉底序（T-AG533）

> 台账号 `T-AG533` ｜ 分区 A（历史线 / 号池 pool）｜ 树 `.wt/A331` ｜ 层 判据层
> 依据：magpie 的 Sink 沉底（`internal/gateway/sink.go:31-40/43/53/61/74-82/94-117`、
> `internal/gateway/routing.go:1149-1161` 的 `case failRate`、`internal/gateway/routing.go:1701`
> 的 `weigh()`、`internal/gateway/fallback.go:734` 的 `sinkOwn()`），移植设计见
> `_ext/_port_design_quota_routing.md` 的 `## F19 Sink 沉底`（`:629-801`）。
> 实测现场（HEAD `17cc103a`，工作树 `.wt/A331`）：`git grep -n "sink" HEAD -- tools/` **退出码 1、
> 零命中**；`git grep -n "沉底" HEAD -- tools/ tests/` 只命中一句无关文案
> （`tests/test_team_line.py:4`「分配出去就沉底了」）；`git grep -n "pool-sink" HEAD` 零命中 ——
> 也就是说「429 打过的候选要沉到队尾，且先沉的排后续沉者之前」这件事，本仓一行都没有。

## 要解决的问题

magpie 在 429 之后不是原样重试，而是把**还有配额**的候选沉到次序末尾：

```go
// internal/gateway/routing.go:1149-1161
case failRate:
    d, r.By, r.Failures = s.rateRest(c, header, body, sharedPool, now)
    if c.full(now).IsZero() && !(c.isOpenRouterFree() && sharedPool) {
        if remoteModelRest(c, failRate, header) {
            sink(c.restID(), now)   // 模型级
        } else {
            sink(c.restKey(), now)  // 账号级
        }
    }
```

而沉底本身是一个**有态的序号**（`sink.go:31-40` 的 `sunk.m[key] = sinking{at, n}`）加一个
**稳定排序**（`sink.go:94-117` 的 `sinkOrder`）：

```go
seq := make([]uint64, n) // 0: never sank
for i := range idx {
    idx[i] = i
    if s, ok := sunkAt(at(i)); ok { seq[i] = s.n }
}
slices.SortStableFunc(idx, func(a, b int) int { /* sa==0 ⇒ -1；sa<sb ⇒ -1；否则 1 */ })
```

即「未沉者在前（保原序），沉者按沉序，先沉的排在后续沉者之前」。

本仓此前**没有这一层**：`tools/wb_dispatch.py:436` 的 `next_whitelist_model()` 是静态链序
（`chain[idx + 1] if idx + 1 < len(chain) else None`），429 主流程（`:3440-3475`）探不过就
「按序换」，换回来的那一轮**不记得谁刚被 429 打过**。于是同一轮里刚撞墙的候选可能立刻又被端上来。

病灶：429 之后缺一份「沉底序号」这一层状态，也缺一条「先沉的排后面」的稳定序 —— 而这层
状态与序是纯判据，与派活主流程无关，可以单独落地并被钉子钉死。

## 判据（8 条）

1. **`sink()` 序号单调递增、同 key 再沉刷新**：每次调用 `n = 上次 + 1`（从 1 起），
   同 key 再沉 ⇒ 序号刷新成新的（不是保持老的）。照 `sink.go:43-48`。
2. **`sunk_at()` 先模型级再账号级**：先查 `<account>/<model>`，查不到才查 `<account>`；顺序
   不许反。照 `sink.go:74-82` 的 `c.restID()` 先于 `c.restKey()`。
3. **`sink_order()` 是稳定序**：`seq == 0`（从未沉）全在前且保持原序；沉者按 `seq` 升序。
   key 必须是两段式 `lambda i: (0, 0) if seq[i] == 0 else (1, seq[i])`。照 `sink.go:94-117`。
4. **`unsink()` 只擦精确 key；`unsink_all(prefix)` 删 `k == prefix || k.startswith(prefix + "/")`**
   并返回删掉几个。照 `sink.go:53/61-69` —— 账号级回原位时必须连带它下面的模型级一起擦。
5. **只因「限流」沉，余额耗尽绝不沉**：`should_sink(kind, routing)` 里 `kind == "限流"`
   才真；`kind == "余额耗尽"` 硬拦。硬证据：magpie 的 `failQuota` / `failCredit` 分支
   （`routing.go:1096-1148`）里**没有任何 `sink(` 调用**。
6. **`sinks(on, routing)` 的开关口径**：`on and routing not in ("rotate", "weighted") and
   routing != "manual"`。照 `sink.go:87-89` + `goesRound`（`routing.go:1724-1727`）。
7. **状态文件的边界**：落 `gates/diag/pool-sink.json`（gitignored 的运行状态，不许进 `docs/`）；
   不存在 / 坏 JSON ⇒ 只读回空、**不抛**、**不重写**；`seq` 非正整数 ⇒ 该 key 视为从未沉并在
   **stderr** 说一句（不静默）；写盘用同目录 `tmp` + `os.replace`（不写半截）。
8. **「有配额却 429」不算已核实**：本仓没有 magpie `c.full()` 的等价物（`tools/pool/registry.py`
   只有 `model` 字段，`:283`，无用量读数）⇒ `sink()` 的 docstring 必须逐字写明：这一前提是
   **假定**成立、由调用方保证、**不算已核实**。设计节原话：「这是本节唯一一处不允许含糊的地方。」

## 不许做

- **不许接线 `tools/wb_dispatch.py`**：那个文件 3533 行、被大量用例钉着（`next_whitelist_model`
  在 `:436`，429 主流程在 `:3440-3475`），接线要另开一张卡；本卡只落「判据层 + 状态文件」。
- **不许碰 `tools/pool_quota.py`**：另一张在跑的卡正在改它，改了会撞车。
- **不许做 TTL / 到期自动 unsink**：magpie 的 sink 自己也不带到期时间（只有手动 `unsink` 或重启
  才回原位）；加 TTL 是另一种语义，那是 F20 的 rest，不是本卡。
- 不许把 `gates/diag/pool-sink.json` 放进 `docs/` 或任何被 git 跟踪的位置（它是运行状态，
  参照 `gates/diag/quota-state.json` 的既有位置口径）。
- 不许放宽判据来换绿：不许把 `sink_order` 的两段式 key 换成单段、不许删
  `test_reverse_sink_order_without_seq`、不许加 `noqa` / `# type: ignore` 消警告。
- 不许为了让只读一侧「看起来干净」而在读到坏 JSON 时顺手重写那个文件（判据 7）。
- 不许在本卡里把 sink 的 `at` 当成判据（排序只比 `n`；时钟倒流不影响次序）。
