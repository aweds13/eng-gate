**自动解决其实全成功**（:114 与 :116 两个 `--check` 都是 0），却仍然卡在 `--continue` —— 也就是说，出队+需人工是**误判**：机器手里已经有答案，只差一次 add。

机制实证（临时仓真 git，三组，本卡起草时实跑）：

- **实验 1**：冲突文件已 `git checkout --ours` + 内容已重写 + 已 `git add`，**另有一个未暂存的跟踪文件改动** ⇒ `git rebase --continue` 退 1，报的就是现场那两行（「You must edit all merge conflicts and then / mark them as resolved using git add」），**不点名是哪个文件**。
- **实验 2**：有冲突文件**没 add** ⇒ 同样两行，但**前面多一行** `shared.txt: needs merge`（点名）。
- ⇒ **判别法**：现场日志那两行前面**没有** `X: needs merge` ⇒ 冲突文件其实都已 add，卡住的是**别处的未暂存改动**（工作区脏）。这正是「先 add 再重试」能救的那一支。
- **实验 3**（索引状态轨迹）：rebase 失败后 `git status --porcelain` = `UU shared.txt`；`git checkout --ours -- shared.txt` **不动索引**（仍 `UU`）；重写内容后 `git add -- shared.txt` ⇒ 变 `M  shared.txt`（干净）；此后若再写一个 tracked 文件不 add ⇒ ` M other.txt` + `M  shared.txt` ⇒ `--continue` 退 1。

**机制落点**（读代码得出，标注是推论不是日志逐字节证明）：`resolve_derived_conflicts` 在 `:263-264` 只 add 了 `conflicted` 名单里的路径：

```python

    run(["git", "add", "--", *add], cwd=wt)
```

而它在 `:250-262` 跑的 `scripts/check_derived_docs.py`（写模式）会**真写盘重算** `docs/subsystems/pool/README.md` 与 `docs/INDEX.md` 两份（`scripts/check_derived_docs.py:6-8` 的目标表）。**只要是「冲突表里没有」的那一份被动过，它就永远进不了 add 名单**。E136b / E120b 的冲突表（:112）里都只有 `docs/INDEX.md`、没有 `docs/subsystems/pool/README.md` ⇒ 机制可复现。`tests/test_landing_derived_resolvable.py:32-34` 自己就写着「只有 `tools/sync_docs.py` 与 `scripts/check_derived_docs.py` 是**桩**」—— 真件在这里会写盘，桩不会，所以 E86 的钉子钉不出这一支。

### 问题 3 · 委派里的第三个坑（冲突解决后不跑 `sync_counts`）—— **取证后不成立**，本卡删掉

先把事实摆清（这一半是真的）：`resolve_derived_conflicts`（定义 `:193-265`）内部只跑两个工具 —— `:239` `tools/sync_docs.py`（+:241 `--check`）与 `:252/:258` `scripts/check_derived_docs.py`（+:258 `--check`）。**确实不跑 `tools/sync_counts.py`**。

但「所以交接文档那行台账分布会与台账不一致」推不出来，两条理由：

1. **那一行不会被冲突改旧**。`sync_counts.py` 换的是 `复盘/交接-重构进度.md` 里**一行**数字（`tools/sync_counts.py:42` `HANDOFFS`、`:46-49` 的 `NUM` 正则只换 done/partial/todo/deferred/共 N 条五个数字）。这一行埋在一个 4500+ 行的文档里；`resolve_derived_conflicts` 对三份共享文档取的是 `--ours`（`:222-224`）= **主树那一版**（本来就是刷过的值）；随后 `sync_docs.py` 只把本笔那一节**按片段插回去**（幂等、不动数字）。⇒ 冲突解决**不会**让那行变旧。
2. **冲突路径上本来就不该再跑它**。`refresh_counts` 的调用点是 `:2978`（定义 `:458-502`），在 `if not a.commit_only` 的 ⑤′ 段「翻账之后、暂存之前」；`:481-484` 的文档串把位置口径写死了（「为什么位置是「翻账之后、暂存之前」… 放在 `recount_derived()` **之前**」）。⑥ 提交在 `:3098`，⑦ rebase 在 `:3125` —— **都在它后面**。所以在 rebase 冲突路径上再加一次 `sync_counts`，等于给同一条事实造**第二处投影**，正是仓库规矩里禁止的那种。

⇒ **本卡不写这条判据**；只在「不许做」里留一条「不许顺手在 `resolve_derived_conflicts` 里加 `sync_counts`」，免得下一个人照着旧描述把它加回来。

### 判据 2 · ⑦ `rebase --continue` 失败后：先按白名单补一次 add、**只重试一次**，仍失败才停手出队

- **断言**：
  - `tools/pool/landing.py` 新增 `def _continue_rebase_after_resolve(wt: pathlib.Path, env: dict, *, task: str) -> tuple[int, list[str]]`（名字与语义见「交付 4」），返回 `(退出码, 本次补 add 的相对路径清单)`；`:3137-3151` 整段搬进去，`main()` 里只留一次调用 + 按返回值打印/出队。
  - **补 add 的白名单只许是已有的三张表**：`RESOLVABLE`（`:109`，= `DERIVED` + `RECOUNT_DOCS`）、`GATE_ARTIFACTS`、`_queue_rels(wt)`（台账，`:217` 已在用）。做法：`git status --porcelain` 取脏名单，**与白名单取交集**再 `git add --`；交集为空 ⇒ 不 add、直接按「重试也无法继续」处理。
  - **只重试一次**：`--continue` 第二次仍非零 ⇒ 打印「★ 重试一次仍失败 ⇒ 停手」，**保留既有 `_mq.drop(a.task)` 与出队文案**（`:3145-3150` 的语义一字不变），`return 3`。
  - **白名单外的脏文件 ⇒ 不 add、点名、返 3**：打印必须列出那些路径，并写明「不 add：那是本笔之外的改动，吞进来就是把人的东西混进这一笔」。
  - **留痕三行可 grep**（无论成没成）：`★ rebase --continue 失败 ⇒ 先补 add 再重试一次：`、`↳ 补 add：N 个：a · b`、`↳ 重试退出码 = N`；成功时再加一行 `★ 重试后 rebase 成功（本笔补 add 了 N 个派生文件）`。
- **什么情况下红**：
  - 现场那种形状（冲突已全 add、只有 `docs/subsystems/pool/README.md` 脏）重放时，仍然 `return 3` + 出队（没补 add，或补了没重试）。
  - 重试了**两次以上**（变成无限重试；或重试里套重试）。
  - `git add` 落到白名单外的路径（例如用了 `git add -A` / `git add -u`）。
  - 二次失败时不出队（把 E5 判据 4 的语义悄悄放宽）。
- **钉子**：`tests/test_landing_derived_resolvable.py` 的六条既有用例 —— `:194` `test_resolvable_is_both_tables_and_the_extra_filter_uses_it`、`:206` `test_a_conflict_on_the_two_recount_docs_is_resolved`（`:215` `assert _unmerged(repo) == []`，注释原文「checkout 之后没 git add ⇒ 索引里仍是 UU（本卡实测）」）、`:218` `test_recount_runs_the_checker_in_write_mode_then_checks`、`:230` `test_the_two_recount_docs_take_the_baseline_not_the_card_tree`、`:239` `test_the_gate_artifacts_still_take_ours_own`、`:248` `test_a_still_inconsistent_recount_stops_the_landing`、`:259` `test_a_real_code_conflict_still_stops_and_is_named`、`:272` `test_the_existing_paths_are_untouched_when_only_derived_conflict` —— 它们钉的是 `resolve_derived_conflicts` 本体，本卡**一个字节都不许改**（新函数不碰它，只是它的调用方）。新用例挂**同一个文件**（真 `git init` 仓库 + 真 rebase 的形状已经在 `:128` `_make_repo` 里）；新用例**不许**改成「桩掉 `git`」—— 这一支的整个病根就是真 git 的索引状态。
