# 卡 E31 —— 覆盖率开销：把 `--cov` 从每次门禁的固定税里拿掉

> 台账号 T-AG485 ｜ 树：`.wt/E31` ｜ 分区：E（CI 子系统）
> 依据：2026-10-25 实测（`addopts` 里挂着 `--cov=timeflow`，而开销**本仓未测**）

## 现在疼在哪（实测 + 一条未验证）

1. **覆盖率是每次都交的税**：`pyproject.toml` 的 `[tool.pytest.ini_options]` 里
   `addopts = "-q -m \"not acceptance\" --cov=timeflow --cov-fail-under=70"` —— 每一趟门禁、
   每一个 worker 都在记账，而门槛（70%）是**发布口径**，不是「每次内循环都要看」的口径。
2. **这笔税有多大，本仓不知道**：我昨天用 `-o addopts="-q -m 'not acceptance' --cov=timeflow"`
   构造参数时，**shell 把引号剥掉、值里带着裸引号**，读数变成
   `默认cov 467 ms / ctrace 3565 ms / 无cov 2838 ms`（第一档秒退）—— 明显失真，**这组数作废**。
   也就是说「覆盖率到底占多少」目前是空白。
3. **外部有强证据指向一处便宜的改动**：Trail of Bits《Making PyPI's test suite 81% faster》
   （2025-05-01）里 `COVERAGE_CORE=sysmon`（coverage ≥ 7.7.0 + Python 3.12+）把覆盖率开销
   从 58 s 压到 27 s（**−53%**）。前提是 xdist 多 worker 下要有 `sitecustomize.py` 调
   `coverage.process_startup()`。我们 **Python 3.14.6 / coverage 7.16.0**，条件都满足。

## 要做成什么样

1. **先量，再改**：同一棵树、同一 worker 数、同一批用例，跑三档并把**墙钟与用例数**都记下来：
   - A：现状（默认 core，带 `--cov=timeflow`）
   - B：`COVERAGE_CORE=sysmon`（同样带 `--cov=timeflow`）
   - C：`-o addopts="-q -m 'not acceptance'"`（不带 `--cov`）—— **用 `-o` 之外的方式传亦可，
     但必须避免 shell 引号嵌套**（建议写成两行：`PYTEST_ADDOPTS` 环境变量或直接 `--no-cov`）
   命令行不许出现裸引号（`tools/cmd_guard.py` 先过）。
2. **若 B 明显优于 A**：把 `sitecustomize.py` 落到仓内（`scripts/sitecustomize.py` 或仓根），
   由门表在 `pytest` 那道门里设 `COVERAGE_CORE` 与 `PYTHONPATH`；**覆盖率门槛不许放松**。
   ★ **这里的 `PYTHONPATH` 有前科**：卡 063 / `T-G157`「门禁假绿」就是 `run_gates.py` 生成子进程
   环境时 `PYTHONPATH` 排错位，导致真机门验的是主树页面还两边一致 → 假绿
   （见 `复盘/门禁假绿-PYTHONPATH-T-G157.md` 与 `scripts/run_gates.py:293 tree_pythonpath()`）。
   所以本卡**不许另写一段 PYTHONPATH 拼装**，必须复用 `tree_pythonpath()`，并补一条钉子证明
   它是唯一出口。
3. **门槛仍然是 70%**：改完必须有一条读数证明 `coverage report` 的百分比与改前一致（±0.1%），
   否则这卡不许落地（拿速度换门槛就是作弊）。
4. 若三档差不出东西（<5%），**卡就如实收口成「测过，无效，不改」**，把读数写进
   `docs/subsystems/ci/` 下一节，别硬凑改动。

## 判据

1. 三档读数表（墙钟 / 用例数 / 覆盖率百分比）进申报，附 `gates/diag/bench-cov-*.log`。
2. `pytest tests/test_run_gates_cov.py -q -o addopts=`，至少 6 条钉子：门表里 `pytest` 那道门
   的 env 拼装（给了 `COVERAGE_CORE` 就带上、没给就不带）+ `--cov-fail-under=70` 仍然在命令里 +
   `--no-cov` 不被静默塞进默认门 + `sitecustomize` 存在时被 `PYTHONPATH` 指到。
3. **反向验证**：把 `--cov-fail-under=70` 从命令里去掉 ⇒ 钉子必须红；把 `COVERAGE_CORE`
   写死进默认门（不经开关）⇒ 「没给就不带」那条必须红。红色原始输出进申报。
4. 全量门禁 `exit 0`；`coverage report` 百分比与改前一致（±0.1%）。
5. 判定阈值：`--no-cov` 收益 **<5%** ⇒ 本仓受插桩的字节码占比小，收口成「测过不改」+ 写进
   `docs/subsystems/ci/`；**>15%** ⇒ 必须落地（sysmon / SlipCover / 只跑一次 cov 并复用数据，
   三选一按实测）。中间地带由主控裁定，理由写进申报。

## 不许做

- 不许降低或删掉 `--cov-fail-under=70`。
- 不许把 `--no-cov` 塞进默认门（那等于把发布门槛藏起来）。
- 不许在没量出数之前就改门表（这卡的顺序是「先量后改」）。
- 不许用 `--cov-fail-under=0` 或 `continue-on-error` 之类的手段「让它绿」。

## 证据

- 三档实测表 + 三份日志。
- `pytest tests/test_run_gates_cov.py -q -o addopts=` 原始输出。
- 两条反向验证的红色原始输出。
- 改前 / 改后 `coverage report` 尾行（`TOTAL … 8x%`）。

## 检索证据（2026-10-25 回灌）—— 这是六张卡里乘数最大的一张

- **coverage.py 本身很贵**：SlipCover（ISSTA 2023，arXiv:2305.02886）实测传统 trace 式覆盖率让
  Python 代码慢 **180%–1300%**，它靠字节码级探针 + 已覆盖路径渐进退插桩做到 **5% 中位开销**。
  推论：我们每次门禁都挂 `--cov=timeflow`，被插桩的那部分时间可能被放大 2.8–14 倍
  —— 但**只对被插桩的 Python 字节码有效**，起子进程的 e2e（E32 那 22 条）几乎不受影响。
- **本仓可用的两个现成开关**：`COVERAGE_CORE=sysmon`（coverage ≥7.7 + Py3.12+，走 `sys.monitoring`）
  与 `COVERAGE_CORE=ctrace`（C 层 trace）。第三方实测：Trail of Bits 的 PyPI 案例
  `COVERAGE_CORE=sysmon` 让 58 s → 27 s（**−53%**）；curl 的 CI 也在用 sysmon。
- **第三条路（若前两条不够）**：SlipCover 是可直接替换的覆盖率后端（近零开销），但会改变
  `.coverage` 数据生成方式，需要先验证 `--cov-fail-under=70` 与 `pytest-cov` 的兼容性。
- **反证**：`pypa/build` 的 PR #1148 显示 `ctrace` 与 `sysmon` 在「动态上下文记录」上行为不同，
  ⇒ 必须实测覆盖率数字是否一致（判据 4 的 ±0.1% 就是为这个写的），不能只看时间变快。
- 采样剖析器的开销下界参考：Scalene（arXiv:2006.03879）**26%–53%** —— 任何逐行插桩都贵。
