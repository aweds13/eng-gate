## 要解决的问题

pool 的 `gates/diag/wb-usage.jsonl` 是**按轮**记账，而且**没有任何地方回答「这个请求最后到底成没成、试了几次」**：

- `tools/wb_dispatch.py:1623 usage_summary` 把 `len(mine)` 当「本卡 N 轮」—— 它说的是**轮**，是对的。
- `tools/pool/ledger_spend.py:151-184 sums` 把**每一行**都 `calls += 1`（`:182`）⇒ `calls` 是**轮数**不是**请求数**，一个重试 3 轮的请求被算成 3 次。
- `tools/pool/usage_ingest.py:83-100 FIELDS` 二十个字段里**没有** `tries` / `handed_on` / `stop` / `tier_*`。

「第 2 行的失败是否被第 3 行接住了」今天**读不出来**。`轮次` 只给序号。`判决` 是自由文本（`"空转"` / `"被中断"` …），拿它猜 `handed_on` 就是「拿字符串猜结构」。

## 判据（9 条，逐条可执行）

**本卡的判据就是设计原件 §F40「判据逐条」那 9 条**，逐字照做：

1. `is_failed(code, reason)`：**用 `code` 判**（`code >= 400`），`reason` 只在 `reason != "正常收工"` 时才算 —— 这写成显式判断，**不许**照抄 Go 的 `code >= 400 or reason != ""`（pool 的 `reason` 是判决文本，非空 ≠ 失败）。
2. `handed_on` **由写侧一次算好**：在 `append_usage_line` 之前就知道「这一轮之后会不会续」，所以 `handed_on` 就是**该轮的判决**，**一次写对、不做二次改写**（绝不许「先写一行再补一行 `handed_on: true`」）。
3. `is_outcome(row)`：`not row.get("handed_on")` —— 只有非 `handed_on` 的行才是「请求的结局」。
4. `count_requests(rows, card=...)` 返回 `{"requests": n, "errors": m, "retried": k, "handed_on": h}`，口径**逐字照 `usage.go:777-806`**：`handed_on` 的行**不计** `requests`、**不计** `errors`；`errors` = 是结局且 `is_failed`；`retried` = 是结局、不失败、且 `tries > 1`。
5. `tries` **只写在结局行上**（`handed_on` 的行 `tries` 恒 1）。
6. `stop` 空值：上游没报就写 `""`，**不写 `"unknown"`、不写 `"none"`**。
7. 三个 `tier_*` 各自独立，`tier_served` **绝不**从 `tier_asked`/`tier_sent` 推导。
8. `count_requests` 对**老行**（没有 `tries`/`handed_on` 键）**不许崩**，且**不许当 `handed_on`**：缺键 ⇒ `tries = 1`、`handed_on = False`。
9. `usage_summary` 的「本卡 N 轮」**不改**；新加一行「请求 N / 失败 M / 重试答上 K」。

**常量逐字**：`OUTCOME_TRIES = "tries"` / `OUTCOME_HANDED_ON = "handed_on"` / `OUTCOME_STOP = "stop"` / `OUTCOME_TIERS = ("tier_asked", "tier_sent", "tier_served")`。

## 不许做

- **不许「二次改写」**：绝不可以在 `should_resume` 为真时回头去改刚写那一行。`handed_on` 必须在写之前就知道。
- **不许让 `should_resume` 被调两次**（判据只有一份）。
- **不许改 `usage_summary` 的「本卡 N 轮」文案**（它说的是轮，是对的）；只追加新行。
- **不许改 `ledger_spend.sums()` 的 `calls` 口径**（它是轮数，不是请求数；请求数归 `outcomes.count_requests`）。

## 缺口的如实交代（进 changelog 的 gaps）

1. **`tries` / `handed_on` / `stop` / `tier_*` 四样只在 pool 的**续跑循环**语义下成立，与 magpie 的**路由重试**不是同一层：magpie 的重试是「换上游再试一次」，pool 的续跑是「同一个工人带同一会话接着干」。`Tries` 在 pool 侧实为「续了几轮」。
2. **magpie 有 `RouteID` 能把同一次请求的多个 try 串起来；pool 没有这种 id**，只能按「同卡、连续轮次、前一轮 `handed_on`」串 —— **这是弱口径**。若将来出现「同卡并发两条流水」或「轮次跳号」，这个串法会错，届时要加显式 id。
3. **`tier_*` 今天没有写方**：上游（`usage_ingest.py` 的二十字段）不报任何 `tier_*`，所以三个键恒为 `""`。本卡只把容器与判据备好，**不许造假数据**。
4. **`stop` 今天没有写方**：同上，恒为 `""`（而 `""` 恰好就是「上游没报」的正确取值）。
5. **本卡不动 `wb-usage.jsonl` 的既有行**：老行读出来是 `tries=1, handed_on=False`，与「一轮一请求」同义 —— 这不是修复，是「老行就是不知道」。
