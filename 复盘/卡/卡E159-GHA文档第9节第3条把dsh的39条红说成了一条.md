## 要解决的问题

### 问题 1 · 文档说「唯一 FAIL」，实测是 39 条红里的 1 条

`docs/subsystems/ci/GitHub-Actions-云门禁.md` §9 的第 3 条现在这么写：

> **`dsh-gate` 那条红是 Windows 的 chmod 语义，不是代码坏**：唯一 FAIL 在 `tests/store.spec.ts`（「目录只有属主可进、库只有属主可读」），
> 断言原文 `AssertionError: expected [ 438, 438 ] to deeply equal [ 448, 384 ]` —— 它比的是 `statSync(...).mode & 0o777`，
> 而 NTFS 上 `0o700` 目录 / `0o600` 文件会落成 `438`（`0o666` 家族）。

「唯一 FAIL」是**错的**。`dsh-gate` 那一趟（job `137015005171`）的读数原文是
`passed: 1158 / failed: 39 / numTotalTests: 1197 / numFailedTestSuites: 16`，
`tests/store.spec.ts` 那条只是**日志尾巴里唯一打印出来的一条** —— 适配器只打 vitest 输出的末 25 行，
39 条里另外 38 条被挤出了窗口。文档把「打印出来的一条」写成了「全部」。

全量清单不在日志里，在 vitest 的 JSON 报告里。本机在同一棵源树（`dsh-superagent-prototype` HEAD `6337fc8`，
与 `dsh-gate` 快照 `1f9fde2c` 同一棵树）上跑
`corepack pnpm exec vitest run --reporter=json --outputFile=vitest-local.json`（vitest 4.1.8，72–77 s）得到 39 条红，按文件分布：

| 文件 | 红条数 |
|---|---|
| `tests/service-script.spec.ts` | 15 |
| `tests/environment.spec.ts` | 6 |
| `tests/sources.spec.ts` | 6 |
| `tests/deployment.spec.ts` | 5 |
| `tests/docs.spec.ts` | 3 |
| `tests/commands.spec.ts` | 1 |
| `tests/prompts.spec.ts` | 1 |
| `tests/runtime.spec.ts` | 1 |
| `tests/store.spec.ts` | 1 |

按**成因**分五类（同一次跑，按首条 `failureMessages` 归类）：

| 类 | 条数 | 症状 |
|---|---|---|
| A 符号链接要特权 | 7 | `EPERM: operation not permitted, symlink ...` —— Windows 上建 symlink 要开发者模式或提权 |
| B 依赖外部命令不在 PATH | 16 | `code: 9009` / `spawn gh ENOENT` / `Error: STACK_TRACE_ERROR` —— 树里假定有 `gh` / `tmux` / `sh` |
| C 源仓文档表与 `src`/`tests` 不同步 | 3 | `expected [ …(110) ] to deeply equal []` —— 文档债，不是环境 |
| D NTFS chmod 语义 | 1 | `expected [ 438, 438 ] to deeply equal [ 448, 384 ]` |
| E 其它（路径 / 格式 / 飞书消费者） | 12 | 提示词路径被拼成绝对路径、git 配置路径、纯文本 `file:` 比对、`sources.spec.ts` 的飞书消费者状态机 |

⇒ 「不是代码坏」这句话只对 A / B / D 三类成立（24 条）；C（文档债）是源仓自己的问题，
E（12 条）里有几条看着也不是环境（例如 `prompts.spec.ts` 把 `C:\\Users\\...` 当相对路径拼进去）。
一句话定性 39 条是把判据讲丢了。

### 问题 2 · 本机与 runner 的读数不是同一条，文档没说

两边**用例级数字一致**：`numTotalTests 1197` / `numPassedTests 1158` / `numFailedTests 39`。
但**套件级不一致**：runner 的 `numFailedTestSuites` 是 **16**，本机是 **15**。
本机 node 是 `v24.19.0`，runner 上是 `v22.23.5`（`steps` 里的 `node --version` 打的）。
⇒ 文档里把本机分类表当 runner 的分类表用是不成立的，必须写明「分类表来自本机同树重跑，两边用例数相同、套件数差 1」。

## 判据（逐条可执行）

### 判据 1 · §9 第 3 条不许再说「唯一 FAIL」

`docs/subsystems/ci/GitHub-Actions-云门禁.md` 里搜不到「唯一 FAIL 在」这个说法。
要改成：日志尾巴里唯一**打印出来**的是 `tests/store.spec.ts` 那条，全量 39 条要看 JSON 报告。

### 判据 2 · 39 条的红要按文件与成因两张表列出来，每个数字可复算

两张表进 §9 第 3 条（或它下面新开的小节）：

1. 按文件 9 行（上面那张表，行数与条数都要能对上 39）；
2. 按成因 5 类（A 7 / B 16 / C 3 / D 1 / E 12，加起来 39）；
3. 取法写出来：`corepack pnpm exec vitest run --reporter=json --outputFile=<文件>`，
   并说明这是**在源树上重跑**，不是从 runner 日志里抠出来的。

### 判据 3 · 本机与 runner 的差异要写明

写明三件事：用例级 `1197 / 1158 / 39` 两边相同；套件级 `numFailedTestSuites` runner 16 / 本机 15；
node 版本本机 `v24.19.0` vs runner `v22.23.5`。

### 判据 4 · 「留给源仓自己定」的结论要跟着改

现在那句「要它绿只有两条路：换 Linux runner，或让那条判据认平台」只覆盖了 D 类。
改成**分层的处置建议**：A / B 类换 Linux runner 大概率转绿（不需要 symlink 特权、有 bash），
C 类是源仓文档债（与 runner 无关），D 类只能换 runner 或改判据，E 类要逐条看。

### 判据 5 · 三道文档门不涨

`check_docs` 死指针仍是 147（基线 147，+0）、`check_layers` PASS、`check_derived_docs --check` 双 OK。
新增的分类表**不许**用反引号写仓外路径或计划建的片段文件。
