# 卡 E34 —— 门禁请求队列：多会话并发时不再抢内存、不再撞端口

> 台账号 T-AG488 ｜ 树：`.wt/E34` ｜ 分区：E（CI 子系统）
> 依据：2026-10-25 实测（门禁进行中 `available_memory_gb() = 1.61 GB`；两趟并行把 5 分钟拖到 8 分钟）

## 现在疼在哪（都是实测）

1. **多个会话同时跑门禁 = 互相拖死**：12:22 那趟 E28 门禁与 bench 矩阵并行，
   `pytest` 从常态 341 s 变成 **506 s**（+48%）；同时 `available_memory_gb()` 掉到 **1.0–1.6 GB**。
   现在没有任何机制说「现在只能再进一个」，全靠人记得错开端口段（`TF_GATE_PORT_BASE`）。
2. **端口段靠人分配**：E10=9781、E28=9741、E29=9761、bench=9811…… 谁先起谁占，撞了就
   靠门禁里的「清遗留」兜底（杀别的树的无头浏览器）。这不叫调度，这叫运气。
3. **门禁没有「请求」这个概念**：谁想验，就自己 `cd` 到树里敲 `run_gates.py`；
   `wb_land` 也只能同步等。多窗会话想「先排队、跑完通知我」做不到。
4. **零件已经有了**：`gates/diag/gate_lock.py`（门禁锁 + 租约 + `liveness_text()`）、
   E28 刚落进主树的 `tools/pool/queue.py`（合并队列：**单写者** + 投机预检，状态落
   gitignored 的 `gates/diag/merge-queue.json`）。缺的是「按内存与端口分槽 + 跑完回传」。

## 要做成什么样

1. **新增 `tools/gate_queue.py`**（形状对齐 `tools/pool/queue.py`：单写者、原子写、人可读，
   **不新造第二套语义**）：
   ```
   python -X utf8 tools/gate_queue.py submit  --tree .wt/E10 --card E10 [--profiles auto] [--port-base auto]
   python -X utf8 tools/gate_queue.py status  [--json]
   python -X utf8 tools/gate_queue.py run     --slot 1        # 前台占槽跑一条，跑完回填
   python -X utf8 tools/gate_queue.py release --slot 1
   ```
   状态落 `gates/diag/gate-queue.json`：`{"slots":[{id,state,tree,card,port_base,pid,at}],
   "waiting":[…], "done":[…]}`。
2. **槽位按内存与端口算**：槽数 = `max(1, floor((可用内存 − 预留 2 GB) / 3 GB))`，默认预留
   可配；端口段从 `TF_GATE_PORT_BASE` 起点按槽号切片（步长 ≥20，避免撞）。
   **拿不到槽就排队，不许「先跑再说」**。
3. **跑完回传**：`run` 结束时把该树的 `gates/last.json` 与 `gates/logs/` 摘要写回队列条目
   （`state:"done"`, `ok`, `rev`, `door_failures`），并追加一行到
   `gates/diag/notifications.jsonl`（**复用 `wb_watch` 的行格式**，不另造文件）。
4. **`wb_land` 认识队列**：`wb_land --from-queue --card X` 时先查队列里该卡最近一条 `done`
   的 `last.json` 是否 `ok` 且 `rev == 父提交`，满足才继续（否则报「队列里没有可用读数」）。

## 判据

1. `pytest tests/test_gate_queue.py -q -o addopts=`，至少 9 条钉子（用假 worker，不真跑门禁）：
   两个提交拿到**不同** `port_base` + 内存不足时槽数变 1 + 拿不到槽就进 `waiting` 且不启动子进程 +
   `run` 回填 `ok/rev` + 通知流一行与 `wb_watch` 键名一致 + 队列文件损坏时 fail closed +
   `release` 后槽可复用 + `--json` 键名固定 + 同一 `tree` 不许占两槽。
2. **两个并发请求的实测**（真起两条 `run --slot`，一条在 `.wt/bench` 一条在别的树）：
   各自拿回自己的 `last.json`，互不覆盖；两条的 `port_base` 不相等。原始输出进申报。
3. **反向验证**：把「内存不足降槽」删掉 ⇒ 对应钉子红；把 `port_base` 改成固定值 ⇒
   「不同段」那条钉子红。红色输出进申报。
4. 全量门禁 `exit 0`；`gates/diag/gate-queue.json` 在 `.gitignore` 里（运行态，不入库）。

## 不许做

- 不许新造第二套「队列」语义：形状、原子写、单写者约定必须与 `tools/pool/queue.py` 对齐；
  能复用就复用（优先抽公共函数，而不是复制粘贴）。
- 不许把 `gate-queue.json` 提交进库（运行态；`gates/diag/*` 本来就是 gitignored）。
- 不许在拿不到槽时「先跑一下看看」——那正是现在的问题。
- 不许把门禁结果写进 `gates/last.json` 之外的第二个「权威文件」；队列只存指针与摘要。

- 两条反向验证的红色原始输出。
- 一趟全量门禁的 `gates/last.json`。
