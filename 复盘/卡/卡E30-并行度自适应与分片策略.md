# 卡 E30 —— 并行度自适应与分片策略：把 4 个 worker 的硬顶拆成按内存分档

> 台账号 T-AG484 ｜ 树：`.wt/E30` ｜ 分区：E（CI 子系统）
> 依据：2026-10-25 实测（同树 `.wt/bench` @ `d37cb06`，4 worker 403 s / 8 worker 288 s）

## 现在疼在哪（都是实测）

1. **并行度的天花板被写死在 4**：`scripts/run_gates.py:344` 是 `DEFAULT_PYTEST_WORKERS = 4`，
   `pytest_workers()`（:348-378）最高只到 `min(4, cpu_count)`。这台机器 **32 逻辑核**，
   也就是说 28 个核从没被用过。
2. **4 → 8 是免费的一半**：同一棵树、同一个 commit、依赖不变，只把 worker 数从 4 调到 8，
   `pytest` 从 **403.46 s → 287.56 s（−28%）**，用例数一模一样（3079）。这个档位现在只能
   靠人事先敲 `TF_PYTEST_WORKERS=8`，而 A266 的注释明确写着「**不再靠人**在命令行写变量」。
3. **定档依据是「开工前那一瞬」的可用内存**，不看**已经在跑的别的门禁**：12:56 实测
   `available_memory_gb() = 1.61 GB`、总 15.2 GB，那时 E10 的门禁正在跑 4 个 worker。
   于是第二个门禁会按「1.61 GB」把档位压到 1 —— 它看的是别人的占用，却不知道那是自己人。
4. **分片策略从没测过**：现在用 xdist 默认 `--dist load`（逐用例派发）。业界常用
   `loadfile`（同文件归一个 worker，fixture 复用）与 `worksteal`（把活从忙 worker 挪走）。
   本仓一条读数都没有，而 `tests/test_wb_land.py` 这种「7 条 e2e 各 15–31 s」的文件正是
   `loadfile` 的典型受益者。

## 要做成什么样

1. **把硬顶拆成分档**：`DEFAULT_PYTEST_WORKERS` 保留为「没有内存读数时的兜底」，真实档位由一个
   纯函数给（名字建议 `workers_for(avail_gb, cpu, inflight)`），档口至少四段：
   `≥10 GB ⇒ 8`、`≥6 GB ⇒ 6`、`≥4 GB ⇒ 4`、`≥2.5 GB ⇒ 2`、否则 `1`；**上限仍是 `min(cap, cpu)`**。
2. **把「别人在跑」算进去**：开工前读一次当前在飞的门禁（`gates/diag/*.lock` 与
   `gates/diag/gate-queue.json` 里登记的在跑数，E34 会落这个文件；E34 未落地时只看 lock），
   从可用内存里按「每个 worker 约 0.5 GB」扣掉，再定档。**读不到就不扣**（宁快不宁慢，
   但要把「没扣」打出来）。
3. **分片策略用数选**：同一棵树、同一 worker 数，测 `--dist load` / `loadfile` / `worksteal`
   三档，把三份 `pytest` 墙钟与 `--durations=5` 写进申报，按键值选一个当默认；
   保留 `TF_PYTEST_DIST` 环境变量覆盖。
4. **把「这一趟用了几个 worker、依据是什么」打进日志**：门禁日志第一段加一行
   `[并行] workers=8（可用 10.4 GB / cpu 32 / 在跑 0）dist=loadfile`。

## 判据

1. `pytest tests/test_run_gates_workers.py -q -o addopts=` 全绿，至少 8 条钉子：
   五个档口各一条 + `TF_PYTEST_WORKERS` 显式优先（给 2 就 2，不许被自适应覆盖）+
   `cpu_count=4` 时不许超过 4 + 读不到内存时退回兜底 + 「在跑多少就扣多少」。
2. **实测对照表**（写进申报，不是口号）：`-n 4` / `-n 8` / 三档 `--dist` 的 `pytest` 墙钟，
   同树同 commit。
3. **反向验证**：把 `workers_for()` 改回恒 `min(4, cpu)` ⇒ 档位相关钉子必须红；把
   「扣在跑」那步删掉 ⇒ 对应钉子必须红。两条红色原始输出进申报。
4. 全量门禁 `exit 0`、`pytest` 用例数与改动前一致（不许靠少跑用例变快）。

## 不许做

- 不许把 `TF_PYTEST_WORKERS` 的显式优先拆掉（A266 的约定）。
- 不许取消低内存保护（可用 < 2.5 GB ⇒ 串行）；这条是「不许换页」的安全网。
- 不许 `-n auto`（32 核会拉 32 个 worker，15.2 GB 内存必换页，卡 A266 已裁定）。
- 不许为了变快改 `-p no:cacheprovider`、`--tb=no`、`--maxfail` 之类「少跑 / 少说」的开关。

## 证据

- `pytest tests/test_run_gates_workers.py -q -o addopts=` 原始输出。
- 三档 `--dist` × 两档 worker 的实测表与对应 `gates/diag/bench-*.log`。
- 两条反向验证的红色原始输出。
- 一趟全量门禁的 `gates/last.json` 与日志首段那行 `[并行] …`。

## 检索证据（2026-10-25 回灌）

- **worker 数是亚线性的，有饱和点**：大规模 CI 并行批测研究发现「机器数与反馈时间是非线性关系，
  存在阈值，过了阈值再加机器几乎不改善」（arXiv:2308.13129，BatchAll / TestCaseBatching 在同等
  反馈时间下少用 91% / 81% 的机器）。我们的 4→8 实测 −28%（403→288 s）符合亚线性预期，
  ⇒ 卡里的四段档不要指望线性外推，**8 个以上基本无收益**。
- **真正压住时长的是长尾**：xdist 默认 `LoadScheduling` 把慢用例随机撒到各 worker，收尾阶段会出现
  「一个 worker 还在跑最慢那条、其余全闲」。coverage.py 作者为此写了按历史耗时均分的插件
  （nedbatchelder《Load-balanced xdist》，起因就是「跑完了却卡在最后」）。
  ⇒ 本卡加一条判据：记录 `--durations=0` 下**首个 worker 结束到最后一个 worker 结束的时间差
  （tail）**，要求 tail ≤ 总时长 15%；达不到就说明该换 `--dist worksteal` 或按历史耗时排序。
- **佐证**：curl 的 CI 里实测用 `COVERAGE_CORE=sysmon`（见 E31），Trail of Bits 的 PyPI 案例
  单行 `-n auto` 把 191 s 压到 63 s（−67%），但那是 32 核低负载 CI 机，不是我们的 15 GB 桌面机。

## 合并自 E31（覆盖率开销）——同改 `scripts/run_gates.py`，串行不如一张卡

`pyproject.toml` 的 `addopts = "-q -m \"not acceptance\" --cov=timeflow --cov-fail-under=70"`
让**每次** pytest 都付覆盖率税。文献给的量级很硬：传统 trace 式覆盖率让 Python 慢
**180%–1300%**，SlipCover 类方案能压到 **5% 中位开销**（ISSTA 2023, arXiv:2305.02886）。
本仓开销**至今未测**（我上一组读数被 shell 引号搞坏，作废）。

判据增补：

1. 同树三档先量后改：默认 / `COVERAGE_CORE=sysmon` / `--no-cov`，各跑一次 `pytest -q`，
   取三次墙钟与覆盖率数字，写进申报。
2. `--no-cov` 相对默认 **<5%** ⇒ 收口不改（不值当）；**>15%** ⇒ 必须落地优化；
   5–15% ⇒ 由申报人给结论并写理由。
3. 若落 `COVERAGE_CORE=sysmon`：需 `scripts/sitecustomize.py` 里 `coverage.process_startup()`，
   且 **xdist 每个 worker 都要走到**（`scope="session"` 的 fixture 是每 worker 各执行一次，
   这是 xdist 的既有语义，见 cnblogs/yorgoskatsaros 两篇实测文）；
   `PYTHONPATH` **必须**复用 `scripts/run_gates.py:293 tree_pythonpath()`（卡 063 / T-G157
   「门禁假绿」前科）。
4. 覆盖率数字必须**一致**（±0.1%），`--cov-fail-under=70` 不许放松。

**今天新得的代价数据（写进门禁文档的口径）**：全量门禁一趟 ~7 分钟，而**主树每前进一笔提交**，
未落地的卡树就要 realign 并重跑一趟（今天就因为主树连推 4 笔，同一张卡跑了 4 趟门禁）。
所以并行度与覆盖率两条省下来的时间，会**直接**转化成「能同时推几张卡」——这是本卡的真实收益口径。
