# 卡 E7：工人完工事件接进派活链（派活即看守）

> 分区 E（CI 子系统）。目标：解放「派活之后主控只能轮询」这件事，
> 并把新窗口最容易忘的四条口径写进 `skills/`（删掉 skills 目录框架仍可用，所以口径写两处：工具里 + 技能里）。

## 现在疼在哪（实测）

1. `tools/wb_dispatch.py --detach` 派完工**没有回推通道**，工具自己打印
   「完工不会自动通知主控 —— 请轮询」。今天第一批 5 张卡做完，我是靠每 2 分钟敲
   `wb_dispatch --card X --status` 才发现的。
2. 仓里其实有 `tools/wb_watch.py`（「一次盯多张卡，收工就出结论」），但**要我手动起**。
   忘了起 → 就把「等通知」退化成「轮询」。
3. 派活的看门狗（dispatch 自带）只管「挂死」（日志静默 / 同动作 5 次），成功后不报。

## 判据（五条）

1. **派活即看守**：`wb_dispatch.py --execute` 成功起工人后，自动起一份看守
   （后台进程），盯这张卡直到出判决；不再需要人记着起 `wb_watch`。
2. **完工事件落盘**：判决出现时写 `gates/diag/wb-<卡>.done`（一行 JSON：
   `{"card","task","exit_code","at","log","report"}`），并往
   `gates/diag/notifications.jsonl` 追加一行（复用 `tools/wb_notify.py` 已有机制）。
3. **`--no-watch` 能关**：不想起看守时显式关；关的时候必须打印
   「已关看守：完工后请自己轮询」——**明说，不静默**。
4. **看守不许骗人**：看守进程自己不判断成功与否，只读磁盘上的 verdict；
   超时没判决就写 `state:"timeout"`，不许把「没判决」当成功。
5. **技能口径同步**：`skills/README.md`（顶部四条新窗口常忘）、
   `skills/pipe-card/references/dispatch.md`（派活必带看守）、
   `skills/pipe-workbench/SKILL.md`（`wb_watch` 用法与读法）、
   `skills/pipe-land/SKILL.md`（落地串行于门禁锁；文书 gaps 指针只认主树现有文件；
   `--evidence` 是文件路径不是散文）四处都要能被新窗口直接照做。


## 看守的两种形态（用户 m02402 定的口径，本卡必须两种都实现）

派活器不再"只管派、不管收"：`--execute` 成功起工人后，**自动**起看守。两种形态由
`--watch one|shared` 选（**默认 `one`**，理由见下节「为什么默认专属」）：

- **`one`（专属看守）**：这张卡一个看守，只盯它；出判决就写事件并退出。
  好处是逐张推送最快；坏处是 N 张卡就有 N 个进程。
- **`shared`（合用一个，引用计数）**：全局一份看守。**每派一张卡，引用计数 +1；每出一张卡的判决，
  引用计数 -1；计数归 0 时看守退出，并写一条"这一批做完了"的通知。**
  好处是只有一个进程、天然攒批；坏处是最后一张没完成前不通知（所以每次判决都要落盘，
  主控随时能查中间态）。

计数必须**抗崩溃**：状态落 `gates/diag/watch-registry.json`（内容 = 看守 pid、心跳时间、
`cards: {卡: 状态}`、`refcount`）；看守重启时**从磁盘重建**计数（已出判决的卡不算未完成），
不许靠内存变量。

## 为什么默认专属（m02402 / m02432 的裁定 + 外部证据）

- 我们的痛点是**推送粒度**：作业/进程退出才算一次通知。专属看守 = 一张卡一次通知；
  合用看守 = 整批一次通知。默认选能最早给我信号的形态。
- 合用看守（一个 informer 盯全部对象）在**对象多、单 watch 贵**时才划算 ——
  Kubernetes 的 `SharedIndexInformer` 是「一个 GVK 一个 informer，进程内所有控制器共享」，
  因为每个 watch 都常驻一整份对象快照（[controller-runtime watch 的实际内存成本](https://bex.co/zh/blog/2026/08/24/controller-runtime-cache-hetzner-control-plane)）。
  我们这批最多 10 张卡、每 30 秒轮询一次文件，单看守成本可以忽略 ⇒ 不套那个优化。
- 但**大批判跑**时逐张推送会刷屏，所以 `shared` 保留：引用计数 +1 / -1 / 归 0 一次通知
  （Java 线程池的经典计数写法、以及批处理 watcher 容器的做法都是这个形状：
  [线程池任务完成计数](https://www.jiangmingtao.com/what-are-the-use-cases-of-java-notify)、
  [ECS 并行批处理里的 watcher 容器](https://aws.amazon.com/cn/blogs/china/amazon-ecs-parallel-solution/)）。
- 两条都要**事件驱动优先、日志轮询兜底**：能拿真实完成信号时用信号，
  拿不到才退回"日志静默 + 去抖"推断（[ai-cli-complete-notify 的经验](https://github.com/ZekerTop/ai-cli-complete-notify/blob/main/README_zh.md)）。

## 判据（在原有五条上补三条）

6. **两种形态都要有，默认 `one`**；`shared` 下引用计数语义与上段逐字一致（`+1 / -1 / 归 0 通知`）。
   两种形态都往 `gates/diag/notifications.jsonl` 逐张追加判决事件（`shared` 也留中间态，只是不退出）。
7. **计数错误要被测出来**：派 3 张卡、2 张先出判决时，`refcount == 1`；最后一张出判决时
   `refcount == 0` 且写了 `batch-done` 事件（钉子 `tests/test_wb_dispatch_watch.py`）。
8. **看守自己死了不算完**：心跳超过 `--timeout` 且没有全部判决 ⇒ 写 `state:"watcher-stale"` 事件并退非零，
   **不许**留下一个"看起来还在盯"的假象。
