# 卡 E22 · 看守判「这一轮产物」要给文件时间戳留粒度容差

## 为什么开这张卡

2026-10-25 01:16–01:23 的 F1 落地门禁在本机（`TF_PYTEST_WORKERS=4`）**偶发红一条**：

```
FAILED tests/test_wb_dispatch_watch.py::test_shared_registry_rebuilds_from_disk_after_restart
AssertionError: 已出判决的卡（402）不许再算进未完成
assert 3 == 2
```

同族 `test_shared_refcount_three_cards_two_finish_then_one` 在主树也会红。实测根因**不是**逻辑错：

```
since(登记时刻)      = 1792862663.2439      ← time.time()
verdict 文件 mtime   = 1792862663.2402365   ← 比 since 早 3.7 ms
```

Windows 上**文件时间戳比墙钟粗**（实测 mtime 可落后 `time.time()` 1.4 ms；NTFS 更新周期约 15.6 ms），
于是 `tools/wb_watch.py:188` 的 `mtime >= since` 把**刚写的判决**判成「上一轮」，
`rebuild_registry` 就把已收工的卡算进未完成（`refcount` 多 1）。

这条判据不只影响测试：派活器 `--since` 也是这么切的（`wb_dispatch` 派活后立刻起看守），
真现场同样会偶发「刚出判决却仍算在飞」。

## 判据

1. `_fresh()` 用**粒度容差**比较：`mtime >= since - _MTIME_GRANULARITY_SLACK`，`_MTIME_GRANULARITY_SLACK = 1.0` 秒，
   常量旁写明实测依据（1.4 ms / 15.6 ms）与「1 秒不会把真·上一轮判决混进来」的理由。
2. 新增钉子 `tests/test_wb_dispatch_watch.py::test_fresh_tolerates_a_file_timestamp_behind_the_wall_clock`：
   文件写完后用 `since = mtime + 0.0014` 探，必须判 `STATE_DONE`（复现真现场）。
3. `test_old_verdict_is_not_this_rounds_completion` 改口径：旧件用**5 秒前**造，不再用「刚写完就拿 `time.time()` 当 since」——
   那写法考的是时钟精度，不是「旧件不算数」，本身就是会闪的钉子。
4. 全量门禁绿、审计通过。

## 不做什么

- 不改 `--since` 的语义范围（只加时间容差，不加别的窗口）。
- 不在测试里 `sleep` 等时钟推进。
