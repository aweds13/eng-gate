# 卡 E42 —— 门禁默认上云：本机只编排，云机当门禁池（T-AG494）

- 层：工具层
- 树：`.wt/E42`
- 分区：E
- 风险：high（改的是「落地链跑哪跑」这条主干口径）

## 1. 疼在哪（都是实测，不是推测）

1. **本机跑全量门禁时，工人就没内存了。** 本机 15.2 GB / 32 逻辑核，跑 19 门
   门禁时 `available_memory_gb()` 实测掉到 **0.6–1.0 GB**；今天 E30 的工人
   直接写着「机器内存已经耗尽（可用 1.58 GB，已提交 27 GB），我先写基准测试
   脚本」然后放弃。工人是拿 token 换时间的，卡在内存上等于白烧钱。
2. **两趟门禁并行互相拖。** 实测：E28 门禁与 bench 并行时 `pytest` 从
   `341 s` 涨到 `506 s`；E39 门禁与云机同步并行时 `pytest 449 s`、`acceptance 88 s`
   （常态 8–50 s）。本机实际上只能跑一趟门禁，等于把派活并行度锁死在 1。
3. **云机已经证明能跑。** `scripts/cloud/bootstrap.ps1`（E35 入库）钉死
   `pytest 9.1.1 / ruff 0.16.6 / mypy / httpx / fsrs / psutil`，实测
   `deps-ok 0.28.1 7.2.2 9.1.1`；`gates/diag/cloud-verify-E35.sh` 能把
   主树任一提交同步到云机 `C:/eng` 并整趟跑完。
4. **云机慢 1.7×，但这不影响工人。** 同 commit 受控 A/B：本机 `pytest 403.46 s`、
   云机 `684.27 s`。门禁是**批处理**，晚 5 分钟不花钱；本机被占住 7 分钟则直接
   挡住一张卡的自测与一趟落地。

## 2. 要做成什么样

### 2.1 一条开关：`--gate-on`

`tools/pool/landing.py` 与 `tools/wb_land.py` 新增 `--gate-on local|cloud`
（默认读 `TF_GATE_ON`，再默认 `cloud`）：

- `cloud`：② 按域门禁这一步**不在本机跑**，改成「提交给云机门禁池 → 等回传 →
  校验 → 继续 ③ 之后的步骤」。
- `local`：今天的行为，一行不改（离线、云机停机、排障时用）。
- 落地笔的 trailer 必须记实际位置：`Gates-on: cloud@<hostname>` 或
  `Gates-on: local`（审计 ⑫ 之外新增一条判据：`Gates:` 里的数字必须能在
  `gates/last.json` 里对上，且 `Gates-on: cloud` 时 `last.json` 必须有
  `host` 字段）。

### 2.2 云侧门禁池：`tools/gate_pool.py`

不是「一台机器跑一趟」，而是**槽位**：

- 云机上 N 个独立 checkout：`C:/eng-pool/slot0 … slotN-1`（`git worktree` 在
  云机侧对同一个裸库做，避免 N 份 `10 MB` bundle 全量搬运）。
- 槽位数按云机规格算：4 vCPU / 15.5 GB ⇒ **1 槽**；8 vCPU ⇒ 2 槽；
  判据 `min(cpu // 4, floor((avail_gb - 3) / 4))`，下限 1。
- 每槽一个端口段（`9200 + slot*40`，步长 40 ≥ 一次全量用掉的 20 个端口）与一把
  锁（`gates/diag/gate-pool-slot<n>.lock`，复用 `gates/diag/gate_lock.py` 的
  `acquire/release` 语义）。
- 提交一次门禁请求 = 写一条 json 到 `gates/diag/gate-pool-queue.json`
  （**单写者 + 原子替换**，形状对齐 `tools/pool/queue.py`：
  `{"head": {task, card, commit, port_base, at}, "waiting": [...]}`），
  然后 `--detach` 起一个 `wbg` 进程去云机跑；跑完把 `last.json` + `logs/`
  回传到 `gates/diag/pool/<卡>/`，并把队列行改成 `done` 带读数。
- **断连可续**：远端跑在 `schtasks`/`nohup` 等价物下（Windows 用
  `Start-Process -WindowStyle Hidden` + 把 PID/日志落 `C:/pool/logs/`），
  本机 ssh 断了不影响远端继续；本机重连后按 `commit + port_base` 找回结果。
  这条是今天踩过的坑：`Start-Process` 直接起会随 ssh 会话结束被掐（`C:\bench-cloud.log` 只有 1 行）。

### 2.3 回传校验（fail closed，一条都不能松）

`wb_land` 拿到云机 `last.json` 后必须逐条核，任一条不过就**拒绝继续落地**：

1. `rev == <卡树基点提交>`（云机跑的是不是这一笔的父提交）。
2. `ok is True`，且 `gates` 条数等于该档要求的门数（A327 `required_profiles()`）。
3. `host` 字段存在且非空（证明真的是云机跑的，不是本地冒名）。
4. 回传的 `gates/logs/*.log` 至少含 `pytest.log` 与红门日志；`pytest.log`
   末行必须是 `N passed` 且 N ≥ 该树用例数的 95%（防「跑了个子集当全量」）。
5. 云机侧 `git status --porcelain` 必须为空（`run_gate.sh` 的
   `require_no_residue()` 已经实现，直接复用）。

判据 1/2 今天的 `wb_verify` 已有，3/4/5 是这张卡新增的。

### 2.4 云机不可用时的行为

- `--gate-on cloud` 且云机不可达 ⇒ **退 2 并明说「云机不可达，未跑门禁」**，
  绝不回落到本机静默跑（否则「门禁到底在哪跑」就没法审计了）。
- 想回落必须人来显式 `--gate-on local`。
- 云机停机时段（03:00–08:00 省 V 模式）里落地 ⇒ 同上，退 2 并给出提示。

## 3. 判据

1. `tests/test_gate_pool.py` 至少 10 条钉子：槽位计算（4 vCPU⇒1、8 vCPU⇒2、
   内存不足⇒1）、端口段不重叠、同一槽并发提交被排队（不是并行）、队列文件
   原子替换（并发写不丢行）、`done` 行必须带 `ok/rev/port_base`、
   断连后能按 `commit` 找回结果。
2. `tests/test_wb_land_gate_on.py` 至少 6 条钉子：`--gate-on cloud` 但云机不可达
   ⇒ 退 2 且**没有**继续落地；`last.json` 缺 `host` ⇒ 拒；`rev` 不匹配 ⇒ 拒；
   `pytest.log` 说 `N passed` 但 N < 95% ⇒ 拒；`Gates-on:` trailer 与实际一致。
3. 端到端一次：拿一张真卡在 `--gate-on cloud` 下落成主树一笔提交，
   `wb_verify` `FAIL=0`，且 `gates/last.json` 里 `host` 是云机名。
4. 反向验证三条（每条都要贴红原文）：把 `host` 检查去掉 ⇒ 钉子红；
   把槽位数写死 1 ⇒ 8 vCPU 那条钉子红；把退 2 改成回落本机 ⇒ 第一条钉子红。
5. 本机侧证据：`--gate-on cloud` 全程本机 `pytest` 进程数为 0
   （用 `scripts/run_gates.py` 的进程计数或 `psutil` 断言），且本机
   `available_memory_gb()` 全程 ≥ 3 GB。

## 4. 不许做

- 不许把「云机慢 1.7×」当理由把默认留在本机——慢的是**墙钟**，省的是**工人的机器**。
- 不许在云机上跑工人（工人要读本仓工作树、要落盘到 `.wt/`；云机没有那些树）。
- 不许跳过封存指纹核验（云机算的 `tree` 必须与本地复算一致；
  E35 那次就踩过「主树有别的窗口的未跟踪文件 ⇒ 指纹对不上」，本卡要把
  「用干净 worktree 复算」写成默认路径）。
- 不许让云机与本地各跑一半门（档位必须整体在一边）。
