# 卡 A318 —— 单账本：状态从 git 派生，账本只存计划（T-AG432）

**树**：`.wt/A318` ｜ **base**：A317 落地后的 HEAD ｜ **风险**：high（动台账格式与判据）

## 来路

线上事故形状：A315 / A316 两张卡已经落地（`dfef650` / `94d343c`），但 `docs/workbacklog.toml` 的 HEAD 版本里**根本没有这两条**——`wb_land` 在卡树里找不到卡就跳过翻状态，条目只活在我的工作区。下一轮全量门禁会因为「提交挂了 `Task: T-AG429/430`、台账里却没有」而转红。

根因不是谁手滑，是**同一件事存了三份事实**：

| 事实源 | 谁写 | 什么时候写 |
|---|---|---|
| `workbacklog.toml` 的 `status` | 人 / `wb_land` / `wb_task` | 登记时、落地时、收批时 |
| git 提交（`Task:` trailer） | `wb_land` | 落地时 |
| 批次围栏（`B-2026xxxx`） | `wb_task` | 收批时 |

三份里有两份是副本，副本必然漂移。

历史成因（有据可查，不是设计失误）：

- `6268ce9` / `5f99780`（09-26）台账从清单扩成队列时加 `status` —— 那时**没有门禁**，git 看不出做完没。
- `ac5968d` / `30a6503`（10-02）引入批次与 `awaiting-commit` —— 多卡攒批省门禁，需要第二个状态。
- 更晚引入封存 `rev == HEAD^` —— 防假绿，但把「改一行账」的成本抬到一次全量门禁，于是大家倾向攒着改、一起落，积账就此产生。

## 目标

**账本只存计划，状态由工具算。** 单一写者、单一事实。

## 交付

1. `docs/workbacklog.toml`：删 `status` 字段（保留 `id / task / title / tree / spec / files / depends / risk`）。
2. 新增 `tools/wb_status.py`：派生状态并输出 JSON。
   - 有 `Task: <task>` 的提交（且该 task 在本卡条目里）⇒ `done`
   - 被某批围栏收（`landed`）⇒ `done`；`awaiting-commit` ⇒ `awaiting-commit`
   - 其余 ⇒ `pending`
3. `tools/wb_land.py`：卡在台账里**找不到条目 ⇒ 拒绝落地并退非零**（不再「跳过翻 status」）。这条是本次事故的直接钉子。
4. `tools/wb_reconcile.py`：改成纯派生视图，去掉「认账 / 黄灯」判词；保留「提交挂了 Task 但台账没有该任务」的检查并升级为**红**。
5. 面板「看板 / 号池」两页改读 `wb_status.py`（派生视图），不再读 `status` 字段。
6. 迁移：一次性把现有 187 条卡的 `status` 与派生结果比对，输出差异表；差异逐条定性后落 `docs/status-migration.md`（只读记录，不进判据）。

## 判据

- `python -X utf8 tools/wb_status.py --json` 对当前仓：`done` 数 == 提交里出现过的 task 数（允许显式白名单，白名单要写理由）。
- `pytest tests/test_wb_status.py tests/test_wb_land.py tests/test_wb_reconcile.py -q --no-cov` 全过。
- 反例钉子：造一份台账缺 A999 条目、提交却挂 `Task: T-A999` ⇒ `wb_land` 退非零、`wb_reconcile` 红。
- `scripts/audit_progress.py` 不变红（台账格式改了，审计要跟着改）。

## 验收

1. 在迁移后的仓里跑 `wb_daily`、面板看板、`wb_plan check`，三处状态一致。
2. 走一遍完整流程：开卡 → 派活 → 落地，中间**不需要手工改 `status`**。
3. 故意从台账删掉一张已落地卡 ⇒ `wb_land` 拒落、`reconcile` 红。
