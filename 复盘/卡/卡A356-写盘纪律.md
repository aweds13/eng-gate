## 要解决的问题

`tools/pool/lastgood.py` 已有原子写（`write_atomic`），但它在**四个方向上会毁掉现场**（设计原件 §F76 的实测场景 A–E）：

- **A**：旧文件**坏**时，`write_atomic` 直接跳过备份（只备份「好的」）⇒ 那份坏文件被新内容覆盖，**现场永久丢失**，事后没人知道它当时坏成什么样。
- **B**（`rpm._write_stamps` 那一族）：整个目录被重生成 —— 本卡不管（见禁令 5）。
- **C**：换行跟着 `newline="\n"` 写死，而本仓文本**一律纯 CRLF** ⇒ 写一次就把 CRLF 抹成 LF。
- **D**：权限位不保留（`0o600` 的账本写一次变成 `0o666`）。
- **E**：BOM 不保留（原来带 `\ufeff` 的，写一次就没了）。

另有一个**更贵的**洞：`tools/pool_accounts.py:266-269 save_ledger` 用 `_dump_toml(data)` **整份重生成**再写 —— 如果账本里有人手写注释（行首 `#`），它会被无声抹掉。

## 判据（11 条，逐条可执行）

**本卡的判据就是设计原件 §F76「判据逐条」那 11 条**，逐字照做：

1. `describe_bad(None)` ⇒ `"it doesn't parse"`；全零字节 ⇒ `f"{len(raw)} bytes, every one zero"`；只有空白 ⇒ `"it is empty"`；其余 ⇒ `"it doesn't parse"`（**逐字**照 `lastgood.go:93-103`）。
2. `keep_bad` 在 `write_atomic` 发现旧文件**坏**（`_is_good` 为 `False` 且文件存在）时**先**调，落成 `<名>.bad-<stamp>`，权限 `0o600`，`O_EXCL` 语义（`open(..., "xb")`）。
3. `keep_bad` 遇同名（同秒）往后加 `-2`、`-3`…，最多 `MAX_BAD_NAMES` 次；用尽返回 `None` 并**不抛**（magpie 是抛的，本仓选不抛 —— 写盘不许因为「旁存不了」就停）。
4. **同样的坏字节已经旁存过**（按长度 + 字节比）⇒ 返回已有的那个路径，**不再存第二份**（照 `keptAlready`，`lastgood.go:207-218`）。
5. `write_atomic` 写完的字节**必须**与原文件的 BOM 状态一致（原 BOM ⇒ 新也 BOM；原无 ⇒ 新也无）。
6. `write_atomic` 保留原文件的权限位（`keep_mode=True`）；原文件不存在 ⇒ `DEFAULT_PERM`。★ 这一条**修的是场景 D 的实测缺陷**（`0o600` → `0o666`）。
7. `follow_ending=True` 且原文件是**纯 CRLF**（`b.count(b"\r\n") == b.count(b"\n")` 且 `> 0`）⇒ 落盘用 `"\r\n"`；否则用调用方给的 `newline`（照 `joinLinesLike`，`text.go:111`）。
8. `save_ledger` 在写之前调 `ledger_would_lose_comments(path)`：返回**非空行号列表** ⇒ 抛 `LedgerError`，消息含「账本里有注释，`_dump_toml` 会整份重生成把它抹掉」+ 前 3 个行号；**一个字节都不写**。
9. `ledger_would_lose_comments` 只看**行首（允许前置空白）是 `#`** 的行 —— 行尾注释**不算**（`_dump_toml` 已经会丢行尾注释，但那不是「整份重生成」能避免的，管不了就**明说管不了**）。
10. `save_ledger` 的 payload 必须仍能过 `_validate_ledger_toml`（既有行为，不许放宽）。
11. 老调用点（不传新参数）的输出**除换行/BOM/权限位外**逐字节不变 —— 三个新参数默认值 `keep_bom=True, keep_mode=True, follow_ending=False` 都不改字节内容。

**常量逐字**：`BAD_SUFFIX = ".bad-"` / `BAD_STAMP = "%Y%m%d-%H%M%S"` / `BAD_PERM = 0o600` / `DEFAULT_PERM = 0o644` / `MAX_BAD_NAMES = 1000` / `BOM = b"\xef\xbb\xbf"`。

## 缺口的如实交代（进 changelog 的 gaps）

1. **行尾注释仍然会被丢**：`_dump_toml` 整份重生成时行尾注释没了，而 `ledger_would_lose_comments` 只管**行首** `#` ⇒ 今天的真账本没有行尾注释所以不流血；一旦有人加了，钉子 14 会保持绿（它只管行首），**这是个已知的洞**。
2. **`follow_ending` 默认 `False`，而本仓文本「一律纯 CRLF」**（`tools/pool/rpm.py:237` 的 docstring 原话）⇒ 真正的修法是**先定一条仓级换行策略**（像 `.gitattributes` 对 `gates/render/*.txt` 那样），再让所有写盘点跟随。那是另一张卡，本条只提供**能力**（`follow_ending`），不替它做决定。
3. **`.bad-*` 旁存会不会被 git 看见判不出**：仓外账本的宿主机目录不在本仓里、`gitignore` 管不到；`gates/diag/` 是 gitignored；若落在被追踪的目录（如 `tools/pool/*.toml`）会脏树。没找到「哪些目录被追踪」的单一真源，**不下结论**。
4. **没加 fsync**：magpie 的 `KeepBad` 用 `steady.Sync(f)` 前后各一次 fsync，pool 的 `write_atomic` 一次都没有 ⇒ 「断电留全零文件」这个 magpie 的**原始动机**（#1505）在 pool 侧**没有被防住**。
5. **只在合成夹具上验过**：`describe_bad` 的三支、`keep_bad` 的碰撞编号、混合换行，全部用 `tmp_path` 造的数据；**没有**拿一次真实的「账本被写坏」事故复核过。
6. **`target.is_symlink()` 未处理**：magpie 有 `Target()`（`file.go:295`）把符号链接指向真身再写；pool 的 `write_atomic` 会**把链接替换成普通文件**。没在仓里找到用符号链接管账本的实践，也没验过 Windows 上的行为。
