## ★★ 本卡最要紧的一条：**先立「该不该写成 skill」的判据**

用户要「泛用性」和「别人也能用」。★ 而 **skill 是绑 agent 生态的**（换一个 harness，skill 就要重写）—— 这是**泛用性最差的一层**。
⇒ 所以本卡的第一件产物是**判据**，不是 skill 本身：

**分工判据（必须写成表，并给出反例）**
| 这东西该放哪 | 判据 |
|---|---|
| **核心库** | 逻辑与判据；不 print、不 `sys.exit`；换个前端照样成立 |
| **CLI 子命令** | 人/机器都能用的**稳定契约**（参数 / 输出 / 退出码 / `--json`） |
| **skill** | ★ **只有**「怎么用 CLI 才不出错」这层**操作知识**：顺序、前置检查、常见错、该看哪个产物 |
| **不许进 skill** | 任何**判据本身**、任何**业务逻辑**、任何**只能在这个 harness 里成立**的东西 |

⇒ 并写清**反例**：把一条判据塞进 skill 会怎样（换 harness 就没了）？把一条操作知识留在库里会怎样（库被迫知道交互顺序）？

## 你要产出什么

**① `skills/` 目录**（照官方 Agent Skills 规范：每个 skill 一个目录，含 `SKILL.md`，frontmatter 至少 `name` + `description`）
覆盖核心动作，至少：`pipe-init`（铺骨架）· `pipe-gate`（跑门禁并**读懂三值判决**）· `pipe-card`（写卡 / 认领 / 申报）· `pipe-land`（集成与发布）· `pipe-forensics`（出事了从证据里查）。
★ 每个 `SKILL.md` **必须**含：**什么时候用 / 什么时候别用**、**前置检查**（怎么知道现在能不能跑）、**真命令**（照 179 的实际命令面）、**怎么读结果**（尤其 `inconclusive`）、**常见错与处置**。

**② 一份契约文书**：`skills/README.md`
- ★ 写清**与 CLI 的分工判据**（上面那张表 + 反例）；
- ★ 写清**换 harness 要改什么**：哪些是通用的（`SKILL.md` 的内容）、哪些是每个 harness 的胶水（注册方式 / 目录约定）—— **清单式列出**，不许含糊；
- 写清**版本**：skills 跟框架版本怎么对齐（哪一版 skills 配哪一版 CLI）。

**③ 反例钉子**
- 至少一条钉子：**skills 里引用的每个命令名，都能在框架的 CLI 里找到**（★ 机器可判：扫 `SKILL.md` 里的命令，与 `pipe --help` 的输出对账）。引用了不存在的命令 ⇒ **红**。
- 至少一条钉子：**`SKILL.md` 缺 frontmatter / 缺「什么时候别用」那节** ⇒ **红**。

## 三条硬要求

1. ★ **不许绑一个 harness**：不许出现「只有 DSH 才有的」路径或工具名当作**前提**；harness 特有的东西一律**集中在一处**并标明是胶水。
2. ★ **不许把判据写进 skill**（判据在库里 / 门里）。
3. ★ **不许动 `skills/` 之外的文件**（不改核心库、不改 CLI、不改队列），**不许 commit**。
