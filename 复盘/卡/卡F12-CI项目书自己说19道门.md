## 要解决的问题

1. **同一份文档里自相矛盾**。`:11` 的门数已经是 **22**（2026-10-27 实测，还逐字记了 F6 把 `docs`
   接进 `audit` 档 20→21、本批把 `skills_claims` 接进来 21→22），`:21` 却仍写 **19 道**。
   同一份 README 的两个章节对同一件事给出两个数 —— 读者无法判断哪个是真的。
2. **数字全是三天前的且已经漂**。现读真值 vs `:21`–`:28` 的记载：
   - 门数：**22**（记载 19）
   - `pytest` 收集条数：`pytest --collect-only -q` ⇒ **4031**（记载 2955）
   - `pytest` 耗时：2026-10-30 全量门禁 `968.09 s`／`4016 passed, 1 skipped`；同日另两趟
     `414.77 s`（`rev=2fdaba1f`）与 `580 s` 级 —— 记载「350–910 s（2955 条）」区间两端都过期
   - 「其余 16 道」这个口径 = 22 − 6，本身就要跟着门数重算（现为 **16 道**，巧合相同，
     但推导来源不能靠巧合）
3. **没有任何钉子在看这份文档的计数**。`grep -rn "2955\|19 道" tests/ scripts/` 零命中 ⇒
   它必然一直过期。`docs/subsystems/ci/事后判据清单.md:41` 同样写「pytest 2955 条」。

## 判据（5 条）

1. **门数不许写死**。`docs/subsystems/ci/README.md` 的门数一律由
   `len(run_gates.build_jobs(False, False))` 现读得到 —— 本文件正文里出现「N 道门」时，
   N 必须等于现读值；不许再出现「19 道」这个具体数字（除非写在「历史沿革」句里并标明日期）。
2. **pytest 条数不许写死**。收集条数改成「`pytest --collect-only -q` 现读数」这个口径句，
   或写成带日期的快照并附一条**能重跑的探针命令**；`2955` 这个数字必须清零
   （`grep -c 2955 docs/subsystems/ci/README.md docs/subsystems/ci/事后判据清单.md` ⇒ 0）。
3. **耗时区间必须带出处**。区间两端各写明「哪一天、哪一趟、`rev` 是什么」，或者干脆改成
   引用 `gates/last.json` 的口径句；不许只写一个无出处的范围。
4. **新增 `tests/test_ci_docs_counts.py`**（≥5 条钉子）：
   - ① 现读 `build_jobs` 与 README 里出现的门数一致（正则取「全量 N 道」这类句子）；
   - ② 反向：把 README 里的门数改成 `build_jobs` 返回值 ±1 ⇒ 该钉子必须红并点名；
   - ③ `2955` 与「19 道」在 CI 两份文档里零命中（反向：塞回去必须红）；
   - ④ 事后判据清单里的条数句与 README 口径不冲突（同一数字在两处必须相同）；
   - ⑤ 反向：把两处改成不同数字 ⇒ 必须红。
   钉子必须**现读真源**（`build_jobs`），不许把 22 写死在测试里 —— 门表加一道门时
   本文件一行都不用改（体例照 `tests/test_ci_docs.py`）。
5. **行尾不变**。`docs/subsystems/ci/README.md` 现为纯 CRLF（69 行 / 4706 B / crlf 69 / bare 0），
   改完仍是纯 CRLF、仍是 69 行上下（允许 ±15 行）。
