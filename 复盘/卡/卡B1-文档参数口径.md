# 卡 B1 · 参考文档里 `parameters` 的口径写反了

**task**：T-BG001　**risk**：low　**tree**：`.wt/B1`

## 为什么

`DSH-技能与插件开发参考.md:274` 关于自定义工具的参数只有一条：

> ⚠️ `harness.defineTool` 的 `parameters` **不能写 `additionalProperties: false`**（隐式参数根是开放的）

这句话把 `parameters` 说成了 **JSON Schema 的一个位置**。照着它写，就会写出
`parameters: { type: "object", properties: {...}, required: [...] }` 这种形状。

**实测后果**（2026-10-23，OpenMAIC 能力插件）：5 个工具注册，只有零参的那个挂上，
其余 4 个被**静默丢弃**，DSH 启动只能看到一句红字
`failed to load 3 plugin(s): Cannot read properties of undefined (reading 'properties')`。
排查花了整轮会话——因为文档里没有任何一处正面写 `parameters` 的形状。

正确的形状（同一个插件修好之后，从装好的副本里读出来的原文）：

```js
parameters: {
  path:     { type: "string", required: true, description: "本机文件绝对路径（.pdf/.docx/.pptx 等）" },
  maxChars: { type: "number", description: "markdown 最多回多少字符（默认 20000）" },
  texts:    { type: "array", items: { type: "string" }, required: true, description: "要转向量的文本列表" },
},
output: { schema: { type: "json" }, render: (_args, value) => textOut(value) },
```

即：**`parameters` 是「参数名 → 参数描述」的映射**（`type` / `required` / `description` / `items`），
零参工具写 `parameters: {}`。`output` 是另一段，与 `parameters` 平级。

## 判据（怎么算做完）

1. `DSH-技能与插件开发参考.md` §4.7 那一条改写成**正面口径**：`parameters` 是参数名映射，
   不是 JSON Schema；顺手保留原来那条真结论（参数根是开放的，所以别指望 `additionalProperties` 兜底），
   但要说清「这不是可以在 `parameters` 顶层写的键」。
2. 附上**错误 → 正确**的最小对照样例（上面两段），并写明错误形状的**可观测症状**：
   工具不出现在工具表 / 启动日志里那句 `Cannot read properties of undefined (reading 'properties')`。
3. 给一条**可证伪的验收**（不需要新工具）：照文档示例写一个带参动态插件 → 重启 →
   工具表里必须出现它；不出现就是文档错。把这一步写进文档，让后来人能自己验。
4. 全文只清 `parameters`/`output` 这处口径；**不做整篇重写**，不动别的章节。
