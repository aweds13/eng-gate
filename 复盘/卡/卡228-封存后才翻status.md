# 卡 228 —— 封存之后才翻 status：封存树必然对不上提交树（T-G344）

**树**：`.wt/sealorder` ｜ **成员号**：`B-20261018` 的 `228`。★ `depends = ["225"]`（同在 `tools/pool/landing.py`，串批）。

## 为什么有这张卡
2026-10-14 收卡 218 那笔时，收口链自己的**复核**（`tools/wb_review.py`，第 ⑦/⑧ 步）报了：

```
problems = ["封存树 vs 提交树：last.json.tree=23a9cfe ≠ 本笔提交去 gates/** 的 tree=fa6dcba
            —— 提交树 ≠ 封存树（封存之后又动了文件？）；差在这些路径：['docs/workbacklog.toml']"]
```

根因不是"谁手欠改了文件"，是**链子自己的顺序**：
- ⑤ **封存**（`--seal`）算一份"树指纹"（去掉 `gates/**`）写进 `gates/last.json`；
- ⑥ 提交前，链子按"这笔带了哪张卡的产物"去**翻那张卡的 `status`**（`docs/workbacklog.toml`）——
  **翻在封存之后**。

⇒ 只要这笔翻了一张卡的 status，**封存树与提交树必然不一致**，复核**必然报这一条** ✗。
卡 218 那笔就翻了（`218: pending → done`，结果是对的），复核因此 `problems=1`。

★ 与 225（声明域写了不用）、226（`--fast` 有却不调）**同一种病**：顺序/能力都在，**没判据钉住**。

## 要做的事
### 1. 把"翻 status"挪到**封存之前**
- 让**封存算的就是最终树**（先翻账、后封存、再提交）；链子每一步的顺序要在注释里写明**为什么**这么排。

### 2. 兜底：封存后若仍改了被追踪的文件 ⇒ **重新封存**
- 不许多算一次门禁；只重算那份 tree 指纹（幂等）。

### 3. ★★ 顺带同一个函数的第二个缺陷：`--batch` **永远翻不了成员的 status**`flip_card_status` 的判据是「那张卡的 `task` 字段 == 传进来的 `task`」，而 `--batch` 时
链子传的是**批的台账号**（`T-G340`），拿去比**每张卡自己的台账号**（`T-G333`…）⇒ **永远比不中** ⇒
**批量收口一张都翻不了**。现场：卡 219~224（批 `B-20261016`）、卡 210~214（批 `B-20261014`）
落地后 `status` 全挂在 `pending` ⇒ 14 张（2026-10-14 主控手工翻的一次）。
后果不只是难看：`wb_plan.py plan` 把**已落的卡**当成"待派" ⇒ 排批/冲突判定全被污染 ✗。

**要做的**：`--batch` 时按**栅栏成员**翻（批的 `[[member]].id` → 队列里那一张），
判据仍是"这是它自己的落地"（成员的产物确实进了这笔提交）；**单卡路径行为不变**。

### 4. 判据（★ 本卡的核心）
- 在**临时小树**上跑一遍完整链（假门禁/假提交），断言**复核 `problems == []`**；
- ★ **反例（先红后绿）**：故意在封存之后改 `docs/workbacklog.toml` ⇒ 复核**必须**报
  `封存树 vs 提交树` 那一条 —— 钉住"这道复核真的看得见东西"，而不是"顺便绿了"；
- ★ **批模式翻账的判据**：一笔 `--batch` 落地后，**它每个成员的 `status` 都必须是 `done`**；
  配一条**先红后绿**的反例：把 `--batch` 的 `task` 传成批台账号 ⇒ 旧码一张都不翻（红）。
- ★ 再加一条**漂移判据**（进 216 那道队列审计）：围栏已 `landed`，而它的成员卡里还有
  `status = "pending"` ⇒ **红**（今天 14 张就是没人看得见才挂那么久）。

### 5. ★★ 第三个盲点（同一天第二笔真读数）：封存把**未跟踪文件**也算进树指纹
2026-10-14 收「队列账目修复」那笔（`--tree .`，主树里有一堆未跟踪杂物）时，复核又报：

```
封存树 vs 提交树：last.json.tree=39e013d ≠ 本笔提交去 gates/** 的 tree=5af543f；差在这些路径：
['AGENTS.md', 'DSH-窗口化方案.md', 'Hermes-数据位置.md', 'blobs/**…（上百条）', 'tools/replay_worker_edits.py']
```

差的全是**未跟踪文件** ⇒ **封存算指纹时把未跟踪文件算进去了，而提交装不下它们** ⇒
**只要树里有未跟踪杂物，这条复核必然报**（卡树干净时不报 —— 批 3 没报、这笔报了，就是这个差别）。
★ 判据要能区分：「封存后有人改了**跟踪**文件」（真问题）vs「树里本来就有**未跟踪**杂物」（不是问题）。
要么封存只算跟踪文件（与提交可比），要么复核按"提交能不能装下"来判 —— **别把两者混成一条**。
