## 要解决的问题

magpie 有一层耐心：一组候选**全都以「会过去」的方式失败**（overloaded / busy / 短暂限流）而且**一个字节都没发出去**时，它不停在原地空转，也不立刻放弃，而是「歇一会儿再问一次」，每轮更久，但**永不短于成员自己报的 `Retry-After`**，直到这一组的预算耗尽。

pool 今天没有这层：`tools/wb_dispatch.py:3740` 的 `quota = quota_error(round_lines)` 一认出「限流」就走 `:3773` 的 `wait = pool_quota.wait_seconds(quota.get("reset_at"), args.quota_wait)` —— 那是**照记录算一次等多久**（卡 201 的活），不是「这一组全都忙，我要不要再来一轮」。重试轮次由 `:3758 if attempts > args.retry` 硬判，中间没有任何「忙也该再问一次」的概念。

差别的实际代价：厂商返回的是 `429 rate limited`、`reset_at` 没写（或写了很远的未来）时，`wait_seconds` 退回 `args.quota_wait`（默认 300 秒）—— 一个 1 分钟后就该好的限流被当成 5 分钟；反过来 `reset_at` 很远时又直接按 300 秒封顶睡过去，`--retry` 的轮次照样烧掉。magpie 的做法是：**限流这种「会过去」的失败，值得用越来越长的间隔问几次**，而不是用同一个间隔（或硬轮次）敷衍。

## 判据（6 条，逐条可执行）

1. **常量逐字搬进 `tools/pool_quota.py`**（紧挨 `:564 def round_wait(` 之后，不新起文件）：
   - `RETRY_PAUSE_S = 1`（magpie `fallback.go:1610` 的 `retryPause = time.Second`）
   - `REPLAN_LONGEST_S = 30 * RETRY_PAUSE_S`（`patience.go:52` 的 `replanLongest()`）
   - `PATIENCE_OFF = -1` / `PATIENCE_DEFAULT_S = 60` / `PATIENCE_LONGEST_S = 240`（`provider/group.go:145-149`）
   - `REPLAN_ROUNDS = 12`（`patience.go:48`）
   六个常量都要在注释里写清 magpie 的出处行号。

2. **`patience_waits(patience: int | None) -> int`**：三支，顺序与边界逐字照 `patience.go:91 waitsOf()`：
   - `patience is None` 或 `patience < 0` ⇒ `0`（**`-1` 是「关」不是「最短」**）
   - `patience == 0` ⇒ `PATIENCE_DEFAULT_S`（0 是「没配」，用默认 60 秒）
   - 其余 ⇒ `min(patience, PATIENCE_LONGEST_S)`（上限 240，配 3600 也只给 240）

3. **`replan_wait(round_no: int, *, soonest_s: int = 0) -> int`**：`wait = min(RETRY_PAUSE_S << (round_no + 1), REPLAN_LONGEST_S)`，再 `max(wait, int(soonest_s))`。逐个取值必须实测：`0⇒2 / 1⇒4 / 2⇒8 / 3⇒16 / 4⇒30 / 5⇒30 / 12⇒30`（第 4 轮起封顶 30）。`round_no < 0` ⇒ `ValueError`。`soonest_s` 只做下限，不做上限（成员自己报的续期可以比 30 秒长）。

4. **接入 `tools/wb_dispatch.py` 恰好一处**：`:3740 quota = quota_error(round_lines)` 之后、`:3758 if attempts > args.retry:` 之前。只有 `quota.get("kind") == "限流"` 才进耐心 —— 与 magpie 的 429 支（`!creditWords.Match(...)`）**判据同构**，`余额耗尽` 必须排除（照 `tools/wb_dispatch.py` 现有的两档 `kind`：`限流` / `余额耗尽`）。循环变量 `patience_left_s` / `patience_round` 初始化在 `:3672-3673`（与 `quota_seen` / `usage_total` 同一处）。预算耗尽时**必须**照原样走 `:3758` 的 `attempts > args.retry` 出口 —— 不许改退出码。

5. **新 CLI `--patience <秒>`**（`tools/wb_dispatch.py:3076` 附近的 argparse 段）：默认 `0`（⇒ 60 秒预算），`-1` ⇒ 关（行为与今天逐字相同），上限收 240（配 3600 实际用 240，与判据 2 一致）。参数进 `--help` 文案，写清「-1 = 关」。

6. **`round_wait()` 一个字节不动**：它的 `clamp(diff + WAIT_MARGIN_S, WAIT_MIN_S=60, WAIT_MAX_S=600)` 是「按记录算一次等多久」，与本卡的「递增重问间隔」是两件事，不许合并、不许互相调。

## 缺口（如实说，不许当成已解决）

- **「组」没有真源**：magpie 的 Patience 挂在「候选组」上（组有预算、成员有各自的 `Retry-After`）。pool 有三套已有的「一组号」：`tools/pool/lanes.toml`（每号并发闸）、`tools/pool/model_registry.py:335 rotation_chain_for()`（每池模型链）、`approved_models`（每号白名单）。硬造第四套「组」= 造一个谁也不认的假源。所以本卡**不造组**，耐心作用于「这一轮这一张卡的重试」，预算是单卡单轮。
- **触发层搬不过来**：magpie 的 `busy(status, body)` 读 **HTTP 状态码**（`408/500/502/503/504/529` + 429）。pool 的 worker 是子进程，`gates/diag/wb-002.jsonl` 的事件里**没有任何 HTTP 状态码**；`overloaded|503|529` 在 `tools/pool/` 零命中。本卡只认 pool 已有的 `quota_error()` 两档 `kind`，`overloaded` 那一族今天根本到不了这里。
- **保活层完全不可移植**：`pauseAlive()`（暂停期间还活着、可被取消）、`didNotStream`（一个字节都没发出去）、`protectionRefused()` / `failOther` / `failRate` 都是 HTTP 网关的形态，pool 没有「还没开始发」的等价边界。
- **`classify()` 不是 `busy()`**：`tools/pool_quota.py:309 classify()` 今天**零生产调用方**（`grep -n "classify" tools/wb_dispatch.py` 只出 `_classify_probe`，那是 auth 三态），本卡不许拿它当触发判据。
- **`tools/pool/lanes.py:82 _as_lane` 的 `wait` 字段是 F22 的空槽**（读进 `Lane` 但零调用点），本卡不许用它当「组预算」。
- 本卡落地当天，`--patience` 默认 0 ⇒ 60 秒预算会**真的**让限流卡多跑几轮。这是行为变化，不是纯新增；`--patience -1` 是回退开关。
