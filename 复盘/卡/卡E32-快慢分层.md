# 卡 E32 —— 快慢分层：把 22 条「起真子进程跑落地链」的 e2e 移出默认 pytest 门

> 台账号 T-AG486 ｜ 树：`.wt/E32` ｜ 分区：E（CI 子系统）
> 依据：2026-10-25 实测（默认门 pytest 403 s = 全量门禁 417 s 的 **96.6%**；最慢 15 条全是 e2e）

## 现在疼在哪（都是实测）

1. **默认门背着全部慢货**：`pyproject.toml` 只定义了一个 marker（`acceptance`），而最慢的
   15 条用例**全在默认门里**，各 15–31 s，清一色「起真子进程跑一遍完整落地链 / 审计」：
   `test_contract_audit::test_real_repo_audit_has_expected_shape` 31.06 s、
   `test_docs_fragments::test_audit_verdict_unchanged_by_sync` 27.39 s、
   `test_wb_plan::test_check_passes_when_no_landed_but_pending` 23.64 s、
   `test_card_specs_tracked::test_every_registered_spec_exists_and_is_tracked` 23.59 s、
   `test_wb_land` 那 7 条 e2e（22.37 / 20.60 / 17.00 / 15.57 / 15.49 / 15.28 / 15.06 s）、
   `test_partitions` 2 条（21.12 / 17.23 s）、`test_evidence_map` 17.11 s、`test_wb_dispatch` 19.66 s。
2. **卡内自测与落地趟付一样的钱**：A327 已经把门分了三档（lang 5 / audit 3 / product 11），
   可 `tools/` 层的卡内自测仍是 8 道门里那道最贵的 pytest —— 一整趟 403 s，就为了改 30 行代码。
3. **改一个变量的速度上限就在这**：墙钟 417 s 里 pytest 占 403 s，其余 18 道门加起来 14 s。
   不做分层，怎么调 worker、怎么关覆盖率，都是在同一块石头上磨。

## 要做成什么样

1. **新增一个 marker + 一道门**：`chain: 起真子进程跑完整链路（默认排除；落地趟与夜间跑）`，
   门表（`gates/defs/lang_python.py` 的 `GATES`）新增 `pytest_chain`，命令
   `python -X utf8 -m pytest -m chain --no-cov -q`；同时默认 pytest 门加上
   `-m "not acceptance and not chain"`（现在只排 `acceptance`）。
2. **按实测清单打标**：把上面点名的 22 条（清单以本票 §1 为准，落地前用
   `pytest --collect-only -q -m chain` 数一遍）打 `@pytest.mark.chain`。**一条用例都不许删、
   一条断言都不许改**，只加标记。
3. **`domains.py` 认这道门**：`REQUIRED_PROFILES` 里 `pytest_chain` 归 `lang` 档，并且
   **落地档（全量 / `product`）必须包含它**；`wb_land` 落地趟自动两门（`pytest` + `pytest_chain`），
   卡内自测默认只跑 `pytest`。
4. **把数写进申报**：改前 / 改后两道门的墙钟、以及「默认 + chain 的用例数之和 = 改前总数」
   （现在 3175，改后必须还是 3175）。

## 判据

1. **默认门 ≤ 150 s**（同 4 worker、同机器、不与其他门禁并行时测），`pytest_chain` 独立跑绿；
   两个数都进申报，并附 `gates/diag/bench-split-*.log`。
2. **覆盖面一条不丢**：`pytest --collect-only -q -m chain` 与 `-m "not chain"` 的用例数之和
   = 改前 3175；`pytest -m chain` 全绿、`pytest`（默认）全绿。
3. `pytest tests/test_gate_split.py -q -o addopts=`，至少 7 条钉子：`chain` marker 已注册 +
   默认门命令里有 `not chain` + `pytest_chain` 在 `GATES` 里 + `required_profiles()` 把它算进
   `lang` + 落地档包含它 + 只打链路的文件必然全在 chain 里（防漏打）+ 打标集合与清单一致
   （清单写死在钉子里，防悄悄少打）。
4. **反向验证**：把 `-m "not chain"` 从默认门去掉 ⇒ 「默认门命令」那条钉子必须红；
   把一条已打标的用例的 marker 删掉 ⇒ 「打标集合与清单一致」那条必须红。红色输出进申报。
5. 全量门禁（含新门）`exit 0`。

## 不许做

- **不许删用例、不许 `skip`、不许把 e2e 改成 `@pytest.mark.acceptance` 蒙混**（那是换名字不换成本）。
- 不许只加 marker 而不加门（那样 e2e 就永远不跑了，等于把安全网摘掉）。
- 不许让 `pytest_chain` 变成「可选门」：落地档必须包含它，否则落地可以绕开 e2e。
- 不许改 `tests/conftest.py` 的 `run_git` 语义（E14 的抖动重试在那儿，动它会把 55 条钉子搞红）。

## 证据

- 改前 / 改后两道门的墙钟与用例数（`gates/diag/bench-split-before.log` / `-after.log`）。
- `pytest --collect-only -q -m chain | tail -3` 与 `-m "not chain"` 的计数。
- `pytest tests/test_gate_split.py -q -o addopts=` 原始输出。
- 两条反向验证的红色原始输出。

## 检索证据（2026-10-25 回灌）

- **慢用例也是 flaky 用例**：SAP HANA 的实证研究给出执行时间与 flakiness 的相关系数 **r = 0.79**，
  并且明确把「测试拆分」列为缓解手段（可并行、缩小重跑范围），同时警告**准备开销可能吃掉收益**
  （arXiv:2409.10062）。⇒ 把 22 条慢 e2e 单独成门，除了省时间，还顺带把最不稳的一批从
  「每次都要等」里摘出去。
- **预提交跑得太频繁**：工业 CI 研究显示 pre-merge 检查的运行次数是 post-merge 的 **15 倍**，
  失败率比 5:3（arXiv:2504.11839）⇒ 「贵的检查放在 pre-merge」是当前最大的浪费形态，
  这条同时支撑本卡与 E36（台账驱动选测）。
- **没有文献量化「单独 E2E 阶段的墙钟收益」**：所以卡里的 ≤150 s 是自测目标值，不是引用值。
- 补充机制事实：同一文件内的用例如果互相污染，`--dist loadfile`（同文件归一个 worker）能避免
  「并行才红」的假红 —— 与本仓 `test_docs_fragments::test_real_repo_is_in_sync_and_merge_is_noop`
  的并行 flake 直接相关。

## 合并自 E34（门禁请求队列）——同改 `tools/wb_land.py`，串行不如一张卡

**实测的并行代价**：E28 的门禁与 bench 并行时 `pytest` 从 **341 s 涨到 506 s**，
跑门禁期间**可用内存只剩 1.0–1.6 GB**（机器 15.2 GB / 32 逻辑核，占用前列
`python.exe 2.78 GB`、`DeepSeek Harness.exe 2.38 GB`、`node.exe 0.64 GB`）。
端口段目前靠人分配，两趟撞上就互相踩。

判据增补：

1. 新增 `tools/gate_queue.py`：`submit / status / run --slot / release`，状态落 **gitignored** 的
   `gates/diag/gate-queue.json`（形状对齐 `tools/pool/queue.py` 的单写者 + 原子写）。
2. 槽数 = `max(1, floor((可用内存 − 2 GB) / 3 GB))`；端口按槽切片（步长 ≥20）。
3. 跑完回填 `ok / rev / door_failures`，并追加 `gates/diag/notifications.jsonl`
   （复用 `wb_watch` 的行格式）；`wb_land --from-queue` 只认「该卡最近一条 done 且 `rev` == 父提交」。
4. `tests/test_gate_queue.py` ≥9 钉子 + 两并发请求实测 + 反向验证（槽数算错要红）。

**今天新得的运营事实**（写进判据 1 的注释）：派活器给工人的预算是 **25,000,000 input tokens**，
E28 那张五件合并卡跑到 **32,421,196** 被止损（`退出码` 非零、改动保留）。所以「一张卡做五件事」
要同时受两个上限约束：内存槽位与工人预算。本卡的分层要顺带把这条写进 `wb_dispatch` 的拒绝理由里。
