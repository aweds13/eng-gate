## 怎么审（要**对抗性**，不要客套）

逐层问下去，**每条发现必须带证据指针**（`路径:行` / 函数名 / 用例名 / 命令读数）：

1. **需求 ⇄ 实现对不对得上**：需求里写了、代码里**没有**（或反过来）的地方。
   ★ 重点找「**文档说做了、其实没接线**」这一类（这套设施的**历史高发区**）。
2. **判据有没有牙**：每条"机器判据"追问一句 —— *它真会咬吗？什么情况下它**看着绿其实没查**？*
   ★ 重点找**假绿路径**（历史上最贵的一类缺陷：ff 失败照样打印成功、退出码 0 其实没跑完、
   自证把源文件放进被测目录、兜底 `except` 把守卫异常收成退出码）。
3. **状态机与并发**：任务栅栏（`collecting→ready→gating→awaiting-commit→landed`）·
   一树一写者 · 门禁锁 · 封存指纹 —— **哪些时序/竞态让它提前放行或永久卡死**？
4. **权威与真源**：同一个东西有几个真源？哪一份会被漂掉？（例：两个模型白名单、快照 vs 现场、
   scratch 工具 vs 进 git 的工具。）
5. **可替换性与演进成本**：换模型 / 换号池 / 换项目 / 换机器时，**哪里会碎**？
6. **谁判 vs 谁自觉**：凡"靠纪律"的地方，问一句"**机器能不能判**，不能的话代价是什么"。

## 产物骨架（照这个写，别自创结构）

1. **结论摘要**：**3~5 条最重的**（每条一句话 + 严重度），放最前面。
2. **逐条发现**（按严重度降序）：每条 = `严重度（阻断/重/中/轻）` + **是什么** + **证据指针** +
   **为什么是问题**（后果）+ **建议方向**（**方向**，不是补丁；★ 不许给大段代码）。
3. **判据漏洞专项**：列出"**看着绿其实没查**"的路径（没有就写"没找到，我查了哪几处"）。
4. **与需求不符专项**。
5. **排序建议**：如果只做三件事，做哪三件、为什么。
6. **★ 我没能验证的**（如实写：你只是读了什么、没跑什么 —— 你**没有**跑门禁/测试就直说）。
