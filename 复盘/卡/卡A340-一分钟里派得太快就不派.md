# 卡 A340 —— 一分钟里派得太快就不派：magpie 的 MaxRPM 移植进 pool（T-AG542）

> 台账号 `T-AG542` ｜ 分区 A（历史线 / 号池 pool）｜ 树 `.wt/A340` ｜ 层 判据层
> 依据：magpie 的**每分钟请求数闸** —— 窗口由两个常量相加 `var rpmWindow = time.Minute`（`internal/gateway/rpm.go:44`）
> 加 `var rpmSlack = time.Second`（`:52`）构成，`func rpmSpan() time.Duration { return rpmWindow + rpmSlack }`（`:55`）
> ⇒ **实占 61 秒，不是 60**；`var rpmLongest = 2 * time.Minute`（`:59`）是一个请求最多等多久。
> 核心判据 `func (l *rpms) reserve(who string, limit int, longest time.Duration, now time.Time)`（`:122-138`）逐字：
> 先 `ts := l.prune(who, now)`，再 `at := now`；`if len(ts) >= limit { at = ts[len(ts)-limit].Add(rpmSpan()) }`；
> `if d := at.Sub(now); longest > 0 && d > longest { return time.Time{}, &errRPM{...} }`
> ⇒ **判据不是「数一数 60 秒里有几个」，而是「取倒数第 limit 个时间点 + 61 秒」** —— 这一句是本条的全部算法。
> `prune()`（`:104-117`）丢掉 `!ts[i].After(now.Add(-rpmSpan()))` 的前缀（即 `<= now - 61s` 的）。
> 上限 `const MaxRPMLimit = 10000`（`internal/provider/concurrency.go:185`），校验 `func CheckRPM(n int) error`（`:203`）
> 文案逐字 `a limit on requests a minute is from 0 (none) to %d, not %d`。
> 那 1 秒 slack 的**理由逐字在源码注释里**（`:46-51`）：「A request is counted when it starts to go, but the vendor
> counts it when it arrives: the first on a connection arrives later than the next ones by its dial and TLS handshake,
> so with the bare window the vendor could see one more than the limit in its own minute (TestMaxRPMWaitsForRoomInTheMinute
> went red under CI load, and does every time when the first is held 150ms on its way).」
> 实测现场（2026-10-30，本树 HEAD `4f7ee638`）：`grep -rniE "\brpm\b" tools/ --include=*.py` ⇒ **0 行**；
> `grep -rniE "MaxRPM" tools/ --include=*.py` ⇒ **0 行**；`grep -rniE "per[._-]?minute|每分钟" tools/ --include=*.py`
> ⇒ **1 行**，唯一命中是 `tools/pool_quota.py:131` 那条识别 429 文案的正则（不是闸）。
> 与在飞卡的关系：本卡改 `tools/wb_dispatch.py` ⇒ A339 也改 `tools/pool/registry.py`/`guards.py`，两者**文件不相交**，
> 但都动派活路径，落地时按主树 HEAD 先后 rebase（谁先落谁先合）。

## 要解决的问题

一个号**一分钟里能被派几次，今天没有任何判据**。

派活侧今天唯一的节流是「撞了 429 才等」：`tools/wb_dispatch.py:218 DEFAULT_QUOTA_WAIT = 300` 与
`:293 DEFAULT_RETRIES = 1`，配合 `:3450` 起的三拍循环（等 → 探 → 换模型）。这是**被动**的：
只有在 vendor 已经回过 429 之后才起作用。**主动**那条 —— 「我这个号这一分钟已经派出去几趟了」—— 一条都没有。

已有的两个名字像的东西都不是它，不许拿它们顶：
- `gates/diag/gate_lock.py:18` 的 `TF_GATE_MAX_CONCURRENT`（默认 2）限的是**同时持锁的段数**
  （`:148` docstring 逐字「全局并发上限：**同时**持锁的段数 ≤ N」），**没有时间窗**这个概念。
- `tools/pool/plan.py:40 DEFAULT_CONCURRENCY = 2` 是**批大小**。
- `tools/pool/plan.py:39` 是 `DEFAULT_BACKLOG`（不是并发），行号别写错。
- `tools/pool_quota.py` 的四态（`STATE_REL = "gates/diag/quota-state.json"`，`:56`）判的是「这个卡 × 这个模型被 429 后
  的 `reset_at` 到了没」，**被动记 429**；本卡是**主动数派活次数**。两者方向相反，各自一个模块。

★ **语义差别必须写进新模块的文件头，不许含糊**：magpie 计的是**它转发的每一个 HTTP 请求**；
pool 里一次「派活」背后是**一整个 CLI 会话**（几十到几百次上游请求）。
⇒ pool 的「每分钟派几次」与 magpie 的「每分钟请求几次」**不是同一个量**：
本闸只能防「同一个号被同时/接连轰太多趟」，**防不了 vendor 侧的 RPM 429**（那个仍由 `pool_quota` 的四态负责）。
不写这句话，下一个人会以为加了本闸就不会 429。

## 判据（8 条，逐条可执行；判据 3 分 ①写 ②还两步 —— 见裁定 1）

1. 新增 `tools/pool/rpm.py`（纯判据 + 一个派生账本读写），公开面**恰好**这些：
   - 常量 `WINDOW_S = 61`（**不是 60**；注释里逐字抄 magpie 那 1 秒 slack 的理由）、`LONGEST_WAIT_S = 120`
     （`rpmLongest`）、`MAX_RPM = 10000`（`MaxRPMLimit`）、`STAMPS_REL = ("gates", "diag", "pool-rpm.json")`。
   - `class RpmError(ValueError)`：文案照抄 `CheckRPM` 的语义（`0` 到 `MAX_RPM`，越界点名收到的值）。
   - `@dataclass(frozen=True, slots=True) class RpmDecision:`，**恰好四个字段** `allowed: bool` / `next_at: datetime` /
     `wait_s: float` / `why: str`；不含任何建议字段。
   - `def now_tz() -> datetime`：复用 `tools/pool_accounts.py:48 TZ`（`timezone(timedelta(hours=8))`），
     **不许**新造第二个时区常量（`grep -n "^TZ = " tools/pool_accounts.py` 实测只有这一处）。
   - `def decide(account: str, stamps: Sequence[datetime], *, limit: int, now: datetime,
     longest: float = LONGEST_WAIT_S) -> RpmDecision`：三步逐字对应 `prune` → 「倒数第 limit 个 + 61 秒」→ 与 `longest` 比。
     **纯函数**：不读钟、不读文件、不写文件、不 print、不起进程。
   - `def load_rpm(path: Path | str | None = None) -> dict[str, int]`：文件不存在 ⇒ `{}`（一条闸都没开）；
     坏 TOML / 负数 / 超 `MAX_RPM` ⇒ `RpmError`（**绝不许静默当 0**：0 = 不限 = 悄悄松开判据）。
   - `def read_stamps(*, root: Path | None = None) -> dict[str, list[datetime]]` / `def note_stamp(account: str,
     at: datetime, *, root: Path | None = None) -> None`：读写上面那个派生账本（JSON，键是账号 id，值是 ISO 时刻数组）。
2. `decide()` 的六条边界必须精确成立（写测试时逐条断言）：
   - `limit=0` ⇒ 恒 `allowed=True`（`0` = **关闸**，不是全拒 —— 照 `reserve()` 里 `longest > 0` 那条同向的宽容）。
   - 空 `stamps` ⇒ `allowed=True`、`next_at == now`、`wait_s == 0.0`。
   - `limit=2`、`stamps=[now-10s, now-5s]` ⇒ `allowed=False`、`next_at == (now-10s) + 61s`、`wait_s == 51.0`。
   - `limit=2`、`stamps=[now-70s, now-5s]` ⇒ 前者被 prune ⇒ `allowed=True`、`wait_s == 0.0`。
   - 算出来 `wait_s > longest`（`longest=120`）⇒ `allowed=False`，`why` 里含「超过最长等待」四个字。
   - `stamps` 里有**未来时间**（钟坏了）⇒ 不许崩：按 prune 口径它们未过期 ⇒ 拒；但 `why` 必须带「记录里有未来时间」。
3. **写分两步，照 magpie 的 `reserve` + `giveBack` 那一对**（不是「晚点再写」—— 那样两个窗口会双双放行）：
   - **① 判完就写**：`note_stamp()` 必须和 `decide()` 在**同一把锁里**（⇒ 判据 5）。判之前写，一次中断会白占一个分钟位；
     判之后不写，隔一秒的第二个窗口看不到这一趟。对应 magpie `reserve()` 里「持锁时就把 `at` 追加进 `l.m[who]`」
     （`internal/gateway/rpm.go:122-138`）。
   - **② 没派成就还回去**：占树那两步失败（`pool_registry.reserve(...)` 抛 `GuardError`、或
     `pool_registry.RegistryError`）的 `return 2` 之前必须调 `give_back(account, at)`，**也持同一把锁**；
     对应 magpie `giveBack()`（`rpm.go:141-154`，按值删回去）。还不上只白占一个分钟位（61 秒后自己滑出窗口），
     所以还自身的异常要吞掉、但**必须**往 stderr 喊一声，不许盖掉原本的失败原因。
   ★ 缺口（如实说）：magpie 的回滚挂在 ctx 取消上，pool **没有**等价的可取消边界 ——
     进程被强杀 / 异常退出**不会**还，只能等那一趟 61 秒后自己滑出窗口。
4. 接入点固定在 `tools/wb_dispatch.py` 的**占树之前**（`reserve_tree = worker_tree_label(...)` 在 `:3294`，
   往上到 `:3285` 的 `queue_files(args.card)` 之间）；判不过 ⇒ `print(..., file=sys.stderr)` + `return 2`，
   **不占树、零副作用**。`args.account` 为空 ⇒ 整套跳过（今天行为逐字不变）。
5. 「读 → 判 → 写」三步必须在**同一把文件锁**里（复用 `tools/pool/task.py:254` 的 `spin_lock(target, timeout=...)`，
   它已是租约制陈旧接管 + 按时间判陈旧，`registry.py` 的 `os.kill` 硬禁令不适用于它）。
   不许自己写第二套锁；不许 `time.sleep` 自旋等待（锁本身有界）。
6. `MAX_RPM` 之外的越界一律 `RpmError`，**不许** clamp 成 `MAX_RPM`（magpie 的 `RPMLimit()` 会 clamp，但那是**读 provider
   配置**的路径；本卡是**人写配置文件**的路径，写错要立刻说，不许悄悄改成合法值）。
7. 时区只有一处：`now_tz()` 用 `pool_accounts.TZ`；账本里的时刻一律带 `+08:00`。
   `decide()` 收到的 `stamps` 若不带时区 ⇒ 按 `now.tzinfo` 补，**不许**假设 UTC。
8. 反向钉子必须有判别力：**把 `WINDOW_S` 从 61 改成 60 必须变红**。
   做法：`limit=1`、`stamps=[now-60s]`，断言 `allowed=False`（须等到 `now-60s+61s`）；
   改成 60 之后 `now-60s` 恰好落在 `<= now-60s` 上被 prune ⇒ `allowed=True` ⇒ 红。
   理由必须写进测试注释：那 1 秒是 magpie 在 CI 负载下**实测挖出来的**，丢了它就会「本地放行、上游 429」。

## 缺口（如实说，不许当成已解决）

- **profile 名 ↔ 账本稳定 id 今天没有映射代码**（`tools/wb_dispatch.py` 的 `--account` 收的是
  `codebuddy_accounts.py` 的 profile 名，`infra/pool/accounts.toml` 的 id 是另一套；两者的对应关系只体现在
  `credential.locator` 的末段），所以 `rpm.toml` 保持**空表**、本闸今天**默认不生效**；键的正确口径仍是稳定 id。
  映射与接线**不在本卡**（另开卡）。
- **强杀不还**：见判据 3 的缺口（进程被 `kill -9` / 解释器崩溃时 `give_back` 不会跑）。
- 本闸数的是**派活趟数**（一趟 = 一整个 CLI 会话），**防不了** vendor 侧的 RPM 429 —— 那个仍归 `pool_quota` 四态。
