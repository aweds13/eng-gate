# 复盘 · 质量门提速：pytest 并行（T-G7）

> 性质：**工程提速复盘**（先量了什么 / 瓶颈在哪 / 定案 / 怎么改 / 验证 / 风险）。
> 触发：用户 2026-09-22 问「为什么跑门禁跑那么慢」。
> 定案：用户选 **1+2** —— ① 内循环只跑相关文件、提交前才跑全套；② 上 `pytest-xdist` 并行。
> 结果：**门禁整轮 266s → 87s**（pytest 232s → 53s），用例集合与覆盖率口径**都没变**。

---

## 一、先量，不猜（这一步是本次复盘最重要的部分）

一次门禁约 **4.4 分钟**，实测拆开：

| 项 | 耗时 |
|---|---|
| **pytest** | **204–240s**（多次实测，占 ~88%） |
| check_layers_selftest | 9.0s |
| acceptance / web_live / audit / mypy / lf1_live | 2–7s 各 |
| ruff / check_layers / dom_probe / audit_titles | < 1.5s 各 |
| **其余十项合计** | **~30s** |

"门禁慢"其实 99% 是 pytest 一项。继续往里拆（`--durations=0` 全量相统计）：

- **call 阶段** 621 项合计 **114.5s**（均值 184ms）；**setup 阶段** 654 项合计 **33.5s**（均值 51ms）；
- **最慢的 25 个用例加起来只有 40.6s** —— 没有"一个病态用例拖垮全队"，是**普遍成本**；
- 最慢的那几个都是**真起子进程/真并发**的用例（bench 6.9+6.7s、示例脚本 3.2/1.7/0.55s、
  提醒脚本 2.5+0.78s、audit CLI 1.9s、并发 2.8+1.4+1.3s）—— 它们"慢"得有理由。

单次成本直接量：

```
create_app()            193 ms   ← 每个用例都建一个（~200 条路由 + pydantic 响应模型 + 读配置 + 日志）
db.connect + 迁移        26 ms   ← 每个用例一个新库（幂等加列一路跑下来）
TestClient 首次请求       57 ms
```

**结论**：瓶颈是"**每个用例都起真 app + 真库**"这件事被**串行**执行了 757 遍。
这是这套测试的设计选择（不 mock），也正是 T-D12 时区缺陷、T-G3 热力图空渲染那类问题能被抓住的原因
—— 所以要提的是**并行度**，不是把它们改成假库。

## 二、两个我怀疑过、但被实测否掉的猜测（记下来，免得下次又猜）

| 猜测 | 实测 | 结论 |
|---|---|---|
| 覆盖率（`addopts` 里的 `--cov`）拖慢 | 同一命令：带 `--cov` **154s** / `--no-cov` **152s** | ❌ 只差 1–2s |
| `-q` 或 `.pytest_cache`（本机该缓存目录创建报 WinError 183） | 同一组文件四种组合：10.3 / 11.3 / 12.4 / 12.6s | ❌ 无差别 |

另外把波动也量了：门禁那几次 204/217/232/240s，而我单独跑 152/154s —— **同一份代码、同一组参数，
波动就有 ±15%**，差值落在机器 I/O（用例的库文件建在 C: 的临时目录、仓库在 D:，一轮跑要创建/删除
上千个小文件，实时杀毒会吃掉这部分）。所以"门禁比其他时候慢"未必是门禁的问题。

## 三、定案（用户 2026-09-22 选 1+2）

1. **内循环**：改哪块跑哪块（相关文件 / `-k`），**提交前才跑全套门禁**。门禁是**提交闸**，
   不是开发内循环 —— 这条不用改代码，改的是我的习惯。
2. **并行**：上 `pytest-xdist`。判据是"**用例之间有没有共享状态**"：
   - 每个用例 `tmp_path` 一个**自己的库**；
   - 事实总线、覆盖的 `app_settings` 都是**进程内**状态；
   - 探针/真机自检（node、子进程那几项）**不在 pytest 里**，不受影响。
   → 没有共享状态 = 并行是"安全的那一类提速"。

## 四、怎么改的

- **`scripts/run_gates.py`**：新增 `pytest_cmd()` / `xdist_available()` ——
  **装了才并行**（`-n auto`），没装就串行，并且**开头打印这次用的是哪种跑法**
  （`=== pytest 跑法：并行（pytest-xdist，-n auto） ===`）。**不谎报**、也不因为别人机器上缺插件
  就把门禁弄红。另加 `--serial`：并行下万一偶发失败，用同一条命令单进程跑一遍做对照。
- **`tests/conftest.py`**：并行时每个 worker 一个日志文件。`create_app()` 会调
  `logs.setup_logging()`，默认写仓库里的 `logs/timeflow.jsonl` —— 16 个 worker 同时 append 会互相插行
  （那是 gitignore 的本机产物、不影响判定，但没必要让它变脏）。串行（你平时手敲 `pytest`）
  **保持默认**，与真实运行一致。
- **`pyproject.toml`**：`[project.optional-dependencies] dev` 加 `pytest-xdist`
  （一条新依赖 = 用户点头过的事，记在这里）。
- **没动**：`addopts` 里的覆盖率门槛、任何一条用例、任何生产代码。

## 五、验证（都要看得出"没变"）

- **用例集合完全一致**：`pytest --collect-only -q` 与 `pytest -n auto --collect-only -q` 的输出
  **逐行相同**（757 项；另有 `tests/acceptance/test_mvp_journey.py` 的 2 项由验收门单独跑，合计 759）。
- **结果与覆盖率不变**：757 passed；覆盖率 **93.27%**（并行）/ 93.32%（串行），门槛 70% 没动。
- **耗时**：pytest 57.2s（单独跑）/ 53.4s（门禁里）；整轮门禁 **55.65s + ~31s ≈ 87s**。
- **十一项门禁全绿**、`gates/last.json ok=true`、审计 0 豁免（与上一版同样的判定）。

## 六、风险与边界（诚实清单）

1. **并行会暴露"跨用例共享状态"**：现在没有（每个用例自己的库），但将来若有人写了依赖
   固定路径/全局单例的用例，并行下会偶发失败 —— 那**正是它该暴露的**，排查路径是 `--serial`。
2. **`-n auto` 在本机 = 32 个进程**：内存峰值比串行高（实测没出问题）；换台小机器也安全，
   `auto` 会按核数自适应。
3. **别人机器上没装 `pytest-xdist` 时**：门禁照常跑（串行）并把跑法打印出来 ——
   门禁语义（跑哪些、判什么）一点没变，变的只是快慢。
4. **速度仍受机器 I/O 影响**：±15% 的波动还在（杀毒/磁盘），别把单次数字当基准。
5. **`复盘/长任务执行协议.md` 没动**（那份由人维护）：协议里写的命令还是
   `python -X utf8 scripts/run_gates.py`，**没有变化** —— 并行是这条命令内部的事。

## 七、教训

1. **先量后猜**：我一开始怀疑覆盖率，实测差 1–2s，直接否掉 —— 若照着猜去改 `addopts`，
   既没提速又把覆盖率门槛从"每次跑"降级成"想起来才跑"。
2. **提速要找结构性瓶颈**：单次 `create_app()` 193ms × 757 个用例才是账本；
   配置层面的微调（`-q`/缓存）量出来是噪声。
3. **提速不能改判定**：这一卡的验收标准是"同样的用例、同样的覆盖率、同样的结论，只是更快" ——
   所以我把"集合逐行一致"也当成证据留了下来。
