## 二、关键认知演进（本轮的"想通了什么"）

### 演进 1：从「文件归位」到「信息类型分流」
最初任务只是"检查文件是否放对文件夹"。但很快发现更本质的问题：**同一份文档里混着"长期稳定规则"与"当前任务细节"**，这才是让人和 AI 都不知所措的根源。
→ 确立了**三层信息架构**：约定层（稳定横切）/ 功能层（按需细节）/ 契约层（行为链路）。

### 演进 2：从「规格缺约束」到「规格只承接了承诺」
第一份复盘的核心发现——**Intent→Spec 的转录丢了四要素中的三样**（行为规则、护栏、why）。规格只写"必须支持 X"，不写"不得 Y / 为什么 / 边界在哪"。
→ 治理手段：建 `conventions.md`，把散落、丢失的护栏集中成"简短规则"。

### 演进 3：从「模块联动」到「操作闭环」（用户纠正所致）
我最初只看到模块之间的断裂（专注不记账）。用户指出**模块内部的使用逻辑**也不完整（新建任务、关闭任务），这才是更基础的问题。
→ 重构为**三层断裂**：①操作闭环（地基）②模块联动 ③使用动线。**①不成立，②③无意义。**

### 演进 4：从「结果验收」到「行为契约」
发现根因：`implementation/` 只写"有哪些模块、负责什么"，**从未定义"一个操作怎样才算做完"**。AI 按模块打勾，打勾即算完 → 必然"做一半"。
→ 新建**契约层**：`interactions.md`（单操作六要素）+ `flows.md`（多操作链路）。

## 三、三个"最"（本轮最重要的发现）

| 排名 | 发现 | 影响 |
|---|---|---|
| **最根本** | **impl 层缺"操作闭环"定义**——只列模块不定义行为，导致 AI"做到存在"而非"做到闭环" | 解释了全部"功能只做一半"现象 |
| **最隐蔽** | **死代码**：`process_repeats`（Repeat 生成）、`log_conflict`（冲突提示）写了但**无人调用**；`stats.py` 在 modules.md 声明但**文件不存在** | 说明缺少"声明-实现"对账 |
| **最讽刺** | **后端接口齐备，前端从不调用**：`DELETE /tasks`、`finish_session`、`/focus/guard`、`add_assessment` 等接口都写好了，前端零入口 | "做了一半"的另一种形态：半在服务端、半在前端 |

## 七、方法论沉淀（可复用到其他项目）

1. **三层信息架构**：稳定约定 / 当前细节 / 行为契约 —— 三者分离，各自按需加载。
2. **六要素操作契约**：入口 / 前置 / 输入 / 后续 / 可逆 / 反馈 —— 一个操作缺任一要素即"没做完"。
3. **三层断裂检查**：操作闭环 / 模块联动 / 使用动线 —— 从内向外逐层验。
4. **判据：问"这句是给读者看的，还是给我自己看的"** —— 用于区分约定层与细节。
5. **"声明-实现"对账**：凡文档声明了模块/函数，必须能扫出对应实现；凡写了代码，必须能扫出调用者。
