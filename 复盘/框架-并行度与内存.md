# 并行度 × 内存：实测 + 文献（怎么在不加内存的前提下提并行度）

> **触发（用户 2026-10-03 16:4x）**：「怎么通过提高并行度的同时又保证内存减少？**是不是你现在派活的方式，以及调用的方式有明显的区别**？」
> ⇒ 先**量**（不猜），再检索（秘塔 + DeepXiv 两条路）。

---

## 一、★ 本机实测（2026-10-03 15:59，现跑）

| 进程（按名字聚合） | 进程数 | RSS 合计 |
|---|---|---|
| ★★ `DeepSeek Harness.exe` | **10** | **2.468 GB** |
| `python.exe`（门禁 + 派活器 + 门锁 + 探针） | 11 | 1.217 GB |
| `svchost.exe` | 90 | 0.607 GB |
| `MemCompression`（★ Windows 正在压内存 = 机器紧） | 1 | 0.451 GB |
| `MsMpEng.exe`（Defender） | 1 | 0.405 GB |
| ★ `node.exe`（**两个 CLI 工人**：CodeBuddy + 码道） | 6 | **0.236 GB** |
| 其余（explorer / dwm / docker / NVIDIA…） | — | ~0.5 GB |

**可用 3.56 GB / 总 15.21 GB。**

### ★★ 这张表直接回答用户的问题

1. **工人很省**：两个 CLI 工人合计 **0.24 GB**（每个 ~40 MB 级）。⇒「派活方式」不是内存问题。
2. ★★ **最大的一项是我自己**：`DeepSeek Harness.exe` **10 个进程 2.47 GB** —— 比整套 pytest 门禁还多。
   ⇒ 「调用的方式有区别」的答案是：**有，而且是我这边的**（我为了不空转，把门禁与工人叠在一起跑）。
3. **链条**：我同时跑工人 + 门禁 ⇒ 可用内存掉到 3.4~4.0 GB ⇒ 门禁的内存闸（默认 4.0）逼我 `TF_PYTEST_WORKERS=1`
   ⇒ pytest **620~700 秒**（默认 4 worker 只要 **250 秒**）。★ **12 分钟一趟的真因是排班，不是门数。**
4. `MemCompression` 在干活 ⇒ 已经在换页/压缩，**这本身就是"内存不够"的读数**。

**⇒ 结论**：**要提并行度，先别加门禁的并行度，先把「谁在什么时候跑」排开。**
门禁跑的时候**不派工人**；工人跑的时候**不必跑门禁** —— 这两件事本来就不必重叠（门禁是收口那一步）。

## 二、文献（DeepXiv，带真实编号）

### 2.1 ★★ 最直接的一条：**「预测 + 装箱」而不是「固定并行度」**

| 证据 | 读数 |
|---|---|
| **Smart Build Targets Batching Service**（Google）[arXiv:2102.09098] | 用 ML 预测每个 target 的**峰值 post-full-GC 堆内存**与 executor 占用率，把 target **按内存装箱分批**（不超内存、不超 deadline）。生产：平均 batch size **300**、日 1.47M target、日 2.92M build ⇒ **OOM 压到 0.08%**、deadline 超时 **0.05%** |
| **SAP HANA CI 资源预测** [arXiv:2604.12673] | 300,000+ 次生产 build / 1000+ 节点：★ **平均 >60% 的已分配内存没被用掉**，**8.6% 的失败源于内存欠分配**。用分位数回归预测峰值 ⇒ **每 build 省 ~36 GB**、欠分配率降到 **<0.3%**、构建时长不变 |

★ 对我们的意思：**我们现在的 4.0 GB 阈值是拍脑袋的**（而且它只防"跑不起来"，不防"浪费"）；
SAP 那条「**>60% 已分配内存没被用**」说明**我们大概率也在浪费**。⇒ **先量一趟门禁的真实峰值 RSS**，再定阈值。

### 2.2 ★★ 第二条：**内存紧张会制造假红**（这条把排班从「快慢」升级成「判据正确性」）

| 证据 | 读数 |
|---|---|
| **The Effects of Computational Resources on Flaky Tests（RAFT）** [arXiv:2310.12132] | 52 项目 / 27 种资源配置：★ **46.5% 的 flaky test 是「资源敏感」的**；**CPU <1 core 或内存 <1 GiB 时 flakiness 激增**；个别项目失败率升 **>200×**。★ **反直觉**：**主动降低资源是检测 flaky 的高性价比手段** |
| **SAP HANA flaky** [arXiv:2409.10062] | ★ **相反**信号：执行时间与 flakiness 强相关（r=0.79），但**基础设施负载与 CPU/内存需求无显著相关**；支持 **test splitting** 作为并行化的缓解手段 |

★ 对我们的意思：**两条证据互相打架 ⇒ 必须自己量**。但 RAFT 那条足以支撑一条纪律：
**「降级跑法」不只慢，还会把 flaky 制造出来 ⇒ 在降级状态下看到的红，不许直接当结论。**
（这正是我们今晚咬过的「假红」族；也说明卡 184 那条「降级必须留痕」是对的。）

### 2.3 其他可用的杠杆

| 杠杆 | 证据 | 怎么用在我们身上 |
|---|---|---|
| **动态批大小**：BatchAll / TestCaseBatching 减少 **91% / 81%** 机器数，反馈时间不变 | [arXiv:2308.13129] | 把大测试文件**拆小块**，让调度器能塞满；★ 这是「不改子集、改批处理」那条的延伸 |
| **消除内存缓冲**：拉大镜像时数据块直接落盘，daemon 峰值内存降 **8.7–25.3×** | [arXiv:2607.05596] | pytest 的 `--basetemp` / 大对象**落盘**、别留内存；★ 思路是「消除缓冲」，不是「加内存」 |
| **内存换速度是明账**：Bazel 比 Go Build 内存高 **81–351%**，但全量快 23–39%、增量快至 75% | [arXiv:2510.20041] | 若内存是硬约束，就得**反向选择**（别盲目上重工具）★ 与「不许砍控制面」并存：**该加的是排班，不是砍门** |
| **每 worker 要有内存下限** | [arXiv:2310.12132] | 我们的闸现在只有**上限**（4.0 GB）；应补**下限**（低于 X 不许跑/必须降并行并留痕） |

### 2.4 明确的证据空白（照 F10 附检索面）

- **test sharding / 测试分片对每 worker 内存的影响**：**没有**实测论文（最接近的是批处理 [2308.13129] 与 test splitting [2409.10062] 的提及）。
- **remote execution / remote cache 的每 worker 内存**：**没有**（只报加速 4.22×/4.71×）。
- **per-worker 内存剖析与排名（测试场景）**：**没有**。
- **fork/spawn 模型对内存的影响（测试场景）**：**没有**实测（只有 LLM 推理侧 fork+CoW 的 [2604.06370] 可类推）。
- **检索面自述**：DeepXiv / arXiv（秘塔那一侧命中的都是文档与博客级，**没有**可比读数）；2 组问题各 top_k 10–15；
  试过的词：`memory-aware test scheduling` · `per-worker memory CI` · `test sharding memory` · `remote execution memory` ·
  `cgroup memory limit test parallelism` · `bin packing test scheduling`。★ **是「检索面内未见」，不是「没有」。**

## 三、★ 立刻能做的（按收益/代价排序）

| # | 动作 | 收益 | 代价 | 可逆 | 依据 |
|---|---|---|---|---|---|
| **P1** | ★★ **排班互斥**：门禁跑的时候**不派工人**（反之亦然）—— 让门禁拿回默认 4 worker | 门禁 **700s → 250s**（每笔省 ~7 分钟） | 几乎为零（只是不重叠） | 可逆 | ★ **本机实测**（DSH 2.47 GB 是大头） |
| **P2** | ★ **量门禁真实峰值 RSS**：跑一趟 4-worker 门禁，记峰值与各 worker 峰值 ⇒ 用实测替换 4.0 GB 阈值 | 可能把阈值下调 ⇒ 允许更多并行 | 一次测量 | 可逆 | [2604.12673]（>60% 内存闲置） |
| **P3** | ★ **补每 worker 的「内存下限」判据**（不只是上限） | 防止降级制造假红 | 一条判据 | 可逆 | [2310.12132]（<1 GiB 时 flaky 激增） |
| **P4** | **门按内存分池**：轻门池 / 重门池（我们已有「轻门 12 道 ∥ 浏览器 0 道」的泳道）⇒ 重门单独排 | 减少同时抢内存 | 改 `run_gates` 的泳道 | 可逆 | [2102.09098]（按内存装箱） |
| **P5** | **大测试文件拆块**，让调度器能塞满 | 同内存下并行度更高 | 拆测试（有改动成本） | 可逆 | [2308.13129]（BatchAll 减 91% 机器） |
| **P6** | **DSH 侧省内存**（少开会话/窗口 —— 这是我自己的 2.47 GB） | 直接腾出 1~2 GB | 我的使用习惯 | 可逆 | ★ 本机实测 |

★ ★ 其中的 **P1 / P6 是零代码改动**，**今晚就能生效**；**P2/P3/P4/P5** 应并入**卡 184（收口增量门禁）**或**另立卡**。
