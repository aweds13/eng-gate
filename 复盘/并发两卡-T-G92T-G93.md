# 并发两个工人 · 第一次真跑（卡 003 + 卡 004 → T-G92 + T-G93）

> 用户 2026-09-26：「可以并发多个 workbuddy 跑任务吗，保证稳定性与项目干净程度的情况，同时开发
> 一个插件，可以让我看到它们工作状态」→「**并发两个，明确分工，试试看**」。
> 这份记的是**第一次真跑**的结果：两卡都落地，撞到 6 个坑，其中 1 个是"必须改阈值"的真问题。

## 1 分工（两条规矩：白名单不相交 + 一人一棵树）

| 卡 | 树 / 分支 | 活 | 白名单 | 产物 |
|---|---|---|---|---|
| 003 | **主工作区** `line/impl-v1` | 修 `--detach` 的前置检查顺序 | `tools/wb_dispatch.py` / `tests/test_wb_dispatch.py` / 台账 / changelog / 复盘 / 交接两篇 | `T-G92` = `b6c36ba` |
| 004 | **`.wt/004`** 分支 `wt/004` | 状态面板转正 | **只有** `tools/wb_dash.py` / `tests/test_wb_dash.py` / `复盘/wb_dash转正-T-G93.md` | `T-G93` = 本笔 |

为什么 003 留在主树、004 进 worktree：**主树同时只能有一个写者**（一写一读）。让 A 留主树是因为
它要改台账/changelog/交接文档 —— 那些**必须**由它那一笔原子地一起改（audit 会查）。B 的活与它们无关，
所以把 B 挪到别的树，顺手验证"共享文件从工人手里拿走"这条规矩。

## 2 凭什么说"项目还是干净的"（四道隔离，缺一条都不行）

1. **一人一棵树**：`git worktree` 放在 `.wt/<卡>` —— ★ 必须**在仓库里面**，因为 CodeBuddy CLI 的
   `trustedDirectories` 只放行 `D:/repo/engineering/**`，放到仓库外它每次动文件都要问。
2. **白名单不相交**：004 的白名单里**没有** `tools/wb_dispatch.py` —— 003 正在改那个文件。
3. **共享文件从工人手里拿走**：台账 / `docs/changelog.md` / 两张交接文档 / `gates/last.json`
   004 的卡里写死了"一个字都不许碰"，由主控**串行**收口。否则两张卡都写台账 → 合并必冲突，
   audit 也会因为两份条目互相盖而红。
4. **工人只跑轻门，全量门禁由主控收口时跑一次**：并发跑两个 `run_gates.py` 会抢 CPU 和端口
   （`ui_flow` / `web_live` / `lf1_live` 都要起服务）。

外加一条：`.wt/` 写进 `.git/info/exclude`（**不是**被跟踪的 `.gitignore`）—— 这样主树的门禁看不见
worktree 里的东西，也不会有人把 `.wt/` 提交进去。

## 3 结果（我逐棵验的，不是看它们的报告）

- **两棵树都没越界**：`git status --porcelain` 下，004 的树里只有它那三个新文件（+ 我放的卡规格），
  **没有任何被跟踪文件被改**；主树收口时也只有我加的那几个。
- **门禁是对的那一笔跑的**：`gates/last.json` 的 `rev` 等于该提交的父提交（003 与 004 都核过）。
- **真机证据都真**：003 的 `--detach` 我用三个探针**自己复现**过（缺规格 → 退 2 + 留判决、不扔子进程；
  `detached_argv()` 里脚本恰好一次 + `--no-preflight` 恰好一次；不加 `--execute` 时子进程真跑出 dry-run）。
  004 我自己跑了 `ruff` + `pytest tests/test_wb_dash.py` → 11 passed，面板 JSON 与端口释放也验了。
- ★ **最值钱的一件事**：003 的工人**自己**用"真机证据 (b)"逮到 **T-G91 留下的第二个洞** ——
  `detached_argv()` 少了脚本自己，`--detach` **从来没真扔出去过**。这条不是卡里写的，
  是它按"证据要真跑、不能只靠读代码"的要求撞出来的。**说明"卡规格 + 铁律 + 要真机证据"这套是管用的。**

## 4 撞到的坑（每条都改了规矩或进了候选卡）

1. **worktree 的基点不能取"另一张卡飞行中的提交"**。A 先提了 `3333404`，B 的树就建在它上面；随后 A
   为了重做那一笔 `git reset --soft 162e376` → `3333404` 成了**孤儿提交**，B 的分支基点漂了。
   规矩：**并发建树一律从"我这边已复核过的提交"起**；真要重做，先确认没有别的树建在上面。
   这次没出事只因为收口是**按文件复制**（不是按分支合并）—— 运气好，不算设计。
2. **共享文件必须从工人手里拿走**（见 §2.3）。这条这次**完全奏效**：B 一个共享文件都没碰。
3. **轻门 / 全量门禁分层**。004 的卡里明确"别跑 `run_gates.py`"。
4. **收口是串行的，真正的瓶颈在我**。一次只收一张卡（读 diff → 五条复核 → 补台账 → 门禁 → 提交），
   所以**并发上限 2 起步**是有依据的 —— 再往上加，工人那边省的时间会被我排队等回来。
5. ★ **看门狗的"静默 480 秒"会误杀正常的长工具调用**（**这条要改**）。派活器的看门狗口径是
   "日志静默 ≥ 480 秒 → 判卡死、掐掉整棵进程树"，它假定"一次工具调用最多几分钟"。但实际上：
   主树全量 `run_gates.py` 要 **~4 分钟**（`pytest` 一项就 110 秒），冷缓存的 worktree 里更久
   （`ui_flow` 起浏览器能到十几分钟）。也就是说工人**只要在卡里跑一次重门禁，就会被自己的看门狗掐**。
   本轮的规避办法是工人**不许跑全量门禁**（本来就该如此），但这是**靠规矩绕开阈值**，不是阈值对。
   → 候选卡：把静默阈值改成"**max(固定下限, 最近一次工具调用的耗时或调用名)**"，
   或者对已知的长命令（`run_gates.py` / `pytest` 全量 / 浏览器类）单独放宽；同时看门狗报现场时
   要把"最后一次工具调用是什么"打出来，免得我拿到现场还得猜。
6. **读 detach 出来的日志要显式指定 UTF-8**。`wb-902.dispatch.log` 是**正经 UTF-8**（我按字节验过：
   开头是 `5b 4f 4b 20 5d 20 e5 89 8d e7 bd ae`），但 PowerShell 的 `Get-Content` 默认按 GBK 读 →
   同一份文件读出来是「`[OK ] 鍓嶇疆妫€鏌ュ叏杩囷紙瑙勬牸鍦?`」这种乱码，**看着像文件坏了**。
   过夜起来读日志的人（或下一个我）极容易据此误判"子进程把编码搞坏了"。
   规避：一律 `Get-Content -Encoding utf8`（或我这种 `[System.IO.File]::ReadAllText(..., UTF8)`）。
7. **工人会在复盘里写错可核对的事实**。B 把原型文件名写成了"带 `.proto` 的那个"
   （真名是 `gates/diag/wb_dash.py`，那个 `.proto` 名字**从来不存在**）。它的技术描述全对，
   就这个名字错。收口时我改了，并在那份复盘里留了记录。教训：**收口不是签字，是逐条核对可核对的
   东西**（文件名、数字、函数名）—— 这正是台账里 `text:` / `file:` 证据断言存在的意义。

## 5 副产品：状态面板（T-G93）

并发之后**必须**能看见"谁在动" —— 于是有了 `tools/wb_dash.py`（零依赖本地面板，默认
<http://127.0.0.1:8787>）：状态四档 / 多卡多树 / 只读。它读的就是派活器落的那些状态文件
（`wb-<卡>.jsonl` / `.heartbeat.txt` / `.verdict.txt` / `.session.txt`），所以**面板不引入新真源**。
详见 `复盘/wb_dash转正-T-G93.md`。

## 6 还没保证的（如实写）

- **看门狗的寿命 = 那个进程的寿命**：`--detach` 之后是子进程自己带着看门狗，被系统杀掉就没人盯
  （T-G91 已记，仍待解决）。
- **收口没有并发**：两张卡同时落地时我要排队收尾；这次是 A 先落地、B 后落地，正好串上。
- **面板只报"在不在动"，不判断内容对不对** —— 那是主控复核的事。
- **派活器的 print 在非 TTY 下是块缓冲**：后台 job 的输出看着像空的（心跳因此早就改成落盘）。
  仍应加 `flush=True` / `-u`，否则 `--detach` 的父进程输出在某些情况下会晚到甚至丢。
- **没有"工人之间"的通信**：两条卡若有依赖，只能靠我串。
