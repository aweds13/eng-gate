# 独立实现的最小 MCP 客户端（T-G78）—— 换个实现来读，才算验过协议

> 一句话：服务端是 T-G65 手写的，`tests/test_mcp_line.py` 也真起子进程走过 stdio ——
> 但那两边的**作者、假设、读法是同一套**。这一张卡写**另一个实现**去读它：
> `tools/mcp_client.py`（**不 import 本项目的任何东西**，源码级护栏钉着），
> 而且**故意按最挑的读法**判：`id` 必须原样含类型回来、`required` 每项都得真在 `properties` 里、
> 回话必须是 UTF-8 字节、`tools/call` 必须有 `content[0].text`。
> 2026-09-25；分支 `line/impl-v1`；台账 `T-G78`；`src/` **一行没改**。

---

## §1 它补的盲区（为什么"自家脚本 + 自家服务端"不算验过）

T-G74 的现场最清楚：服务端的 stdout 中文是 **GBK**（规范要求 UTF-8），而当时的"真 stdio 测试"
起子进程时带着 **`-X utf8`** —— **正好把要验的那件事关掉了**，一路全绿。
T-G69/T-G71 那族写着同一句话：**判据自己会在错的地方替被测者兜底**。

同作者、同假设的两份代码之间，这种兜底是**看不出来**的。要跳出来只有一个办法：
**另写一个实现**，并且让它**只在规范允许的地方让步**。

| 这一层怎么做的 | 为什么 |
|---|---|
| 不 import 本项目（连常量都不借） | 借一个常量就等于借来一套假设 |
| `id` 用**字符串**（`tf-1`…）并断言类型也要一样 | "整数 id 才管用"这种假设，自家测试里永远看不见 |
| 回话先按 **UTF-8 解字节**，解不开就判违规 | T-G74 就是编码上的病；"换个编码再试试"会把病盖住 |
| `required` 里每一项都要**真的在 `properties` 里** | 规范的一致性要求；自家生成的 schema 很容易漏 |
| 结果按 `{content:[{type:text,text}], isError}` 严格判 | 少一样客户端就没法用，而这正是"兼容"的含义 |
| 一条消息必须**以换行结束** | stdio 的 framing 就是"一行一条"，不是"看着像 JSON 就行" |

## §2 验收（8 条 pytest，全走真子进程真 stdio）

`tests/test_mcp_client_independent.py`：

1. ★ **它真的独立**：源码里**没有**一条 import 提到本项目、没有服务端路径、也不是把服务端源码抄一份；
2. **握手**：协议版本 `2025-06-18`、`capabilities.tools` 在、`serverInfo.name == timeflow`、
   **stderr 干净**（协议消息不许混进日志）；
3. **工具清单**：≥14 个只读工具、关键的几条（today/tasks/week/board/sync）在、
   **写工具一个都不列**、`readOnlyHint` 全是 true，且逐条过客户端的 schema 自检；
4. **字符串 id 原样回来** + 不认的方法回 `-32601`；
5. ★ **反空转（两条）**：拿两个**故意坏掉的服务端**证明客户端的判据真的会咬 ——
   ① 把字符串 id 改成整数 → 客户端判"id 没有原样回来"；② `required` 写一个 properties 里没有的参数
   → 客户端当场拦下。**没有这两条，"通过自检"可能只是"它什么都没查"**；
6. **写工具默认关**：没开开关时调 `add-task` → `-32602`，消息里写着"写操作"与怎么开；
   **被拒的写操作不许留下库文件**；
7. ★ **中文一字不差**（T-G74 的独立复核）：开写后用**这个客户端**建一条中文标题的任务，
   再从另一个只读工具读回来，标题逐字相同；
8. **工具失败如实报**：库不存在时服务端回 `isError`（不是 JSON-RPC 错误），客户端按**退出码 4**
   报出来，且只读命令不许把库建出来。

## §3 它同时是"给人用的小工具"

```
python -X utf8 tools/mcp_client.py handshake        # 握手一眼
python -X utf8 tools/mcp_client.py list             # 工具清单（逐条自检 schema）
python -X utf8 tools/mcp_client.py call today       # 调一个只读工具
python -X utf8 tools/mcp_client.py call add-task --arg title=写点什么 \
       --server-arg --allow-write --server-arg --db <临时库>
```

退出码是机器可读的那半：`0` 正常 / `2` **协议违规**（客户端判它不合格）/ `3` 服务端起不来 /
`4` 工具执行失败 / `5` 服务端回了 JSON-RPC 错误 / `6` 超时。
服务端命令三选一：`--server-json` > 环境变量 `TIMEFLOW_MCP_SERVER`（JSON 数组）> 默认
`timeflow mcp`（就是 DSH / Claude Desktop 那种配法）。

**边界（不假装）**：

- 它**不是**第三方 MCP SDK，也**不能替代**"在真客户端里接一次"那条人工项 —— 它证明的是
  "stdio + JSON-RPC 这一层按规范能不能被另一个实现读懂"，不是"某个具体客户端的 UI 里好不好使"；
- 只做 **stdio**：没有 resources / prompts / sampling / 进度通知，没有 HTTP/SSE；
- 超时靠后台读线程 + 队列（Windows 上管道没法 `select`）—— 一个验证工具自己卡死是最糟的形态。

## §4 顺带更正一句**代码里的**诚实边界（T-G74 留下的那段）

`src/timeflow/mcp/server.py` 的模块注释原写：

> 我们**没有**第三方 MCP SDK…… 验的是"**我们的客户端脚本 ↔ 我们的服务端**"

这句话在 T-G78 之后不再准确（客户端已经不是"我们那套脚本"了），改成：

> 第三方 SDK 仍然没有；但**协议这一层有一个独立实现的客户端在盯**（`tools/mcp_client.py`，
> 不 import 本项目）—— 真正没验的还是"**某个具体第三方客户端**里接一次"。

> 与 T-G67/T-G77 那族同一条规矩：**文档里的话要跟着事实走** —— 但这一句是"把已经变强的说成还弱"，
> 方向相反、同样要改。
