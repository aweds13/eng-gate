## 二、为什么 `SR-F2.6b` 原来是写错的（顺手记一条教训）

- **规格原话**：「未绑定专注也计投入（手动补记）；跨端同 id 去重（**来源标记** + LWW）。」
- **台账原 gaps**：「「未绑定专注也计投入」有手动补记入口；**来源标记未落库**；跨端推拉传输也未做。」
- **实际核出来的**（逐条到代码）：
  1. `facts.source` **一直在写**（`desktop` / `internal` / `ai`，五处写入点：`focus/timer.py`、`memo.py`×4、`review.py`×3、`tasks/manager.py`、`api/app.py`）；
  2. `focus_sessions.device_id` 在写（**哪台机器在计时**）；
  3. 同步包每行带 `device_id`（`syncpack._pack`），导入状态里记 `from_device`；
  4. `sync.py` 的「同 id 去重」有 docstring 与用例钉着（`test_sync_pack_line.py`、`test_offline_phone_line.py`）。
- **所以缺口只在"逐条"那一层**：桌面写的普通事实（任务完成/习惯/备忘/复习）`facts.device_id` 是 NULL；
  两台机器互导后想**逐条**追溯"这条谁写的"，只能看**包一级**的导入日志。而用户定：**这个不做**。
- **教训（建议以后写 gaps 遵守）**：`gaps` 里的**否定句**（"未落库""无 X 字段""未做"）最容易过期 ——
  它描述的是"当时没有"，而"当时"会变。写的时候尽量带 **日期 + 哪一层 + 谁定**，
  例如「2026-09-23 核：`facts.source` 已落，仅"逐条 `device_id`"未落（用户定不做）」。
  机器能自动查的只有"**子卡全 done、母条仍 todo**"这一类（T-G18 §六 第 2 条）。

## 三、两条新能力的设计（都还没写代码，等你开工）

### 3.1 `T-G20` · 跨端实时专注（`SR-F3.4`；口径 = 实时启动 + 结束时同步）

**目标**：电脑或手机任一台开始专注 → 另一台**当场**看到「另一台设备正在专注（任务 X · 已 12:34）」
并进入专注态/勿扰；**结束不做实时推**，记录各自入库，之后走已有的同步包通道合并。

**为什么这么切**：跨端要传的东西分两类 ——
**状态**（谁在计时）只需要一条**只读查询**，不需要写库、不需要新表；
**数据**（`focus_sessions` 记录）已经有 ③①② 那套通道（同步包 / 手机离线记 / 局域网直连 / 手机直传），
所以"结束时再同步"就是**什么都不用新做**。

**做法草案**：
1. **后端**：`GET /api/focus/active` 已存在（返回 `task_id` / `kind` / `started_at` / `device_id`）。
   局域网配对之后这个路由天然可访问 —— **不需要新表、不需要新字段**。
   （真要加，只是给它加一个"对面设备还在不在"的说明性字段，属可选。）
2. **前端**：计时器加一个**只读镜像态** —— 轮询对方的 `active`（建议 **10 秒**一次），
   发现对面在计时就显示镜像卡；自己开始计时时对面同理。
3. **勿扰**：镜像态即本机进入专注态（沿用现有专注态样式与白名单/勿扰设置，不另造一套）。
4. **先写死的边界**：只在**同一局域网且已配对**时有效；明文 HTTP（与局域网那道门同一档）；
   轮询失败/对方不在线 → **不报错、静默退回本机态**；**不做**云端、不做离线队列、不做"镜像态停对面的计时"。

**需要你点头两点**（都很小）：轮询间隔 10 秒可以吗 / 镜像态**不能**停对面的计时（我建议不能）。

### 3.2 `T-G21` · AI 写事实回报进展（N46 × N23；口径 = 你选的方案 3）

**目标**：AI 干完/干到一半 → **记一条事实**（`source=ai`、只追加、可撤销）；
**AI 仍然改不了你的任务字段、删不了任何东西**。这样"AI 当执行者"这条链通后半段，
而"不改不删"这条约定**一字不用松**（松的只是"新增"的范围：新增的是**事实**，不是任务）。

**做法草案**：
1. **新事实 kind**：`task.progress.reported`（`subject_id` = 任务 id，`value_text` = 一句话，
   `extra` 记 `actor`/`device`），与现有 `task.attempt.failed` 同族。
2. **新路由**：`POST /api/ai/tasks/{id}/progress` —— 挂在现有 AI 组（**默认关**、本机来源、`source=ai`）。
   **不开**改状态/改字段/删除的任何路由。
3. **解读层**：任务卡片与详情显示「AI 报告：…（时间）」；**不自动改 `status`**。
4. **可撤销**：加一条 `task.progress.retracted`（与 `review.undone` 同款：追加、不删原事实），
   而不是去实现 `revision`/`supersedes` 那套预留机制（MVP 不做修正机制，这条写在架构决策里）。

**需要你点头两点**：① "AI 说完成了要不要**自动**标完成"（我建议**不要** —— 你看到再勾，
数字才可信，也是这个项目一贯口径）；② 约定层措辞（§3.3）。

### 3.3 约定层那行（`docs/specification/conventions.md` 第 34 行）—— **待批措辞**

**现文本**：
```
- AI 接口（N23/N46）：第一版只读+新增，不改不删；写/改/删后置。（N23/N46）
```

**建议改成**：
```
- AI 接口（N23/N46）：第一版**只读 + 新增**（新增含"记一条事实"）；**不改不删用户的数据** ——
  AI 的进展以**事实**回报（`source=ai`、只追加、可撤销），状态由解读层算；写/改/删用户数据仍后置。（N23/N46）
```

**为什么这一改就自洽**：N46 要的"回报进展"落地成**事实**，而事实只追加 → 与你手动操作冲突的可能
**天然不存在**（也就解释了原来那句"避免和你手动冲突"的担忧，其实靠"只写事实"就解决了）。
`conventions.md` 是你拥有的文档，**我不擅自改正文**；你说"改"我就改（这是这一行唯一需要你过的关）。
