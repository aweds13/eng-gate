## §1 要修什么（事实 + 可复现证据）

`T-G79`（今天清单拖拽排序）的文档与提交信息写着：拖到自己前面、已在头尾按 ↑↓ 这些**幂等动作
"原地不动且不写库"**。**这句是错的。**

复核证据（两处独立）：卡 001 的探针 `gates/diag/wb001_probe.py`（33 条 check，3 条 FAIL）；
主控的探针 `gates/diag/probes/myday_noop_write_check.py` —— 复现得很干净：

```
① 调用前：3 行 myday_rank 全是 None
② 拖到自己前面 → HTTP 200，**3/3 行被改写**：v1→2，且 rank None→1 / None→2 / None→3
③ 已在最前按 ↑ → 同样 3/3 行被改写
结论：『幂等 = 不写库』站不住（幂等动作确实在写库）
```

**根因（自己读代码确认）**：`place_myday()` / `move_myday()` 的**第一句**都是
`items = _myday_sequence(conn)`，而 `_myday_sequence()` 会把今天清单**每一行**都
`_write_myday_rank(conn, item.id, i)`（`version + 1`）—— 于是**任何**调用（包括空转）
都会整表重写一遍，并把 `NULL` 变成显式 `1..N`。

**为什么这是真缺陷**（不是"多写几行无所谓"）：

- 「没拖过 = NULL、排在后面」这个语义**被一次空转抹掉** —— 之后的顺序规则与"进今天排最后"的
  感觉会变（新来的仍然是 NULL，但你已经分不清哪些是"没拖过"）；
- 跨端合并按 `version` 判谁新（`syncpack`）：空转把 `version` 抬高却不改 `updated_at`，
  真实改动更容易**输给**这些空写（卡 001 的边界 C 指出的那类风险）。

## §2 修完必须成立的口径（验收就照这几条写）

1. **幂等动作零写库**：拖到自己前面 / 已在头尾按 ↑↓ → **被改写的行数必须是 0**
   （`version` 不变、`myday_rank` 不变）。
2. **不许"冻结 NULL"**：任何调用都不许把 `NULL` 改写成显式序号 —— 除非那条任务**真的换了位置**。
3. **只在顺序真变时写，且只写真的变了的行**（不要整表归一化）。
4. **排序语义一个字不改**：拖过的按 `myday_rank` 升序在前、没拖过的（`NULL`）按老口径
   （截止日 → 优先级 → 创建时间）垫后；进「今天」= `NULL`；离开「今天」= 清空。
5. **接口语义一个字不改**：两键要么给一个要么不给（都给/给空 → 400）；任务不存在 → 404
   **先于**「不在今天」那一步；`myday_rank` **不是 PATCH 可写字段**。
6. **界面一行不改**（本卡不该动 `src/web/**`；若你认为非改不可，**停下来在回报里说明**，不要自己决定）。
