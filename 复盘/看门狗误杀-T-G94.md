# 看门狗会误杀正常的长工具调用（T-G94 = 外包卡 005）

> 一句话：看门狗判「卡死」的口径是「**日志静默 ≥ 480 秒 → 掐掉整棵进程树**」，它假定
> 「一次工具调用最多几分钟」。**实测不是** —— 于是一个正常的重门禁会把工人自己送上断头台，
> 而且掐的理由写着「卡死」、报告里没有它当时在跑什么。这张卡把阈值改对。

## 1. 病灶（真机撞到的，不是猜的）

- 主树全量 `python -X utf8 scripts/run_gates.py` 一次约 **4 分钟**（其中 `pytest` 一项就 110 秒）；
- 冷缓存的 worktree 里 `ui_flow`（要起浏览器）能到 **十几分钟**。

这两件事都**大于 480 秒**。也就是说：**工人只要在卡里跑一次重门禁，就会被自己的看门狗掐掉**——
现在的绕法是「工人不许跑全量门禁」这条**规矩**（`复盘/外包-卡表与规矩.md` §16）。规矩只对
「卡里不跑门禁」的活有效，**不是阈值对**。而且旧报告只说「X 分钟没有新事件」，主控拿到现场
还得自己翻 log 去猜「它当时在跑什么」。

## 2. 关键发现：静默 ≠ 卡死，因为「在跑什么」是可测的

主控已在**真 log** 上验过形状，工人直接用：

- agent 的事件流里**每个事件都带 `__timestamp`**（**两个下划线**，值是 ISO-8601 UTC 字符串，
  例如 `2026-09-26T02:39:42.910Z`）；
- `assistant` 事件里的 `tool_use` 块与 `user` 事件里的 `tool_result` 块**一一配对**
  （`id` ↔ `tool_use_id`）。

于是「某次工具调用跑了多久」「现在有没有调用在飞」都是**可测的**，根本不用猜。

## 3. 修法（只改「判卡死」这一件事）

三件：

1. **`inflight_tool(lines) -> (工具签名, 已跑秒数) | None`** —— 数 `tool_use` 与 `tool_result`，
   **没配对的**就是正在跑的（多个在飞时取跑得最久的那次）；没有在飞的返回 `None`。秒数用那个
   `tool_use` 事件的 `__timestamp` 算到「现在」。
2. **在飞就不按普通阈值判卡死** —— 静默是**预期**的，用新常量 `BUSY_STALL_SECONDS`
   （**1800 秒 = 30 分钟**），只有超过它才判卡死。
3. **按实测耗时自适应** —— 新增 `tool_durations(lines) -> list[float]`，算**每一次已完成调用**的
   耗时；阈值改为 `max(底线, 2.5 × 已完成调用里最长的那次)`。跑过一次 12 分钟的 `ui_flow` 之后，
   看门狗自动知道这活儿能跑 12 分钟（取**最长**而不是平均、乘 2.5 是留余量：宁可晚掐、不要误杀）。

★ **报告必须带现场**：判卡死时把「在跑什么 / 已跑多久 / 历史最长一次 / 这一次用的阈值」全写进
原因；心跳末尾**追加**「在跑 <工具>」（现有字段一个不删）。

```python
def stall_threshold_seconds(*, stall_seconds, inflight, durations) -> float:
    base = float(stall_seconds)
    if inflight:
        base = max(base, float(BUSY_STALL_SECONDS))      # 在飞 → 底线上抬到 30 分钟
    longest = max(durations) if durations else 0.0
    return max(base, TOOL_DURATION_FACTOR * longest)      # 再按历史最长 × 2.5 自适应
```

两种放宽**只叠加放宽、不收紧**；两样都没有 → 就是 `stall_seconds`（**老口径，一个字没变**）。

## 5. 真机证据：桩命令证明「长工具调用不再被误杀」

探针（**不进仓库**，`d:/tmp/t094_probe.py`）：桩吐一条 `tool_use` 后**真睡 500 秒**，
让 `run_worker()` 真去跑它。★ **如实写**：为了让证据别等太久，这里把 `--stall-seconds` **压到 20 秒**
（阈值是可配的）—— 真机是「480 秒底线 + 在飞 1800 秒 + 自适应」，20 秒只是同一套逻辑的压缩演示。

```
=== new_inflight（桩 带 __timestamp；stall=20s 压缩阈值；timeout=40s）===
  退出码=1  实际耗时=40.6s
  判决：超时：40 秒到了（`--timeout`）→ 成功: 已终止 PID 84376 (属于 PID 87596 子进程)的进程。
        （原始那半句是 GBK 乱码 —— taskkill 的输出，见 §6-⑥）

=== old_no_stamp（桩 不带 __timestamp；stall=20s 压缩阈值；timeout=40s）===
  退出码=1  实际耗时=20.7s
  判决：卡死：0.3 分钟没有新事件（这一次的阈值 0.3 分钟；没有在飞的调用；历史最长一次调用：没有记录）

=== 判卡死报告（在飞用例，静默 1810s > 30 分钟底线）===
  新口径：卡死：30.2 分钟没有新事件（这一次的阈值 30.0 分钟；在跑 Bash(command=python -X utf8
          scripts/run_gates.py)（已跑 33.3 分钟）；历史最长一次调用：没有记录）
  旧口径：卡死：10.0 分钟没有新事件（这一次的阈值 8.0 分钟；没有在飞的调用；历史最长一次调用：没有记录）
```

读法：**同一份静默、同一个压缩阈值**——

- 桩**带** `__timestamp` → 认得出「在飞」→ 20 秒**不掐**，一路跑到 `--timeout 40` 才报「超时」（40.6s）；
- 桩**不带** `__timestamp` → 退回保守行为（阈值不放宽）→ 同样静默 **20.7 秒**就判「卡死」。

最后那两行是**判卡死报告文本**的对照：新口径报出「在跑 `Bash(command=…)`（已跑 33.3 分钟）」与
这一次用的阈值；旧口径（不给 `lines`）只说「10.0 分钟没有新事件」。

## 6. 边界（如实写）

1. **只改「判卡死」这一件事**：`repeat_signal()` 的空转判据（T-G88 那道）、`kill_tree()`、
   `cap_verdict()`、`finish_verdict()`、`--max-turns` 口径、`detached_argv()` 与 `--detach` 整条路
   （T-G92 刚修完）、模型默认值、`--autocompact 1m`、超时默认 7200 —— **一个字没动**。
2. **不给 `lines`** 调用 `watchdog_verdict()` 就是**老口径**（阈值 = `stall_seconds`）—— 这一条
   留作对照（老代码/老测试的调用方式仍然成立）。
3. **缺 `__timestamp`（半截 log / 对方改格式）→ 一律退回保守行为**：不放大阈值、不抛异常。
   代价是读不到时间戳时宁可早掐一次 —— 但**不会**因为读不到时间戳就把卡死判成健康。
4. `tools/wb_dash.py` 的状态四档仍写「≥ 480 秒 = 可能卡死」，与本卡的新口径**还没对齐**
   （卡的白名单不许动它）—— 面板档位要跟上得**另立一张卡**。
5. 真机证据里的「20 秒」是**压缩后的可配阈值**，不是真机行为；真机是「480 秒底线 +
   在飞 1800 秒 + 自适应」。
6. 顺带**观察到**（**既有**行为、卡明令不许动 `kill_tree()`，未修）：`kill_tree()` 用 UTF-8 解
   Windows `taskkill` 的输出，而这台机器上它是 GBK → 掐进程成功但那句回话是乱码。
7. `tools/wb_status.py` 一行没动（新代码复用它的 `_clip` / `_tool_line`，不写第二份渲染）。
