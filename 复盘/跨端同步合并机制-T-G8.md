# 复盘 · 跨端同步的合并机制（T-G8，场景 ③）

> 性质：**功能落地 + 口径复盘**（为什么要先做 ③ / 包长什么样 / 怎么判谁新 / 删了怎么办 / 边界与证据）。
> 上游：`复盘/口径定案-待定清单.md` §3（用户 2026-09-21 定：**③ → ① → ②**）+ N25 / SR-NF17 / SR-F9.2。
> 结果：**走文件**的跨端同步能用了（导出同步包 → 拷过去 → 预览 → 导入）；
> 走网络的 ①② 仍未做（**分开报，不拿一个布尔糊过去**）。

---

## 一、为什么先做 ③（合并机制），而不是先做"手机能连上"

你 2026-09-21 定的顺序是 **③ 合并机制 → ① 手机离线记 → ② 同 WiFi 直连**，理由是依赖关系：

- ① 的手机端导出的是**一个同格式的包** —— 没有包格式，① 就没有东西可导出；
- ② 直连传输的仍然是**同一套合并规则** —— 先把"合起来会怎样"定死，传输层才是纯管道；
- ③ 只要**两个库**就能立刻验证（不需要第二台设备、不需要网络），错了当场看得见。

所以这一卡只做"**包 + 合并 + 导出/导入**"，一行网络代码都没写。

## 二、包长什么样（也是给 ① 的地基）

一份 UTF-8 JSON，默认写到**数据库同目录**（与 `.bak-*` 备份放在一起，用户找得到）：

```json
{
  "format": "timeflow-sync", "format_version": 1, "schema_version": 17,
  "device_id": "a1b2c3d4e5f6", "created_at": "2026-09-22T21:00:00",
  "tables": { "tasks": [ … ], "facts": [ … ], "memos": [ … ], … },
  "tombstones": [ { "entity": "tasks", "entity_id": "…", "deleted_at": "…" } ],
  "counts": { "tasks": 3, … },
  "note": "同步的是你的数据；不含本机设置…；导入不会删你本地的任何东西。"
}
```

文件名 `sync-<设备号>-<时间戳>.json`：自带来源与时间，拷来拷去不会认错；
同一秒连点两次导出会加 `-2`（**不覆盖上一份** —— 你还想拿它做对照）。

**包里没有什么，和有什么一样重要**：

| 不进包 | 为什么 |
|---|---|
| `app_settings` | 导出目录 / Vault / AI 开关 / 口径开关都是**这台机器的事**；带过去会把对方设置改掉 |
| `sync_logs` | 本机的冲突历史（合来合去会互相污染） |
| `schema_version` | 结构由迁移管，不由包管 |

## 三、怎么判"谁新谁旧"

**version → updated_at**（`sync.newer_is_win`，沿用既有语义）：
先比版本号，版本相同再比时间；内容完全一样就直接跳过（不算冲突）。

麻烦在于：**全库只有 `tasks` 有 `updated_at`/`version`** —— 别的表改了名字、推进了复习间隔、
改了成绩，库里**没有任何痕迹说明它变过**。于是 v17 补两件事（一个声明式的地方管全部）：

1. **六张会被改的表补 `updated_at`**（`habits`/`groups`/`course_assessments`/`review_items`/
   `team_assignments`/`feedback_logs` + `memos`），由**触发器**在每次 INSERT/UPDATE 后写当前时间。
   为什么用触发器而不是逐个改代码：更新入口散在五六个模块里（十几处），**靠"记得每处都加"必然漏**
   —— 这正是 T-G9 刚教过的（判据要能自证）；一个声明式的地方管全部，**将来新加的更新路径也自动被管住**。
   老行回填 `COALESCE(created_at, 现在)`（**不猜**：能考证的最早时间就是它）。
   **`tasks` 故意不挂触发器**：它自己维护 `updated_at` + `version`，而且有一条刻意的例外 ——
   调整「进行中」顺序**不动** `updated_at`（T-F1："换顺序不是内容变了"）。这条被测试钉住。
2. **删除墓碑 `sync_tombstones`** + 各表 DELETE 触发器（见下节）。

## 四、删掉的东西怎么办（这一卡最容易做错的地方）

`tasks` 的常规删除是**软删除**（状态写成「已删」），走 LWW 就没问题。但有些是**硬删**：
彻底删除任务、删备忘、删成绩/考核项、取消打卡、把任务移出分组、删习惯/分组。
没有墓碑的话，"在 A 上删掉的东西"会被 B 的**旧包原样带回来** —— 用户只会觉得同步在骗他。

于是：

- **本地有墓碑 → 不复活**（旧包里的那一行跳过，报告里写"按墓碑跳过 N 行"）；
- **远程墓碑 → 记下来（好继续传给下一台）**，但**不删本地已有的行** ——
  这是 **v1 的明确边界**：**导入永不删你的数据**。宁可"两边暂时不一致 + 如实告诉你"，
  也不要"一个旧包把你本地的新东西删了"。
- 代价（如实写在这里）：**删除不会跨端传播**。你在 A 删掉的，B 那边还在，只是 B 也不会再被旧包
  复活它。要"删除也传播"得给墓碑加上时间比较并允许导入侧删行 —— 那是下一张卡（T-G8b），
  属产品决策（要用户点头：导入是否允许删本地数据）。

## 五、三类表，三套规则（不能一刀切）

| 类别 | 表 | 规则 |
|---|---|---|
| **LWW 行** | tasks / habits / groups / course_assessments / review_items / team_assignments / feedback_logs / memos | 内容一样→跳过；远端较新→覆盖；否则保留本地（两种都逐条记日志） |
| **只增行** | facts / focus_sessions / courses / grades / ledger_entries | "发生过的事/建过的东西"：**只插不改**；同 id 内容不同→只记冲突 |
| **关系行** | task_groups / habit_logs | 只有"在不在"（没有时间可判新旧）：缺则插（除非被墓碑拦住） |

**事实（facts）只增不改**这一条最关键：账本（债务/投入/复习/产出/习惯）全部由事实派生，
所以"事实合上了"就等于"**两边的账目一致**" —— 这一点有测试直接对着 `ledger.summary()`
逐字段比（不是只看行数）。

## 六、不静默（"不静默覆盖"这条规格要落到实处）

每次导入都把**每一条决定**记进 `sync_logs`：`result`（覆盖 / 保留本地 / 按墓碑跳过 /
远程已删（本地保留））+ 一句 `note`（差在哪，最多三处）。v17 给 `sync_logs` 补了 `result`/`note`
两列 —— 原来只有两个时间戳，**看不出这次是覆盖了还是保留了本地**，等于"日志写了但说明不了什么"。

界面上的顺序也照这条走：**先预览（`dry_run`，一个字节都不写）→ 二次确认（把"新增/覆盖/冲突"
写在确认框里）→ 才真导入**。预览与真导入**是同一套判断**（先规划 `plan_merge` 再执行），
所以不会出现"预览说一套、执行做另一套"。

## 七、证据

- **单测 30 条**（`tests/test_sync_pack_line.py`）：包的身份与"不含什么"、坏包四连拒
  （不存在 / 非 JSON / 不是我们的格式 / 版本比我们新）、自己导给自己被拒、LWW 两向、
  只增行不被覆盖、关系行缺则插、**墓碑防复活**、**远程墓碑不删本地**、`dry_run` 不动库、
  重复导入幂等、老包容错、六张表的触碰、`tasks` 的刻意例外、触发器的声明式与幂等、
  五种硬删都留墓碑、**app_settings 不跨端**、API 三条路由 + 跨站 403 + 状态只报事实。
- **真机自检 10 条**（`tools/web_live_check.py`，真服务上真导出/真预览/真导入）：
  能导出、报告含条数与设备号、状态分"文件/网络"两笔、写明不含本机设置、坏路径 400、
  跨站 403、自己导给自己 400、**预览不动库**、导入后数据真过来、**导入没删本机任务**。
- **DOM 探针「跨端同步 1/1」**：设置页真的渲染出三个入口 + 设备号 + 上次导出/导入读数 +
  "导入不会删你本地的任何东西"这句。
- **测试逼出来的两个真 bug**（都已修，且都加了护栏）：
  1. **主键不能假设都叫 `id`**：`feedback_logs` 的主键是 `date` → 原先整张表被**静默跳过**
     （用户手写的每日反馈跨端凭空消失，还没报错）。修好后补了一条**拿 `PRAGMA table_info` 对账**
     的护栏（`PRIMARY_KEYS` 与真实主键必须一致），以后加表/改主键会立刻红。
  2. **`dry_run` 会偷偷写设备号**：预览第一次跑时 `device_id()` 顺手把设备号落进了 `app_settings`
     —— "预览一个字节都不写"当场破功。改成 `peek_device_id()`（只看不写）。

## 八、边界与后续（诚实清单）

1. **删除不跨端传播**（见 §四）—— v1 明确取"保守"：导入不删你的数据。要改是产品决策（T-G8b）。
2. **解绑类关系同样不传播**：把任务移出分组、取消打卡，在另一台**不会被撤销**（那边还在），
   但**也不会被旧包加回来**（墓碑挡着）。
3. **时间戳精度是秒**：同一秒内两边都改了同一行 → 时间打平，规则是"**保留本地**"，
   并如实记一条冲突（不是随机选一个，也不是偷偷覆盖）。
4. **包是明文 JSON**：里面就是你的任务/备忘/复习内容。所以它写在**本机目录**、**不会自动上传**；
   拷给别人之前请自己判断（SR-NF16 隐私那条）。将来 ① 走网络时要有鉴权（那是 ② 的事）。
5. **没有增量**：每次导出都是全量（当前规模=几 MB 级别，够用）。数据大了要改增量，
   属性能问题（SR-NF18 那套基准可以量）。
6. **`device_id` 存在 `app_settings`**：它是"本机"的东西，所以**不进包**（进包的是包里那个字段值，
   不是本机设置）—— 两台机器的设备号必然不同，这也是"自己导给自己"能被拒的依据。
