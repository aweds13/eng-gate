# 验证分层的行业做法（外部证据 + 我们要改什么）

> **为什么要这份**：2026-10-03 我们按用户令把收口从「**每笔全量门禁**」改成「**受影响的门 + 每天一次全量兜底**」。
> ★ 用户同时要求：「**想一下行业有没有相关的，通过文献的搜索，看看还有什么调整的方法，然后把这个东西纳入我们的软件工程执行框架上**」。
> 本文件是那次检索的结果（**带真实 arXiv 编号**，全部来自 DeepXiv 的带引用问答），逐条对我们，最后给出**要折进框架的条目**。
> ★ **一句话结论**：我们要走的方向与行业一致（**增量选择 + 兜底全量**），但**文献里有两处硬读数直接改我们的做法**：
> **① 优先提并行度/批处理，而不是先砍子集**；**② 选择面必须报「选择率与召回」，不能只报「跑了几道门」**。

## 一、我们遇到的流程问题（现象，都是这一晚咬出来的）

| # | 现象 | 代价 |
|---|---|---|
| P1 | **每笔收口跑全量门禁**：pytest 2066 条 → 4 worker 250 秒 / 1 worker **620~700 秒** | 每笔 12 分钟；19 张卡就是小时级空耗 |
| P2 | **门 × 输入表有洞**：`render` 真读 `tools/render_signatures.json`、`web_live` 真跑 `tools/phone_check.mjs`，两个文件都不在门的输入表里 ⇒ 改它们时增量会**跳过这两道门** | 「看着绿其实没查」 |
| P3 | **空集绿灯 / 部分跑冒充全量**：退出码不可信、`--no-cov` 绕过覆盖闸、旧判决冒充当前 | 假绿 |
| P4 | **复用缓存会 stale**（`gates/reuse.json`） | 假绿 |
| P5 | **flaky 与「与本次无关的失败」混在一条读数里** | 逃逸率被高估 / 真失败被掩盖 |

## 二、行业/文献怎么说（逐条对我们）

### 2.1 变量一：**并行度/批处理**（★ 最该先吃的一条）

| 证据 | 读数 | 对我们的意思 |
|---|---|---|
| **Accelerating CI with Parallel Batch Testing** [arXiv:2308.13129] | 并行批处理（BatchAll / TestCaseBatching）分别减少最多 **91% / 81%** 的机器数，**反馈时间不增** | ★★ **「合并时跑全量」的成本有第二条解法：批处理与并行度**。我们那条「落地窗口不跑工人 ⇒ 默认 4 worker，250 秒 vs 700 秒」**正是这条** ⇒ 它应该是**默认策略**，不是临时手段 |
| **CI at Scale: Lean, Green, and Fast**（Uber SubmitQueue）[arXiv:2501.03440] | 投机式 CI + 构建时长预测 + BLRD：资源 −53% / CPU −44% / P95 等待 −37% | 排队与调度本身是**一等优化面**（我们已有「门禁在跑 ⇒ 拒派」的守卫，可再进） |

### 2.2 变量二：**选择面**（我们叫「受影响的门」）

| 证据 | 读数 | 对我们的意思 |
|---|---|---|
| **Predictive Test Selection**（Google 单体仓）[arXiv:1810.05286] | 选择率 **<0.33**；单测失败召回 **>0.95**、坏变更召回 **>0.999**；机器减半。选择集 = `LikelyFailing ∪ HighlyRanked` | ★ 选择面要**报两个数**：**选择率**（省了多少）与**召回**（漏了多少）；只说「跑了几道门」不够 |
| **T-TS**（生产部署 2025）[arXiv:2509.10279] | 只选 **15%** 的测试 ⇒ 检出 **>95%** 的失败；流水线快 5.9×；选择率 0.8%→15% 时检出率 26%→95% | ★ 精度/召回是**可调旋钮**，要留痕「这一趟拧到哪」 |
| **NodeSRT**（Node.js）[arXiv:2104.00142] | **方法级**选择，比工业标准快 250%、精度高 450%，声称 100% inclusiveness | ★ **粒度越细越安全**：文件级依赖图**不安全**（动态语言尤甚） |
| **Ada 混合影响分析** [arXiv:1606.04568] | 静态依赖 + 动态耦合混合 ⇒ 测试执行减 **97%** | ★ **动态读数（真读了哪些文件）必须能被登记** —— P2 那两个洞就是「动态读的没进表」 |
| **Jin & Servant 大规模对照**（100 项目）[arXiv:2102.06666] | **测试级**选择/排序平衡最好；**构建级**（跳过整个 build）漏检风险更高 | ★★ **按门/测试粒度切，不许按「整棵树跳过」** |
| **召回 vs 精度** [arXiv:2110.02682] | ★ **召回每降 5% ⇒ 平均少检 7.5 个 bug**（共 420）；**精度影响可忽略** | ★★ 给我们的「**宁多勿漏**」一个量化依据 —— 这条判据不是拍脑袋 |

### 2.3 变量三：**兜底层**（我们的「每天一次全量」）

| 证据 | 读数 | 对我们的意思 |
|---|---|---|
| Facebook PTS [arXiv:1810.05286] | 选择漏掉的，**稳定期（stabilization）会检出**；稳定期检出的故障数远多于选择漏检 | 兜底层**必须存在**，且它的产出要被记 |
| T-TS [arXiv:2509.10279] | 明确「**被漏掉的失败测试仍会在夜间全量运行中被检出**」 | 同上 |
| **工业嵌入式** [arXiv:1905.01928] | 日常只跑 **0.4%~2.0%** 的用例，全量留作**周期性验证**（176 构建 / 6720 改动文件） | 「小步 + 周期全量」在工业里是成熟做法 |
| **Pipeline-aware 优化** [arXiv:2501.11550] | pre-submit：**首个失败出现在已执行测试的前 16%**；post-submit：用 **pass↔fail 跃迁**识别，**5 个 CI 周期内 99.78%** 检出 | ★ 我们的每日全量应当**盯「跃迁」**（昨天绿今天红的那些），而不只是「再跑一遍」 |
| **"Good" and "Bad" Failures**（4 家公司）[arXiv:2504.11839] | **pre-merge 执行频次是 post-merge 的 15 倍**，失败率比 **5:3**；**post-merge 失败 sticky 且被系统性低估** | ★ **合并点就是关键里程碑** ⇒ 「**红着绝不提交**」（用户已明令）在文献上是**对的** |

### 2.4 silent failure：★ 我们咬过的三族，文献里正好是三大主题

| 证据 | 读数 | 对我们的意思 |
|---|---|---|
| **On the Illusion of Success** [arXiv:2509.14347] | **11%** 的「成功」CI 作业被重跑（35% 在 24h 后），吃掉 **48%** 的重跑机时；失败主题 = **制品操作错误 28% · 缓存错误 23% · 被忽略的退出码 18%** | ★★ 这三族**正是我们今晚咬过的**（退出码不可信 / 复用缓存 stale / 派生物没进提交）⇒ 在框架里列为**一等风险**，不是杂项 |
| **无关构建失败** [arXiv:2605.05564] | 77,354 次失败里 **20%** 与本次推送**无关** | ★ 必须区分「我的变更导致的失败」与「环境/他人/flaky」⇒ **否则逃逸率被高估**（P5） |
| **All Green, Still Broken** [arXiv:2606.22475] | 252 个修复中 **44%** 的缺陷**绕过单元测试**，从 runtime / market / flow / system **四个接缝**逃逸 | ★ 与「判据强度 / 接缝」同族：**单元测试绿 ≠ 没坏** |
| **Does Unit-Tested Code Crash?** [arXiv:1903.04055] | 单元测试覆盖与现场崩溃**无相关性** | ★ 别把覆盖率当结论（我们已有覆盖闸，够用即可） |
| **Field failures** [arXiv:1705.07359] / [arXiv:1708.09494] | **70%~78%** 的现场故障源于**真实环境交互**，内部测试本质上测不到 | ★ **兜底层也有上限**，别指望全量把这类抓出来 |

## 三、★ 「检索不到」还是「没有」——**先把话说准**（主控 2026-10-03 16:1x 自我纠正）

★ **初版这里写的是「这一层完全没有实证」。那是错的写法** —— 我把「**我没检索到**」说成了「**没有**」。
这正是本仓天天在治的那个错（`Silent Success`：**「我没看」不等于「我看了且没问题」**）。
⇒ 换词换源重搜之后，**准确的说法**是：

> ★ **在 arXiv / DeepXiv 的检索面内、用 5 组同义检索词都没检到**直接测量这一层的实证；
> 而这类数据**已知主要落在工业报告与 ICSE-SEIP / FSE-Industry 的工业论文**里 —— **arXiv 收录不全**。
> ⇒ 所以「没有」这个词**我们现在没有资格用**；能用的是「**检索面内未见** + **检索词与范围在此（可复核）**」。

**检索词与范围（可复核）**：`categories=["cs.SE"]`，top_k 10–15，逐条试过：
① 原问题逐字（语义）② `nightly build regression test suite fault detection empirical study continuous integration`
③ `pre-submit versus post-submit testing defect detection staged integration` ④ `daily build and smoke test defect detection cost empirical`
⑤ `regression test suite frequency scheduled periodic testing fault detection industrial study`。
★ **术语层面的实测**：`post-submit` 在检索结果里**根本没出现**；`nightly build` 只出现在**构建自动化分类**与**嵌入式工业测试**两处。

★ **这条纠正本身就是一条要折进框架的规范**（见下方 **F10**）：
**凡写「文献里没有 X」，必须附检索词与范围** —— 否则那句话**不可复核**，等于自证清白。

### 3.1 重搜新拿到的（都比我初版写的更有用）

| 证据 | 它给的是什么 | 对我们的意思 |
|---|---|---|
| ★★ **Classification of automatic software build methods** [arXiv:1305.4776] | **权威术语**：构建方法先分 **levered（受令）vs continual**；continual 再分 **scheduled（transitional，周期）vs triggered（strict，事件驱动）**；还有 `quiet time periods` 这个「高负载下队列延迟」的现象名 | ★★ **我们那两个触发有官方词了**：收口 = **triggered (strict) build**；每日全量 = **scheduled build**。⇒ 折进术语表（卡 177 的产物）与框架产物字段名 |
| ★★ **Formalizing Regression Testing for Agile and CI** [arXiv:2511.02810] | 把经典两 build 模型扩展成**时间有序的 build 序列**，定义 **`regression test window`**（时间受限的测试窗口），并**证明**该形式化让「时间/资源/成本 ↔ 覆盖率/缺陷检出」的权衡**可被精确量化**（但论文自己**不报任何实测**） | ★★ **我们那套「受影响的门 + 每天全量」在文献里有形式位置**：增量那一趟 = 一个 **regression test window**。⇒ **F3 的捕获率**正好是这个形式化**缺的那个实测输入** |
| ★ **缺陷检出经济学（综述 + 模型）** [arXiv:1612.04590] [arXiv:1612.03785] | 给出 setup / execution / fault-removal 的成本参数与统一模型，并**明确记录「实证数据有缺口」**（长期效应、跨工件依赖） | ★ 成本侧唯一成体系的工作；它**点名了缺口** ⇒ 我们量 F3 = **填一个被文献点名的缺口**（这话比「我们觉得该量」硬得多） |
| **CI 内优先级排序** [arXiv:1809.00143] | 只靠历史失败知识就能捕获 **57–97%** 的回归故障，不需要额外多样性 | ★ 「一次回归执行能抓多少」的**量级锚点** |
| **Travis CI 的重启与 flaky** [arXiv:2003.11772] | 1.72% 的 build 被重启；重启让 PR 中位合并时间 **16h → 48h** | ★ flaky/重启的**成本**是实打实的 ⇒ 支持 F6/F7 |
| **工业嵌入式：daily cycle 只跑 5–25%** [arXiv:1905.01928] | 每日周期跑的是**子集**（1254 个里的 5–25%），声称不牺牲故障检出 | ★ 「每日跑子集」在工业里是既有做法；★ 但**它也没量「全量比子集多抓到什么」** |
| **用夜间测试数据的工业博士论文** [arXiv:2111.08312] | 数据来自 **nightly testing cycles**（用例/硬件选择、间歇性失败分类、跨版本失败模式） | ★ **夜间数据是有的**，只是**没人把它与提交前子集做差** |
| **构建/回归的形式化** [arXiv:2511.02810] · **分类学** [arXiv:1305.4776] | 两条最好的**引文回溯起点**（forward/backward citation） | ★ 下一步若真要挖，从这里回溯工业论文（ICSE-SEIP / FSE-Industry） |

⇒ **结论（不变，但理由更硬了）**：这一层的实测**我们自己做** ——
**每一次 scheduled（每日）全量跑完，记录「抓到几条失败、其中几条是增量跳过的门本该抓的」= 兜底捕获率**。
★ 它同时是：**F3**、**填 [1612.04590] 点名的缺口**、**给 [2511.02810] 的形式化补第一个实测输入**，
以及用户要的「**把经验沉淀成证据**」。

⇒ **结论（也是本文件最重要的行动）**：**这两处空白我们自己补** ——
**每一次兜底全量跑完，必须记录「这一趟抓到了哪些失败、其中哪些是增量跳过的门本该抓的」= 兜底捕获率**。
这就是把我们的经验变成**证据**（而不是又一条口号），也正是用户要的「沉淀成框架」。

| **F6** | ★ **区分无关失败**：标出「与本次变更无关的失败」（环境 / 他人 / flaky） | [2605.05564] [1810.05286] | 失败读数必须带「是否与本次相关」一栏 |

| **F10** | ★★ **外部证据纪律**：凡写「文献里没有 X」，**必须附检索词与检索范围**，否则**不许写这句话**（不可复核 = 自证清白） | ★ 主控自己的现场错误（本文 §三 的自我纠正） | 文书里出现「没有/不存在 + 文献」而无检索词 ⇒ **红** |
| **F11** | ★ **术语对齐（官方词）**：收口 = **triggered (strict) build**；每日全量 = **scheduled build**；增量那一趟 = 一个 **`regression test window`** | [1305.4776] 分类学 · [2511.02810] 形式化 | 框架的产物字段／术语表用这几个词；旧土话要么并存标注、要么退场 |
