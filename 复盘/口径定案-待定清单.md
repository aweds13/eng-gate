## 1. 任务状态机 + 大任务管理（原「任务存档」，2026-09-21 用户给出完整设计）

**原文依据**：
> **N9** 任务详情与状态机：…状态 = 未开始 / 进行中 / 完成 / **逾期** / 取消 / 归档
> **N10** 大任务→小任务拆解…子任务全完成父任务才自动完成
> **N11** 任务存档：记录当前状态 + **过去做过的尝试（简版）**；详细信息写在本子，任务列表记「笔记名称」
> *为什么*：历史与尝试要可追溯，但不想在任务列表堆长文本。
> **N8** 自定义分组：按项目/领域分类 + 分组计数（*为什么*：跨领域任务要分区）
> **N3 结算决策**：不设独立「目标」实体（伪需求）—— **目标 = 大的任务分组/项目**，
> 必要时给任务打**多分组/领域标签**。

**用户原话（2026-09-21，摘成结构）**：
- **进行中**：「我可以自由选择某些任务在进行中，这样方便我看到底自己在做什么任务」；
  且「**同时**（多个），可以自己标顺序」。
- **完成**：「假如我完成的话，那就完成」。
- **归档**：「归档是说我完成某个任务之后，他就进入档案中，方便我后期以后的查阅」。
- **取消**：「类似于我打错任务了或者我觉得这个任务没必要做了」（≈删除但留痕）。
- **待定**：「闲置或者挂在那儿、没放弃、不计债」。
- **子步骤**：「子步骤也能加 deadline」「对子步骤有一个拖延推迟的效果」
  「子步骤完成前，它变成主任务的一个显现（任务卡里显示一个子步骤）」。
- **大任务**：「大任务 → 子任务 → 子步骤」「或者程序里像文件夹那样，可以嵌套、归在一起」。
- **尝试失败**：「设一个新的标签/功能，我点了就是尝试失败」「让我写相关的文档，或者已经沉淀了那些日志」
  「然后我选择把这个任务取消、还是待定（挂在那里没 deadline）、或者推到明天」。

**用户决定（2026-09-21）**：
| 议题 | 决定 |
|---|---|
| 「尝试失败」怎么计 | **只认你显式点**「尝试失败」（不自动从"推到明天/取消"推断）—— 数字要可信 |
| 完成 → 归档 | **过几天再归档**（不是立刻）→ 落地为「完成 N 天后进档案」，N 可配置 |
| 「进行中」 | **可同时多个**，**且能自己标顺序**（用显式序号，不做拖拽 —— 守段2 决策） |
| 新状态命名 | **「待定」**（**不叫「悬赏」**：那个词在 conventions 里已经是"完成收益"的意思，不能一词两义） |
| 「待定」计债务吗 | **不计债**（行为同「取消」：不提醒、默认视图可见） |
| 「收益」读数 | **要**：账本补「完成收益」（约定层本来就写了"储蓄 = 完成悬赏/复习完成"，但一直没有读数） |
| 大任务形状 | **嵌套 + 分组都要**；分组加父子（可嵌套）且**保留多归属**（不动 SR-F1.3） |

**★ 一并查清的两件事**：
1. **「悬赏」不是任务类型/状态**，它是 B 系统记账的**收益侧口径**
   （`needs.md:34`：逾期=债务、专注=投入、**完成悬赏=收益/储蓄**；`conventions.md:20`；`SR-F2.1`）。
   没有实体、没有字段、没有界面 —— 只体现在"完成会记一条事实"上。
2. **缺口**：「悬赏=收益」这条贯穿口径**没有落成任何账本读数** ——
   现在的 `summary` 只有债务/投入/手动投入/复习/产出/习惯，**没有"收益"**。用户已定要补。
3. 另外查明：任务的 **「进行中」「归档」两个状态在代码里从来没有任何地方会写它们**
   （`focus` 的"进行中"是专注会话的状态，另一张表）；**「逾期」只在"新建时截止日已过"才写进字段**，
   之后过期是**派生显示**（进逾期栏 + 标红，但字段值还是"未开始"）——这是个要顺手修的不一致。

**落地拆成 F 批（任务卡 T-F1~T-F9）**：见 `任务重规划-剩余工作.md` §F 批。
**进度**：**F 批主体全部落地** —— T-F6（完成收益读数）、T-F1（状态机）、T-F7（派生逾期口径统一）、
T-F8（债务计数=明细，用户定案 A）、T-F3（「尝试失败」显式计次）、T-F2（完成 N 天后进档案 + 档案视图）、
T-F4（子步骤截止日/推迟/当前步骤）、**T-F5（三层嵌套 + 分组可嵌套，schema v14）**、
**T-F9（债务里建父任务状态卡，逾期的子孙挂在卡下面 —— 用户定的第四种答案）**、
**T-F10（分组名允许重名 + 成员关系改按 id，schema v15）**。

**T-F5 落地的两条实现口径**（都写进了代码注释与 changelog）：
- **层数上限 3** 对任务与分组**同一个常量**（`MAX_TASK_DEPTH` / `MAX_GROUP_DEPTH` = 3）：
  两处都是"分类/拆解"的深度，各写一个数字迟早互相矛盾；
- ~~**分组名仍全局唯一**~~ → **已由 T-F10 放开**（见下）：用户 2026-09-21 追加定案「允许重名」。

**T-F10：分组名允许重名（用户原话「允许重名」，schema v15）**：
- 分组名改成**同层唯一**（同一父下不重名；跨父可以有「高数 / 作业」和「英语 / 作业」）；
- 因为老口径的成员关系是**按名字**存的（名字一重复就指不回是哪一个），

  洞察按**路径**归桶（两个同名分组不能被混成一格）；
- 「没有就建、有就用」与"改名合并"都缩到**同层**语义；同层重名仍然拦（没用，只会选错）。

**T-F4 落地时一并查出来的新待定（T-F9）**：子步骤能设截止日之后，一个过期的子步骤会
**单独进逾期栏、单独算一笔债**（`overdue_tasks()` 不过滤 `parent_id`），而父任务可能也有截止日
→ 同一件事在债务里可能出现两次。**问用户**：算 / 不算 / 只出现在逾期栏但不计数？（三选见 §1 末尾）

**T-F1 落地时一并定的几条小事**（实现细节，不改用户口径）：
1. **「待定」在默认列表里看得见**（与「取消」一致）：搁置不是删除 —— 不进 My Day / 逾期 / 提醒，
   但仍在「全部任务」里（单独一段「搁置」，可一键取回）。`ledger` 的债务由 `overdue_tasks` 派生，
   所以"不进逾期栏"就等于"不计债"，一个口径而不是两处规则。
2. **手动「归档」不强制先完成**：档案主要是完成的归宿，但取消掉/搁置的也该有地方收
   （否则"整理一下列表"没法做）。**自动归档（完成 N 天后）仍只作用于完成**（T-F2）。
3. **「进行中」的顺序**用 schema v13 的 `doing_rank`：进去排到末尾、离开清成 NULL；
   调顺序只改序号、**不动 `updated_at`**（换顺序不是"内容变了"，别把完成时间/重复基准弄歪）。
4. **状态变化留痕但不动账本**：这些动作只记 `task.status_changed`（带 from/to，供 N11 存档/查阅），
   债务、投入、收益一律不受影响（`tests/test_task_line.py` 里那条"其它状态变化不记事实"的断言
   随之改为"只记状态事实、不进账本"——口径变更已在该测试里写明原因）。
5. **逾期一律按派生算**（T-F7）：`tm.overdue_days(task, today)` 是唯一算天数的地方，
   界面显示「存储状态 + 已逾期 N 天」而不是把 `逾期` 写回字段 ——
   写回状态 = 两套真相 + 要定时器（本项目明确避免定时任务）。
6. **T-F8 已定案（A 案）**：无截止日、但昨天就该做的 My Day 老任务**算一笔债务**，
   **天数从创建日算起**（用户 2026-09-21 原话：A「算，天数从创建日算起（它就是"昨天没做完"
   才进逾期栏的）→ 计数和明细都是它」）。落地为 `_is_stale_undated_myday()` 被
   `overdue_tasks()` / `overdue_days()` 共用，保证 `debt_count == len(debt_items)`；
   挂成「待定 / 取消」后照旧不计债。**"从创建日算"只给这种老账**，不外推到所有无截止日任务。

7. **T-F9 已定案（用户 2026-09-21，比三个选项更好的第四种）**：带截止日的子步骤**不单独算一笔债** ——
   用户原话：**「可以在债务那里，建个父任务状态卡，然后挂？」**
   落地为**归卡**：逾期的东西沿父链上溯到**最高一层"还在手上的"祖先**，
   父任务一张卡、逾期的子孙挂在卡下面（`tm.debt_groups` / `DebtGroup.steps`）；
   卡的 `overdue_days` = 父任务自己的天数与挂着的步取**最大**（不做折算）；
   **完成 / 搁置（取消·待定）/ 归档 / 已删的祖先不配当卡**（"搁置不计债"不能被绕过）；
   `debt_count` = 卡的张数，账本 / 洞察 / 自检**共用** `tm.debt_count()`。
   **逾期栏不跟着改**：那里仍如实列出每一条逾期（干活的地方 vs 读数的地方）。

## 2. AI 接口边界（SR-F7.3）—— ✅ 已定（乙案）

**原文依据**（`docs/intention/needs.md`）：
> **N23** 为 AI 智能体（Hermes）提供读写任务的接口/端口；**第一版只读 + 新增**（不改不删，避免和你手动冲突）…
> *为什么*：要和 AI 协作，AI 需能读任务、写任务；第一版保守，**避免覆盖你的操作**。
> **N46** …AI 作为执行者之一，通过 N23 接口**接收任务 + 回报进展**。

**张力**：N23 说"不改不删"，但 N46 要"回报进展" —— 而回报进展今天的实现是 `PATCH`（属于改）。

**用户决定（2026-09-21，用户在追问中自己提出了"进展可以是一种子步骤形式"）**：
- **进展用子步骤表达**（而不是另记一条"进展"文本）—— 因为"加步骤"本身就是**新增**，天然符合 N23；
- **AI 可以勾掉它自己建的步骤，不能碰你建的步骤**（乙案）。
- 判据从"改不改"换成"**动的是不是你亲手写的东西**"。

**落地要点**：
- 需要给任务/步骤加一个"**谁建的**"标记（schema **v14** —— v13 已被 T-F1 的 `doing_rank` 用掉）——AI 建的 vs 你建的；
- 新增一组 **`/api/ai/*`**（只读 + 新增 + 勾自己建的步骤），**默认关**（口径同 N16"默认收严、用户再放宽"）；
- AI 的所有动作都**发事实**（可审计、可撤销、可回溯"这是 AI 干的"）；
- 你建的步骤被 AI 试图勾掉 → **400 拒绝**（不静默忽略）。

## 3. 跨端同步（SR-F9.2 / SR-F3.4 / SR-NF17）—— ✅ 已定（先 C 后 A）

**原文依据**：
> **SR-NF17**：PWA + IndexedDB 本地缓存 → 离线能记/看/提醒；**回电脑网络异步对齐**（LWW 不静默覆盖）；
> …**首版不做公网远程实时**。
> **N25**：本地优先、可跨端同步、可被 AI 读写；存储已决为混合模式（Markdown 为共享真源 + 结构化索引）。
> **N17**：电脑或手机开始专注后，另一设备同步进入专注计时。

**三个场景（我给用户摆的，用户按场景编号作答）**：
1. 在外面离线记（技术上是"手机离线队列 + 导出文件 + 电脑导入"）
2. 在家/宿舍同 WiFi，手机直接连电脑用
3. 只先把"合并"机制做对（电脑 ↔ 电脑导出/导入）

**用户决定（2026-09-21）**：**①②③ 全要**（只排除"先不做"）：
- ① 手机离线记 → 回家导出文件 → 电脑导入
- ② 同一 WiFi 下手机直接连电脑用
- ③ 两台电脑之间的导出/导入

**落地顺序（依赖决定的，不是偏好）**：**③ → ① → ②**
1. **③ 先做**：定义**同步包文件格式** + 合并机制（谁新谁旧 / 同一条不重复 / 冲突留痕）+ 导出/导入入口。
   它是 ① 的**地基**（手机导出的是一个同格式的包），而且能在两个库之间立刻验证。
2. **① 再做**：手机端 PWA **离线队列**（IndexedDB，GAP-F9-02）+ 用同一格式导出。
3. **② 最后**：服务支持**显式开启**局域网访问（默认关，口径同 N16"默认收严、用户再放宽"）
   + **配对码**；开启时明确提示"同一 WiFi 下其他设备也可能访问到"。

**边界（要写进界面与文档）**：局域网方案**只在同一个 WiFi 里管用**；不涉及公网（原文把"出门实时"列为后置）。

## 9. shadow + 一键回退开关（SR-NF8）—— ✅ 已定（B 案）

**原文依据**：
> **N37** 可测试 + 可回退：模块单测 + 回归；敏感改动 shadow + 一键回退（开关默认不改变现状）。

> **GAP-NF-05**：单测 / 回归 / 快照导出**有**；**shadow 对比与回退开关不存在**（所以这条一直是欠账）。

**两个词在说什么**：
- **shadow（影子）**：新口径先在暗处跑一遍 —— 算出来，但**不改显示、不写数据**，只把"新旧结果不一样的地方"列出来；
- **一键回退开关**：不对就拨回默认位 —— **不改代码、不回滚库、不恢复备份**。
  后半句「开关默认不改变现状」是安全保证：默认位 = 不动。

**摆在桌上的四个歧义（先定才敢动手）**：

| 歧义 | 建议 | 结果 |
|---|---|---|
| 「敏感改动」包不包括**不可逆**的改动 | 只含**可重算的派生口径**；动数据的走备份/恢复 | ✅ 采纳（见下） |
| 开关粒度 | **每条口径一个开关**（默认全 old），不用全局总开关 | ✅ 采纳 |
| 影子产出给谁看 | 设置页一节：差异条数 + 最多 3 条样例；**不做逐条审批** | ✅ 采纳 |
| 现在是 v1，**没有"旧版本"当参照物** | **B 案**：机制前向 + 拿 T-F8 计债做样板对比 | ✅ 用户选定 |

（不是搭个空架子等将来；也不为了影子养四套废弃实现）。

**★ 顺手钉死的一件事（重要）**：**默认位 = 现状位**，不是"一律放旧做法"。
T-F8 的口径**已经上线**，此刻库里跑的就是"算" —— 默认位若放"不算"，开关一落地就等于**偷偷改了数字**。
规格里「开关默认不改变现状」的本意是"**你不切，它就不变**"，所以：
- **已上线**的口径 → 默认位 = **新做法**（= 现状）；
