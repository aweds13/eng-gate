## 2. 病根：和 AC-11 同一条，但更隐蔽

T-G67 抓的是「把做完的事说成没做」；这一批是「**把定过的事又说成待定**」。
共同点：**状态字段没人复查就会漂**。区别在于这批的漂法是**复制**——

```text
T-G39 定完 → 之后每张卡的"下一步"都从上一张卡抄一遍 → 抄了十几轮
```

抄的时候没人回头看 T-G39，于是三条已经关闭的项一直在清单上挂着。这比 AC-11 更难发现，
因为**每一份交接看起来都自洽**（清单内部没有矛盾），矛盾只在"清单 vs 台账/代码"之间。

**处置（做了三件）**：
1. 两份交接里那几处"下一步"**全部改成真的开放项**（签名断言 / 非文字对比度 3.0 表 /
   MCP+写 / `T-G33` 残留 / 人工验收）；
2. 幽灵那几行**写明「已定/已做 + 指向 T-G39」**，但**不删历史块原文** ——
   "当时这么写"本身是事实，留着才能看见漂是怎么发生的；
3. 这条漂法进 §6 陷阱表（对策：**清单里的每一项，写之前先 grep 它的关键名词**，
   看台账里有没有已经 done 的同名卡）。

## 4. 写操作那一卡开工时要带的三件事（先记下来，免得到时忘）

1. `docs/commands.toml` 现在只有一个 `cli` 字段、而且**只登记了只读那批** ——
   写命令要新增一栏（可用性/默认关），否则"哪些写操作可达"又会变成口头约定。
2. **MCP 的工具清单必须由那张表生成**，不许手抄第二份 —— 这与 CLI 的 `registry.py` 同一条规矩：
   `check_commands.py` 要能双向核对。
3. **"默认关"要有机器判据**（一条测试/一道门），不能只在文档里写一句 ——
   项目里"默认关"已经有三处（通知、局域网、AI 接口），这一处要跟它们同一个做法。
