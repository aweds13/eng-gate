# git 基线：按「正经多人开发」保证项目的稳定运行与维护

> **触发（用户 2026-10-03 17:3x）**：「**留快照，根据 git 正经的多人开发思路去保证那个项目的稳定运行和维护。**」
> ★ 本文是**审计 + 口径 + 落点**。★ 审计读数都是 2026-10-03 17:3x 现跑的。

---

## 一、审计：我们 vs 正经做法（差距就三处，但都打在要害上）

| 正经多人开发 | 我们现状（现量） | 判定 |
|---|---|---|
| **每张卡一条短命分支**（feature branch） | ★ 主树在 `line/impl-v1` ✓，但 **177 个卡树是 `detached HEAD`** | ✗ **偏离**：detached 的提交**没有 ref** ⇒ `git branch --contains` / `clone --mirror` **都带不走它** |
| ★★ **小步提交**（WIP 也提交，未提交 = 无保护） | ★★ **工人一律"不许 commit"** ⇒ **成果全部停在未提交区** | ✗✗ **今晚数据丢失的直接原因** |
| **PR + 评审 + 受保护主干 + CI 在分支上跑** | 门禁**在卡树里跑** ✓（这点对）· 成送申请/复核机制**在**，但**复核零接线** · ★ **我一直在直接改主树工作区** | ✗ 主干没保护 |
| **远端 / 异地备份** | ★★ **一个 remote 都没有** | ✗✗ **最大缺口** |
| **stash / worktree 只当临时态** | worktree ✓ 用得很多（177 个）| ✓（但 detached 的问题见上） |
| **CHANGELOG / tag** | changelog ✓ + 每笔 trailer ✓ | ✓（缺 tag） |

★ 三个真缺口：**① 无备份 ② 工人成果全在未提交区 ③ 主干工作区被直接改**。

---

## 二、★ 根因：一条规矩写错了对象

> 我们的规矩是「**工人不许 commit**」。它的**初衷**是「**不许把提交弄到主树/主干上**」——
> ★★ 但它被写成了「**不许提交**」⇒ **把唯一的保护机制（提交）给禁掉了**。
> ⇒ **未提交 = 无保护**，而**工人干活的产物永远是未提交的** ⇒
> ★★ **缺口正好打在流水线最脆弱的那一环上**（今晚卡 160 的 6/9 个文件被覆盖就是这么来的）。

★ **正确的写法**：**工人必须"小步提交到自己的卡分支"**（`card/<号>`）——
**提交只进卡分支，不碰主干**；主干**只接受 ff / 合并**。

---

## 三、改法（按优先级；每一条都要能落到机器判据上）

### P0-1 ★★ **工人改成"小步提交到 `card/<号>` 分支"**
- 卡树创建从 `git worktree add --detach` 改成 **`git worktree add -b card/<号>`**；
- 工人规矩从「不许 commit」改成「**每完成一小步就 commit 到本卡分支**；★ **不许碰主干、不许 push 主干**」；
- ★ **收口时**：主树 `git merge --ff-only card/<号>`（或 `--no-ff` 保留"这一笔是一个 topic"的拓扑）；
- ★★ **收益（结构性）**：**未提交的成果不再存在** ⇒ 今晚那类事故**在结构上不可能**（覆盖已提交内容会被 git 拒）。
- ★ **代价**：`landing.py` 的"卡树 HEAD 必须是主树 HEAD 的祖先"那条守卫要跟着改（卡分支是从主树 HEAD 开的 ⇒ 天然满足 ✓）。

### P0-2 ★★ **备份：镜像 + 每次落地后推**
- 现状：★ **已建第一份镜像** `D:/repo/backup-engineering.git`（`git clone --mirror`，**21 MB**，32 个 ref）；
- ★ **每次落地后**：`git push --mirror` 到镜像（归收口链自动做）；
- ★★ **注意（今晚踩到的）**：`clone --mirror` **只带 ref** ——
  **detached 的卡树提交与未挂 ref 的悬空对象它带不走** ⇒ ★ **所以 P0-1 与快照锚定是镜像生效的前提**；
- ★ 建议再加**第二个物理位置**（另一块盘 / U 盘 / 网盘同步目录）——「异地」才是真备份。

### P0-3 ★★ **快照：`stash create` + **挂 ref** + 进镜像**（★ 已实现，2026-10-03）
- `gates/diag/_snapshot.py`：`git stash create` **造对象、不动工作区**（**不是** `git stash`），
  ★ 并 **`git update-ref refs/snapshots/<树>-<时间> <sha>`** ⇒ **可达** ⇒ **镜像带得走**；
- ★ **踩过的坑**：ref 段名**不许以 `.` 开头**（`.wt-invgate-…` 被 git 拒）⇒ 现在会 lstrip 成 `wt-invgate`；
- ★ **接进流程**：`_batcher.py` 的 **step 0**（任何写之前先打）；**收口链**落地前也打（归卡 184）；
- ★ 台账：`gates/diag/_snapshots.txt`。

### P1-1 **主干工作区禁改**（保护主分支）
- ★ 主树**只做 ff/merge**；**任何**文档笔/队列/规格的编辑都在**卡分支**或 **`docs/<批次>` 分支**上做；
- ★ 判据：收口链发现「主树工作区不干净且不在白名单」⇒ **拒**（现在已经有"主树不许留本地副本"的坑 41，但**没强制执行**）。

### P1-2 **复核 = code review，必须接线**
- `tools/wb_review.py` 已经在（权威域 / 门数 / trailer 真伪 / 封存树对账）⇒ ★ **接进收口链**（归卡 184 追加三）；
- ★ 独立检查（`wb_advcard.py` + **不同族**模型）**按 `high` 风险触发**（规矩 §25 已有）。

### P2 **tag 里程碑 + 合并拓扑**
- 框架 MVP、独立仓落地这类节点打 **`tag`**（可回溯、可发布）；
- 选一种合并策略并写死（**建议 `--ff-only`；需要保留 topic 拓扑时显式 `--no-ff`**）。

## 四、★ 这套为什么能"保证稳定运行与维护"

| 目标 | 靠什么 | 属于哪一层 |
|---|---|---|
| **不丢东西** | ① 小步提交（未提交→不存在）② 快照挂 ref ③ 镜像（仓外一份） | ★ **结构**（不靠人记得） |
| **不出错** | ① 门禁在分支上跑（已 ✓）② 复核接线 ③ 动别人东西前的前置守卫（已 ✓） | ★ 判据 |
| **可追溯** | 一笔一个 `Task:` + 台账证据指针 + tag + `refs/snapshots/*` | ★ 记录 |
| **可维护** | 短命分支 + 主干只合流 + 复核 + changelog | ★ 流程 |
| **可交接** | `导读-怎么读这套工作流.md` + `_HOLD.md` + 交接卡 | ★ 文档 |

★ **判据（别只说"我们照 git 做了"）**：**上面每一条都要有一条机器能判的读数** ——
例：`git worktree list | grep -c detached` 应为 **0**（新卡）；`git remote`/镜像 ref 数 ≥ 1；
`refs/snapshots/*` 在镜像里存在；主树 `git status --porcelain` 在收口后**只剩用户自己的未跟踪文件**。
