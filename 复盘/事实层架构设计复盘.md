## 一、Q1：理想架构能否继续加新功能？

### 现状的问题

```
现有架构：  壳 → API → core(10个并列模块) → storage
                         ↑ 模块间互不感知
```
**加一个新功能的代价**：改 core + 改 ledger + 改 api + 改前端，且要**自己记得"还有别处要改"** → 这就是"做了这个忘了那个"的架构级根因。

### 理想架构：补上"交叉层"

```
壳 → API → ┌─ 业务线(tasks/focus/review/academic...) ─┐
           │              ↓ 发布事实(事件)              │
           │         ★ 事实层 / 事件总线 ★               │  ← 现在缺这一层
           │              ↓ 订阅事实                     │
           └─ 框架(ledger 账本：唯一的账)               ─┘
```

**加新功能的代价变为**：新线只负责"发自己该发的事实"，框架只负责"收事实记账"，**两边互不知道对方存在**。

### 与 intent 的对应

| intent 概念 | 架构对应 |
|---|---|
| **框架**（债务/储蓄账本） | `ledger` —— 唯一账本，**订阅所有事实** |
| **线**（任务/专注/复习…） | 各 `core` 模块 —— **发布事实，不直接记账** |
| **交叉** | **事实层/事件总线** —— 把"线发生的事"传给"框架" |
| **节点** | 一条 `fact` / 一条账目记录 |

> **intent 的心智模型与理想架构完美对应**——只是现有代码没实现它。

## 二、Q2：换心智模型怎么办？

### 核心原则：区分「事实」与「解读」

| 类型 | 例子 | 会变吗 |
|---|---|---|
| **业务事实** | "2026-09-17 任务A 完成，专注 25 分钟" | **永不变**（发生过的事） |
| **解读/心智模型** | "专注 25 分钟 = 储蓄 +25" | **会变**（可能改成"精力值"…） |

**架构必须做到：事实只记一次，解读可以随便换。**

### 三层分离

```
① 事实层（Fact）         —— 与心智模型无关，只记"发生了什么"
② 派生层（Derived）      —— 从事实算中间量（可选，为性能；MVP 不做）
③ 解读层（Interpretation）—— 按当前心智模型算成"账目/指标"
```

**换心智模型 = 只换 ③；事实永不动。**

### 反面教材：现在的代码

```python
# ledger.py 现状：事实与解读混在一个函数
def summary(...):
    # 直接读 focus_sessions 表 → 当场算成"投入"
```
**后果**：换算法要改这个函数；且它只会算"投入"，想不到别的心智模型。

### 边界（诚实说明）

**不是所有东西都该事实化**：

| 该事实化 | 不该 |
|---|---|
| 会被**多种解读消费**的（专注/完成/逾期） | 纯查询（列表、详情） |
| 会被**历史追溯**的（账目、统计） | 临时状态（UI 开关） |
| 会被**新心智模型复算**的 | 一次性计算 |

## 三、Q3-1：JSON 是必须的吗？——**不是，降级为"兜底"**

### 此前的过度设计（已纠正）

我上一轮把 `payload JSON` 称为"扩展性的关键"，**言过其实**。实际情况：

- 事实**类型**有限；加新**类型**靠 `kind` 自由字符串即可，**不改表**
- 只有"给已有类型**加新字段**"才需 `ALTER TABLE`——**低频**，且 SQLite 的 `ADD COLUMN` 是秒级

### 正确设计：公共列 + JSON 兜底

```sql
CREATE TABLE facts (
    id           TEXT PRIMARY KEY,
    kind         TEXT NOT NULL,      -- ★ 自由字符串："域.动作"（核心扩展点）
    subject_type TEXT,               -- 松耦合主体
    subject_id   TEXT,
    value_num    REAL,               -- ★ 高频数值（有索引，查询主用）
    value_text   TEXT,               -- ★ 高频文本
    extra        TEXT,               -- JSON：兜底，不用于查询
    occurred_at  TEXT NOT NULL,      -- 事实发生时间
    recorded_at  TEXT NOT NULL,      -- 记录时间
    source       TEXT,               -- desktop/mobile/ai/import
    device_id    TEXT,               -- 跨端去重
    revision     INTEGER DEFAULT 1,  -- ★ 预留（MVP 不启用）
    supersedes   TEXT                -- ★ 预留（MVP 不启用）
);
CREATE INDEX idx_facts_kind_time ON facts(kind, occurred_at);
CREATE INDEX idx_facts_subject   ON facts(subject_type, subject_id);
```

**扩展性排序（真正的关键在哪）**：
1. **`kind` 自由字符串** ← 最重要（加新事实类型不改表）
2. **公共字段列**（查询快）
3. `extra` JSON 兜底（罕见字段有地方放，非核心）

## 四、Q3-2：异步架构？——**要"事件驱动"，不要"异步队列"**

### 三种"异步"的区分（先确认语义）

| 含义 | 对你的项目 |
|---|---|
| A. 写事实与算账异步 | ❌ 过度——本地单机无性能压力 |
| **B. 事件驱动（发布-订阅）** | ✅ **这才是要的**（解耦） |
| C. 跨端同步异步 | 已定（PWA + LWW），另说 |

### 选定：事件驱动 + **同步执行**

| | 同步调用 | **事件驱动（同步同进程）** | 异步队列 |
|---|---|---|---|
| 耦合 | 高 | **低** | 低 |
| 复杂度 | 低 | **中** | 高 |
| 调试 | 易 | **易** | 难 |
| 一致性 | 强 | **强**（当场完成） | 弱 |

**理由**：
1. **解耦**是目标 → 事件驱动能给
2. **本地单机无性能压力** → 不需要队列
3. **强一致性** → 不会出现"完成了但账还没记"
4. **易调试** → 用户是新手，同步堆栈看得懂

```python
# 事件总线（同步、同进程）
bus.publish("focus.finished", {task_id:..., duration:...})
   ↓ 当场、按顺序通知订阅者
ledger.on_focus_finished()    # 记账
feedback.on_focus_finished()  # 累加反馈
tasks.on_focus_finished()     # 累加任务时长
```

> 将来若要"AI 大批量写入"或"跨端同步"，再加队列层——**现在不需要**。

## 五、Q3-3：修正机制是什么？——**预留字段，MVP 不实现**

### 要解决的问题

事实记错了（写错数值 / 事实变了），但**直接 UPDATE 会丢失"当时记的是什么"**。

### 方案：追加式修正（不改旧记录）

```sql
F1: kind=task.completed, subject=T-001, revision=1, supersedes=NULL
F2: kind=task.completed, subject=T-001, revision=2, supersedes=f1  ← 修正 F1
```
**读账时**：取"每个 subject 下最新、且未被后续 supersede 的"那条。

### 关键：它与"换心智模型"**无关**

| | 解决什么 | 需要吗 |
|---|---|---|
| **换心智模型** | 用新规则**重读**同一批事实 | ❌ 不需要修正机制 |
| **修正机制** | "事实**本身**记错了" | ⚠️ 视场景 |

消费场景判断：
| 场景 | 需要修正机制吗 |
|---|---|
| 本地单机、自己用、写错直接改 | ❌ 不需要（直接 UPDATE 更简单） |
| 跨端同步（冲突） | ⚠️ 需"版本"，未必需 supersede 链 |
| 审计/回放历史 | ✅ 需要 |
| **换心智模型** | ❌ **不需要** |

**决策**：**两列预留，MVP 不实现逻辑**（成本几乎为零，需要时再启用）。

## 六、最终设计决策汇总

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| 1 | 架构补"交叉层" | ✅ 立事实层 | 解耦线↔框架，加功能不改核心 |
| 2 | 事实与解读分离 | ✅ 三层（事实/派生/解读） | 换心智模型只换解读层 |
| 3 | 字段存储 | **公共列 + JSON 兜底** | JSON 非核心，`kind` 自由才是 |
| 4 | 事件传递 | **事件驱动 + 同步执行** | 解耦够用，不需异步队列 |
| 5 | 修正机制 | **预留字段，MVP 不实现** | 与换模型无关，成本零，按需启用 |
| 6 | 不为"可能的需求"过度设计 | ✅ 派生层 MVP 不做 | 等性能真有问题再加 |

## 七、重构顺序（据此调整）

```
第 0 步：建 facts 表 + 事件总线（同步）        ← 地基
第 1 步：ledger 改为"读 facts → 按当前心智模型解读"
第 2 步：各线改为"发事实"（focus/tasks/review）
第 3 步：旧数据迁移（focus_sessions/tasks → facts，双写过渡）
第 4 步：前端补交互（计时器/结束/截止日/加入 My Day…）
```

**每一步都要能跑通测试（44 项 + 新增）。**

## 八、方法论沉淀（可复用）

1. **事实与解读必须分离** —— 这是"能换模型"的唯一前提。
2. **扩展性来自"自由 kind + 公共列"，不是 JSON** —— 别用 JSON 逃避表设计。
3. **事件驱动 ≠ 异步** —— 本地单机用"同步事件"即可，强一致且易调试。
4. **预留 ≠ 实现** —— 低成本预留字段可以，逻辑等需要再写（避免过度工程）。
5. **能跑就实测** —— 本轮实测纠正了一处"读代码得出的错误判断"。
6. **不为假想的未来设计** —— 派生层、修正逻辑，都是 M**V**P 之后的事。
