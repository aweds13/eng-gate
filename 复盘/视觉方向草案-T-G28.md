## 2. 先回答你问的那两条（"这个怎么说"）

**`ui-ux-pro-max` ★ 值得装 —— "可查证'这种数据该用什么图'"是什么意思**

它的 `data/charts.csv` 是一张**按数据类型查的表格**（23 KB），每行给：最佳图形 / 备选 / 什么时候用 /
**什么时候不该用** / 数据量阈值 / 配色指引 / **无障碍风险与退路** / 交互级别。实测输入
`heatmap calendar` 那一行，直接吐出了我们 `SR-F1.5b` 正好需要的硬约束：

- 「**calendar heatmap: 365 cells max per SVG**」（超过要聚合）
- 「少于 20 个格子别画热力图（用柱状）」
- 「**不要只靠颜色**：格子里要印数值或符号、用纹理/标签」+「键盘聚焦露出格子数值」
- 无障碍风险 `conditional`，退路 = 「网格数据表 + 强度摘要」

**这就是"可查证"**：不是它说"这样更好看"，而是它给**可判定、可反证**的约束
（"365 格上限""少于 20 格用柱状""不许只靠颜色"），我拿它对照我们的热力图就能判对错。
它一次性给了 25 类图表 × 这套字段 —— 我们那 6 个手写 SVG 图表（T-G24 §4）正好对着它做规范。

**`design-system` "令牌架构那部分有用"是什么意思**

它的 `SKILL.md` 讲的是**令牌分三层**：`primitive`（原始值，如 `blue-500 = #3b82f6`）→
`semantic`（语义，如 `--accent` / `--surface-raised`）→ `component`（组件层，如 `--button-bg`），
并配了 `generate-tokens.cjs` / `validate-tokens.cjs`（Node，能查"有没有裸值漏在组件里"）。

**"有用"是指它的分层说法**，不是它的脚本 —— 我们现在的令牌区是**扁平一层**（42 条，
`--accent` / `--card` / `--sp-*` 混在一起）。分层的好处是：换皮肤时只动 semantic 层，
component 层不用碰。**但它的脚本我不建议用**，理由在 `复盘/外网工具链与技能包勘察-T-G27.md` §8：
那份代码在一个 **gitignored、版本没 pin** 的克隆里，接进门禁等于门禁依赖一个"在别人机器上不存在"的东西。
→ 所以：**分层的思路可以借鉴，脚本要用就自己写**（我们现在也是这么做的）。

## 3. 我的独立拆解：这三家**各自是什么机制**（不是"什么感觉"）

要"截精华"，先得把"精华"从"感觉"里拆出来 —— 否则抄到的是壳。我逐家拆成**可实现的机制**：

### Linear —— "骨架"（它真正值钱的是**层级不靠字号**）

| 机制 | 具体是什么 | 对我们 |
|---|---|---|
| 行，不是卡片 | 列表是 32–40px 的**行** + 1px hairline 分隔；卡片只用于少数聚合块 | 我们 66 个 `.card` 全一个样（T-G24 §5-1）—— **这是"平"的第一来源** |
| 层级靠**字重 + 次级色** | 标题与正文**字号差别很小**，靠 `600` 与 `--muted` 拉开主次 | 我们反过来：层级几乎全靠字号撑（全文只有 4 处 `font-weight`、1 处 `line-height`） |
| 骨架 | 常驻左栏 + 列表 + 右侧详情滑入 | 我们**已经是**这个骨架（`.shell` 200/1fr/340）→ 这条不用抄 |
| 焦点态清晰 | 键盘焦点有明确 2px outline | 我们有 `focus-visible`？→ **要查**（列入体检表） |
| 乐观 UI | 点一下立刻变，不等请求 | 我们多数操作是等请求 + toast；**"立刻"这一层是缺的** |
| 极短动效 | ~100–150ms，只用于状态变化与面板进出 | workbench 上限 0.12–0.18s，**同向** |

### Things 3 —— "留白"（它真正值钱的是**用空白和字体分块**）

| 机制 | 具体是什么 | 对我们 |
|---|---|---|
| 几乎没有边框 | 分块靠**留白 + 字号/字重**，不是线 | 我们分块全靠 1px `--line` |
| 页面标题**很大** | 页标题与正文的字号差是**跨档的**（不是 15 vs 13） | 我们页标题几乎不存在（14 个视图没有统一的页标题层） |
| 一次只让少数东西可见 | 屏上同时可见的信息量小 | ⚠️ **与我们冲突，见 §7** |
| 温和且"一次只动一个"的动效 | 勾选填充、列表重排的短动画 | 可借（但我们有 `prefers-reduced-motion` 义务） |

### Raycast —— "交互反馈"（它真正值钱的是**反馈契约**，不是"都靠键盘"）

| 机制 | 具体是什么 | 对我们 |
|---|---|---|
| 键入即过滤、**零延迟** | 本地过滤，不等请求 | 我们有本地数据，但过滤是否零延迟**要查** |
| 每个动作旁边写**快捷键徽标** | 可学习性 | 我们是中文 + 鼠标为主 → **只借"可学习"，不借"都靠键盘"**（§7） |
| 错误**内联**说明，不弹窗 | 错误落在它发生的地方 | 我们有 `ask()` 模态 + toast —— **够不够"就地"要查** |
| 动作**立刻可见**结果、可撤销 | 每次操作都有确定回应 | 我们已有 toast + 撤销；缺的是**局部即时状态**（比如行内"正在保存"） |

> **一句话**：三家给的其实是三样**不同层次**的东西 —— Linear 给**层级语法**、
> Things 给**分块语法**、Raycast 给**反馈语法**。它们**不冲突**，因为它们管的是不同的轴。
> 这才是"截精华"能成立的真正原因（不是"把好看的部分拼起来"）。

## 4. 为什么否掉 MS To-Do 那一路（**可检查的**理由，不是口味）

你说它"吵、繁琐"。我不用附和 —— 我把它翻译成三条**能对着界面数出来**的问题：

1. **一行里有多个并列强调**：彩色清单圆点 + 大圆角卡片 + 右侧日期药丸 + 星标 ——
   同一层级里 4 个视觉重量相当的信号 → **眼睛没有落点**（违反"有且只有一个焦点"）。
2. **颜色被当成"分类装饰"**：用色块表示"这条属于哪个清单"，而不是表示**状态**。
   这正好撞上 workbench 的硬禁令「**语义色只表状态，never decoration**」，
   也撞上我们自己 `N30` 的「素雅、克制、统一」。
3. **装饰性容器 + 插画空态**：属于 workbench 说的「**不 inform 也不 act 的东西就不该存在**」。

**所以否掉它不是我"看法不同"，是它同时违反了我们早就写下的 N30 和刚钉的 workbench 禁令。**
（如果我记错了 MS To-Do 的某个细节，这三条原则本身不受影响 —— 它们是对着**方向**说的。）

> 顺带说一件对你有利的证据：**这份判断和"蓝色不换"是一致的**。
> 你要的"素雅克制"（N30）和 MS To-Do 的"多彩分类"是相反方向 —— 你的两个要求内部自洽，不需要我调和。

> Contract: core — this pack does **not** specify `## Components`, `## Hero`, `## Responsive`

## 7. 我的不同意见与风险（**你要我别迎合，这里是三处**）

1. **Things 的留白不能整体搬** —— 它和 Linear 的密度**是对立的**：Things 一屏约 10 个元素，
   Linear 列表一屏 30+ 行。我们是一本**账**：一屏要看到"今天要做的 + 逾期 + 该复习的"。
   整体搬到 Things 的松，等于把效率工具变成阅读器。
   **→ 我的折中（也是我建议写进规则的）**：**留白分工** ——
   区块之间/视图之间/空态/标题周围**松**（Things），数据行**紧**（Linear）。同一屏里两者并存。
   这**不是和稀泥**：Linear 自己就是这么做的（列表紧、区块与空态松）。
2. **Raycast 的"键盘优先"不能整体搬** —— 你是**中文界面、鼠标为主、手机上还要用**。
   要借的是它的**反馈契约**（零延迟过滤 / 立刻可见 / 错误就地 / 快捷键可学习），
   不是"所有东西都得敲键盘"。把"键盘优先"搬进来会做出一屏只能键盘用的中文 App。
3. **"通过审美门去找风格"这句话，我只能做到一半** —— 门能证明的是
   「**这个风格没有破例**」（对比度、间距在网格上、字号都在令牌上、动效不超时、触摸目标够大……），
   它**不能证明"好看"**。谁能证明好看？**你的眼睛**。所以我建议：**门负责把不达标的候选杀掉，
   你负责在活下来的 2–3 个里挑**（§9）。我不想让一句话听起来像"门能替你审美"。

另外一处**风险**要提前说：这四段（组件状态/首屏/响应式/签名元素）**workbench 没给值**，
按包自己的规矩，**我们自己定完必须"说出声"**（写进文档），否则就是"用发明的值配一条引用"。
所以 §6 那张表最后会长成一份**我们自己的 house style**，这份 house style 是要**署我们的名**的。

## 8. 蓝色不换 —— 那 18 条欠账怎么修（★ 这里有一条**定理**，不用改任何颜色）

你说"蓝色本身不换"，我照办。那么 18 条要分三种修法，其中**两条根本不用动颜色**：

### ★ ③ 那 7 条（`--accent-on` vs 6 个预设）：**用机制解决，一个颜色都不用换**

现在 `--accent-on` 是**固定的白**（`#fff`）。但 **WCAG 有个可以证明的性质**：

```
白字达标 ⟺ 强调色亮度 L ≤ 0.1833
黑字达标 ⟺ 强调色亮度 L ≥ 0.1750
两个区间有重叠（0.1750 < 0.1833）→ 任何颜色，在"黑/白二选一"下都能到 4.5:1
```

实测（本项目 6 个预设 + 默认，`contrast()` 就是门里那个函数）：

| 强调色 | 白字 | 黑字 | 自动选 | 结果 |
|---|---|---|---|---|
| `#3b82f6`（默认/预设1） | 3.68 | **5.71** | 黑 | ✅ |
| `#8b5cf6` | 4.23 | **4.96** | 黑 | ✅ |
| `#10b981` | 2.54 | **8.28** | 黑 | ✅ |
| `#f59e0b` | 2.15 | **9.78** | 黑 | ✅ |
| `#ef4444` | 3.76 | **5.58** | 黑 | ✅ |
| `#0ea5e9` | 2.77 | **7.58** | 黑 | ✅ |
| （参考）workbench `#2f6feb` | 4.57 | **4.59** | 黑 | ✅ |

**做法**：`applyAccent(color)` 里顺手按亮度算一次 `--accent-on`（现有代码只设 `--accent`）。
这样**用户挑任何颜色都不会糊**，7 条欠账一次消掉，**且一个颜色都不用改**。

> 这不是我发明的花招：**workbench 自己就是这么干的** —— 它暗色下 `--accent-ink: #0f1218`
> （深字）配 `#4b8bff`，因为"白字在那个蓝上不过 AA"。我只是把"随主题翻转"推广成"**随亮度选择**"。
>
> ⚠️ **但它是可见变化**：`#3b82f6` 上的按钮文字会从**白**变成**深**。所以这条要你点头（§11）。

### ② 那 3 条（徽标里同色写字）：**改写法，不用改颜色**

状态词改用 `--text` 写，颜色由**底**承担（实测 12.57 / 11.92 / 11.51，workbench 的原话解法）。
字还是那个字、底还是那个底，只是**不再用状态色写字**。

### ① 那 8 条（强调色当小字）：**改写法，也不用改颜色**

不换蓝 ⇒ `--accent` on `--bg` 永远是 3.52。所以只剩一条路：**别拿它写小字**。

- **大号保留蓝色**：`--fs-num` 30px / `--fs-num-xl` 44px 属"大字"，只要 **3.0** —— 3.52/3.68 **本来就达标**。
  同一个颜色，**大号能用、小号不能用**，这就是全部的道理。
- **小号改正文色**：`.accent` / `.flag`(12px) / `.prio.mid` / 底栏选中 改成 `--text` 写，
  蓝色改为**色块 / 左边条 / 圆点 / 下划线 / 图标**承担（"颜色由形态承担"）。
- ⚠️ 这里有一条**要你拍板**：底栏选中的那一个（`color: var(--accent)`）是**状态**，
  改成正文色会**变淡**。可选的第三条路：底栏选中用 `--accent-weak` 底 + 正文色字 + 一条 2px 蓝条
  （workbench 给"选中行"的原文做法就是「`--accent-weak` fill + 2px accent inset indicator」）。

**结论：18 条可以全部修掉，而这**不需要**换蓝色** —— 需要的是"**颜色由形态承担、字用正文色**"
这条规矩，加上 §8-③ 那条自动 on 色。

## 9. 审美门：从"拦回归"扩到"帮你找风格"

你说"通过一个合适的审美门去找到一个不错的风格"。我理解成：**门应该能淘汰破例的候选**。
现在门只有对比度一条。我建议扩成一张**可测量的体检表**（**都能从 CSS/HTML 静态算出来，不需要浏览器**）：

| 体检项 | 判据 | 现状 |
|---|---|---|
| **对比度** | 正文 ≥4.5 / 大字 ≥3.0 | ✅ 已有（T-G27，42 条组合，18 条欠账） |
| **间距在 4px 网格上** | 所有 `margin/padding/gap` 落在 `--sp-*` 或 4 的倍数 | 尺度令牌已有护栏；**114 处内联 style 是漏洞**（步 0 做完才可强制） |
| **字号只在令牌档位上** | 无 ad-hoc `font-size` | 部分（R5 护栏覆盖尺度） |
| **字重 / 行高档数** | 字重 ≤3 档、行高 ≤3 档且都是令牌 | ⏳ 现在**几乎没有**（4 处 font-weight、1 处 line-height）→ 步 2 建令牌后再强制 |
| **圆角只用 3 档** | 6 / 10 / 999 | 现在 5 档（`--r-xs..lg` + pill）+ 2 处裸像素 |
| **动效不超时、无循环** | `transition/animation` ≤200ms 且没有无限循环 | ❓ 没量过（workbench 的硬禁令，值得一量） |
| **触摸目标 ≥44px** | 移动端可点元素 | ❓ 没量过（2019 起苹果/谷歌的常识门槛） |

## 10. 皮肤 / variant 怎么办（按你的意思）

你的意思我读成：**皮肤形式你不反对，但你自己暂时不需要；考虑到以后开源，可以按那个方向做。**

所以我建议**分两件事**，别混：

| | 现在做 | 以后（开源时） |
|---|---|---|
| **对比脚手架** | ✅ 做：同一个**真实页面** + `?variant=<风格>` 只换令牌层，用来做这次的选择。**选完就撤**（sheleg 原文：comparison harness 是脚手架，不是交付物） | — |
| **常驻皮肤系统** | ❌ 不做 | 多套令牌 + 切换 + 无闪烁 + 记住选择 |

**唯一现在就要付的代价**：把令牌层写成"**可替换的一层**"（比如语义层与组件层分开，见 §2 的
`design-system` 分层思路），这样以后升级成皮肤是**加一层**而不是重写。
这条几乎不花成本，而且正好符合我们"颜色只住令牌区"的既有纪律。
