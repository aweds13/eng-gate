### facts 表结构（已落地）

```sql
CREATE TABLE IF NOT EXISTS facts (
    id           TEXT PRIMARY KEY,
    kind         TEXT NOT NULL,      -- 自由字符串 "域.动作"
    subject_type TEXT,               -- 松耦合主体
    subject_id   TEXT,
    value_num    REAL,               -- 高频值（可索引）
    value_text   TEXT,
    extra        TEXT,               -- JSON 兜底
    occurred_at  TEXT NOT NULL,
    recorded_at  TEXT NOT NULL,
    source       TEXT,
    device_id    TEXT,
    revision     INTEGER DEFAULT 1,  -- 修正机制预留
    supersedes   TEXT                -- 修正机制预留
);
CREATE INDEX idx_facts_kind_time ON facts(kind, occurred_at);
CREATE INDEX idx_facts_subject   ON facts(subject_type, subject_id);
```

## 二、关键设计落地说明

### 1. 事件总线：同步执行 + 异常隔离

```python
def publish(kind, payload=None) -> int:
    """同步通知所有订阅者；单个订阅者异常被捕获，不中断其它。"""
```
- **同步**：`publish` 返回时，订阅者已处理完（强一致、易调试）
- **异常隔离**：订阅者抛错记入 `errors`，不向上抛（对应 SR-NF6 局部错误隔离）
- **通配**：`"focus.*"` 能匹配 `focus.finished`
- **空订阅安全**：无订阅者时 `publish` 返回 0，是空操作

### 2. 事实的落点：`focus_session` vs `task`

```python
subject_type = "task" if task_id else "focus_session"
subject_id   = task_id or session_id
```
- 绑定了任务 → 事实挂在**任务**上（便于"该任务累计投入"）
- 未绑定 → 挂在**会话**上（如实记录，不硬归因）

### 3. 修正机制：字段预留，不实现逻辑

`revision` / `supersedes` 已在表中，但 **MVP 不写逻辑**（`latest_by_subject` 注释中已标注将来要过滤 supersede）。

## 五、教训

1. **"只建管道不接逻辑"是安全的重构第一步** —— 现有代码几乎不动，44 项测试作为回归网。
2. **测试要覆盖"升级路径"** —— `test_upgrade_from_v2_preserves_data` 专门验旧库升级，这是迁移类改动的必备项。
3. **`__init__.py` 的导出容易漏** —— 本次测试直接抓出 `unsubscribe`/`errors` 未导出（第一次跑就红）。
4. **端到端实测 ≠ 单测** —— 单测说"能落库"，实测才证明"真实服务跑起来真的落库了"。
5. **行尾符（CRLF/LF）会造成假 diff** —— patch 改动时注意，避免混入无关行尾变更。
