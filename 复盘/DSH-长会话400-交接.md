# DSH 长会话 400 —— 诊断结论与修法（交接 Cards）

> 写于 2026-10-16，2026-10-17 **已修完并实测生效**。
> 只写结论与可执行步骤；推理过程见会话。

---

## 1. 现象（两次实测 400，逐字）

```
This model's maximum context length is 1048576 tokens. However, you requested 1236025 tokens
This model's maximum context length is 1048576 tokens. However, you requested 1108132 tokens (852132 in the messages, 256000 in the completion)
```

两次的共同签名：**`256000 in the completion` 一模一样** —— 这不是"上下文忽然暴涨"，
是**客户端每轮都固定声明 256K 输出预算**，长会话一路吃光输入空间。

## 2. 根因之一：DSH 的默认每请求输出上限是 256000

`resources/app.asar` 里 `@deepseek-ai/dsh-llm-deepseek-api-key`：

```js
const DEFAULT_CONTEXT_WINDOW = 1e6;
/** Default per-request output-token cap. */
const DEFAULT_MAX_TOKENS = 256e3;      // ← 每轮请求都带 max_tokens: 256000
```

- 该模型配置里**只有** `contextWindow: 1000000`，**没写** `maxTokens`，于是落到默认 256000。
- 1,048,576 窗口 = 输入 + 输出共用；客户端预留 256K 输出 → **输入硬顶只剩 792,576**。
- 这是**客户端 DSH 自己**的行为，不是 bili 的。bili 只是照抄了客户端声明的预算。

## 3. 根因之二（更隐蔽）：DSH 自带压缩的判据低估真实 24%

`@deepseek-ai/dsh-compaction-basic`：

```js
const thresholdTokens = Math.floor(
  Math.min(contextWindow * policy.thresholdRatio, pressureBudgetTokens)
);
// pressureBudgetTokens = W − O − B,  B = 65,536；retain = 16% × (W − O)
```

W=1,000,000、O=256,000 时阈值被 O 拉到 **678,464**（不是 800,000）。

但死会话自己的状态行是 `surfaceTokens: 645431`，而同一轮上游实际收到 **852,132**：

```
645,431 / 852,132 = 0.757      ← DSH 的 token 估算只有真实的 76%
```

于是：**触发点换算成真实 ≈ 896,000，而不越线的上限是 792,576** —— 自动压缩永远晚一步。
这就是"以前没 bili 没出过"的真因：以前会话没长到 89 万，bili 把里程拉长后，这个
"估算 vs 真实"的暗沟第一次被踩到。bili 自己的 75% 判据同样基于估算，两套保险同时哑。

## 4. 修法（已落地，2026-10-17 10:08）

改 `C:/Users/example/.dsh/profiles/desktop/cordis.patch.yml`（**不要直接改 `cordis.yml`**，
它由运行中的 DSH 从 patch 自动重生成）：

```yaml
- id: llm-deepseek
  name: "@deepseek-ai/dsh-llm-deepseek-api-key"
  config:
    retryPolicy: { ...原样保留... }
    maxTokens: 65536            # ← 关键：每轮请求的输出预算

# 三个 preset 内的 compaction-basic 各加：
          - id: compaction-basic
            name: '@deepseek-ai/dsh-compaction-basic'
            config:
              thresholdRatio: 0.6
```

注意 patch 语义是**浅替换**（`target[key] = value`，见 `applyEntryPatches`）：
写了 `config:` 就会替换整个 config 对象，所以 `retryPolicy` 必须一起写回去。

| 量 | 改前 | 改后 |
|---|---|---|
| 每轮 max_tokens | 256,000 | **65,536** |
| 输入不越线上限 | 792,576 | **983,040** |
| 自动压缩触发（估算） | 678,464 | **600,000** |
| 换算真实触发 | ~896,000（越线） | **~792,700**（留 19 万） |
| 压缩后保留原文 | 119,040 | 149,514 |

**验证（已通过，无需重启）：** 改完 4 秒后 `cordis.yml` 被自动重生成（mtime 10:08:38），
bili 会话快照的 `outputBudgetHighWater` 从 256000 变成 **65536** ⇒ 出站请求已带新预算。

## 5. 旧会话 `session-3aa2465a` **已成功复活**（2026-10-17 10:28 实测）

先前判断"救不回来"是**按旧预算算的**，改完后不成立，现场证据（transcript 逐条）：

- 死时（turn 431）：`852132 in the messages, 256000 in the completion` = 1,108,132，**只超 59,556**。
- 恢复后（turn 432）`request/header` 里 `config.maxTokens = 65536` ⇒ 852,132 + 65,536 = **917,668 过线**。
- 模型第一步就调 bili 的 `compress`，8 个块回收 **534,358 token**，会话正常往下走。

结论：**被 256K 顶死的会话，改预算后是能原地救活的**，不必新开。
（注意：它是 `delegationDepth: 0` 的主会话，不是 subagent；bili key 里的 `|sub:` 只是 bili 自己的分层键。）

## 6. 其他已知边界

- `contextWindow` 仍是 1,000,000：`DEFAULT_MODELS` 里写死 `contextWindow: DEFAULT_CONTEXT_WINDOW`，
  `defaultContextWindow` 改不动它；比真实 1,048,576 保守 4.6%，可接受（越保守越安全）。
- bili 侧 `outputHeadroomMaxPct` 保持默认 0.25 —— 它只 cap 预留量，改它不影响客户端 max_tokens；
  调 0 等于让长回复直接撞窗。
- **`/compact` 一直都在**（`preset-standard` → `compaction` 组 → `command-compact`），
  `cordis.yml:260` 那个 `disabled: true` 的 `compaction-basic` 是 catalog 模板，不是生效实例。
