# 测试的定时炸弹：判据不许依赖「HEAD 这一笔」（T-G87）

> 一句话：`test_chinese_paths_are_not_escaped` 查的是**真仓库 HEAD 这一笔**有没有中文路径 ——
> 而门禁是**提交前**跑的。同一棵树，**提交前绿、提交后红**。它红了整整一笔，而红的原因
> 跟被验的东西毫无关系。

## 1. 怎么发现的（不是我发现的 —— 是外包工人的独立复核）

卡 002（`T-G86`，修 T-G79 的「幂等也在写库」）那轮，CodeBuddy CLI 工人真跑了全量门禁：

```
16 门里 15 门绿，1 门红
[FAIL] pytest → 1 failed, 1212 passed
       └ tests/test_wb_review.py::test_chinese_paths_are_not_escaped
```

工人的原话：「这一门红是**预存 + 与本卡无关**的，而且修它要动卡白名单之外的文件 → 我停手」。
它的判断与我不谋而合（我独立复现过同一件事）：

```powershell
$env:PYTHONPATH="$PWD\tools\sandbox_shim"
python -X utf8 -m pytest tests/test_wb_review.py -q
# FAILED tests/test_wb_review.py::test_chinese_paths_are_not_escaped
# E  AssertionError: 这一笔里有中文路径（复盘/…），它必须原样出现在清单里
# E  assert []
```

**外包这条线的价值这次是实的**：一个独立的人（模型）逮住了主控自己工具里的真缺陷。

## 2. 根因：它查的是「HEAD 这一笔」，而门禁在提交前跑

```python
names = wr.git("show", "--name-only", "--format=", "HEAD").splitlines()
folded = [n for n in names if "复盘" in n]
assert folded, "这一笔里有中文路径（复盘/…）"
```

- 门禁是**提交前**跑的 → 那一刻 `HEAD` 还是**父提交**。父提交 `404eaa9`（T-G85）恰好带了
  `复盘/外包卡-002-…md` → 中文路径在 → **绿**。
- 提交一落，`HEAD` 变成**自己那一笔** `46be295`（那次只改了 3 个 ASCII 路径：
  `gates/last.json` / `tests/test_wb_dispatch.py` / `tools/wb_dispatch.py`）→ 中文路径不在
  → **红**。
- 于是**同一棵树**（文件内容一模一样）在提交前是绿的、提交后是红的。下一轮门禁必然红，
  而它跟那一轮被验的产品代码**毫无关系**。

这不是「被查对象变了」，是**判据自己的毛病**。

## 3. 为什么这类用例比没有用例更坏

红一次是小事，坏处在于它**把真红灯淹掉**：卡 002 那轮门禁确实红了，可红的是它 ——
看门禁的人（我）得先花时间证明「这个红与我们改的东西无关」，真红灯混在里面就没人细看了。
判据的价值全在**可信**上：一条会无缘无故红的判据，等于把整个门禁的可信度往下拉。

## 4. 修法：不看真实历史，自己搭一个仓库

在 `tmp_path` 里自己 `git init` + 提交一个 `复盘/中文.md`，再用 `monkeypatch` **只把
`wb_review.ROOT` 指向它**（`tools/` 一行都不用改），然后两件事都要判：

1. **普通 git 确实会转义**（`"\\345\\244\\215…"`）—— 少了这一半，夹具就看不见这个现象，
   测试会在任何实现下都绿（同族规矩：**判据自己要能证明它看得到东西**）；
2. `wb_review.git()` 给出来的是**原样**的 `复盘/中文.md`（带 `-c core.quotepath=false`）。

## 5. 证据（三条都真跑过）

**① 夹具先跑通**（`gates/diag/probes/wb_cjk_tmp_repo_probe.py`）：

```
普通 git  : ['"\\345\\244\\215\\347\\233\\230/\\344\\270\\255\\346\\226\\207.md"']
wr.git() : ['复盘/中文.md']
OK：① 普通 git 会转义 ② wb_review.git() 不转义 —— 夹具成立
```

**② 改完之后仍然是 12 条**（就地重写那一条，不新增 —— 省得全项目所有「12 条」跟着改）：

```
python -X utf8 -m pytest tests/test_wb_review.py -q --no-cov
............    [100%]        ← 12 passed
python -m ruff check tests/test_wb_review.py
All checks passed!
```

**③ 突变检验：修好之后这条判据还有牙**（`gates/diag/probes/wb_review_mutation_probe.py`）：

```
① 拿掉 core.quotepath 之后：exit=1（应当 != 0）     ← 没有它，这条用例当场红
② 还原之后：exit=0（应当是 0）
③ 文件还原：True；git 里无差异：True
OK：判据有牙（突变→红、还原→绿），且 tools/ 一字未改
```

（第一版探针把「还原后跑绿」写在了 `try` 里面，结果自己冤枉自己 —— 已改成还原**之后**再跑。
探针也会撒谎，这条留在这里当记录。）

## 6. 边界（如实写，不假装）

- 改的是**一条判据怎么取证**，不是 T-G84 的功能；`tools/wb_review.py` 的技术实现
  （`-c core.quotepath=false`）与五条判据**一条没变**。
- 这个修法只保证「中文路径不被转义」这一条**自包含**；同文件里
  `test_current_head_passes_the_gate_evidence_check` **仍然**查真仓库 HEAD —— 那是有意的：
  「本项目的提交流程应当让这一笔通过第 ③ 条」本来就该拿真仓库验，而且它查的是
  `gates/last.json` 的 `rev == HEAD^`，任何一笔提交后都成立（不是定时炸弹）。
- 没动的：`src/**`、`tools/**`、`docs/contracts/**`。

## 7. 主控处置记录（为什么先修它、再提交 T-G86）

卡 002 的工作**全部做完了**（红→绿两步都跑过、探针 0/3、29 passed、800 行级 diff 我逐行核过），
却卡在「门禁不过就不许提交」上 —— 而挡路的是**我的**测试。所以顺序是：

1. **先**修这条定时炸弹、跑门禁、提交（`T-G87`，本笔）；
2. **再**在工人那棵树上重跑门禁、`--seal`、提交卡 002 的成果（`T-G86`）。

这样 `T-G86` 的门禁结果对应的是**含本修复的那棵树**，不会出现「门禁测的和提交的不是同一棵树」。
换新编号而不是塞进 `T-G86` 的理由：一条 `Task:` 只许一个台账编号，而且卡 002 的白名单
里没有 `tests/test_wb_review.py` —— 塞进去就是越界。
