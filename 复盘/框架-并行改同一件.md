# 并行修改「同一件东西」：我们的机制 ↔ 文献（以及四条强化）

> **触发（用户 2026-10-03 16:1x）**：「**假如用 8 个 worker 可以吗？**……你搜索一下**对同一个东西进行修改多智能体如何并行**？」
> 两条都办了：**worker 数**那半见 §四（**我没有实测读数，不编**）；**并行改同一件**那半见 §一~§三（DeepXiv + 秘塔两条路，带真实编号）。

---

## 一、我们现在是怎么"并行改同一件"的（先把家底写清）

| 机制 | 我们叫什么 | 它其实是什么（文献术语） |
|---|---|---|
| 一张卡一棵工作树 `.wt/<树>`，工人只在里面写 | 卡树 | **分支隔离 / 私有工作副本** |
| 队列里同一文件**不许两张卡同时写**（`wb_plan check` 当场咬） | 域不相交 | ★ **冲突域划分（conflict domain partitioning）** |
| 收口时 `ff 合流` / 冲突则 `rebase` + 自动解派生物冲突 | 收口链第⑦步 | ★ **first-committer-wins 的乐观并发（OCC）** |
| 台账**只许末尾追加**（铁律 35） | 铁律 | ★ **append-only 共享资源** |
| 成送申请 + 证据指针 + 门禁三值判决 | 申报与判据 | **claim / verify**、**证据门控** |
| 派活器「门禁还在跑 ⇒ 拒派」+ 门禁锁租约 | 守卫与锁 | **admission control + 租约** |

★ **一句话**：我们那套「域不相交 + 卡树隔离 + 收口串行 + 台账追加」**在文献里全部有位置** —— 我们不是在自创。

## 二、文献直接支持我们的三条（★ 都是硬读数）

1. ★★ **2 个工人是甜点，再加会退化** —— **AgentRoom**（CRDT 共享工作区 + MCP 暴露的 `claim/status/broadcast`）[arXiv:2608.23740]：
   5 个前沿 coding-CLI 模型、4 个后端任务；**2 个 agent 时弃权率降 13.7×、质量达峰**，且**优于顺序流水线与朴素并行**。
   ★ 同族：**CodeCRDT** [arXiv:2510.18893] 600 次试验 **100% 收敛、零合并失败**，但**有任务 −39.4% 减速**、
   **代码体积膨胀 82–189%、质量降 7.7%**、**N>5 扩展性受限**。
   ⇒ ★ **我们现在就是 2 个工人（框架线 + 外包线，域不相交）。**

## 二·补 ★★ 有效性检验：**"2 是甜点"管不管我们？**（用户 2026-10-03 16:2x 的追问）

> **用户的质疑（原话大意）**：「为什么 2 是甜点？N 大于多少会退化？★ **有个问题：他们针对的问题和我们这个一样吗？**」
> ★★ **答案是：不一样 —— 而且差在一个关键维度上。我上一轮把他们的结论直接套到我们头上，是过度外推。**

### 他们的场景 vs 我们的场景（逐条对比）

| 维度 | **AgentRoom / CodeCRDT** | **我们** |
|---|---|---|
| 工作区 | ★★ **共享工作区**（CRDT-backed shared filesystem / 共享状态里认领 TODO）——**没有分支隔离** | ★★ **每张卡一棵工作树**（`.wt/<树>`）——**物理隔离** |
| 冲突来源 | 大家**同时改同一份文件** ⇒ 结构性冲突 | **只有落地那一刻才合并** ⇒ 冲突只在收口 |
| 协调方式 | MCP `claim/status/broadcast`、无锁认领 | **队列域不相交 + 门禁锁 + ff/rebase** |
| 并行度的收益/代价 | 收益被**相互干扰**吃掉（★ **体积膨胀 82–189%、质量 −7.7%**） | 干扰被隔离挡住；代价是**串行落地**（我的排班问题） |
| 任务类型 | 各自认领**独立 TODO**（本该独立） | 卡之间**可能真的同域**（该串的） |

★ **为什么"2 是甜点、N>5 退化"**（他们给出的机制，文献原文口径）：
1. **协调开销随 N 增长**（两两认领竞争、广播噪声）；
2. ★★ **共享状态的"观察噪声"**：每个 agent 看见别人的**半成品** ⇒ 重复劳动 ⇒ **代码体积膨胀 82–189% 就是这么来的**；
3. **质量稀释**（−7.7%）：各自做局部最优，缺全局一致性；
4. **上下文/注意力稀释**（ALMAS [arXiv:2510.03463] 专门治这个）；
5. ★ **MAST**：根因是**架构与组织设计**，不是模型能力。

### ⇒ 结论（三条，都改了我们的做法）

1. ★★ **"2 是甜点"是"共享工作区"场景的读数，不是我们的上限。**
   我们**恰好避开了那个退化机制**（一卡一树 ⇒ 看不见别人的半成品）。
   ⇒ **不拿它当我们的并行度上限**；★ 我上一轮那句「不要盲目加第 3、第 4 个」**是过度外推，收回**。
2. ★★ **更接近我们的类比对象是"隔离式并行"**：
   - **Uber SubmitQueue / speculative CI** [arXiv:2501.03440]（多候选各自构建、先绿先合，资源 −53%）；
   - **Bazel/远端执行** [arXiv:2405.00796]：**2–16 并行度**下中位加速 **2.0–12.8×**（★ 到 16 还在涨）；
   - **并行批测试** [arXiv:2308.13129]：BatchAll 减 **91%** 机器数。
   ⇒ ★ 这些读数说**隔离式并行到 8~16 仍有收益** ⇒ **我们的并行度上限没有被证伪**，只是**我们自己没测过**。
3. ★ **一条真实的边界**：**若我们把多个工人塞进同一棵树（共享工作区），就落回他们那个场景，2 就是上限。**
   ⇒ ★ 所以「一卡一树」这条规矩**不是形式主义**，它正是**把我们挪出退化区**的那道隔离。
   ★ 而我们的串行**不是**因为在共享工作区里互相干扰，而是因为**域（文件）重叠** ⇒ 解法是**拆域**（卡 188），**不是限并行数**。

★ **仍然成立的一条**：**失败模式那半（MAST 的 14 种）与"判据是设计问题"** —— 那条与场景无关，照用。
2. ★★ **多智能体的失败是"架构与组织设计"问题，不是模型能力问题** —— **MAST**（1600+ 标注轨迹 / 7 个 MAS 框架 / 人类标注 κ=0.88）
   [arXiv:2503.13657]：归纳 **14 种失败模式 / 3 大类**（系统设计问题 · agent 间错位 · 任务验证），
   并给出关键结论：**针对性 prompt 干预解决不了根因**。⇒ ★ 这正好是我们一直在做的事（**改机制、不改措辞**），也给了我们一张**现成的检查表**。
3. ★ **共享资源用"仅追加"**：秘塔那侧的中文实践总结直接给出——「共享资源适合**仅追加语义**：智能体只往共享草稿本追加，不编辑彼此已有的输出」。
   ⇒ ★ 我们的**台账铁律 35** 就是这个，**现在它有了外部理由**。

## 三、★★ 文献给的四条**强化**（我们还没做或做得很粗）

| # | 强化 | 依据 | 落点 |
|---|---|---|---|
| **H1** | **冲突要"预测"，不要"事后合并"**：文本级合并工具**不可靠** —— ★ **79% 的编译期冲突与 75% 的动态冲突逃过现有工具**；而**冲突可预测**（轻量 Git 特征 + RF，7 语言，**98% 精度 / 96% 召回**），可作 speculative merge 的预筛 | [arXiv:2102.11307]（漏检率）· [arXiv:1907.06274]（可预测）· [arXiv:1802.06551] SAFEMerge（语义无冲突性**可形式化验证**，52 场景 75% 通过、找出 11 个语法工具漏的违规） | ★ 我们的「域相交」是**粗粒度预测**；可升成**按历史冲突率预测**（哪两张卡最可能撞） |
| **H2** | ★★ **并行候选 + 差分验证**：**同时跑"打过补丁"与"没打补丁"两个版本**，用代理比对输出、**区分"预期差异"与"意外偏差"** | [arXiv:2106.01154] | ★ 这是**对抗复核的强化版**：现在是「事后异步审」，可以做成「同活双做 + 差分」（代价翻倍，只用在**高风险卡**） |
| **H3** | ★ **并发控制要"自适应"**：agentic 事务的特征是**长执行、不规则间隔、非确定性访问** ⇒ 需在**乐观/悲观之间动态切换**（RL 驱动，吞吐提升达四个数量级、尾延迟降 90%） | [arXiv:2603.13906] ATCC · [arXiv:2110.03028]（★ **高冲突下乐观反而更优**） | ★ 我们现在是**纯乐观**（域不交就放行、撞了才 rebase）；可按「这张卡历史上撞过几次」动态收紧 |
| **H4** | **合并工具的取舍有反直觉结论**：只在**错误合并代价低**时复杂工具才最优；★ **对 Git 的 import 处理做简单增强，常胜过复杂工具** | [arXiv:2410.09934] | ★ 我们收口链的「自动解派生物冲突」是**简单增强**那一类 —— 方向对了，别过度工程 |

## 四、★ 「8 个 worker 行不行」——我**没有实测读数，不编**

**已知（现成的）**：
- `scripts/run_gates.py:22-23` 自己写着默认值的来由：「**不设 = `min(4, cpu)`**（机器 32 核但只有 **15.2 GB 内存**，
  `-n auto` 会拉 **32 个 worker → 换页**）」⇒ ★ **仓库早就把"4"定成这台机器的保守默认**。
- **CPU 不是瓶颈**（32 核）；**内存是唯一约束**（现可用 ~4.5 GB）。
- 今晚实测：**1 worker = 620~700 s；4 worker = 250 s**（≈ **2.8×**）。

**我没有的**：**每个 xdist worker 的常驻内存**（今天量的两次都量歪了：一次在收集阶段、一次把我的探针自己算进去了）。
⇒ ★★ **所以「8 行不行」必须跑一次对照实验**（同一棵树、同一套测试，`-n 4` vs `-n 8`，量**总时长 + 峰值内存 + 最慢的 worker 是谁**）。
★ 我的**预期**（**不是读数**）：4→8 的边际收益**明显小于 2×**（Amdahl + 最慢的测试文件 + 内存带宽），
内存上 8 个 worker 大约要 **2~3 GB**（**估的**）⇒ 在「DSH 2.5 GB 还占着」的时候**不要上 8**。

**⇒ 这笔实验该落在哪**：卡 184（收口增量门禁）的「**跑法落档**」，或卡 164（观测面）—— **把 worker 数变成读数，而不是拍**。
