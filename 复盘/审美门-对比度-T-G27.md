# 审美门 · T-G27 —— 对比度做成一道「棘轮」，以及它第一天就抓出来的那个真缺陷

> 起因：T-G26 用 workbench 判据第一次量出**亮色主题 9 对不达 AA**（最糟的完成徽标 1.96:1），
> 用户看完说「审美门的话做一做了」。本卡把它做成真门禁，接进门禁脚本。
>
> **为什么不能是一把硬门**、**它第一天抓到了什么**、**什么时候能收紧**，都在下面。

---

## 1. 一句话结论

**做成了「棘轮」而不是硬门**：现状一条不放过地登记（18 条，逐条写明根因与修法），
然后**只许变好、不许变坏** —— 出现没登记的不足、或比登记值更差就 FAIL。
接进门禁当第 **12** 项阻断项。**顺手抓到并修掉一个真缺陷**：暗色主题的 toast
文字是 1.0:1（**完全看不见**）。

---

## 2. 为什么是「棘轮」，不是硬门

硬门意味着"只要不达标就红"。可现在**亮色主题有 18 条不达标**，一接进去门禁永远红 ——
而本项目铁律是「**门禁不过 ⇒ 不许提交**」。于是只有两条路：要么先把颜色全改好（= 直接开视觉线，
用户明说那条线**要先商谈**），要么把"现状"如实登记下来、只拦增量。选了后者。

登记表就是 `tools/contrast_baseline.toml`，规则跟台账的 `[exceptions]` 一个精神：
**逐条留痕、修一条删一条，不许静默豁免**。三条判定：

| 情况 | 判定 | 门禁 |
|---|---|---|
| 达标，且没登记过 | `PASS` | 过 |
| 达标，但登记过（说明登记表该删行了） | `FIXED` | 过，**并打印"可以删掉这一行"** |
| 不达标，且登记过、没变差 | `KNOWN` | 过（算已知欠账） |
| 不达标，且**没登记过** | `NEW` | ❌ **FAIL** |
| 不达标，且**比登记值更差** | `WORSE` | ❌ **FAIL** |

为什么 `FIXED` 要放行而不是报错：否则**修好了反而提交不了**（得先删行才能提交，但删行这个动作本身
也需要一次提交）—— 这正是"棘轮只能往一个方向转"该有的样子。
（另：登记值与实测差 0.02 以内算四舍五入噪声，不算"变差"。）

---

## 3. 它量什么、怎么量

- **量的是「字在底上看不看得清」**：WCAG 相对亮度公式算对比度，阈值 正文 ≥ **4.5**、大字 ≥ **3.0**。
  本项目强调色**既当 44px 计时器又当 12px 小字**，所以统一按最小的那个用法取 4.5（保守取法）。
- **只用令牌，不抄表**：值从 `src/web/app.css` 的令牌区（`:root` / `[data-theme="dark"]`）现读，
  `var(--x)` 递归解析（`--toast-bg: var(--text)` 这种一层套一层也认）。
- **两套主题各算一遍**（42 条组合 = 亮 21 + 暗 21）。
- **徽标的底是算出来的，不是令牌**：`.badge.*` 的底写的是
  `color-mix(in srgb, var(--ok) 18%, transparent)` —— 得先合成（18% 状态色 + 82% 卡片色）再算，
  合成比例**从 CSS 里读**，不写死。这一类恰恰是全表最糟的三条。
- **它不需要浏览器**：对比度是纯计算。本环境没有浏览器 GUI ——
  所以这是本项目**第一条能自动验的审美门槛**（T-G26 里"没有视觉基线"的那句遗憾，这里补上了一块）。

```powershell
python -X utf8 tools/contrast_audit.py            # 人读（全表 + 结论）
python -X utf8 tools/contrast_audit.py --json     # 机器读
python -X utf8 tools/contrast_audit.py --check    # 门禁用（脚本里就是接的这一条）
```

## 4. 实测：42 条组合 / 24 达标 / **18 条欠账**（全在亮色主题）

18 条**归到三条根因**（登记表里也是按这三条分组的）：

### ① 亮色下「强调色/状态色当正文小字」——8 条

| 组合 | 对比度 | 谁在用 |
|---|---|---|
| `--ok` on `--bg` / `--card` | **2.18 / 2.28** | 完成色当文字 |
| `--accent` on `--bg` / `--card` | **3.52 / 3.68** | `.accent` / `.flag`（12px）/ `.prio.mid` / 底栏选中 |
| `--danger` on `--bg` / `--card` | **3.60 / 3.76** | 危险色当文字 |
| `--muted` on `--surface-2` / `--accent-soft` | **4.23 / 4.34** | `.badge.todo` / `.badge` 默认底 |

这一档颜色（`#22c55e` / `#3b82f6` / `#ef4444`）当**色块**没问题，当**12–14px 文字**就不够。
workbench 包对这件事有明文规矩：**强调色不做小字**（颜色由填充/标记承担，字用正文色）。

### ② 「色块里用同一个颜色写字」——3 条（全表最糟）

| 徽标 | 底 | 对比度 | 按包的解法的实测值 |
|---|---|---|---|
| `.badge.done` | 18% `--ok` 合成的浅绿 | **1.96** | 字改 `--text` → **12.57** |
| `.badge.doing` | 18% `--accent` 浅蓝 | **3.00** | → **11.92** |
| `.badge.hard` | 18% `--danger` 浅红 | **2.96** | → **11.51** |

**修法不需要发明任何新颜色**：状态词改用正文色写，状态色由**底**承担（workbench 的原文解法）。
顺带说一句：这三处是**同一个原子抄了三份**（`app.css:155/284/287`），
而 workbench 里正好有一条 Gotcha 说"一个 Chip/Badge 原语抄三份，就是令牌层开始烂的方式"。

### ③ `--accent-on` 只有一个值，但强调色有 6 个预设——7 条

| 预设 | 白字对比度 |
|---|---|
| `#f59e0b` | **2.15**（最差） |
| `#10b981` | 2.54 |
| `#0ea5e9` | 2.77 |
| `#3b82f6`（默认） | 3.68 |
| `#ef4444` | 3.76 |
| `#8b5cf6` | 4.23 |

**6 个预设没有一个能让白字过 4.5**。设置页换个颜色，就等于把按钮文字弄糊 ——
「让用户换强调色」这件事必须**连"它上面的字用什么颜色"一起定**（workbench 的做法是
`--accent-ink` 随主题翻转：亮色白字、暗色深字，因为白字在暗色强调上也不够）。
参考值：workbench 自己的 `#2f6feb` 白字 **4.57**（过）；但它在 `--bg` 上当正文仍只有 **4.30** ——
所以"换个色"解决不了①，①的解法是**别让强调色做小字**。

## 5. ★ 第一天就抓到一个真缺陷：暗色主题的 toast 看不见（已修）

写门的时候顺手把 `.toast` 也算进去，结果：

```css
.toast { background: var(--toast-bg, var(--text)); color: var(--text-on-dark); }
```

`--toast-bg` **全项目从来没有定义过**（只有这一处用到，JS 里也没 `setProperty` 过它）。
于是：

| 主题 | 实际底色 | 文字色 | 对比度 |
|---|---|---|---|
| 亮色 | `--text` = `#1e293b`（深） | `#fff` | 14.63 ✅ 侥幸对 |
| **暗色** | `--text` = `#e6edf7`（**浅**） | `#e6edf7`（浅） | **1.00 ❌ 字完全看不见** |

亮色下它侥幸是对的（`--text` 恰好是深色），**暗色下 `--text` 翻成浅色，文字色 `--text-on-dark`
也是浅色 → 一个浅底浅字的白块**。而 toast 在界面里被调用 **161 处**。
之所以一直没发现：**暗色主题是可选开关、而所有护栏都是结构断言（不是渲染断言）**。

**修法（最小、且不发明颜色）**：把这个从来只当"回退值"用的令牌**真的定义出来** ——
亮色 `--toast-bg: var(--text)`（**效果与原来逐字节相同，视觉零变化**）、
暗色 `--toast-bg: var(--surface-2)`（用既有的"更浅的底"这个角色，与浅色文字 13.04 ✅）。
`.toast` 那条回退写法也一并去掉（**回退值是把 bug 藏起来的地方**）。

> 这一条**不在欠账登记表里** —— 它不是"欠账"（欠账是"以后有空再改的审美差距"），
> 它是**字看不见的缺陷**。缺陷当场修，不登记。

## 6. 它挡得住什么 / 挡不住什么（诚实边界）

**挡得住**：
- 改令牌把字改糊（`WORSE`）；
- 新加一处"浅底浅字"（`NEW`）—— 比如以后加一个 `.badge.warn` 又用同色写字，这里会红；
- 徽标换了合成比例（比例从 CSS 读，改了会重算）。

**挡不住**（别把它当"审美已经验过了"）：
- **"好不好看"**：对比度是**可访问性地板**，不是审美判断。层级、留白、字体气质它一概不管；
- **字号 / 行高 / 字重 / 间距**（T-G24 §5 里"平"的主因）—— 那是视觉线的步 3；
- **hover / focus / disabled / 选中态**的对比度（现在只算静态的主力组合）；
- **非文字图形**：图标 vs 背景、图表线条 vs 底、边框是否看得见（WCAG 对非文字要 3.0，
  这一版没覆盖，登记表里也没有对应条目）；
- **只要有人把新欠账写进登记表，门就过了** —— 登记表本身需要人看。所以它的规矩是
  "每条必须写 `why`/`fix`"，且**修一条删一条**；`--strict` 就是用来收口的（见下）。

---

## 7. 什么时候能收紧成硬门（三步，视觉线开工后走）

1. **视觉线修**：按上面三条根因把 18 条修掉（①②不需要发明颜色，③要定 `--accent` 与预设）；
2. **销账**：每修好一条，脚本会打印 `[已修]`，**把那一行从 `contrast_baseline.toml` 删掉**；
3. **收口**：登记表空了之后，把 `run_gates.py` 里那条命令加上 `--strict`
   （或在登记表为空时直接改成硬判），它就变成一把真门。`--strict` 现在就能跑，
   只是会告诉你"还有 18 条没修"。

## 8. 踩过的坑（记下来，别再犯）

- **选择器正则把注释吃进了选择器**：第一版 `badge_pairs()` 只抓到 `.badge.hard`，
  漏了 `.badge.done` / `.badge.doing` —— 因为 `.badge.done` 头上正好有一行注释，
  `.badge.hard` 头上没有。修法是**先把 CSS 注释删干净再匹配**，并且**用一条测试钉住"三块都要在"**
  （`test_badge_shortfalls_are_actually_detected`）—— 这种漏抓最危险的地方在于：
  它会**让门显得是绿的**。
- **TOML 里写 ASCII 双引号**（老坑，第 N 次）：`contrast_baseline.toml` 的 `why`/`fix`
  一律用「」，否则 `tomllib` 直接崩。
- 门禁脚本的 `summarize()` 认的是 `PASS（` / `审计通过` 这类字样，所以工具的**最后一行**
  特意写成 `对比度审美门 PASS（…）`，这样 trailer 里能直接看到数字。
