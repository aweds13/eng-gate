# 复盘 · 文档偏移、接缝断裂与约束框架（为什么要把 git + 台账变成硬约束）

> 时间：2026-09-18（用户提问：「文档在工作时发生了偏移和缺失，怎么更好地处理？你的后端好像和前端连接很差呀。
> 而且后端也做不完整。先商量一个好的方向。好的框架来约束你。」→ 确认：「**审计不通过就别提交**，
> 按你的倾向来，我的要求是把一条线一条线地做完去。」）
> 性质：**问题复盘 + 框架决策记录**。框架的落地规格在 `复盘/长任务执行协议.md` §九；任务清单在 `任务重规划-剩余工作.md`。

## 一、用户指出的三件事（原话 → 我的核实结果）

| 用户说 | 我核实到的事实 | 判定 |
|---|---|---|
| 「文档工作时发生**偏移和缺失**」 | ① R1/R2 的 changelog 直到做 R4 才补；② `modules.md`/`traceability.md` 的"未实现清单"是**两轮前**的（说习惯不能增删、说周结算/可视化没做，实际早已做完）；③ 契约 OP-9 写「入口：任务详情面板」而**该面板当时根本不存在**；④ 交接文档的"未实现"段落与审计结果差 10 余条 | **成立**：文档靠"我记得回填"，**漏了没有任何东西会失败** |
| 「**后端和前端连接很差**」 | 后端有 `/api/groups`（只读）、有白名单/勿扰判定、有 `assignments(assignee=)` 过滤 —— **界面一个入口都没有**；反过来界面想要的能力（按人筛任务、未进 My Day 的独立视图）后端没有对应查询 | **成立**：两边各自"做完"，**中间那条缝没人负责** |
| 「**后端也做不完整**」 | 审计：**没做 22 / 半成品 9**。而且是**成组缺**：任务字段整块缺（提醒/附件/备注/优先级）、跨端同步整条缺、复习的升级/形式/句柄三条缺 | **成立**：按"域"开发时只做了主干、没做配套 |

**根因（一句话）**：**规格文档、后端能力、前端入口三者之间没有"机器可校验的接缝"** ——
全靠我人工同步，我一漏，没有任何机制会失败。所以这三件事本质是**同一个病**。

## 二、决策：让 git 承载"任务身份"，让台账承载"任务状态"，让脚本负责对账

用户提议「每次干完上传 git，然后借 git 和文档一起审计、同步进度」——**这个方向是对的，且比"更努力回填"强一个量级**，
因为 git 是本项目**唯一不可能被我遗漏**的记录（带时间戳、文件清单、内容，且不可篡改）。落地方案：

```
提交信息（git 原生 trailer）
  Task: T-F1-01
  Refs: SR-F1.4, OP-9
  Ledger: SR-F1.4 partial -> done
  Gates: pytest 290 passed; web 18 OK; audit PASS
        │
        ▼
docs/traceability.toml   ← 机器可读台账：每条 SR 的状态 + 可验证断言（backend/api/ui/tests）
        │
        ▼
scripts/audit_progress.py  ← 六项对账（见 §三）；不通过 → 退出码 1 → 不许提交
```

**六个对账项**：

| # | 检查 | 读什么 | 不通过说明什么 |
|---|---|---|---|
| ① | 提交挂了任务号 | `git log` trailer `Task:` | 无卡开工（违反协议） |
| ② | 任务号已登记 | `traceability.toml` | 做了没登记 / 编号写错 |
| ③ | **声称 = 证据** | 台账里 `status=done` 的每条断言（文件/正则/表列/路由/界面元素/测试）逐条实跑 | **"以为做完"当场暴露**（OP-9 那类问题机器可拦） |
| ④ | **文档与代码同提交** | `git show --name-only HEAD` | 改了 `src/` 却没改台账/changelog/CHECKPOINT → **偏移当场暴露** |
| ⑤ | 门禁有**落盘产物** | `gates/last.json`（门禁命令真跑出来的）+ trailer `Gates:` | 声称跑了测试但没产物 → 不许写"已通过" |
| ⑥ | **进度可从 git 重建** | 台账 `todo` ↔ `git log` 的 `Task:` | todo 其实已做（漏登记）/ done 却没提交（虚报） |

**第六项就是用户要的"同步进度"**：以后进度不再由我手写，而是**从 git 推出来**（脚本可复现）。

## 三、为什么"审计不通过就别提交"能治偏移（而不是靠我自觉）

- 偏移的本质是**"我说完了"与"实际做完"之间没有强制对账**。把审计挂到提交前（`run_gates.py` 里同时跑
  审计与质量门，任一失败即退出非零），就变成：**要么对齐，要么提不上去**。
- 我**不能**再用"测试全绿"当挡箭牌：pytest 全绿只证明"已写的测试通过"，
  审计才检查"声称的每一条是否真有证据、文档是否同步"。
- **豁免必须留痕**：过渡期用 `exceptions` 列表逐条列出"已知欠账"（当前 40 条），
  每修一条就删一条 —— 豁免本身就是一份**看得见的欠账清单**，不会变成"永久白名单"。

## 四、诚实的边界（这套机制**不**能保证什么）

| 能保证 | **不能**保证 |
|---|---|
| 谁改了什么文件、什么时候、哪个提交 | 改动**对不对**（功能是否正确） |
| 任务号是否挂、文档是否同提交 | 文档写得**准不准**（可以同提交但内容失真） |
| 台账断言的证据**存在** | 测试**真的跑过**（所以要有 ⑤ 落盘产物） |
| 进度可从历史重建（不靠我记） | **视觉/交互好不好**（只能人工过目，本轮已踩过这个坑） |

所以它是**第三道防线**：① 单测/护栏（对不对）② 人眼（好不好用）③ **git+台账审计（有没有漏、有没有虚报）**。
三者不可互相替代 —— 本轮"UI 修崩了但 268 项测试全绿"就是只有第一道防线的后果。

---

## 五、执行方式（用户定的节奏）

1. **一条主线一条线地做完**：不跨线撒网。
2. **先做主线 F1（任务管理）**：它是所有线的地基（专注/复习/学业/团队都挂在任务上），
   也是缺口最集中的地方（审计里 F1 占 9 条）。
3. **顺带做这条线上的交叉点与依赖模块**，不单独排线。
4. **每条主线做完把前端一起做完**，然后**用户验收这一条线**，通过后再开下一条。

## 六、本轮已发生的"偏移"实例（留证，便于以后对照）

| # | 偏移 | 被抓到的方式 |
|---|---|---|
| 1 | R1/R2 的 changelog 缺失，到 R4 才补 | 我做 R4 文档时发现 |
| 2 | `modules.md` 声称习惯不能增删（实际早实现） | 本次全量审计（脚本比对路由表） |
| 3 | `traceability.md` 声称周结算/可视化未实现（实际早实现） | 同上 |
| 4 | 契约 OP-9 写了入口、界面没有 | 用户反馈「点进去看不到详细」时才发现 |
| 5 | 后端 `/api/groups` 只读、白名单/勿扰无界面 | 本次审计（"有路由但没有任何视图使用"） |
| 6 | 交接文档"未实现"清单与审计结果差 10 余条 | 本次审计 |

> **结论**：这 6 条**全部**是"人工同步"漏掉的，而其中 4 条本可以用机器检查拦住。这就是要做这套框架的全部理由。
