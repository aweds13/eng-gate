## 一、问题：台账里「同号不同义」

`docs/traceability.toml` 是项目的**唯一真源**（五层台账）。它有一批条目的**编号与规格对不上** ——
条目写的是**相邻编号**那条规格的内容。

### 1.1 怎么发现的

不是靠人眼，是靠两个**交叉旁证**：

1. 2026-09-18 的全量五层审计报告（`全量审计报告-五层一致性与缺口登记.md`）里，
   缺口编号 GAP-NF-05/06/10 引用的是 `SR-NF8 shadow`、`SR-NF10 扩展示例`、`SR-NF11 PR 模板`
   —— 与**规格**一致，与**台账**不一致；
2. 写 `SR-NF11 PR 模板` 那条卡时发现：台账 `SR-NF12` 的描述正是「Git 工作流」，
   而规格的 `SR-NF12` 是「数据迁移与备份」，**台账里根本没有这条**。

于是做了工具 `scripts/audit_titles.py`（抽规格标题 × 台账标题做内容字重叠度），一跑：
**15 条确定错位 + 14 条需人核对**（共 64 条可比）。

### 1.2 根因（比"整体挪一格"更麻烦）

把 F1 这一段摊开看就清楚了：

| 规格 | 规格内容 | 台账里对应谁 | 性质 |
|---|---|---|---|
| `F1.1` | My Day 排序 + 昨日未完成进逾期栏 | 台账 **F1.1**（My Day 语义）+ **F1.2**（排序） | 一条规格被**拆成两张卡** |
| `F1.2` | 提供视图 My Day/Important/Planned/Flagged | 台账 **F1.3** | 台账编号比规格**多走一格** |
| `F1.3` | 自定义分组 + 计数 + 多分组 | 台账 **F1.12** | 台账把分组丢到了很后面的自编号 |
| `F1.4` | 任务字段 + 状态流转 | 台账 **F1.4** + **F1.5** | 又是拆成两张 |
| `F1.5` | 重复任务 + 热力图管节奏 | 台账 **F1.6** + **F1.7** | 又是拆成两张 |
| `F1.6`~`F1.9` | 子任务 / 存档 / 逾期处置 / 三类任务 | 台账 **F1.8**~**F1.11** | 一路顺延 |
| — | （规格里没有） | 台账 **F1.13**（编辑）、**F1.14**（软删除+回收站） | **实现层自造卡也占了 `SR-` 号** |

**根因 = 台账既"拆卡"又"顺延编号"**：拆出来的卡继续用 `SR-` 前缀吃掉了后面的号，
于是一条 `SR-F1.3` 在规格里和在台账里**指的是两件事**。
F2/F6/F7/F9 与整个 NF 层（NF2~NF12 整体错一格）都是同一成因。

> 为什么这比"整体错位"更难缠：整体错位只要挪一下；**同号不同义**会让**引用编号的人无法判断
> 说的是哪一个** —— 而"引用编号"正是这套五层文档的工作方式。

### 1.3 为什么审计一直没抓到

`scripts/audit_progress.py` 的「规格覆盖」是 `sr_ids - set(entries)` ——
**只要编号在台账里出现就算通过，从不比对标题/含义**。
这是**检查粒度**的问题，不是检查写错了：它能保证"每条规格都有人认领"，
但保证不了"认领的人真的在做那件事"。

## 二、解决的规则（用户 2026-09-20 决定，选 A）

> 备选 B 是"承认台账自编号，给每张卡加 `covers=[...]` 字段"。
> 没选它的理由：从此台账与规格是**两套编号**，读的人每次都要跨表跳 ——
> 而这次的教训恰恰是"编号本身要能直接读懂"。

**编号规则 A**（已写进 `docs/traceability.toml` 文件头 与 `docs/CODING_GUIDELINES.md` §9.1「台账编号规则」）：

| 号 | 含义 | 约束 |
|---|---|---|
| `SR-Fx.y` / `SR-NFnn` | **规格条目** | 台账条目的含义**必须**与规格同号条目一致；标题约定**以规格原词开头** |
| `SR-Fx.ya` / `SR-Fx.yb` | **规格条目拆出来的卡** | 一条规格拆多张卡时按规格文本顺序加小写后缀；后缀卡**算同一个规格条目** |
| `T-*` / `STEP-*` / `OP-*` | **实现层自造卡** | 规格里没有这件事时**只许**用这三类前缀，**禁止**用 `SR-` |

配套的两条机器口径：
- **覆盖检查按基号判**：`SR-F1.1a` 与 `SR-F1.1b` 合起来算覆盖了规格 `SR-F1.1`；
- **反向也要查**：台账里**不许**出现规格里没有的 `SR-*` 编号（否则 FAIL）。

## 五、怎么执行的（可复制）

1. **先给工具**（T-D2 的上半）：`scripts/audit_titles.py` ——
   抽规格标题（认 `## SR-NFxx · …` 与 `- **SR-Fx.y**（…）～ …` 两种写法）→
   与台账标题做**内容字 Jaccard** → 分 `shifted`（与相邻编号更像）/ `needs_review`（与自己 0 重合）两级。
   在门禁里先挂**信息性**一步（`blocking=false`），让欠账每次跑门禁都露脸，但不挡提交。
2. **工具升级**（本次）：加 `unmapped` 级（台账有、规格没有的 `SR-*`）、`base_id()` 去后缀、
   `--check` 把 `shifted` + `unmapped` 当失败；门禁从"信息性"**转正为阻断项**（第 10 项）。
3. **一次性迁移**：脚本按**两阶段改名**（旧号 → 占位符 → 新号）做，因此与顺序无关，
   不会出现"改到一半撞名"；随后按新编号**重排条目**（TOML 顺序本无意义，但人要读）。
   改名映射就是本文 §三。
4. **收尾**：`audit_progress.py` 的覆盖检查改**按基号**判 + 新增"台账不许有规格没有的 SR 号"；
   `tests/test_audit_titles.py` 上那个 `xfail(strict=True)` 的闹钟**按约定删掉**，换成真断言
   （错位必须为 0）—— 它本来就设计成"修好就 XPASS 逼人删"。
5. **验证**：`audit_titles` 72 条 SR 卡 **0 错位 / 0 无对应**；`audit_progress --no-git` 结构自检全过、
   `done` 条目的断言逐条成立；全门禁（含 `--check` 阻断项）绿。

## 六、防复发：三道机关

| 机关 | 拦什么 | 失败条件 |
|---|---|---|
| `audit_progress.py` 覆盖检查（按基号 + 反向） | 规格有条目没人认领；台账出现规格里没有的 `SR-` 号 | 任一条 → 审计 FAIL（不许提交） |
| `audit_titles.py --check`（门禁阻断项） | 编号在、**含义**错（写成了隔壁那条） | 出现 `shifted` 或 `unmapped` → 退 1 |
| 台账标题约定（**以规格原词开头**） | 读的人分不清"这张卡属于哪条规格" | 人读一眼就能判断，不靠工具 |

> 一句话教训：**只按编号对账的检查，永远抓不住"编号在、含义错"**。
> 编号是给人和机器**共同**用的索引 —— 索引错了，再严的审计也只是在核对一个错的名字。
