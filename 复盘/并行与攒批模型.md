## 二、一天一批（攒批）

```
早上：写卡（一批 N 张，域互不相交）
  → 登记：一次提交（spec 必须进 HEAD，否则卡树里读不到自己的规格）
  → 建 N 棵树（同一基点）+ N 个工人**并发**出去
  → 工人收工 → 各自交成送申请（wb_task.py claim）
傍晚：收口**一次**
  → wb_land.py --batch B-<批号>   ← 本仓**已有**这条：一次门禁、一笔提交，把整批落地
  → 队列 status 一起翻
```

★ 要点：`wb_land.py` 的 `--card` 与 `--batch` **必须恰好给一个**（批号也能当门禁锁的标签）。
所以「一天一次提交」**不需要改收口链** —— 用 `--batch` 那条路。

### ★★ 一条被用户追问才逼出来的规矩：**一天一个栅栏，不是一张卡一个栅栏**

主控 2026-10-13 当天犯的错：给**每张卡**都建了一个栅栏（`B-DTREE` / `B-DSHTIE` / `B-PVIEW` …，
每个只有 1 个成员）。那样的栅栏**永远攒不成批** —— `--batch B-XXX` 一次只能收一个成员的批，
等于逐张落地，只是换了个写法。

**正确做法**：**当天所有卡登记到同一个栅栏**（如 `B-20261013`），成员逐个列进去。
于是「收口一次」= `wb_land.py --batch B-20261013` ⇒ **一次门禁、一笔提交、整批落地**。

用户追问原话：**「这个机制为什么没有固定到工作流里」** —— 答案见卡 212（给机制装牙，
不是再写一份文档）。当天实测的漂移证据（原样）：

```
B-DTREE    collecting 0/1   ← 它的卡 203 早在 e45267b 落地了
B-DSHTIE   collecting 0/1   ← 它的卡 206 早在 64bd500 落地了
（当天 7 个栅栏全部 collecting 0/1 —— 栅栏状态机只有人手工推，而没人推）
```

**为什么能省**：现在一张卡要两趟门禁（登记一趟 + 落地一趟，各约 3~5 分钟）；
改成批之后，**一批**才两趟。N=6 时，门禁时间从 12 趟降到 2 趟。

## 三、并行的硬约束（不许假装能并）

1. **同域不能同批**：两张卡声明要改同一个文件 ⇒ `wb_plan.py check` 会拒。
   ⇒ 写卡时就要把域**切成不相交**；切不开的说明是**真依赖**还是**只是同文件**（本仓 B-DOMAINSYM 的结论：
   串行的真因常常只是共享文件，不是依赖）。
2. **收口串行**：门禁锁是一把（`TF_GATE_MAX_CONCURRENT=2`），落地链靠它串行。
3. **内存闸**：跑门禁要 ≥ **2 GB** 可用（**用户定的阈值，不许绕过** —— 曾经把用户的游戏挤崩过）。
   ⇒ 工人多开时，收口要等它们退。
4. **派活产物必须落主仓**：从**主仓**跑派活器 + `--cwd <树>`（卡 203 修的就是这个；从卡树里跑会把租约登记成主树）。
