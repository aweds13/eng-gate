# 复盘 · 三层断裂诊断（Spec/Impl ↔ 真实代码）

> 阶段：Spec→Impl 的设计与实现判断（接续《意图到规格-产品判断复盘》）。
> 范围：`docs/specification/`（判断依据）+ `docs/implementation/`（被审对象）+ `src/timeflow/`、`src/web/`（证据）。
> 目标：解释 vibe-coding 产出「功能只做一半 + 交互不完整」的机制性原因，给出可修复的断裂清单。
> 方法：以「用户可见闭环」为尺子，逐操作、逐模块、逐链路核对；每条结论附代码/规格证据。

---

## 一、核心结论

**根因不在 spec 层，而在 impl 层缺一种东西：`implementation/` 只描述了「有哪些模块、模块负责什么」，从未定义「每个操作怎样才算做完」。**

由此产生**三层独立断裂**（此前只发现第②层，且不完整）：

| 层 | 名称 | 性质 | 后果 |
|---|---|---|---|
| **①** | **操作闭环断裂**（模块内） | 单个动作只有「做」，没有「改/撤/后续/属性」 | 用户点下去，动作半途而废（如新建任务不能设截止、专注无法结束） |
| **②** | **模块联动断裂**（模块间） | 动作完成后不向其它模块传导 | 数据孤岛（专注不记账、完成不记账、复习不记账） |
| **③** | **使用动线断裂**（跨操作） | 从「想做」到「做完」的完整路径不成立 | 主流程走不通（无法「挑任务→专注→结束→记入→看变化」） |

**①是地基**。操作本身不闭环，②③接得再对也无意义。

## 二、第①层：操作闭环断裂（逐操作核对）

> 尺子：一个操作要闭环，须具备「入口 / 前置 / 输入（属性可设）/ 后续动作 / 可逆性 / 界面反馈」六要素。

### 证据汇总表（前端 `src/web/index.html` 共 195 行，为全部交互面）

| # | 操作 | 现状 | 缺失的闭环要素 | 对应 SR |
|---|---|---|---|---|

### 第①层的模式化归因（5 类）

1. **「只能做，不能改/撤」**：完成不可撤销、无编辑、无删除（#2/#3/#6）。
2. **「属性不可设」**：新建只有标题，其余字段全靠默认（#1/#13/#15）。
3. **「动作缺一半」**：开始不能结束（#7）、打卡无管理（#10）。
4. **「入口不存在」**：应有但完全没有的动作（#4/#5/#8/#12/#14/#16/#17/#19）。
5. **「名实不符」**：按钮名与行为不一致（#3 移除≠移除、#20 切换不生效）。

## 四、第③层：使用动线断裂（主流程走不通）

> 尺子：用户真实的一天，从想到做完，路径是否连续。

**关键动线 A：把一件事做完（最核心）**
```
想做 → 新建任务（✅ 只能输标题）
     → 设定属性（❌ 无截止/分组/重复入口）
     → 加入 My Day（❌ 无法挑选已有任务）
     → 开始专注（⚠️ 能开始，但无法结束/记时长）
     → 完成（✅ 能勾，但不记账）
     → 撤销误操作（❌ 不可撤销）
     → 看到投入/产出变化（❌ 账本无产出轴、无自动投入）
```
**结论：主线在「设属性」处就断了，在「专注结束」「记账」处彻底断。**

**关键动线 B：处理一件逾期（你的痛点场景）**
```
看到逾期（⚠️ 能看到，标红靠 CSS class 但 overdue 卡片不传 CSS 变量给左侧条）
→ 推到明天/改 ddl/标逾期/取消（❌ 四个动作全无入口）
→ 债务变化（❌ 债务靠实时算，无"债务生命周期"落账；约定层要求完成→清零、取消→计完即止，均未实现）
```

**关键动线 C：复习闭环**
```
到期（✅ 列出）→ 优先进 My Day（❌ 无）→ 三态反馈（✅ 有）→ 推进间隔（✅ 有）→ 记投入账（❌ 无）
```

**关键动线 D：学业闭环**
```
建课程（⚠️ 只能输名字）→ 录考核项（❌ 无入口）→ 录成绩（⚠️ 不关联课程）→ 看 GPA（✅ 有）→ 防漏考提醒（❌ 无）
```

## 五、根因分析：为什么 AI 会"只做一半"

| 根因 | 说明 | 证据 |
|---|---|---|
| **R1. impl 层缺「操作闭环」定义** | `modules.md` 写"`manager.py` 管 My Day 与滚动；`status.py` 管状态机"——**只说模块存在，未定义任何操作的完整行为** | `implementation/modules.md:6` |
| **R2. impl 层缺「跨模块调用契约」** | 无"谁在何时调用谁、传什么、失败怎么办"的定义 → 各模块孤立实现 | `implementation/architecture.md` 只有分层图，无接口契约 |
| **R3. spec 的「必须联动」是**结果性表述**，未落成**过程性链路** | SR-F3.1「时长自动计入任务+反馈+投入」是对的，但没写成"调用顺序" | `specification/functional.md:31` |
| **R4. 无「用户动线」定义** | 没人写"从想到做完必须走通哪几步" → AI 按模块清单打勾，打勾即算完 | 全仓无 flows 文档 |
| **R5. 前端与后端契约松散** | 前端 `index.html` 是**单文件 195 行**，各 render 函数独立；后端接口齐备但前端大量**不调用**（DELETE/assessment/guard/finish/selfcheck 等） | `src/web/index.html` |
| **R6. 无验收清单覆盖"闭环"** | `ACCEPTANCE.md` 的 AC 编号被代码注释引用（AC-1~AC-9），但**AC 只验功能存在，不验操作闭环** | `docs/ACCEPTANCE.md` |
| **R7. 死代码与缺失文件无人发现** | `process_repeats` / `log_conflict` 写了不接；`stats.py` 声明不建 → 说明**缺少"声明-实现"对账** | 见 §三 #7/#9/#14 |

## 七、修复方向（结构性，不是打补丁）

**核心：impl 层必须从「模块清单」升级为「行为契约」**，补两类文档：

1. **`implementation/interactions.md`（操作闭环契约）**——给每个用户操作定义六要素：
   入口 / 前置 / 输入（属性可设） / 后续动作（联动） / 可逆性 / 界面反馈。
   例：
   > **操作：结束专注**
   > - 入口：专注页「结束」按钮（计时中可见）
   > - 前置：存在进行中的 session
   > - 输入：无（时长自动算）；中断时三选（暂停｜放弃｜记中断）
   > - 后续：①落库时长 ②ledger 记投入 ③feedback 自动累加 ④绑定任务累加 ⑤刷新界面
   > - 可逆：否（可"放弃"不计入）

2. **`implementation/flows.md`（用户动线契约）**——把主流程写成必须走通的链：
   `挑任务 → 专注 → 结束 → 记账 → 反馈 → 看趋势`。

并配套：
3. **「声明-实现」对账**：扩展 `scripts/check_layers.py`，扫出「引用了不存在的模块/函数」「写了不被调用」。
4. **验收标准升级**：`ACCEPTANCE.md` 的 AC 从"功能存在"升级为"操作闭环"（每个操作有六要素验收）。

## 八、与上一层复盘的衔接

| 层 | 上一份复盘（Intent→Spec） | 本份复盘（Spec/Impl→代码） |
|---|---|---|
| 结论 | 规格只承接了「承诺」，丢了护栏/行为/why | impl 只承接了「模块存在」，丢了操作闭环/调用契约 |
| 共性 | **都是"转录时丢信息"**：需求→规格丢了约束；规格→实现丢了行为 | |
| 修复 | 建约定层 `conventions.md` | 建契约层 `interactions.md` + `flows.md` |

> 一句话：**上一份治的是「该约束的没约束」，这一份治的是「该做的没做完」。**
