# 融洽门 · T-G29 —— 「每个元素都足够融洽」里，能机器判的那一半

> 起因：用户 2026-09-23 说「你能完善那个审美门吗？让这个风格足够的更加融洽，就是每个元素都足够融洽，
> 要有这样的门，能不能做出来？」—— **做出来了，接进门禁当第 13 项。**

---

## 1. 一句话结论

**"融洽"有两半，我只做了能机器判的那一半（一致性），并且把"另一半判不了"写进了代码输出里。**
第一天就有结论：**整张样式表里 `:hover` 和 `:focus-visible` 一条都没有** ——
这既是"每个元素各过各的"最大的来源，也正是你点的「**Raycast 的交互反馈**」要补的那一层，
还正好是「键盘优先做成附加功能」的**前置条件**。

---

## 2. 先说清边界：门判不了"好看"

| | 内容 | 能不能机器判 |
|---|---|---|
| **一致性** | 同一个东西有没有 N 种写法、缺的状态有没有写、只用一次的值有没有溜进来、动效是不是各走各的 | ✅ **本卡做的** |
| **好看** | 这套体系本身美不美、留白够不够、气质对不对 | ❌ **要眼睛** |

所以工具的输出最后一行**固定**打印这句话（并有一条测试钉住它别被删掉）：

> 说明：这只证明「体系里没有新的破例」，**不证明好看** —— 好看要眼睛。

为什么要这么较真：如果这道门被当成"审美已验过"，它就从护栏变成了**假证据**。
它的正确用法是**淘汰破例的候选**（候选方案里有哪些是"看着好看但处处破例"的），
剩下的在活下来的 2–3 个里由人来挑。

---

## 3. 五条判定（都从 `src/web/app.css` 静态算，不需要浏览器）

| 检查 | 判据 | 为什么这等于「融洽」 |
|---|---|---|
| **互动态缺失** | `:hover` ≥1 条规则、`:focus-visible` ≥1 条规则 | 对"手放上去"和"键盘走到这里"都没回应 ＝ 每个元素各过各的；键盘用户还看不见焦点 |
| **一次性裸值** | 尺度类属性上**恰好出现一次**的字面量 = 0 条新 | 只出现一次的值＝它没进体系。**「不融洽」最机械的定义就是「一次性值太多」** |
| **同形状重复** | 属性集相同、只有令牌不同的规则抄 ≥2 份 = 0 组新 | 一个原子抄 N 份，就是令牌层开始烂的方式（workbench 原文），也是"每块长得不一样"的根 |
| **动效超时/循环** | 时长 ≤200ms、无 `infinite` | 各走各的时长＝节奏散；无限循环在工具类界面里是禁忌 |
| **档数**（只报告） | 圆角 ≤3 档（workbench 明文），其余只报数 | 档数就是「语言的收敛度」：同一属性 7 档圆角＝没有语言 |

**判定词汇与对比度门一致**（棘轮）：`OK` / `登记` / `FAIL`；登记表 = `tools/style_baseline.toml`，
**逐条留痕、修一条删一条**。

## 4. 实测：8 条已登记欠账（**这就是视觉线的工单**）

### ★ 最要紧的两条：互动态整表为零

| 检查 | 现状 | 为什么它是要紧的 |
|---|---|---|
| `:hover` 规则数 | **0** | 界面没有任何"手放上去"的回应。这就是"每个元素各过各的"的最大来源，也正是 **Raycast 的交互反馈**那一层 |
| `:focus-visible` 规则数 | **0** | **键盘用户看不见焦点**（WCAG 2.4.7 要求可见焦点）。而这正是用户提的「键盘优先做成附加功能」的**前置条件** —— 没有可见焦点，键盘优先无从谈起 |

> 全表**只有 1 处动效**（`.toast` 的 `transition: opacity .2s`）。也就是说：
> 除了 toast 淡入，这个界面**没有任何状态过渡**。这一条把"我们要补什么"从形容词变成了数字。

### 同形状重复：一个原子抄了 4 份

`.badge.done` / `.doing` / `.hard` / `.todo` —— **四个变体是同一个形状**（`background` + `color`），
只有令牌不同。而其中三个正是**对比度门里最糟的三条**（完成徽标 1.96:1）。
**修法是同一个**：抽成一个原语 + 一张状态映射表（状态色由**底**承担、字用正文色）——
**一次同时解决"一致性"与"对比度"两件事**。这是两道门互相印证的地方。

### 一次性裸值：5 处

| 值 | 位置 | 判读 |
|---|---|---|
| `border-radius: 50%` | `.swatch` | 圆形色块 —— 是**形状语义**不是圆角档位（建议给个语义令牌，别混进"圆角 7 档"） |
| `gap: 2px` | `.rail nav` | 落在最小档 `--sp-1: 4px` **之下** |
| `line-height: 1.5` | `.rail-summary` | **全文唯一一处行高** —— 正是 T-G24 §5-3 说的"行距靠默认" |
| `margin-bottom: 2px` | `.card.panel-card .title` | 网格外的一次性值 |
| `padding: 3px 0` | `.fact` | 同上 |

### 档数报告（只报数、不判）

```
圆角   7 档  ← 超过上限 3：r-lg、r-md、r-pill、r-sm、r-xs、0、50%
字号   9 档：fs-base、fs-lg、fs-md、fs-num、fs-num-lg、fs-num-xl、fs-sm、fs-xl、fs-xs
字重   2 档：600、700
行高   1 档：1.5        ← 字号 9 档 / 行高 1 档，这就是"层级靠字号撑"的数字形态
阴影   2 档：shadow、0 0 0 2px var(--accent), var(--shadow)
```

**读法**：字号 9 档、行高 1 档、字重 2 档 —— 层级几乎全靠字号（T-G24 §5-3 的量化版）；
圆角 7 档 vs workbench 的 3 档 —— 圆角语言还没收敛。

## 5. 它挡得住什么 / 挡不住什么

**挡得住**：新写一个"只出现一次"的间距；把某个原子再抄一份；改样式时把 `:focus-visible` 删了；
加一个 300ms 的过渡或一个无限循环动画。

**挡不住**：
- **好看**（见 §2）；
- **"该有的状态有没有"只到"有没有这类规则"这一层** —— 它不判"这个 hover 好不好看、对比够不够"（那是对比度门的事），
  也不判"哪个类应该有 hover"（它只看整表有没有，不逐类点名：那需要一份"可交互元素清单"，属渲染层）；
- **档数只是报数** —— "几档算合理"是设计决定，工具不给答案（圆角那个 cap 是 workbench 明文给的，不是我定的）；
- **响应式/首屏/签名元素**（workbench 留给我们自己定的那四段里的三段）—— 那需要看渲染，不在这道门的能力范围。

## 6. 踩过的坑（两次都是同一个坑的两种形态）

1. **TOML 里写 ASCII 双引号**（第 N 次）：`style_baseline.toml` 的 `why` 里写了 `"圆角 7 档"`，
   直接 `TOMLDecodeError: Unclosed inline table`。一律改用「」。
2. **注释被吃进选择器**（T-G27 同款）：这次一开始就先把注释删干净，并且**加了一条测试钉住**
   （`test_comments_do_not_leak_into_selectors`）—— 因为这种漏检最坏的地方是"**让门显得是绿的**"。
3. **噪音也要治**：第一版把 `top/bottom/left/right` 也算进"尺度类"，结果 `.toast` 的
   `bottom: 24px`、底部 Tab 的 `left: 0` 全被报成"一次性值"——**定位常量的一次性是正常的**。
   改成：定位属性不算；纯复位值（`0` / `auto`）不算。8 条比 17 条有用得多。
   （门的价值不在"报得多"，在"每一条都值得看"。）

## 7. 怎么用

```powershell
python -X utf8 tools/style_audit.py            # 人读（判定 + 档数 + 销账提示）
python -X utf8 tools/style_audit.py --json     # 机器读
python -X utf8 tools/style_audit.py --check    # 门禁用（脚本里接的就是这条）
```

**什么时候收紧**：这 8 条本来就是视觉线要修的（对照 T-G24 §8 的步 0/1/2）。
修一条、删一行；表空了，它就从"棘轮"变成"硬门"（和对比度门同一个收口方式）。
**现在就已经是阻断项**（第 13 项）—— 因为它**不红**，只是不许再变坏。
