# 复盘 · 意图(Intent) → 规格(Spec) 产品判断检查

> 阶段：先做前半段（Intent→Spec 的产品判断）。后半段（Spec→Impl 的设计与实现判断）另起。
> 范围：仅 `docs/intention/needs.md` 与 `docs/specification/{README,functional,nonfunctional,traceability}.md`。
> 目标：解释为何 vibe-coding 产出「大量功能缺失 + 实现逻辑不完整」，定位意图→规格转换中的产品判断缺陷。
> 约定：不改写任何文档内容，只做诊断与追问。

---

## 一、判断框架：从「意图」到「规格」该保住什么

把一条需求拆成四要素，规格层的质量就看这四要素是否都被等价承接：

| 要素 | 意图层来源 | 规格层应体现为 | 现状评价 |
|---|---|---|---|
| 1. 结果承诺 | 要做什么功能 | 一条可验证的「必须…」 | 多数到位 |
| 2. 行为规则 | 怎么做、边界、异常 | 展开到可执行的粒度 | **普遍不足** |
| 3. 裁决/护栏 | 已定/已砍/暂不写死 | 「**不得**/默认/后置」负向约束 | **系统性缺失** |
| 4. 为什么(动机) | 为何这样定、防什么 | 判断尺度的锚（know-why） | **几乎全部丢失** |

vibe-coding 最痛的病灶集中在 **3 与 4**：规格只保住了「结果承诺」，却剥掉了「护栏」和「为什么」。实现 agent 在缺护栏、缺 why 处必然脑补补全，从而「功能有了、但逻辑错了、约束丢了」——正对应你观察到的现象。

## 二、逐需求锚点扫描（对照 README 领域分组表 + traceability）

先用 `specification/README.md` 的领域分组表做主骨架，找「分组表里没位置，却真实存在的意图」。

| 意图 | 领域分组表(SR-Fx)是否收录 | 实际承接 | 判定 |
|---|---|---|---|
| **N1 本地·轻量·跨设备** | ❌ **无 SR-F 分组位置** | 只在 traceability 挂到 SR-F9.1 + SR-NF16/17/18 | ⚠️ 顶层定位需求在功能分组中无锚点 |
| **N2 长期均匀投入** | ❌ **无 SR-F 分组位置** | 只在 traceability 挂到 SR-F2.5 + SR-NF18 | ⚠️ 同上 |
| N3 债务/储蓄(贯穿) | ✅ SR-F2 | SR-F2.1~F2.8 | ⚠️ 口径被压缩，见问题3 |
| N11 任务存档 | ✅ SR-F1.7 + SR-F8.2 | 承接 | ✅ |
| N30–N34 体验 | ⚠️ 不在 SR-F 表 | SR-NF1~NF5 | 可，但见问题4 |
| N35–N44 工程 | ⚠️ 不在 SR-F 表 | SR-NF6~NF15 | 可，但见问题4 |
| 其余 N | ✅ | 均有 SR | ✅ |

### 发现 A：两个「定位/哲学」级需求在功能分组表里「无家可归」
N1、N2 是项目的底层定位（本地优先、长期均匀投入），却**没有进入 SR-F 领域分组表**，只在非功能规格与 traceability 里零散挂靠。vibe-coder 按 SR-F1~F10 功能分组去查实现时，**N1/N2 这两条会被直接忽略**——但它们是决定「要不要上云、要不要监控、怎么做债务」的根约束。这是第一层结构性空白。

## 三、六类核心产品判断问题（每条给意图原文 vs 规格现状 vs 风险）

### 问题 1｜「贯穿性」需求没有自己的锚点，各领域规格不建交叉引用
- **意图原文(N3)**：「债务/储蓄 记账，实现长期平均投入（**贯穿核心**）… 逾期任务=债务；专注投入=储蓄；完成悬赏=收益/储蓄；复习逾期=轻度债务。」
- **规格现状**：N3 被硬归入 SR-F2；而真正受它贯穿的 **SR-F1(任务/逾期)、SR-F3(专注)、SR-F4(习惯)、SR-F6(复习)** 这些领域的规格里，除了 SR-F1.8 一句「计入债务」、SR-F4.2 一句「纳入B系统同一套可视化」，**没有一处明确写出「此处必须与债务/储蓄口径联动」的锚点**。
- **风险**：vibe-coder 实现 SR-F1 任务管理时只看 SR-F1，不知道「逾期任务要自动落债务账本、要分强/弱、有指标类进产出账」。结果就是**债务/储蓄逻辑割裂、缺失**——正是你看到的「实现逻辑不完整」。

### 问题 2｜意图层的「裁决/护栏」未系统转成「不得/不」负向约束（最严重）
- **意图原文**：明确裁决了——「不设独立目标实体（伪需求，避免过度抽象）」「不硬对标（如实记账+趋势自判断，**不用算法推荐**）」「债务**不折算成精确时间（估不准、不造假）**」「**知识管理未对齐不写死**（toolkit 只有质检/检索评估/文风评审、**无产出打分器**）」「学校硬考核逾期虽计债务但**不可重组清零**」。
- **规格现状**：只转了部分——SR-F2.5（不设目标实体、不硬对标、不用算法推荐）、SR-F2.3（不折算时间）、SR-F2.8（不可重组清零）。但 **「知识资产无产出打分器、知识管理未对齐不写死」这条裁决，规格层只字未提**（只留了 SR-F8.4 「产出评价器接口：第一版手动粗颗粒」）。
- **风险**：护栏只在意图层，没进规格层。vibe-coder 在实现知识资产产出时，几乎必然**自作主张发明「打分器/评分/量化」**，做出意图明确不要的东西。这就是「功能不在意图上」的典型来源。

### 问题 3｜N3 这一条意图「密度过高」，压缩进 SR-F2 时丢了 know-why 与原则
- **意图原文(N3)**：「**原则（温和，⭐）**：B 是**帮你管理时间，不是 push 你**；长期、**慢就是快、打基础**；管理工具**不制造压力**；学生学得慢正常。」＋「结算：以周为主…不硬对标…」＋大量「已定口径」。
- **规格现状**：SR-F2.5 只剩「均衡度指标**温和呈现、不告警、不施压**」一句，SR-F2.3 只剩「如实记账」。**「帮你管理不是 push 你」「管理工具不制造压力」「学生学得慢正常」这整套价值观，只被压缩成「温和」两个零散字眼**，没有上升为一条独立、明确、全局的设计约束。
- **风险**：vibe-coder 看不到「为什么这么温和」，只看到「债务=逾期天数/程度」的机制，极易把 B 系统实现成**「逼迫型/施压型」**——逾期天数越多越红、越催促，与意图的「温和、不 push」南辕北辙。这是**产品原则层面的错位**。

### 问题 4｜体验/质量类意图（N30–N34、N35–N44）被「打包进 SR-NF」，缺乏可验证边界
- **意图原文**：N30 视觉美感、N31 交互低门槛、N32 信息可视化、N33 一屏不淹没、N34 反馈可回退；N35–N44 工程底线。
- **规格现状**：SR-NF1~NF18 基本**逐条对应**，表面承接良好。但几乎每一条都是「必须：界面必须… / 必须轻量 / 必须流畅 / 必须低门槛」这种**形容词式承诺，没有可验证边界**（多轻算轻？多快算快？低门槛的验收标准？）。
- **风险**：质量属性没有**量化阈值/验收标准**，vibe-coder 无法证明自己做到了，只能「凭感觉实现」，导致效果不稳定、与「素雅/极简/不淹没」的品味产生偏差。

### 问题 5｜大量规格「一句带过」，行为规则与异常路径未展开 → 实现 agent 只能脑补
抽样（每条都是「必须支持 X」一句话，X 未定义）：
- **SR-F1.5 Repeat**：意图是「到点**基于上次完成时间**自动生成下一次」。但「上次**没完成**怎么办？」「重复周期（每天/每周/工作日）如何设置？」「补做算不算？」——都未定义。
- **SR-F3.2 专注中断**：「提供暂停/放弃/记中断」。「记中断」要记什么？（时长？原因？断点？）未定义。
- **SR-F6.2 复习任务创建**：「可由学习任务升级为复习任务」→「升级时保住什么？原任务的到期/子任务如何迁移？」未定义。
- **SR-F4.1 每日反馈**：「反映计划 vs 执行差距」→「差距如何量化？用图还是数字？自动算还是手动填？」未定义。

**风险**：越是「必须支持 X 但不定义 X」的地方，vibe-coder 的自由度越高，实现的「逻辑」就越可能与上下文不一致，暴露出你看到的「逻辑不完整」。

### 问题 6｜意图层大量「外部参照物」未传导为规格契约，实现 agent 凭名字猜
- **意图原文**：多处指向参照——「参考 **Microsoft To Do**（My Day/分组/Repeat）」「复习算法**用现成 Python FSRS 库**」「移动端 **PWA + IndexedDB + LWW**」「知识资产句柄参考 **KB-ID / obsidian-vault-notes / manage-personal-knowledge**」「团队状态**参考 toolkit 笔记做法**」。
- **规格现状**：这些参照**绝大部分没有变成规格里的技术契约或引用**。SR-F6.1 提到「用现成 Python FSRS 库」「数据按 FSRS 兼容字段设计」是少数例外；其余（PWA/LWW/KB-ID/obsidian-vault-notes/toolkit）只在 SR-NF17、SR-F8.2 里轻描淡写。
- **风险**：vibe-coder 不知道「句柄到底长什么样（Vault 相对路径 / KB-xxx 资源 ID）」「LWW 冲突如何处理」「PWA 与桌面端数据形态差异」，只能按名字猜实现 → 与参照形态不符、联动断链。

## 四、根因归纳（为什么是「系统性」而非「单点」）

1. **意图层 is 上 & 规格层 is 下 的「语义打包」过了头**：一条高密度意图（尤其 N3）被压成几条 SR 时，**只搬走了「结果承诺」，没有搬走「行为规则、裁决护栏、背后为什么」**。
2. **规格层用的是「正向承诺（必须做 X）」语言，极少用「负向约束（不得 Y / 默认 Z / 后置）」语言**——而意图层的护栏恰恰绝大多数是「不/砍/暂不 / 不写死」。**负向约束转规格时最容易丢**，一旦丢了，vibe-coder 就去补全。
3. **横切约束（贯通/品味/工程底线/价值观）没有「横切性表达」**，被压进单个领域的 SR，或压成非功能 SR 的形容词；vibe-coder 按模块切分工作，横切项天然被忽视。
4. **规格层缺「可执行粒度」与「验证标准」**：一句话承诺多，行为边界、异常路径、量化阈值少。给实现 agent 的自由度被放大到失控。

## 五、修复方向（只指方向，不改动原文档）

**规格层（下一轮主战场）建议补强：**
- 为 **N1/N2** 在 SR-F 分组表立明确锚点，或新增一条「底层定位/贯穿」领域。
- 把意图层的**每条「裁决/护栏」逐条转成规格里的「不得 / 默认 / 后置」负向约束**，尤其「知识资产无产出打分器、知识管理未对齐不写死」「不折算时间不造假」「不用算法推荐」——建立一张「护栏清单一览」。
- 给「贯穿性」领域（SR-F1/F3/F4/F6）**逐个写「此处须与债务/储蓄口径联动」的交叉引用锚点**。
- 为 N3 的「温和不 push、不制造压力」**单列一条全局设计约束**（默认温和、可关闭、无强制红点、不因天数放大焦虑）。
- 为体验/质量规格补**量化阈值**（启动阈值、交互响应、信息密度、留白标准的可验证边界）。
- 为每个「必须支持 X 但不定义 X」的规格**补行为边界与异常路径**，并统一给验证方法。
- 把意图层的外部参照物**转成规格契约**（句柄格式、FSRS 兼容字段、LWW 冲突处理、PWA/桌面数据差异）。

**意图层（若有回溯需要）**：needs.md 本身质量很高，护栏与 why 都很清晰；问题不在意图层写得不清楚，而在**这些护栏/why 没有被规格层等价承接**。

## 六、结论

从 Intent→Spec 这一段，**问题不是「需求没写全」，而是「需求写得很全，但规格层只承接了『承诺』，没承接『护栏 + 行为规则 + why + 可验证性』」**。这四类信息的丢失，恰好是 vibe-coding 在缺边界、缺约束处「脑补补全」的高发区——所以你看到的不是「缺几个功能」，而是「功能逻辑不对、约束丢、体验跑偏」的系统性症状。

> 下一步：按你所述，再做「Spec→Impl 的设计与实现判断」复盘，重点核查架构/模块落点是否在执行层又丢了规格约束。
