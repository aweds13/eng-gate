# 看门狗独立化（架构 C · 兜底告警）—— 外包卡 024 · 台账号 T-G112

> 一句话：`--status` 现在会在「心跳停滞超过阈值且没有判决」时打**醒目告警** ——
> 派活进程被系统杀掉之后，"没人盯"从「只能看到心跳停在几点」升级成「一眼看到没人盯 + 该干什么」。

## 1. 为什么有这张卡（出处）

- 盘点卡 S-1 的 **A17**（`gates/diag/盘点-20260926.md`）。
- `docs/traceability.toml` `T-G91.gaps` + `复盘/长跑保命-T-G91.md` §5：`--detach` 之后
  看门狗是**那个脱离进程自己带着的**；它被系统杀掉（重启 / 休眠断电 / 被任务管理器结束）
  就没人掐工人、没人写判决 ——「想要更强的保证，得让看门狗也独立（**还没做**，是候选）」。
- `复盘/并发两卡-T-G92T-G93.md` §6：「看门狗的寿命 = 那个进程的寿命」。

## 2. 主控裁定与本卡做了什么

主控裁定（卡 §2.9）：**架构选 C（先做"看得见"）**，A（双进程互盯）不做、B（独立看门狗进程）
写成候选卡（§6）。本卡落地：

- `tools/wb_dispatch.py:405` 新增 `heartbeat_stall_alert()`，接进 `status_report()`
  （接线在 `tools/wb_dispatch.py:368` 与 `:381`，告警紧跟 `[心跳]` 行输出）。
- 判据：**只读文件 mtime**（`--status` 只读文件的原则不动）。心跳停滞 ≥ `STALL_SECONDS`
  （480 秒 = 心跳间隔 120 秒的约 4 个周期 —— 派活进程活着时每个周期都该有心跳）且没有判决
  （这张 log 自己的 `*.verdict.txt` 或 log 里有 `result` 事件，与面板同一口径）→ 告警。
  ★ 阈值复用看门狗底线常数，**没有写第二份口径**。
- 顺带修了一处展示：`[心跳]` 原来**只认第 1 轮**的心跳文件，续跑（r2）时会把"还在跑"
  读成"心跳停在几点"—— 现在取**最新一轮**的那份（心跳按轮落是 T-G96 定的，读法跟上）。

## 3. 「孤儿」分支是探针杀掉的（本卡最重要的真机发现）

初版告警分两种：心跳停 + 日志静默 →「没人盯」；心跳停 + 日志还在动 →「孤儿」。
**真机探针 B 证明第二种不可达**：工人的 stdout 是管道，读管道的 pump 线程就在**派活进程**里
（`tools/wb_dispatch.py:886` `_pump`）—— 派活进程一死，没人读管道，log 就**冻结**
（桩工人随管道断裂直接退出；给桩挡住 EPIPE 让它活下来，log 也照样不再增长）。
所以「心跳停了但日志还在动」在真实世界里到不了，按它分叉只会产出**误导性告警**。
已收敛为一种告警，工人生死判不出来这件事如实记进边界与候选卡 B。

## 5. 真机证据（桩命令真起进程；驱动 `%TEMP%/tg112_probe/probe.py`，原始输出 `probe_out.txt`）

★ 如实记：探针把**读状态**那半边的 `STALL_SECONDS` 临时改小（480 → 20），只为不用干等 8 分钟；
进程、文件、心跳、杀进程全部是真的，且全部产物在 `%TEMP%`，没碰仓库。

- **探针 A（`--detach` 真扔 + 按 PID 杀整棵）**：pid 60720 起来、心跳在写
  （`[心跳] 已跑 0.1 分钟 | 日志静默 5 秒`）→ `taskkill /F /T /PID 60720` → `--status`：
  `[★告警] 心跳停滞 0.5 分钟、日志静默 0.6 分钟（阈值 0.3 分钟，与看门狗底线同一口径）且没有判决 —— 派活进程（含看门狗）多半已被杀……没人盯了。`
- **探针 B（只杀派活器，不杀工人）**：`taskkill /F /PID`（不带 `/T`）→ 桩工人存活
  （挡了 EPIPE）、log 冻结在 5 行 → `--status` 打出**同一条**「没人盯」告警 ——
  告警不依赖工人生死（见 §3）。
- **探针 C（工人正常收工）**：桩吐 `result` 收工 → 判决落盘
  （`判决：正常收工（工人退出码 0）`）→ 派活进程**自己退出**（tasklist 按 PID 核过，无孤儿）→
  `--status` **不**告警（收工后心跳停止是正常的）。

## 6. 面板（`wb_dash.py`）那一半 —— 卡内两处条款的取舍

卡 §2.9 说「`--status` **与面板**都加」，但 §3 白名单明令 `tools/wb_dash.py` 一个字不许碰
（两处冲突，按更严的执行）。事实核查：**面板的停滞告警 T-G97 已经有了** ——
`tools/wb_dash.py:54-67` `_state()` 静默超本次阈值 → 红色「静默 N 分钟（可能卡死）」，
阈值复用 `stall_threshold_seconds()` 同一口径。本卡补的是 `--status` 这一半；
面板与 `--status` 一样看不见「看门狗死、工人还活着」（§3 的机理相同）→ 同样记进候选卡 B。

## 7. 候选卡 B 的设计要点（独立看门狗进程；**未开工**，待主控发号）

1. **形态**：`tools/wb_watchdog.py` 独立小进程，只做三件事：轮询读 log / 心跳文件、
   按 PID 文件掐树（复用 `kill_tree`，绝不按进程名）、落判决。派活进程死了它还在。
2. **探活间隔与判定口径**：复用 `stall_threshold_seconds()` 现有口径（在飞抬底线 +
   自适应 + 3600 封顶），不写第二份；轮询沿用 `POLL_SECONDS`（5 秒）。
3. **孤儿退出条件**（不做就会留下永久后台进程 = 新坑）：`wb-<卡>*.verdict.txt` 齐了
   （每轮都有判决且最后一轮有 `result`）→ 等一个宽限期（如 2 个心跳周期）→ 自杀；
   或心跳文件停滞超过自身的倍数（如 10 个周期）→ 判定派活进程已死且无人接管 → 自杀。
4. **它自己被杀时怎么发现**：双进程互盯才是 A 的领域 —— B 的让步是：看门狗被杀
   退回本卡架构 C 的告警兜底（`--status` / 面板），不再往下套娃。
5. **代价提醒**：动派活器进程模型（T-G92/T-G96 刚稳下来），blast radius 大；
   且 §3 的发现说明它才能真正回答「工人还烧不烧 token」。

## 8. 边界（如实写）

- **工人生死判不出来**：派活进程死后 log 冻结（§3），告警只能说「没人盯」，
  不能说「工人还活着/死了」；残余风险 = 工人烧着 token 没人看 → 候选卡 B。
- **系统重启**（连 `--status` 的读者一起没）：最终兜底是人 / 用户的定时调用
  （卡 §2.9 的设计前提），本卡不建定时器。
- **两轮之间的窗口**：第 1 轮判决已落、第 2 轮未起时派活进程被杀 → 判"收工"不告警（误漏）。
- **`--stall-seconds` 自定义值不进告警口径**（`--status` 读不到当时用的旗标，一律按默认 480）；
  `--heartbeat-seconds 0` 时没有心跳文件，退化为「没有心跳文件 + 日志静默」也告警。
- **mtime 依赖**：改系统时钟 / 大幅休眠回拨会误判（保守方向：多告或少告各有可能）。
- **探针的阈值缩放**：真机证据里读状态的阈值是 20 秒（480 的缩放），已在驱动里如实注明。
